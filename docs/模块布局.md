# 模块布局

> 本篇是**维护者视角**的工程地图：不教语言，只回答「东西在哪、链路怎么走、改动落在哪里」。语言特性请按主题域查 wiki 百科条目；模块系统语义（mount/可见性）见 wiki/05-工程-模块与import.md，注解处理器详细机制见 wiki/05-工程-注解与注解处理器.md。

## 一、gradle 六模块依赖图

`settings.gradle.kts` 声明六个子工程（rootProject.name = `sublimation`），根 build.gradle.kts 的 `allprojects` 统一注入 `group = "sugared.functor"`、`version = "1.1-SNAPSHOT"` 与 mavenCentral 仓库；每模块统一 Kotlin `2.1.20` JVM 插件 + `jvmToolchain(17)`（foojay 插件仅为工具链自动解析）。

依赖关系（各模块 build.gradle.kts 的 `implementation(project(...))` 实测）：

```
                    frontend  （无向下依赖）
                       ↑
                    compiler
                       ↑
        ┌──────── interpreter ────────┐
        │              ↑              │
        │         language-service    │
        │        （+annotationproc）   │
        │              ↑              │
   annotationproc      │              │
  （frontend+compiler+interpreter）   │
        │              │              │
        └────────────  cli  ──────────┘
```
| 模块 | 依赖 | 职责边界（一句话） |
|---|---|---|
| frontend | — | 词法（Lexer）、文法（Parser）、AST 定义与打印；零编译器语义 |
| compiler | :frontend | 全部静态语义：符号收集、类型合一、命题与证明、模块系统，以及 JS 代码生成 |
| interpreter | :frontend, :compiler | 脚本模式运行时：大步求值器、宿主函数、运行时帧；以及**脚本模式专属**的全局类型推导 |
| annotationproc | :frontend, :compiler, :interpreter | 注解处理器引擎与流水线；处理器本身是 .subs 脚本，由解释器解释执行 |
| language-service | :frontend, :compiler, :interpreter, :annotationproc | LSP 服务器与分析桥接（诊断/悬停/跳转/补全/文档符号） |
| cli | 全部五模块 | 唯一入口 Main.kt：子命令分派、诊断码解释表、激进模式旗标、fatJar 产物 |

边界要点（实测）：

- 主链是 frontend → compiler → interpreter → cli；annotationproc 与 language-service 是**侧枝**——不在主链中间，但各自向下依赖 compiler/interpreter，最终由 cli 汇聚。
- compiler 不依赖 interpreter：**编译链不运行用户代码**；反过来 interpreter 依赖 compiler 是因为 Evaluator 之前要先过 Checker（脚本模式也检查类型），且 GlobalInference 产出仍要交回 Checker。
- interpreter 是依赖最厚的库模块；cli 是唯一同时依赖全部五模块的模块。
- 所有模块共用包名前缀 `sugared.functor`（frontend 为 `.{ast,lexer,parser}`，compiler 为 `.{checker,codegen}`，interpreter 为 `.interpreter`，lsp 为 `.lsp`，annotationproc 为 `.annotationproc`，cli 入口类直接在 `sugared.functor` 下）——**模块边界靠 gradle project 划分，不靠包名前缀**。
- 两个模块带 `application` 插件：cli（`mainClass = "sugared.functor.MainKt"`，`-Xss16m` 防处理器深帧 StackOverflow，fatJar 落在仓库根 `build/libs/sublimation.jar`）；language-service（`mainClass = "sugared.functor.lsp.LspServer"`）。
- 测试工作目录：frontend/compiler/interpreter/language-service/annotationproc 的 `tasks.test` 都设 `workingDir = rootDir`，使测试内的相对路径 `File("core")`、`File("examples/...")` 可解析（根 build 注释明示此约定）；**cli 的 `tasks.test` 未设 workingDir**（其测试不依赖仓库根相对路径）。

## 三、数据流：parse → check → codegen → interpret 全链

### 3.1 单文件编译链（`compile file.subl`）

```
源码文本
  │  Lexer(src, fileName).tokenize()                    [frontend]
  ▼
Token 流（含 precededBySpace 等邻接标记）
  │  Parser.parseSourceWithNotes → ParseResult(ast,hints,supplements)  [frontend]
  ▼
FileAst
  │  ProcessorPipeline.runBuiltin(ast, extraProcessors, options)  [annotationproc]
  │    （多轮引擎；变换后的 AST 才是检查对象；无关注注解则零开销直通）
  ▼
FileAst′
  │  Checker(ast).run()  → DiagBag                       [compiler]
  │    内部：Symbols 两遍收集 → checkImpls/checkWhens → checkDecl/checkStmt
  │         → Diffusion.Frame 弥散与命题证明 → CallCheck 调用与供给
  │    留痕字段（dictHits/moduleHits/consHits/delegatedImpls/deepCopyHits…）同期填充
  ▼
DiagBag（hasError → 拒绝生成）
  │  JsCodeGen().generate(ast, <Checker 全部留痕字段>)    [compiler]
  ▼
JS 文本（-o 写文件，否则打印到 stdout）
  │  node 执行 / 处理器 postCompile 收尾（诊断只报告不阻断）
  ▼
运行结果
```

关键耦合：**JsCodeGen 不查符号表**（纯语法变换），跨模块调用所需的前缀、类型类字典、深拷贝标记等全部由 Checker 的留痕字段（IdentityHashMap 语义：按调用点实例）在生成时传入——这就是 `generate` 参数列表很长的原因；这也是「处理器改了 AST 必须重建 Checker 重跑」的机制依据（Main.kt 注释明示）。

### 3.2 多模块编译链（`compile <project-dir>`）

目录即模块：`MultiModule` 先 `scanModuleTree` 建模块树（ModuleTree，core/ 包目录嫁接到根），逐模块解析合并（同模块所有 .subl 共享一个 Symbols），再校验 settings/挂载目标/命名冲突/环（E-CIRCULAR-MOUNT），随后三阶段：A 全模块符号收集 → B 类型可解析性+impl+pure → C 声明体检查；注解处理器由 `processModules` 以「每模块一个引擎、模块层统一重查」的形态先于 B/C 跑；最后 `generateJs()` 合并产出。

### 3.3 脚本模式执行链（`run-script file.subs`）

```
源码 → Lexer → Parser(脚本模式：顶层语句直接合法) → [可选 GlobalInference 填标注]
     → Checker(scriptMode) → Evaluator.evaluate(ast, ScriptFrame())
     → 宿主函数 (@host) + core 标准库（stdlibDir=File("core") 递归收集 .subl）
```

解释器**不做类型系统**（Checker 已做完）；Evaluator 只走运行时求值。每条 .subs 脚本独立执行（互不共享、无需 main）；目录无 .subs 时回退按 .subl 工程（`fun main()` 入口）解释执行。

## 五、扩展指引

### 5.1 加一个新诊断码（例：`E-FOO`）

落点依次为：

1. **发射处**：在职责归属的 checker 文件里 `d.error("E-FOO", pos, "…")`（Diag.kt 的 DiagBag）；归属参考：调用/供给 → CallCheck.kt，穷尽 → WhenCheck.kt，impl → ImplCheck.kt，Γ/弥散 → Diffusion.kt，模块 → ModuleTree.kt/MultiModule.kt，解析层异常 → Parser 抛 ParseFailure（非诊断码）。
2. **解释表**：cli/Main.kt 的 `EXPLAIN` 映射加一条——否则 `sublimationc explain E-FOO` 回「未收录」。
3. **同步测试**：cli 的 `ExplainCoverageTest.knownCodes` 加该码（断言 EXPLAIN 与 knownCodes 集合相等，漏加即测试失败）；建议同时在 compiler 的 `DiagCoverageTest` 加触发场景。
4. 诊断码命名随现有三族：`E-` 错误 / `W-` 警告 / `D-` 补充；另有 `H-` 提示族（如 H-ARITH-PRECEDENCE 由 Parser 侧 hints 汇入）。

### 5.2 加一种新语句

新增语句种类需要沿主链全改一遍，落点是：

1. **AST 节点**：frontend 的 ast/Ast.kt 增数据类并实现 `Stmt`（注解字段规则按现有节点形态决定：EnumDecl/ImplDecl/TypeAliasDecl 无注解字段，FunDecl/StructDecl/ClassDecl/VarStmt/VarExpr 有）。
2. **文法**：Parser.kt 的语句分派（parseStmt 区域，约 :796 的 parseUnchecked 是同型参照）加产生式；顶层 vs 函数内的合法性在 parseEntry/parseStmt 分别处理。
3. **语义**：Checker.kt 的 `checkStmt` 分派加分支（类型检查、纯度传播、uncheckedDepth 闸门是否放行的判定参照 :612/:767 一族）。
4. **求值**：interpreter Evaluator.kt 的 `evalStmt` 加分支。
5. **代码生成**：compiler 的 JsCodeGen.kt 加对应生成分支。
6. **语言服务**：language-service 的 LspAnalysis.kt 按需补齐（补全/悬停对新语句的识别——该文件正在被重写，以源码为准）。
7. 若新语句带诊断：同 5.1。

### 5.3 加一个新注解

先分清两层：

- **语言层注解**（语言核心认识，改变检查/生成行为）：声明位注解是自由名字（Parser 的 parseAnnotations 只读 `@IDENT` 不读实参），故**无需改 Parser**；行为落点在 Checker.kt/CallCheck.kt 的注解判定，必要时 JsCodeGen 跟随（@root/@android 的白名单门是同型参照）。类型位注解只有 `@mut`/`@atomic`/`@impure` 三个合法名字，加新的须改 Parser.kt:506–522 的类型位校验（否则 E-PARSE）。
- **工程层注解**（语言核心不认识，由处理器赋予含义）：落点是**脚本处理器**——在 `annotation processer/` 目录加一个 `.subs` 文件（文件主名 = 处理器名 = 关注的注解名），或用 `-p <路径>` 临时追加；处理器通过 ProcessorApi 的宿主函数只读查询 AST、累积注解编辑与结构性编辑、报告诊断，引擎多轮（上限 5）收敛，产物重新接受检查。注意：
  - 内建处理器目录是 **cwd 相对路径**（`File("annotation processer")`，注意拼写），换工作目录即静默失效——CLI 从仓库根运行才能装载内建处理器。
  - 跨注解纪律用脚本首部 `@interested ann1, ann2` 声明；需编译后产物（如安卓 APK）用 `@postcompile <函数名>` 声明入口。
  - 处理器诊断码族：E-PROCESSOR-LOAD/ERROR/LOOP/SCRIPT/EDIT 与 W-PROCESSOR-*。
