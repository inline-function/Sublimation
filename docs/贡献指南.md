## 1 仓库速览

settings.gradle.kts 声明 6 个 Gradle 模块（Kotlin 2.1.20，JVM 17 toolchain，统一包名 sugared.functor.*）：

| 模块 | 职责 | 测试规模（近似，随提交变动） |
|---|---|---|
| frontend | M1 词法（Lexer，224 行）+ M2 语法（Parser，1724 行）+ AST（Ast.kt，77 个声明） | LexerTest / ParserTest / ParserSnippetTest，约 65 例 |
| compiler | M3 语义：Checker（可变性/纯度/证明/when 穷尽）、类型推导、Prop 归一、ArithProve 算术通道；M4 JS 代码生成（JsCodeGen，1797 行）；含 e2e | CheckerTest / TypeInferTest / DiagCoverageTest / E2E 等，约 530+ 例 |
| interpreter | 大步求值 Evaluator（924 行）+ 宿主函数注册；闭包捕获深拷的完整实现侧 | InterpreterTest / GlobalInferenceTest，约 52 例 |
| cli | 命令入口（sublimationc）+ 诊断码解释表常量 | ExplainCoverageTest（解释表双向一致守护） |
| language-service | LSP 诊断/补全/悬停，分析核心为 LspAnalysis.kt | LspAnalysisTest |
| annotationproc | 注解处理器流水线：AnnotationScanner + 内建/安卓处理器改写 | 4 个测试文件，约 21 例 |

依赖方向基本自下而上：frontend → compiler → interpreter → cli（cli `implementation(project(...))` 依赖其余五个模块；language-service / annotationproc 的依赖清单未在本文核实，**待核**）。模块外另有 core/（.subl 标准库）、examples/（可运行示例）、demo/ show/ playground/（演示工程）。

> 语言当前状态（唯一准绳，详见 _facts/_langfacts.md）：程序位 `=>`、命题位 `→`、独立 `axiom p1, p2, ...` 语句、无线性作用域、可变拷贝 4 条规则、`unchecked <语句>` 关键字形态保留。所有提交里的代码与示例都必须用**当前文法**。

## 2 文档层级与更新义务

文档分五层，各层读者与体例不同，**不互相抄录**：

| 层 | 目录 | 读者 | 体例 | 更新义务 |
|---|---|---|---|---|
| 语言手册 | root doc/ | 语言使用者 | 8 篇主题手册（模式匹配、副作用与可变性控制、手动证明、上下文系统、注解处理器、脚本模式、异步、其他语法糖） | 用户面语义一变即更新 |
| 百科条目 | wiki/ | 使用者/速查 | **一个概念一页**，固定四节 `## 语法 / ## 语义 / ## 示例 / ## 陷阱`；40 余条按 01-基础 / 02-类型 / 03-证明 / 04-效应 / 05-工程 编号分组，索引在 wiki/README.md | 出现新概念或条目行为变化时同步 |
| 工程文档 | docs/ | 维护者 | 构建与工具链、贡献指南（本篇）；README 提到的模块布局/诊断码参考/安卓标准库设计将陆续迁入 | 工具链与流程变化时更新 |
| 形式化卷 | boring doc/ | 规范维护者 | 判断式 LaTeX（`$$\frac{前提}{结论} \quad (\text{规则名})$$`，多前提 `\qquad`）；00–11 编号卷 + 形式化语义系列 + 安卓标准库设计；每条规则必须回溯到具体源码位置，每条「已知限制」必须附实测证据 | 语言演进时同步修订 |
| 实现源码 | frontend/compiler/interpreter/cli/language-service/annotationproc | 编译器维护者 | Kotlin，见 § 3 | 语义/文法一变即更新 |

### 2.1 引用顺序与事实来源优先级

写作与排错时的引用顺序（高 → 低）：

1. **实现源码**：代码是唯一事实来源；boring doc/README.md 明确「root doc/idea doc 与代码不一致处以代码为准并如实记录」。
2. **root doc 语言手册**：语义最高权威（面向使用者的表述层）；与代码冲突时如实记录差异，而不是擅自改文档掩盖。
3. **wiki 百科**：每个概念一页，与 root doc 不重叠、不抄录，引用用相对链接。
4. **boring doc 形式化卷**：规则级溯源，引用须带源码锚点（词法/语法/AST 规则给出可回溯的文件与位置）。
5. **旧文档**：仅作结构参照；凡与源码/事实表冲突一律按新事实重写。

文档代理（本篇所属）另有契约级优先级：_facts/_langfacts.md > 源码（file:line）> 旧文档；不确定处显式标 **待核**，绝不推测或编造。贡献者在任意层文档里发现事实过期，正确做法是**修文档或修代码使其一致并在提交里说明**，而不是留着冲突。

### 2.2 新特性落地须同步更新的层

一个语言特性合入时，按影响面同步更新：

- **必须**：实现源码（AST + 解析/检查/求值/生成四处落点，见 § 3.2）+ 对应模块测试。
- **必须**：examples/ 新增可运行示例（一文件一特性，check 零 ERROR，见 § 4.3），并在 examples/说明.md 登记特性与预期输出。
- **新概念**：新增 wiki/ 条目（四节固定）并更新 wiki/README.md 分组表。
- **用户面语义变化**：更新 root doc/ 对应手册。
- **规则级变化**（文法/类型/命题/效应）：更新 boring doc/ 对应卷，规则附源码锚点。
- **新增/改名/删除诊断码**：同步 cli 的 explain 解释表、DiagCoverageTest（每码一触发场景）与 ExplainCoverageTest 的 knownCodes 清单（三者由该测试强制双向一致）。
- **标准库新函数**：更新 core/ 对应 .subl 与 wiki/05-工程-标准库总览.md。

## 3 代码风格（Kotlin 约定）

### 3.1 通用约定

- Kotlin 2.1.20，jvmToolchain(17)；包名统一 sugared.functor.*，模块内按职责分目录（lexer/parser/checker/codegen/…）。
- 测试用 JUnit 5（useJUnitPlatform()），测试方法用反引号中文名，一目了然：

  ```kotlin
  @Test fun `E-TYPE-MISMATCH 函数体`() =
      assertTrue(has("fun f(): Nat = \"s\"", "E-TYPE-MISMATCH"))
  ```

- 重大语义决策**编号化**并在测试注释里引用溯源，例如 DiagCoverageTest 头注「第四轮，决策 72；返工后按新语法规则更新，决策 73/74/75」。新增此类决策时延续编号并在相关测试/文档处标注。
- 测试工作目录统一指向仓库根（workingDir = rootDir，见根 build.gradle.kts 注释），使测试内相对路径 File("examples/…") 可解析；改动测试相对路径前先想清楚这一点。
- 注解处理器深帧偶发 StackOverflow，CLI 运行放宽到 -Xss16m（cli/build.gradle.kts）；调试处理器时注意这条默认值。
- 提交前移除调试/验证用临时脚本（历史上有多次「清理：移除误提交的临时脚本」提交，勿再增加）。

### 3.2 新增语句的解析/检查/求值/生成四处落点

加一条新语句（或新语法形态）时，管线四个阶段都要落点，缺一即断层：

| 落点 | 文件/入口（近似行号） | 做什么 |
|---|---|---|
| ① AST | frontend/…/Ast.kt | 新增/扩展节点数据类 |
| ② 解析 | Parser.kt parseStmt()（:631）；涉及新关键字/算符则先动 Lexer.kt | 识别新形态并构造节点；D-5 中缀糖、符号/运算符前缀调用等消歧规则会「抢先吃」token，新语法须与之划清边界 |
| ③ 检查 | Checker.kt checkStmt()（:513） | 语义闸门（类型/纯度/可变性/证明义务）+ 发射诊断码 |
| ④a 求值 | Evaluator.kt evalStmt()（:160） | 解释器执行（脚本宿主与 run-script 走这条） |
| ④b 生成 | JsCodeGen.kt genStmt()（:793） | 发射 JS；深拷/`__dc` 注入等由这里的命中表驱动 |

以 `unchecked <语句>` 为参照实现：Lexer 无新 token；Parser parseUnchecked()（:796）；Checker 里 uncheckedDepth++（:767）并以此闸住 E-IMMUT-ASSIGN（:612）等检查；Evaluator 直接执行内层语句（:194）；JsCodeGen 生成 `// unchecked` 注释后透传内层（:822）。新语句若也设「检查豁免」语义，照此五处对齐。

> 若新语法涉及**模块**层面（挂载、限制引用），另看 ModuleTree.kt / MultiModule.kt；涉及**注解**行为，另看 annotationproc 流水线（处理器先于 B/C 检查跑）。

### 3.3 诊断码命名

- 三族：E-（错误，阻断编译）、W-（警告）、D-（提示/补充）。全大写、连字符组词、动词-对象或对象-属性式：E-IMMUT-ASSIGN、E-CANNOT-PROVE、W-PROP-UNBOUND、D-DEEP-COPY。全库约 100 个诊断码，其中 compiler 主源里以字面量出现的 E 码约 60 个（近似，**待核**）。
- 发射时给**可操作的中文信息**，附修复建议：

  ```kotlin
  d.error("E-IMMUT-ASSIGN", s.pos,
      "`$lhs` 是不可变的，不能赋值。要改它？声明时写成 `var $lhs : @mut T`")
  ```

- 新增诊断码的完整义务：发射点 → cli/Main.kt 的 explain 表（含义 + 修复建议） → compiler/…/DiagCoverageTest 加一个触发用例 → cli/…/ExplainCoverageTest 的 knownCodes 登记。后两个测试不通过就等于没合入。
- 诊断码可经 `sublimationc explain <CODE>` 查含义；explain 表是用户面对的唯一权威解释，措辞与修复建议要写人话。

## 4 测试要求

### 4.1 分层回归

| 层 | 测试 | 形态 |
|---|---|---|
| 词法/语法 | frontend LexerTest / ParserTest / ParserSnippetTest | 断言 token 流与语法树形态 |
| 语义 | compiler CheckerTest / TypeInferTest 等 | 对 checkFile(parseSource(src, "t")).diags 断言诊断码存在/不存在 |
| 诊断覆盖 | DiagCoverageTest | 每个已知诊断码一个触发场景，断言其确实产出 |
| 解释器 | interpreter InterpreterTest / GlobalInferenceTest | 求值结果断言（脚本模式另测 --global-inference） |
| 端到端 | compiler e2e：E2ETest / ModuleE2ETest / JsEscapeE2ETest / DailyScriptsE2ETest | subl 源 → Checker → JsCodeGen → node 实跑 → 断言 stdout |
| 工具链 | cli ExplainCoverageTest | explain 表与实发码集合双向一致（不缺码、无幽灵码） |
| LSP/处理器 | LspAnalysisTest / annotationproc 四个测试 | 各自回归 |

改了编译器或解释器，至少跑 :compiler:test 与 :interpreter:test；涉及代码生成或模块系统时务必跑 e2e。

### 4.2 e2e 约定

- e2e 断言 bag.hasError == false（**check 零 ERROR 是硬标准**，不是「差不多过」）；node 不可用时 assumeTrue(nodeAvailable()) 自动跳过，不作为失败。
- e2e 与 examples 双向引用：E2ETest 读 examples/特性巡礼.subl，ParserTest / CheckerTest 读 examples/上下文弥散.subl 等真实文件，DailyScriptsE2ETest 读 examples/日常-*.subl。**改 examples 会联动这些测试**——示例的预期输出变了要同步改测试断言。
- 已知非回归：examples/日常-*.subl 是未入库的协作数据，pristine checkout 里 DailyScriptsE2ETest 必然失败（已知，勿当回归修）。

### 4.3 写 examples 的标准

1. **一文件一特性**，中文文件名（空安全.subl、模式匹配.subl 式）；综合门面放特性巡礼.subl。
2. 文件头部注释标明**预期输出**。
3. sublimationc check examples/<文件>.subl **零 ERROR**；若有 W-/D- 级诊断，须在头部注释说明预期。
4. compile + node 实测输出与头部注释一致：

   ```text
   sublimationc compile examples/模式匹配.subl -o /tmp/m.js && node /tmp/m.js
   ```

5. 示例代码一律当前文法：程序位 `=>`、命题位 `→`、独立 axiom 语句；不出现 unchecked.axiom[p]、线性作用域 %{ } 等旧形态。
6. 单文件模式不挂 stdlib（List/Set/Map/Result 需在文件内自声明）；目录模式自动隐式挂载入口下的 stdlib/。
7. 更新 examples/说明.md 的特性表；若值得回归，在 E2ETest / ParserTest 里加一条引用。

## 5 构建与验证流程

```text
./gradlew build                  # 全量构建六模块
./gradlew :frontend:test         # 词法/语法
./gradlew :compiler:test         # 语义 + e2e（主回归，530+ 例）
./gradlew :interpreter:test      # 解释器回归
./gradlew :cli:fatJar            # 打 build/libs/sublimation.jar（含 Kotlin stdlib，独立可跑）
```

- Gradle 8.10.2 wrapper、Kotlin 2.1.20、JVM 17；测试统一 JUnit Platform，compiler/interpreter 的 tasks.test 把工作目录设到仓库根（测试里 File("examples/...") 相对它解析）。
- 典型验证链：改 compiler → :compiler:test → e2e → 手工 sublimationc check examples/ → compile + node 抽查；标准库改动另跑 check core/logic 等模块目录。
- **排障纪律（重要）**：增量编译的**陈旧类**会以 NoClassDefFoundError、数组越界等形态伪装成测试失败；byte-identical 的测试源仍红时，先 ./gradlew :interpreter:clean（或对应模块 clean）再跑，不要去改测试。
- 内建处理器目录是 **cwd 相对路径** `annotation processer/`（注意此拼写是仓库既成事实，保持现状）——换工作目录运行 CLI 即静默失效；验证处理器行为时留在仓库根。
- CLI **没有 run 子命令**（误输入回退 USAGE、退出码 2；工程执行走 run-script <目录> 回退或 compile + node）。docs/构建与工具链.md 的命令总表仍列有 run，与 cli/Main.kt 现状不符，**待核**。
- 其余命令（parse/tokens/check/compile/run-script/explain、-p、-A、--prover=aggressive 等）见[构建与工具链](构建与工具链.md)。

## 6 提交信息与 PR 约定

本仓库无外部 CONTRIBUTING 文件，约定从提交史归纳（231 条提交，实测分布）：

**前缀**：英文 conventional 类型 + 可选 scope + 冒号 + **中文摘要**；或纯中文动词式开头：

| 形态 | 例子（取自 git log） |
|---|---|
| docs: … | docs: wiki 第三波（值与字面量/theorem/模块/脚本/诊断码 + 04 效应组开张） |
| feat(scope): … | feat(lsp): 结构化视图树 API（布局预览悬浮窗）；安卓工程并入 android/stdlib 检查 |
| fix(scope): … | fix(processor): 保留 UncheckedStmt 包装；checker 支持未绑定类型参；LSP 修复 stdlib 诊断泄漏 |
| chore: / test: … | chore: 移除误提交的临时脚本；test: documentSymbol 工程模式含函数体用例 |
| 中文动词式 | 修复 P-3：lambda 读取捕获的外部可变变量即不纯；清理：移除误提交的临时脚本 |
| 阶段/依据式 | Phase 4：安卓目标线与编译器能力扩展；按《修正案》修正编译器（线性作用域删除、axiom 语句、可变拷贝 4 条规则、箭头统一） |

常见 scope：lsp、processor、compiler、interpreter、parser、lexer、when、examples、hkt、infer、v2.0/异步 等。

**正文**：改动较大时写正文，要点以 - 列出机制/决策/边界，并给出**验证结论**——历史惯例如「compiler 全量回归 537 项全绿」「e2e：CLI 编译 + node 执行零错误」「annotationproc 共 21 项全绿」「多轮收敛（2 轮）」。临时验证脚本要在同一提交或紧随的「清理：…」提交里清掉。

**粒度**：文档与代码变动分开提交（docs: 单独成粒度，如「wiki 第 N 波」「boring doc 05-上下文系统」）；一个提交一个主题。

**PR 标题与描述**：标题沿用同式前缀；描述列出：改了哪些层（源码/测试/文档/示例）、测试证据（哪个 gradle 任务绿、e2e 是否过、compile + node 抽查结果）、是否触碰 § 7 的他人区域、诊断码有无增删（增删须说明 explain 表与覆盖测试已同步）。

**不入库**：idea doc/（决策记录，本地）、examples/日常-*.subl（协作数据）、临时脚本。

## 7 协作边界（请勿触碰）

以下区域他人正在编辑或由专门代理维护，提交前确认无人持有：

- **language-service/…/LspAnalysis.kt**：当前正被他人重写（_facts/_langfacts.md § 9 待补项注明）；LspAnalysisTest 随之不稳定，非本人请勿改。
- **root doc / language-service / annotationproc**：写作代理契约明确「不要触碰 _facts 之外的他人正在编辑的文件（root doc、language-service、annotationproc）」——这三处有专属维护者推进，PR 涉及时先沟通。
- **_facts/**：语言事实表（_langfacts.md）与写作契约（writer-contract.md）由事实抽取/写作代理维护；发现事实过期请登记或提请，勿直接改写。
- **docs/**：本目录是工程文档写手域；新增工程文档（模块布局、诊断码参考、安卓标准库设计）按 README 规划逐步迁入，勿另起目录。
- 临时调试产物勿提交（git log 里反复出现「清理：移除误提交的临时脚本」）。

## 8 速查清单
