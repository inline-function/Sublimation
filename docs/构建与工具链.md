# 构建与工具链

> docs/构建与工具链.md · 工程文档（面向维护者）· 事实来源：cli/Main.kt 的 USAGE（编译器内置说明）、settings.gradle.kts 模块清单

## 命令行总表

```text
sublimationc — M1 词法 + M2 语法 + M3 语义 + M4 代码生成

parse <file.subl>        词法+语法分析，打印语法树
tokens <file.subl>       打印 token 流（含邻接标记）
check <file.subl|dir>    语义分析（弥散/证明义务/纯度/可变性/impl/when 穷尽）
                         目录 = 模块：全树一起检查
check <…> -v             同时输出补充级诊断（类型推导结果等）
compile <file.subl|dir> [-o out.js] [-p …]
                         语义通过后生成 JS（默认打印到标准输出）
run <…>                  工程模式解释执行（入口 main）
run-script <file.subs…>  脚本模式解释执行：顶层语句直接运行（无需 main）；
                         多条脚本互不共享
run-script <dir>         运行目录下所有 .subs 脚本（每个独立）；
                         无 .subs 时按 .subl 工程（main）执行
explain <CODE>           打印诊断码含义与修复建议（如 E-TYPE-MISMATCH）

选项（可多次）：-p <processor.subs|dir> 附加注解处理器（目录装载其全部 .subs）
              -A key=value             传给注解处理器的编译参数（安卓 APT 收工具路径）
              --global-inference       run-script 旗标：全局类型推导
                                       （显式标注 > 构造点 > 使用点 > 默认 Any；脚本模式专属）
              --prover=aggressive      激进证明（仅 compile/check；更彻底的搜索，可能很慢）
              --prove-verbose          提高进度输出频率
              --prove-dump=<路径>      中断时的诊断报告（默认 sublimation-prover-dump.md）
              --prove-interval=<2s/500ms>
```

处理器即 Sublimation 脚本：**文件名 = 处理器名 = 关注的注解**，编译时由解释器解释执行。

### 常用工作流

```text
sublimationc check examples/                 # 一个目录 = 一个模块，单次全树检查
sublimationc check examples/特性巡礼.subl -v # 单文件 + 类型推导补充信息
sublimationc compile core/logic -o logic.js  # 编译模块为 JS
sublimationc run examples/特性巡礼.subl      # 解释执行（工程模式）
sublimationc run-script core/logic/list.subl
sublimationc explain E-IMMUT-ASSIGN          # 查诊断码
```

激进模式：出错前先尽力证出（健全性底线不变——绝不猜测）；`Ctrl-C` 中断并基于 `--prove-dump` 生成诊断报告。

## Gradle 模块布局

| 模块 | 职责 |
|---|---|
| frontend | M1 词法（Lexer）+ M2 语法（Parser）+ AST + token |
| compiler | M3 语义：Checker（可变性/纯度/证明/when 穷尽）、类型推导、Prop 归一与闭包、ArithProve 算术通道、M4 JS 代码生成 |
| interpreter | 大步求值 Evaluator + 宿主函数注册 + 脚本帧；闭包捕获深拷贝在此完整实现 |
| cli | 命令入口（本文的工具链表面）；诊断码解释表常量 |
| annotationproc | 注解处理器流水线：AnnotationScanner + 内建/安卓处理器改写 |
| language-service | LSP：诊断/补全/悬停；分析核心为 LspAnalysis |
| e2e（compiler 模块内） | 端到端：examples 批量解析/检查/执行回归 |

### 构建与测试

```text
gradle :frontend:build                # 各模块独立构建
gradle :compiler:test                # 语义测试 536 例（含 e2e）
gradle :interpreter:test             # 解释器回归
gradle clean :interpreter:test       # 增量污染时的排障第一招（见下）
```

> ⚠️ 踩过的坑：增量编译的**陈旧类**会以 `NoClassDefFoundError`、数组越界等形态伪装成测试失败；byte-identical 的测试源仍红时，先 `:interpreter:clean` 再跑。

## 处理器流水线

1. 源码 parse → AST
2. 注解扫描（`@allMut` 等 APT 引入注解；详见 docs/模块布局 与 docs/诊断码参考）
3. A 处理器跑在 **B/C 检查之前**（处理器可改写代码、补类型）
4. M3 语义检查（含证明义务与纯度传播）
5. M4 JS 生成（`unchecked` 语句生成 `// unchecked` 注释后透传内层）

## 已知边界

- JS 侧深拷贝运行时 `__dc` 对**函数穿透**（不复制函数体/其捕获）；解释器侧完整深拷
- 全局推导仅脚本模式（`--global-inference`）；工程模式必须显式标注
- `examples/日常-*.subl` 为未跟踪的协作数据，被 e2e 引用——pristine checkout 里那条测试必然失败（已知，非回归）
