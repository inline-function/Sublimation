# 安卓标准库设计（core/ 模块化标准库设计原理）

> 本篇是**维护者视角**的设计文档：回答「core/ 为什么长这样、模块之间怎么咬合、新增一个子库要动哪几处」。语言面的容器用法与语法糖不在本文范围（查 wiki/05-工程-标准库总览.md 与 02-类型条目）；本文只写**机制与约束**。文中"安卓标准库"指本仓库的标准库落地形态——core/ 是其通用内核，安卓能力层（`@android` 桥）是其工程层延伸，见 §五与 §九。

## 一、core/ 在工程中的位置：不是 Gradle 模块

`settings.gradle.kts` 只声明六个 Gradle 子工程（frontend / compiler / interpreter / language-service / annotationproc / cli），**core/ 不在其中**。core/ 是一棵纯 `.subl` 资源树：

- 它不参与任何 Gradle 编译产物，没有 build.gradle.kts，Kotlin 侧没有任何代码引用它的路径——除了测试（§七）。
- 编译器对它的识别完全靠**目录约定**：`ModuleTree.kt` 以编译入口（cwd 或 `check`/`compile` 给定的根目录）下的 `core/` 子树为标准库包（ModuleTree.kt:51 `STDLIB_MODULE`）。换言之，core/ 之所以是标准库，是因为它"恰好"叫 core 且长成包形态（§三），不是因为构建系统登记了它。
- 推论：把 core/ 挪到别处、或改名、或在里面直接放 .subl 文件，都会使它**静默退出**标准库身份（用户工程回退为普通模块）。这条是 §八扩展指南里多条约束的来源。

## 二、目录即模块与 .settings 挂载（P0 模块系统，决策 76）

### 2.1 目录即模块

每个目录（含根 `/`）是一个模块；同模块内所有 `.subl` 文件**共享一个 Symbols**（ModuleTree.kt:10 注释）。core/collection 的 7 个 .subl 互相直接可见——`list.subl` 直接用 `typeclass.subl` 声明的 Functor，`optional.subl` 直接引用 `result.subl` 的 Result，无需任何挂载声明。模块的 absPath 是相对根的 `/` 连接路径，根模块为空串。

### 2.2 .settings 文件

规则（loadSettings，ModuleTree.kt:99）：

- 文件名 = `<目录名>.settings`，与模块一同加载；根模块**没有** settings（P0 限制）。
- 逐行一条指令，只支持 mount；忽略空行与 `#` 注释（parseSettingsFile，ModuleTree.kt:118）。
- 路径两种等价写法：斜杠形 `mount core/math` 与点分完整包名形 `mount core.math`（:139 归一化为斜杠形）。
- 挂载可带别名：`mount core.math as m`，之后限定位 `m.gcd(...)`。

core 内 16 个 .settings 的实际内容是"一句标题注释 + 零至一条 mount"（本次全部实测），例如：

```
# core.logic —— 命题演算/等式推理/量词定理（依赖 core.math）
mount core.math
```

### 2.3 挂载语义

四条语义由 ModuleTreeDriver 实现，全部可由诊断码观测：

1. **传递闭包（"收编即全收"，用户拍板 Q2）**：挂载 T 则 T 自身挂载的一切也一并可达（mountReach，ModuleTree.kt:283 附近）。core.classic 挂 core.logic、logic 挂 core.math → classic 内裸名 `gcd` 可用。
2. **只向下流淌**：祖先的挂载对后代可见；后代的挂载对祖先不可见；兄弟模块互不可见（visiblePathsOf / visibleChild，ModuleTree.kt:310 与 370 附近）。
3. **完整包名展开**（expandPackageMounts，ModuleTree.kt:220）：`mount core.math` 时前缀包 core 也被隐式挂载（本地名未被占用时），故 `core.math.gcd(...)` 与 `math.gcd(...)` 等价。
4. **校验**：挂载目标不存在 → E-UNBOUND-NAME；本地名与挂载名冲突 → E-DUP-DECL；settings 语法错 → E-PARSE-SETTINGS；挂载链成环 → E-CIRCULAR-MOUNT（cycleDetect，ModuleTree.kt:263 附近）。

工程模式中没有源码级 import 语句（Parser 无 ImportStmt，见 _langfacts §2）；跨模块引用一律靠 mount + 限定引用 `a.b.c`，或裸名（裸名可见集见 §三末）。

## 三、core 隐式挂载机制（决策 78，用户拍板 B）

core 对用户工程不是"可选依赖"，而是**默认导入**。机制链路（ModuleTree.kt）：

1. **候选定位**（:57 `STDLIB_DIR_CANDIDATES = ["core", "test/core"]`）：编译入口下按优先级找 core 包目录；找到 `test/core/` 而根下无 `core/` 时把它**嫁接**为根的 core 子树（graftStdlib，:78）。
2. **形态判定**（isStdlibPackage，:86）：core 包必须**只含子包目录、无直接 .subl 源文件**。用户自己的同名 core/（目录下直接有源文件）保持普通模块语义，不被劫持——这正是 §一"挪了就失效"的具体判据。
3. **隐式注入**（injectCoreMounts，:244 附近）：为树中**所有非 core 自身及其子包**的模块追加 `mount core` 及全部子包（mount core.collection 等）。注入的挂载不经本地名冲突检查：本地同名子目录/别名优先，仅跳过对应子包。core 自身与子包不注入（自挂会成环）。
4. **裸名默认可见**（bareVisibleOf，:340 附近）：根级 core 包对任何模块裸名可见——Kotlin 默认导入语义。用户工程里 `List/Ok/Err/size/filter` 等裸名默认可用。

判定式表述（隐式注入的触发条件）：

$$\frac{\texttt{isStdlibPackage}(\text{core}) \qquad m \notin \text{core} \cup \text{core}/*}{\texttt{mounts}(m) \mathrel{+}= \{\text{core}\} \cup \text{core}/*} \quad (\text{决策78·隐式挂载})$$

$$\frac{\texttt{mount}(m, T) \qquad \texttt{mount}(T, U)}{\texttt{visible}(m) \ni U} \quad (\text{Q2·传递闭包})$$

隐式挂载的一个直接后果：core 内任何子库的新增符号会**立刻对所有用户工程可见**——这是便利，也是 §八"不要随便往 core 塞名字"的约束来源。

## 四、core 子库职责一览（实际目录清单）

本次 glob core/ 实测：16 个子目录、17 个 .settings（core/number 下为 num.settings，见陷阱）、41 个 .subl 文件，core/ 根下无直接 .subl（符合 isStdlibPackage）。

| 模块 | .subl 文件 | .settings 挂载 | 职责 | 函数形态 |
|---|---|---|---|---|
| core/collection | list / map / optional / result / set / tuple / typeclass | 无（叶子） | List/Optional/Result/Set/Map/Tuple 容器 + Functor/Foldable/Monad 类型类；同模块互见 | 纯 .subl 实现（enum + fun + impl） |
| core/math | math | 无（叶子） | Nat 算术工具 gcd/lcm、sqrt（由 pow 定义）、Math 系内建 | 混合：gcd/lcm/sqrt 为普通实现，mathMin…mathTan 为 @root |
| core/logic | logic | mount core.math | 命题演算/等式推理/量词定理（refl/sym/trans/MP/量词四条…） | 纯 @theorem 无体 |
| core/classic | classic | mount core.logic | 经典逻辑定理（tertiumNonDatur/doubleNegation/contraposition） | @theorem 无体，含一条 @classic 标注 |
| core/zfc | zfc | 无（叶子） | ZFC 八组非逻辑公理（外延/配对/并集/幂集/无穷/替换/选择…） | 纯 @theorem 无体 |
| core/number | num | 无 | Num 标记类型类（全局类型推导的数值泛型锚点，仅 Rat 一个实例） | class + impl |
| core/string | string | mount core.collection | 字符串内建 concat/length/charAt/substring/strCmp/toStr/parseNat/strSplit… | 全 @root 无体 |
| core/real | real | mount core.collection | Rat 浮点内建 toRat/parseRat/abs/floor/ceil/pow | 全 @root 无体（sqrt 注释标注仅脚本模式可用，见 §五陷阱） |
| core/json | json | mount core.collection | JSON 内建 jsonParse/jsonGet/jsonAt/jsonStr/jsonToList…（Json 不透明内建类型） | 全 @root 无体 |
| core/io | io | mount core.collection | IO 内建 print/readLine/readFile/writeFile/appendFile/fileExists/readDir/getArgs/sleep | 全 @root 无体 |
| core/async | async / channel / flow / mutex / task | mount core.collection | 异步运行时层：Task/Flow/Mutex/Channel + runBoth/runSeq/delay/collect*/withMutex/channel* | 全 @root 无体（@impure @async，走 Channel/Mutex/Flow 小运行时） |
| core/time | time | 无（叶子） | timeNow | @root 无体 |
| core/random | random | 无（叶子） | rand | @root 无体 |
| core/net | net | mount core.collection | 网络**占位**：httpGet/httpPost/socketConnect 签名先行，体为 panic() | 普通有体（panic 占位，落地后改 @root） |
| core/regex | regex | mount core.collection | 正则**占位**（同套路） | 占位声明 |
| core/encoding | encoding | 无（叶子） | Base64/十六进制**占位**（同套路） | 占位声明 |

依赖图（由 16 个 .settings 实测挂载关系汇总）：

```
math ← logic ← classic
collection ← { async, io, json, net, real, regex, string }
叶子（无挂载）：collection math zfc number time random encoding
```

三条设计原理可以读出来：

- **纯库与内建库分流**：collection/math（number/zfc）是"用语言自身写的库"（可移植、无平台依赖）；string/real/json/io/time/random/async 是"签名即文档的内建层"（实现靠 codegen 特判或宿主函数表）；net/regex/encoding 是"尚未落地的占位"（panic 体划出能力边界）。
- **依赖只指向 collection**：所有内建库只需 Optional/List/Result 这些容器类型，因此它们挂 core.collection；没有内建库互相依赖。
- **定理库自成一支**：math ← logic ← classic 与 zfc 是命题层，与值层容器完全解耦（zfc 的 ∈ 是谓词不是值层 in，见 zfc.subl 头注）。

## 五、内建函数分层：@root / @host / @android

无体函数的豁免链（Symbols.kt:246-270，按顺序判定）：

| 层 | 注解 | 谁豁免无体 | 门 | 实现 |
|---|---|---|---|---|
| 证明层 | @theorem | 无体定理函数 | 无（登记进定理空间） | 编译期擦除，值级调用 → null（§六） |
| 语言层 | @host | 脚本模式宿主函数 | 无白名单 | 解释器侧 Interpreter.register 注入（Interpreter.kt:55/154-172，合成注解为 host 的无体 FunDecl） |
| 工程层（通用） | @root | 内建声明 | **ROOT_WHITELIST**（Types.kt:283，名字全集 = builtinimpure + builtinPure 的键） | JsCodeGen 按名特判翻译为原生 JS，不生成函数定义 |
| 工程层（安卓） | @android | 安卓内建声明 | **ANDROID_WHITELIST**（AndroidBuiltins.kt:21） | JsCodeGen.androidCall 桥接 `__dshAndroid(...)`；桌面/node 注入空操作桩保证产物可运行 |

设计要点：

- **@root/@android 是白名单门 + 按名特判**：`@root fun foo(...)` 的 foo 若不在 ROOT_WHITELIST 内 → E-ROOT-NOT-ALLOWED；普通无体函数不标 @root → E-FUN-NO-BODY。白名单与 codegen 特判表同源——加一个 @root 名字必须同时改两侧（Types.kt 内建表 + JsCodeGen.call 特判），这一约束写进了 ROOT_WHITELIST 的注释（Types.kt:288 附近）。
- **@host 不经白名单**：宿主函数是**运行时注入**的，语言层只负责"放行无体 + 用注入的签名做类型检查"。@host 声明不出现在任何 .subl 源码里（core 内实测仅 real.subl:20 一句注释提到它）——它是脚本模式的私有机制，工程模式不生产它。
- **两种模式的覆盖面不一致**：math.subl 头注"Math 系……脚本模式由宿主函数表提供"，real.subl:20 明确"sqrt 仅脚本模式可用（宿主函数表注入 @host 声明；编译模式尚未落地 JS 特判）"。同一段代码在 run-script 与 compile 下行为可能不同；其余 @root 的模式差异**待核**。
- **@android 与 @root 同构而非同层**：@android 内建（log/toast/layout/生命周期钩子/intent 系 openUrl…/platform 系 clipboardSet…）白名单更宽（AndroidBuiltins.kt:21），且桥接目标是宿主容器（webview 注入）而非 JS 内建。用户自定义同名函数优先于 @android 桥（JsCodeGen.kt:216-217 注释：仅带体函数算"用户定义"接管名字）。

## 六、@theorem 无体函数：签名即定理的信任来源约定

机制（Diffusion.kt / Symbols.kt / JsCodeGen.kt）：

- 判据：`isTheoremFun = "theorem" in d.annotations`（Diffusion.kt:340）——必须**显式**标注 @theorem；纯 + 返回 Null 但未标注的函数不进定理空间。
- 登记：`syms.theorems[decl.name] = decl`（Symbols.kt:185）；跨模块定理 = 可见路径内各模块 theorems 的并（Diffusion.kt:267/352，随 core 隐式挂载对用户可见）。
- 使用：`∴ q` 与任意证明位把目标与定理**后件做结构合一**；理论参数（`[a, b]`、`[@P]`）是元变量，命题级元变量 p/q 可绑定任意命题，项级元变量 a/b 只绑定到原子命题的直接项位（证明器不支持 CallExpr 内部解构，core/logic 头注）。
- 擦除：JsCodeGen 不生成 @theorem 函数体（:576）；值级调用翻译为 `null`（:1042-1045）。定理函数因此可作普通函数调用——值固定 Null，上下文推导中为空操作。

**信任来源约定**（core/logic 与 core/zfc 头注的成文约定，维护者必须遵守）：

1. @theorem 无体函数 = 签名即定理（即旧文档所称 @axiom 语义）：**定义性/结构性事实，不经证明**。
2. 每条定理必须在注释「依据」中写明信任来源（如"等式的自反/对称/传递是等词理论的标准定律"；zfc 每条公理注"ZFC 中集合相等性的唯一来源"）。公理即"被作者接受的真理"——**可靠性由人负责**，这正是 @theorem 无体签名的语义。
3. 形式去重自律：公理一多就容易互相打架。zfc 头注【健全性】自证八条公理与 core.logic/core.classic 既有定理形式无重叠（那里不出现非区间右操作数的 ∈）；P-3 形式去重未实现，由各库自行保证。
4. 值级调用不产生实现——别在定理函数里写"假装"的体：有体定理照常生成运行时代码（Types.kt:362 注），但 core 内所有定理均为无体形态。

用法示例（zfc.subl 头注官宣的实测形态，当前文法）：

```
axiom ∀x . ((x ∈ s1) ↔ (x ∈ s2))
`set extensionality`<s1, s2>()
∴ (s1 = s2)
```

## 七、跨模块 e2e 测试：位置与依赖

位置：`compiler/src/test/kotlin/sugared/functor/e2e/`，四个文件——E2ETest.kt（基础）、JsEscapeE2ETest.kt（JS 转义）、DailyScriptsE2ETest.kt（脚本集）、**ModuleE2ETest.kt（多模块 + core 标准库，本文相关）**。

ModuleE2ETest 的机制（本次实测源码）：

- `runTree(spec)`：把"相对路径 → 内容"映射写进临时目录 → `MultiModule(dir).checkAll()`（语义检查必须无错）→ `mm.generateJs()` → 写临时 .js → `node` 实跑并断言 stdout 与退出码。
- `coreSpec()`：从**工作目录相对路径 File("core")** 读取 core/ 全树 .subl，内联进测试的临时模块树（key 形如 "core/collection/list.subl"）。⚠ 依赖测试 cwd = 仓库根——换工作目录即静默拿到空标准库（与 annotationproc 的 cwd 相对路径同病，见 _langfacts §8）。
- node 不可用时 `assumeTrue(nodeAvailable())` 整体跳过，不报失败。
- 覆盖情况：M3/M5/M6/M8 多模块 semantics；P2/P3/P5/P6 决策点；v2/v3 标准库补全（strSplit、List any/all/indexOf/slice/sortBy、IO 扩展、同名重载路由、Tuple 族）；core.async 运行时（Task/Channel/Mutex/Flow/@atomic）；core 隐式挂载（"深处子模块也能引用 core 标准库"用例：a/b/c/main.subl 裸名用 size/range）。

依赖关系要点：

- e2e 不依赖 Gradle 产物里的 core（core 不是 Gradle 模块），只依赖**文件系统上的 core/ 目录 + node 可执行文件**。
- 测试内的 core 是"内联副本"——CI 上跑 e2e 等价于跑当前工作树 core/ 的快照；core 与 compiler 的版本一致性由同一 commit 保证，无额外同步机制。
- 反向约束：e2e 里大量用例（range/size/map/fold/setOf/zip…）直接以 coreSpec() 为底，**core 的回归即 e2e 的回归**——改 core 前先跑 compiler 的 test 任务。

## 八、扩展指南：新增一个标准库模块

### 8.1 纯 .subl 模块（无内建）

1. 建目录 `core/<名字>/<名字>.subl`。⚠ settings 文件名必须等于**目录名**（loadSettings 按"目录名 + .settings"查找）。反例：core/number 的文件是 num.settings/num.subl，按约定实际不会被加载（其内容本就无挂载，暂无影响）——是否刻意**待核**，新模块不要模仿。
2. 需要跨包类型就写挂载：`mount core.collection`（斜杠形与点分形等价）。注意依赖图：只向下流淌、兄弟互不可见、不得成环。多数情况挂 core.collection 即可。
3. 文件头按本库惯例写三段：模块名与职责、依赖、机制（@root/纯实现/占位）——core 内 16 个子库的头注都遵守这个格式，签名即文档。
4. 在 ModuleE2ETest 加一条 coreSpec() 覆盖的用例（示例形态见 §七）；node 不可用自动跳过，所以本地与 CI 都安全。
5. 校验你不会破坏 isStdlibPackage：core/ 根下**永远不要直接放 .subl**（否则整个 core 降级为用户模块，全局默认导入失效）。

### 8.2 新增 @root 内建（要动编译器两侧）

1. 在 `Types.kt` 的内建表（builtinimpure / builtinPure）加签名。
2. 在 `ROOT_WHITELIST`（Types.kt:283）加名字——白名单门与 codegen 特判一一对应。
3. 在 `JsCodeGen.call()` 加按名特判（异步类还要登记 CHANNEL_BUILTINS / MUTEX_BUILTINS / FLOW_BUILTINS，checker 在调用点置位、codegen 注入小运行时 class）。
4. core 侧只放 `@root fun 名字(...): T` 无体声明 + 注释依据；脚本模式若要可用，还需解释器侧 `Interpreter.register` 注册宿主实现（否则该内建只存在于编译模式，出现 real.sqrt 式的模式差）。
5. e2e 落点同 8.1 第 4 步。

### 8.3 新增 @theorem 定理

1. 目录挂载：命题层模块挂在 math/logic/classic 链上，或独立叶子（如 zfc）。
2. 形态：`@theorem fun `名字`[参数]: Null <后件>` 无体；参数位元变量（p/q 命题级、a/b 项级、@P 命题参数）。
3. **必须写「依据」注释**——这是信任来源约定的成文义务（§六）。
4. 自查形式去重：新定理后件不得与既有定理后件结构重叠（P-3 未实现，靠人）。
5. 兼容性：旧名定理可保留（core/logic 有"旧名兼容区"，定理搜索按后件合一，新旧皆可命中）。

### 8.4 新增 @android 内建

1. `ANDROID_WHITELIST`（AndroidBuiltins.kt:21）加名字 + `builtinAndroid(name)` 加签名。
2. `JsCodeGen.androidCall` 侧加桥接（资产名 `__dshAndroid`）；生命周期钩子名同步 JsCodeGen 的 7 个生命周期名集合。
3. ⚠ 白名单注释引用的 intent.subl / platform.subl **当前在 core/ 树中不存在**（本次 glob 全库 .subl 无 openUrl/clipboardSet 等名字）——安卓能力层目前只有编译器侧白名单 + 桥接，.subl 声明层落地位置**待核**。

### 8.5 硬约束速查

| 约束 | 违反后果 |
|---|---|
| core/ 根下无直接 .subl | isStdlibPackage 失败 → core 降级为普通模块，隐式挂载与默认导入全部失效 |
| .settings 文件名 = 目录名 | settings 不被加载（静默，净效应取决于其内容） |
| 挂载不成环 | E-CIRCULAR-MOUNT |
| @root 名字在白名单 | E-ROOT-NOT-ALLOWED / E-FUN-NO-BODY |
| 定理形式去重 | 定理搜索歧义（无编译期守护） |
| e2e 的 coreSpec() 依赖 cwd = 仓库根 | 换工作目录跑 e2e → 空标准库，用例大面积失败 |

## 九、已知限制与待核

1. **core/number 的 settings 名不合规**（num.settings）：按 ModuleTree.kt 约定不被加载；内容无挂载故暂无影响，是否刻意**待核**。
2. **安卓标准库的 .subl 层未落地**：ANDROID_WHITELIST 注释宣称的 intent.subl / platform.subl 在 core/ 中不存在；当前安卓能力 = 编译器白名单 + `__dshAndroid` 桥 + 注解处理器（AndroidViewEdits），声明层与文档（boring doc/ 形式化卷另有"安卓标准库设计"卷，体例不同，勿与本文混同）**待核**合并计划。
3. **@root 的宿主/编译模式覆盖差**：sqrt 明确仅脚本模式；其余内建未逐一核对两个模式的覆盖面，**待核**。
4. **net/regex/encoding 是 panic 占位**：调用即抛异常，提醒能力边界；落地改 @root + codegen 特判（三库头注自述）。
5. **隐式挂载不经本地名冲突检查**：注入挂载按目录名追加，本地同名子目录优先时仅跳过对应子包（injectCoreMounts 注释）——用户侧同名覆盖是设计行为（wiki 陷阱 7），不是 bug。
6. **e2e 对 node 的依赖**：CI 环境无 node 时 core 相关用例静默跳过，core 回归可能漏检。
