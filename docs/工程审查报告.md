## 二、已核实的不一致清单（两后端分叉）

先给总表，再逐项展开。表中「解释器」= `run-script`（Evaluator 大步求值），「JS」= `compile` + node（JsCodeGen）。除特别注明外，行为差异均经 wiki 实测探针确认（探针位于 `_facts_tmp`，验后已删除）。

| # | 维度 | 解释器（run-script） | JS（compile + node） | 性质 |
|---|---|---|---|---|
| D-1 | 闭包捕获 | 函数值被深拷时 `copyCapture` 沿父链逐值深拷捕获（快照隔离） | `__dc` 对函数**穿透**（永不拷捕获，活共享） | 既定边界 + 缺陷（见 2.1） |
| D-2 | 元组解构 `var (a, b) = t` | **损坏**：整个元组绑到首分量，其余分量不存在 | `const [a, b] = …` 正常 | 解释器缺陷嫌疑（待核） |
| D-3 | ⊤ / ⊥ 求值 | 均为 `ScriptValue.Null`；`print(⊤)`→`null`、`⊤ == ⊥`→`true` | `true` / `false` | 解释器缺陷嫌疑（违反静态类型 Bool） |
| D-4 | @theorem 函数 | 照常求值函数体 | 整体擦除，值级调用恒为 `null` | 设计差异未写入用户契约 |
| D-5 | Nat 不变量 | `Num(Long)`，算术走 double 通道；`-5` 可入 `Nat` | 统一为 JS number（IEEE double）；负数与 ±2^53 外精度不拦截 | 类型层不变量跨端均不保证 |
| D-6 | 深拷留痕条件 | `bindCopy` 即时求值，不限源形态 | 留痕只在**源为 NameRef** 时包 `__dc` | 判据相同、落地条件分叉 |
| D-7 | panic / async 内建 | Checker 放行、运行时不可达（`InterpreterError`） | 按名特判为 JS 原生（`throw` / Promise） | 已知开口（11 卷 §8.2） |

### 2.1 D-1 闭包捕获：快照隔离 vs 活共享【高】

- **解释器**两段机制（wiki/04 实测）：lambda 创建时**共享创建帧**（`Evaluator` 的 `evalLambda` 直接持有 `frame`），`f()` 会写穿捕获的 `@mut` 对象；只有当**函数值本身被深拷**（作为 `@mut` 绑定的值、或被拷结构体/容器的字段）时，`deepCopy` 的 Fun 分支触发 `copyCapture()`——它用 `copiedFrame` 沿父链收集全部局部并逐值深拷装入新帧，快照在此刻定型（快照双向隔离：读不到外部后续前进、写也落不到原件）。
- **JS 侧**：`__dc` 对函数值穿透（`typeof v !== "object"` 早退），闭包捕获**永不复制**，含函数字段的深拷在 JS 里是浅的；跨 `runBoth` / Flow 边界共享的闭包一律共享捕获，可变状态的并发竞争靠 `withMutex` / Channel 纪律而非拷贝隔离。
- **可观测分叉**（wiki/04 示例 3，同一程序）：`var h : @mut Holder = Holder({ => y.n })` 之后 `y.n = 9`，`h.f()` 解释器输出 `0`（快照隐形），JS 输出 `9`（活捕获）。
- **附带缺陷（解释器独有）**：被扫帧上存在任何闭包变量时，`copiedFrame` 构成自指递归——`@mut var g = { => y.n }` 之后再让含函数字段的结构体触发深拷，即 `StackOverflowError`（wiki/04 示例 6；形式化语义 04 卷 §7 待核 2 已登记）。JS 侧因函数穿透根本不扫帧，无此问题。
- **性质**：`__dc` 对函数穿透是**既定边界**（形式化语义 00 卷 §3.5、06/07 卷均如此记载）；快照隔离效应当前只在解释器成立、而解释器没有并发原语——「拷贝隔离并发」这一效应当前无处成立，设计缺口（待核）。

### 2.2 D-2 元组解构：解释器损坏【高】

- **JS**：`var (a, b) = (1, 2)` 生成 `const [a, b] = …`（`JsCodeGen.kt:799-801` 附近），行为正确。
- **解释器**：`Evaluator` 的 `VarStmt` 分支未判 `destruct` 子句，而 `Parser` 又把 `destruct.first()` 填进 `stmt.name`（`Parser.kt:808-813` 附近）——结果**整个元组绑到第一个分量名**（实测 `print(a)` 输出 `[1, 2]`），`b` 未定义（引用即报「未定义的变量」）。形式化语义 06 卷 §11 待核 2、07 卷 §12 差异 #2、wiki/01-基础-元组与解构 陷阱节均已登记。
- **结论**：解构当前**不是事实上的拷贝触发点**（两后端都不拷），且解释器侧连绑定都是错的。静态检查（`E-TUPLE-DESTRUCT` / `E-TUPLE-ARITY`）完整，故用户在 `check` 阶段看不出问题——只有 `run-script` 才暴露。书写规避：脚本模式用 when 模式解构取元。

探针（两后端对照）：

```subs
var (a, b) = (1, 2)
print(a)            // run-script 输出 [1, 2]（整个元组绑到 a）；compile + node 输出 1
print(b)            // run-script：报「未定义的变量 b」；compile + node 输出 2
```

### 2.3 D-3 ⊤ / ⊥：解释器求值为 Null，违反静态类型【高】

本会话直接核验的三角：

| 层 | 事实 | 出处 |
|---|---|---|
| 静态类型 | `TopExpr`/`BotExpr` 类型为 `Bool` | `Checker.kt:903` |
| JS 生成 | `⊤`→`"true"`、`⊥`→`"false"` | `JsCodeGen.kt:867-868` |
| 解释器求值 | 两者→`ScriptValue.Null` | `Evaluator.kt:270` |

后果（形式化语义 07 卷 §12 差异 #1 引 wiki 实测）：`print(⊤)` 在解释器输出 `null`；`⊤ == ⊥` 为 `true`；`¬⊤` 为 `true`（Null 被当假值）。静态层断言 Bool、JS 后端兑现 Bool、解释器兑现 Null——这是**运行时行为违反静态类型契约**，不像 D-1 那样可以援引「既定边界」解释。是否既定边界**待核**（若非既定，应修 `Evaluator.kt:270` 为 `ScriptValue.Bool(true/false)`）。

探针（两后端对照，当前文法）：

```subs
// run-script 输出 null / true / true；compile + node 输出 true / false / false
print(⊤)
print(⊤ == ⊥)
print(¬⊤)
```

### 2.4 D-4 @theorem：编译期擦除 vs 解释器求值【高】

- **JS 侧**（`JsCodeGen.kt:576`）：`@theorem` 函数不生成运行时代码；值级调用翻译为 `null`（`JsCodeGen.kt:1042-1046` 的 `theoremJsNames` 判定）。
- **解释器**：`Evaluator` 无 theorem 特判（本会话检索 `Evaluator.kt` 无 `theorem` 命中），照常求值函数体——wiki/03-证明-theorem与@simp 实测 `@theorem fun t(): Nat = 7` 在 `run-script` 打印 `7`，compile 后同一调用为 `null`。
- **登记判据本身是清楚的**：`"theorem" in decl.annotations`（`Diffusion.kt` 的 `isTheoremFun`），与 00 卷 I-6 擦除性条款一致；问题只在于**擦除只发生在 JS 侧**，且 `Types.kt:356` 的旧注释仍称「有体定理照常生成运行时代码」，与 `JsCodeGen.kt:576` 的实现冲突（以实测为准，见 §三 3.3）。
- **结论**：定理函数按约定只用于证明位；但语言没有阻止用户在值位调用它，而两后端在值位的行为相反。建议方向见 §六。

### 2.5 D-5 Nat 跨端不变量不保证【高】

`Nat` 的非负性与精度在**两个后端都不被运行时保证**，且静态层与推导层口径互相打架：

| 事实 | 出处 |
|---|---|
| 静态层：一元负号保留操作数类型，`-5 : Nat`，`var n: Nat = -5` 通过 check 并输出 `-5` | `Checker.kt:947` 附近（wiki/01-基础-值与字面量 陷阱 2） |
| 非负性只在命题层：每个 Nat 字面量注入 `n ≥ 0`（`D-NAT-PROP`），类型层不强制 | `Checker.kt:896-900` 附近 |
| 解释器：字面量保留精确 `Long`，但**算术走 double 通道**——`9007199254740991 + 2` 输出 `9007199254740992` | `Evaluator.kt:311-316` 附近（wiki 实测） |
| 解释器：超 Int64 的字面量词法与 check 均通过，运行时报「非法整数」 | `Evaluator.kt:202-203` |
| JS：Nat/Int/Rat 统一为 JS number（IEEE double），负数与超 ±2^53 精度不被拦截 | `JsCodeGen` 数值生成通道（形式化语义 07 卷 §12 差异 #3） |
| 推导层：全局推导把 `-5` 直接推为 `Int`，与 Checker 的 `-5 : Nat` 口径不一致 | `GlobalInference.kt:549` 附近（07 卷同条） |

即：`Nat` 目前是**命题层约定 + 双端共同的运行时现实（都不保证）**。形式化语义 00 卷把 `Nat/Int/Rat → Num/Real` 记为值域映射，未宣称运行时range检查——所以这不是实现 bug，而是**「Nat 承诺什么」这一语言契约本身未在任何用户文档中说清**（待核：是否在 wiki/02-类型条目与 00 卷 §2.1 显式登记该边界）。

### 2.6 D-6 深拷留痕只认 NameRef 源【中】

- 两端**何时深拷**共用同一谓词（`Evaluator.bindCopy` 与 `Checker.binderNeedsCopy`），这是核实过的一致点。
- 但 JS 侧的拷贝是「编译期留痕 + 运行时回放」：Checker 三处留痕条件都要求源表达式是 `NameRef`（`Checker.kt:587/:626/:1299` 附近），并发 `D-DEEP-COPY` 补充级诊断；JsCodeGen 只在留痕非空时注入 `__dc`（`JsCodeGen.kt:319-332`），逐绑定/赋值位点用 `dcWrap` 决定是否包装（`JsCodeGen.kt:790-791`）。
- 结果：`var b : @mut T = T(0)`（构造器源）在解释器里照拷（`bindCopy` 无此限制），JS 里**不生成 `__dc`**（实测编译产物对照）。可观测差异只在「构造器表达式自身闭包了外部状态」的场合；形式化语义 04 卷 §7 待核 4 与 wiki/04 陷阱节均已登记。判据相同而落地条件分叉，属系统性风险面（同 §五 5.3 的「同一语义两处实现」类）。

### 2.7 D-7 panic 与 async 内建：脚本模式 Checker 可过、运行时不可达【中】

- `panic`：Checker 内建表放行（`Types.kt` `builtinPure`），但解释器没有宿主实现——`Evaluator` 的 `callFunction` 兜底抛「未定义的函数 panic」（`Evaluator.kt:533` 附近）；编译模式则特判为 `throw new Error('panic: unreachable')`（`JsCodeGen.kt:1256`）。两端不等价：脚本模式把 unreachable 变成「未定义函数」而非显式停机断言（11 卷 §5.4）。
- async 族：脚本模式对 `Task{…}`/`Flow{…}` 显式拒绝（`Evaluator.kt:268`，「异步特性不在脚本中支持」），但 core 的 `@root @impure @async` 内建（`delay`/`runBoth`/`runSeq`/`withMutex`/`channelPipe` 等 14 个）被 prelude 过滤且未注册宿主实现——脚本里调用它们 Checker 可过、运行时不可达。同理 `emptyTuple`/`mathSin`/json 全族等纯内建亦无宿主实现（wiki/04-效应-@root原生绑定 实测）。
- 11 卷 §8.2 已把这一类登记为「已知开口（实现差异，非 bug 判定）」；本报告维持该口径，但提醒：**「check 过」是脚本模式的唯一门禁，用户在 check 与 run 之间会遭遇静默落差**——建议至少在 CLI 层对脚本模式的不可达内建给 `D-` 级提示（路线 §六 梯队二）。

## 三、诊断文案与实现不符

### 3.1 E-IMMUT-ASSIGN 的建议文案指向依旧报错的写法【高】

本会话逐字节核验的三方证据：

| 来源 | 文案 | 出处 |
|---|---|---|
| 编译器实发消息 | 「`$lhs` 是不可变的，不能赋值。要改它？声明时写成 `var $lhs : @mut T`」 | `Checker.kt:612` |
| CLI explain 表 | 「要么改成 `@mut var xxx = …`，要么换个新变量名」 | `Main.kt:100` |
| LSP 快速修正 | 「使变量可变（声明加 @mut）」——代码注释自述「`@mut var x = …` 即可变」 | `LspAnalysis.kt:1644-1645/:1859` |

而**赋值闸只认注解式**：`isMut(n) = n in muts || parent…`（`Diffusion.kt:27-28`），`muts` 仅由 `declareMut` 在 `"mut" in s.annotations` 时登记（`Checker.kt:583` 附近）。因此按编译器消息写出的：

```subs
var x : @mut Nat = 0      // 按编译器建议改写
x = 1                     // 依旧 E-IMMUT-ASSIGN——类型位的 @mut T 不登记重绑权限
```

类型位 `@mut T` 允许**字段写**（接收者类型是 MutType）但**不允许重绑**——这正是 wiki/04-效应-可变性与深拷贝 陷阱节明示的语义（「E-IMMUT-ASSIGN 只认 `declareMut` 登记的注解式 `@mut var`」）。结论：**实发消息与自身语义矛盾**，与 CLI explain 表和 LSP 快速修正也不一致（三处对同一码给出两种互相排斥的修复指导）。修复方向：将 `Checker.kt:612` 的建议改为 `@mut var $lhs = …`，与 explain 表对齐（路线 §六 梯队一）。

### 3.2 E- 前缀码以 WARN 级发射【中】

`E-PROP-UNBOUND` / `E-QUANT-UNPROVEN` / `E-THEOREM-SEARCH-DEPTH` 在源码中以 `d.warn` 发出，与 E 族「错误（阻断编译）」的命名约定不齐（09 卷 §2.4 实证表、§十一 待核 2；02 卷 §十 待核 2）。已知的有意降级（推导能力边界的温和化）与命名债两种解释，**裁决待核**；裁决前阻断性判断一律以严重级标签而非码前缀为准。

### 3.3 Types.kt:356 注释与 JsCodeGen 实现冲突【中】

## 四、词法与文档层勘误

### 4.1 ≤ / ≥ 是 SYMBOL 而非算符【中】

本会话直接核验的词法事实：

- `Lexer.kt:110-111` 只把 `<=`→`LE`、`>=`→`GE` 收为算符 token；**lexer 没有 `≤`/`≥` 分支**（`'≤' -> …` 那类单分支不存在，与 `⊤`/`⊥`/`→` 等逻辑单 token 不同——`≤` 不在 logicalSingletons）。
- `≤` 走 `isSymbolStart`（`Lexer.kt:231`）→ `readSymbol`（`Lexer.kt:235-242`）→ **SYMBOL token**（连续符号字符合并，`≤≥` 是一个名字）。wiki/01-基础-名字与作用域 已如此登记（「符号名：`∈`、`≤`、`⊕`」）。
- 表达式位：`Parser` 的 `binops`（`Parser.kt:50-56`）与 `symbolCallStart`（`Parser.kt:61`：LT/GT/EQ/NEQ/LE/GE）**只认 Kind，不认 SYMBOL**——`a ≤ b` 依赖中缀糖 D-5（SYMBOL 前后带空格，`Parser.kt:1076`/:1089 附近）解为 `CallExpr("≤", [a, b])`；`a<=b` 则是真正的算符 BinExpr。
- 命题位：`Prop.kt:764` 的归一表把 `"<=", "≤" -> "<="`，故命题层 `≤` 与 `<=` 等价（算术通道差分图按归一后的 `<=` 建边）。

由此得到一组**用户可见的不对称**（未逐项实测，行为标待核）：

| 写法 | `<=`（算符） | `≤`（SYMBOL） |
|---|---|---|
| 粘连 `a<=b` / `a≤b` | 合法（算符中缀） | 中缀糖要求前后空格，粘连形态的行为 **待核** |
| 前缀调用 `<=(1,2)` | 合法（LE ∈ symbolCallStart） | `≤(1,2)` 不在 symbolCallStart，行为 **待核** |
| 命题位 `a ≤ b` | `<=` 归一 | `≤` 归一同结果 | 

结论：`≤`/`>=` 的 Unicode 形在**值位是二等公民**（靠中缀糖、受空格约束），在**命题位与 ASCII 形完全等价**。该事实各层文档均未集中说明（形式化语义 00 卷 §1.2 只规定了 `→`/`=>` 的分野），建议在 wiki/01-基础-值与字面量或调用形式条目补一条对照（路线 §六 梯队三）。
