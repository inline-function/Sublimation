# 诊断码参考

> 给维护者的全量码表与机制手册。读者预设：正在改编译器、加诊断码、或排查「为什么这条诊断没出来/出错了」。

## 0. 读法

- **码**：诊断码字面量，形如 `E-IMMUT-ASSIGN`（族字母 + 连字符大写词组）。规范拼写全大写；`explain` 入参会 `uppercase()`，故终端敲小写也命中。
- **含义 / 修复建议**：浓缩自 EXPLAIN 表项（Main.kt:69–176）；表项原文是「含义。—— 修复建议」两段式，本文拆成两列。
- **源码产生点**：`文件:行` 为主源（非测试）实测发射位；多处发射的给主要位点。标 **待核** = 未找到生产发射点（表内留存或已废弃，见 §3.4 与 §11）。
- 标记：**†** = 显式废弃码（发射器已删）；**‡** = 以非码族严重级发射（阻断性以严重级标签为准，见 §1.3）；**✶** = 无生产发射点。
- 与 boring doc/形式化语义09 的关系：本文给操作视角（码表 + 闸门怎么用），09 卷给形式判断式（`N-EMIT`/`N-GATE-V`/`N-DEDUPE` 等规则名与健全性条款）。两者冲突以源码为准。

## 1. Severity 四级机制

### 1.1 诊断四元组

每条诊断是五元组（Diag.kt:6–12）：

```
δ = (severity, code, pos, message, modulePath)
```

- `severity`：四级枚举 `Severity { ERROR, WARN, HINT, SUPPLEMENT }`（Diag.kt:4）；
- `pos`：`"行:列"`（从 1 计），空串 = 无位置；
- `modulePath`：归属模块 absPath，根模块为 `""`，core 标准库为 `"core/..."`——由 `DiagBag.modulePath` 在 Checker 构造时自动携带，是多模块补充级过滤的键（§2.3）。

发射只有四个入口，各固定一个严重级（Diag.kt:39–42）：`bag.error(...)` / `bag.warn(...)` / `bag.hint(...)` / `bag.supplement(...)`。**码族字母只是命名约定——发射端调哪个入口，才决定阻断性。**

### 1.2 四级对照

| Severity | 渲染标签（Diag.kt:14–16） | 规范码族 | 阻断编译（hasError，Diag.kt:45） | 默认输出 |
|---|---|---|---|---|
| ERROR | `[错误]` | E- | **是** | 是 |
| WARN | `[警告]` | W- | 否 | 是 |
| HINT | `[提示]` | H- | 否 | 是 |
| SUPPLEMENT | `[补充]` | D- | 否 | **否**（仅 `-v`） |

族的语义（形式化见 09 卷 §2.3）：**E 族**断言「语言规范的前提被违反」；**W 族**是「编译器证不出、但不敢断言为错」的出口（证不出 ≠ 错误）；**D 族**是编译器隐式决定（脱糖/推导/深拷贝/命题注入/效应降级）的可审计回声，恒不阻断；**H 族**是程序正确但有更佳写法的supplementary教学提示。

### 1.3 阻断性看严重级，不看码族字母（重要）

`hasError = all.any { it.severity == Severity.ERROR }`（Diag.kt:45）——与码族字母无关。实测存在以 `bag.warn(...)` 发射的 `E-` 前缀码，**不阻断**：

| 码 | 发射位（实测） | 实际严重级 |
|---|---|---|
| `E-PROP-UNBOUND` ‡ | Checker.kt:742（∃ 消去前提不在已知事实）、CallCheck.kt:907（显式供给不成立）、:914（命题参数无 0 元供给） | WARN |
| `E-QUANT-UNPROVEN` ‡ | Checker.kt:735（∃ 引入实例证不出，ERROR）；:754（局部函数无体，**WARN**） | 混合 |
| `E-THEOREM-SEARCH-DEPTH` ‡ | Diffusion.kt:348（定理搜索超深度，默认两跳） | WARN |

同族对照：`E-PROP-AMBIGUOUS`（CallCheck.kt:915）以 `error` 发射、阻断。**读诊断时以 `[错误]/[警告]` 标签判阻断性；写发射端时想清楚该用 `error` 还是 `warn`。**

### 1.4 渲染形态

基本形态（Diag.kt:17）：`[标签][行:列] 码: 消息`；`pos` 为空则省略 `[...]` 段。单文件 check/compile 传 `source` 时追加源码片段上下文（Diag.kt:19–32）：回读该行、行号右对齐、`^` 指到列（`col-1` 以 `coerceIn(0, text.length)` 夹逼）。目录模式不带 source（无片段，待核，见 §11）。

输出通道（Main.kt）：check 报告走 **stdout**（:304 单文件 / :258 目录），compile 报告走 **stderr**（:322，使 stdout 只剩 JS 产物）——两者通道相反，是有意的「诊断/产物分离」。

## 2. 诊断的生命周期与四道闸

产生 → 归并 → 闸门 → 渲染。袋（`DiagBag`）为保序插入，**所有闸门只过滤不重排**（确定性条款，09 卷 N-DET/N-ORDER）。

### 2.1 归并 absorb

`absorb(other)` 直追加 `other.all`（Diag.kt:48）。目录模式在 `MultiModule.runPhases` 把每个模块 Checker 的袋并入总袋。

### 2.2 闸 1：`-v` 补充级闸门

`report(includeSupplement)`（Diag.kt:64–66）：不带 `-v` 时过滤掉全部 SUPPLEMENT；`verbose = args.contains("-v")`（Main.kt:194）是**全局旗标**，对 check/compile、单文件/目录一致生效，与激进证明旗标正交。过滤**只作用于输出**，不作用于 `hasError`——D 本来也不阻断，故 `-v` 与否均不改退出码。

### 2.3 闸 2：多模块 `dropSupplementsOutside`

`dropSupplementsOutside(rootPath)`（Diag.kt:51–53）删掉 `severity == SUPPLEMENT && modulePath != rootPath` 的诊断。唯一调用点：`MultiModule.runPhases` 的 `bag.dropSupplementsOutside("")`（MultiModule.kt:143）。根模块键为 `""`，故即便 `-v` 也看不到 core 标准库等挂载模块自身的推导/方法糖补充——有意设计（用户工程的 `-v` 不被标准库内部噪声淹没）。**只在目录模式存在**：单文件 Checker 未设 modulePath 且从不调用本闸。

### 2.4 闸 3：`dedupe` 三元组去重

`dedupe()`（Diag.kt:56–61）以 `Triple(code, pos, message)` 为键，保留首发。两个触发点（都是**重查**场景）：

1. 类型推导定点反推：泛型调用的 lambda 实参在 ≤8 轮迭代环里重复检查，`if (rounds > 1) d.dedupe()`（CallCheck.kt:837，注释 :804）；
2. 注解处理器改写后重查：`if (checked) bag.dedupe() else checked = true`（MultiModule.kt:113）。

推论：**两处同种错误互不吸收**（位置不同即不同键）——别误以为修一处就够。

### 2.5 旁路：run-script 的 inferNotes

脚本模式（含 `--global-inference`）有一条绕过整个 Φ 的直通通道：全局类型推导产物不进 DiagBag，而由解释器暴露为 `inferNotes`（Interpreter.kt:33–34；元素 `InferNote(severity, code, pos, message)`）。CLI 打印位：Main.kt:392 / :404：

```
interp.inferNotes.forEach { n -> println("[提示] [" + n.code + "] " + n.message) }
```

特征（09 卷 N-NOTE-BYPASS）：标签**硬编码 `[提示]`**（与 `n.severity` 无关）；不打印位置与源码片段；**无任何闸门**（恒打印，不受 `-v` 控制、不经 dedupe/drop）。

两个走旁路的码：

- `D-AUTO-IMPURE`：GlobalInference.kt:670 以 `severity = "SUPPLEMENT"` 发射（停机检查失败 → 自动标 @impure 放行），打印为 `[提示] [D-AUTO-IMPURE] …`——码族字母（规范对应 `[补充]`）与渲染标签双偏差；
- `E-TYPE-CONFLICT`：GlobalInference.kt:332/:349/:390 在推导期即抛 `InterpreterError`（Interpreter.kt:206–209），被 main 的 RuntimeException 兜底 → 退出码 1，永不作为 δ 进袋。

此外脚本模式下 Checker 的诊断若有 ERROR 级同样抛 InterpreterError；**警告及以下被丢弃**（只取 ERROR 级拼消息），脚本用户看不到 W/H/D 级袋内诊断（待核：是否有意，§11）。

## 3. explain <CODE> 查表语义

### 3.1 纯查表

`explain <CODE>` **不读源码、不跑管线、不做任何分析**（Main.kt:182–192）：

- 命中（`EXPLAIN[upper(code)] != null`）：stdout 打印 `$code — <表项文本>`，退出码 0；
- 未命中：stderr 打印 `[错误] 未收录诊断码 $code（现有：<字典序全量码列表>）`，退出码 2——失败列表本身是全表目录的副带入口（106 条会刷很长一屏）。
- 入参先 `uppercase()`（Main.kt:184）；无模糊匹配、无别名、无前缀补全。

### 3.2 EXPLAIN 常量

`val EXPLAIN: Map<String, String>`（Main.kt:69–176），106 条，本文全量码表即由该 map 抽取。表项固定两段式：「含义。—— 修复建议」。部分表项仍带「错误：/警告：/补充：/提示：」前缀（如 :134/:136/:138 等），是历史写作遗迹，**与实际严重级无绑定关系**。

### 3.3 覆盖不变量（ExplainCoverageTest）

`cli/src/test/kotlin/sugared/functor/ExplainCoverageTest.kt` 以 `assertEquals(knownCodes, EXPLAIN.keys.toSortedSet())` 双向断言：既不缺实码（用户查不到），也无幽灵码。注意：`knownCodes` 是**人工维护清单**（该测试 :14–121），不变量是「表 ⇄ 清单一致」，**不是「表 ⇄ 发射点一致」**。

### 3.4 表收录 ⇏ 现役发射（实测四类失配）

| 类别 | 码 | 状态 |
|---|---|---|
| 历史预留（无生产发射点）✶ | `W-CANNOT-PROVE`、`D-BECAUSE-PROVED`、`D-THEREFORE`、`D-PLUSBECAUSE-PROVED` | 全库仅见于 EXPLAIN 与 knownCodes（待核：预留还是废弃，§11） |
| 显式废弃 † | `E-ANY-CALL`、`E-ANY-STRUCT` | Any 已为自动类型类；DiagCoverageTest.kt:123–127 钉住不再触发 |
| 通道专属 | `E-LEX`/`E-PARSE`/`E-CHECK`（LSP 通道：LspAnalysis.kt:275/:291/:378；CLI 走异常，无码）、`E-TYPE-CONFLICT`（脚本推导通道，§2.5） | 有发射点，但 CLI check/compile 袋里看不到 |
| 码族/严重级错位 ‡ | 见 §1.3 | 有发射点，阻断性与码族字母不符 |

**反向失配**：存在在役发射但**未收录于 EXPLAIN** 的码（`explain` 查不到、knownCodes 也没有）——单独列在 §8，维护者须知情。
