## 一、为什么必须用旗标门控

### 1.1 问题的形状

凝华的类型系统当前处在两个极端之间：一边是 01 卷记录的**宽松实用主义策略**（推导失败填 `synthetic` 占位、合成类型在一切比对中恒放行，Diffusion.kt:413），另一边是 [12 卷](形式化语义12-有界高阶类型.md) 规格的**严格有界高阶子类型**（Kernel Fω<:）。这两者不能同时无条件生效——合成类型在 `<:` 里恒放行的话，`synthetic("(推导:参数)") <: Nothing` 会成立，任何推导失败的表达式都能被当作底类型流向任意上下文，连带 W-UNREACHABLE 与 E-NON-SEALED-MATCH 的判定失效（12 卷 §8.3）。

同时，凝华已有 536 个 compiler 测试、65 个 frontend 测试、52 个 interpreter 测试（_langfacts §8），加上 examples 被 ParserTest/CheckerTest/E2E 引用。**任何一次性收紧类型系统的改动都会击穿这批既有测试**，而且击穿的形态是"原本合法的代码开始报错"——这是最难向用户交代的一类回归。

### 1.2 学术对应：Progressive Types

"用编译器旗标渐进扩展类型系统"在类型系统学术文献中没有直接对应的标准术语，最精确的对应概念是 Politz、Quay-de la Vallee 与 Krishnamurthi（2012）提出的 **Progressive Types**：让程序员**选择类型系统提供哪些静态保证**，而非强制接受全部检查。

它与 Gradual Typing（渐进类型）正交，二者的区别决定了本方案的设计取向：

| 维度 | Gradual Typing | Progressive Types |
|---|---|---|
| 控制对象 | 代码被类型覆盖的**范围** | 类型系统提供的**保证种类** |
| 类型系统本身 | 固定 | 可变／可配置 |
| 未覆盖部分 | 动态检查 | 由运行时安全系统兜底 |
| 适用场景 | 向无类型语言添加类型 | 在已有类型系统中选择性**放松或收紧**检查 |

凝华的需求是后者：不是"给无类型代码加类型"，而是"给已有类型系统增加一档更强的保证，并让用户选择要不要"。

Progressive Types 的形式化通过把类型环境扩展为 `(Ω; Γ)` 实现，其中 `Ω` 是**允许错误集**（allowed error set），类型判断形如 `Ω; Γ ⊢ e : τ`，表示 `e` 将求值为 `τ` 类型的值、发散、或以 `Ω` 中的错误终止。其**渐进声音性定理**（Progressive Soundness）包含两条：

- **Progress**：若 `Ω; Γ ⊢ e : τ`，则 `e` 是值、是允许的错误 `err-ω`（`ω ∈ Ω`）、或可归约；
- **Preservation**：若 `Ω; Γ ⊢ e : τ` 且 `e → e'`，则 `Ω; Γ ⊢ e' : τ`。

这里的关键洞察直接约束了本方案的设计：**Progressive Types 只放松 progress 保证，不放松 preservation 保证**。即使允许所有运行时错误，类型系统仍能保证计算结果不会是无意义的。

映射到凝华：`--types` 各档位改变的是"哪些诊断被发出"（progress 侧的严格度），**绝不改变**"已通过的代码是否仍然类型正确"（preservation 侧）。这正是总纲 I-7「普通模式稳定性」与 I-2「宽松不误报，但闸不绕过」的形式化版本。

### 1.3 相关概念的定位

| 概念 | 提出者／来源 | 与本方案的关系 |
|---|---|---|
| Pluggable Type Systems | Bracha（2004） | 为可选类型系统设定设计目标；Checker Framework 与 JavaCOP 是实例化 |
| Soft Typing | Wright & Cartwright（1997） | 类型系统**可能太弱**而无法类型化程序时插入动态检查；Progressive Types 基于"类型系统**可能太强**"的理念，方向相反 |
| Deferred Type Errors | GHC（Vytiniakis 等，2012） | 把类型错误推迟到运行时；共享"类型系统可能太强"的理念 |
| Like Types | Wrigstad 等（2010） | 同时放松 progress 与 preservation；Progressive Types 仅放松 progress |
| Gradual Typing with Union/Intersection | Castagna（2017） | 带集合论类型连接词的渐进类型系统 |
| Polyglot | Nystrom 等（2003） | 可扩展编译器框架，支持创建类似 Java 的语言编译器、避免代码重复——凝华的 `Checker`/`Symbols` 分层已接近此形态 |

凝华选择 Progressive Types 而非 Soft Typing 或 Like Types 的理由是单一的：**preservation 不可放松**。凝华的设计公理之一是"健全但不完备"（总纲 §1.3），而 Like Types 同时放松两个保证，与该公理直接冲突。

### 1.4 工程先例

旗标门控在编译器工程里是成熟做法，可直接参照：

- **Rust feature flags**：通过 Cargo 的 feature flags 在编译期控制可选特性，实现零成本抽象；实验性特性用 `unstable-` 前缀标注、通过 feature gates 标记。例如 box syntax 由 `BOX_SYNTAX` feature gate 控制，防止在稳定版 Rust 中使用；
- **GCC Rust feature gate**：实现了 `FeatureGate` 访问者模式，对 AST 节点进行检查，未启用的实验性特性触发编译错误；
- **C++26 渐进式 adopt**：新特性默认关闭，需通过 `-std=c++2b` 与 feature test macros 显式启用；Clang 18、GCC 14、MSVC 19.40 分别通过不同标志支持实验性特性。

凝华自身的 `--target=node|browser|wasm`（_langfacts §8，t35）已经是同一模式：新装载模型 S-1 默认关闭（`Target.NODE` 向后兼容），非 node 目标才启用导出 `globalThis.__subl.main`、走宿主桥 `__subl.call(op,args)`、wasm 拒同步 IO 报 E-PLATFORM-UNAVAILABLE。**`--types` 应当复用 `--target` 的实现形态**（枚举参数 + 默认档向后兼容），不另创模式。

从 GCC Rust 的 `FeatureGate` 访问者模式可以直接借一条做法：**门控检查放在 AST 遍历层，而不是散落在各个语义分支里**。凝华对应的落点是 `checkTypeResolvable`（Symbols.kt:325）——它已经是遍历类型 AST 的单一入口，基础方言的 E-KIND-MISMATCH 与 E-NON-PATTERN-HKT 都在这里发。方言（`fomega-bound`）的门控应当加在同一处，不新开遍历。

## 二、旗标设计

### 2.1 形态

```
--types=sub|fomega-bound
```

**只有两档，不做能力阶梯。** 理由：凝华的基础方言**本来就有 HKT**（扁平 kind `★ⁿ→★`，由 `Symbols.kindArity` 承载，配 E-KIND-MISMATCH 与 E-NON-PATTERN-HKT）。既然 HKT 不是方言带来的新能力，就不存在"只开 HKT"这样一个有意义的用户档位；同理，"只开一般 kind 而不开子类型"对用户也没有独立价值——一般 kind 箭头（`𝕂₁→𝕂₂`）的实际拉动需求是构造子级约束（`X <: λY. Optional[Y]` 这类），而它本身就需要 `<:`。故用户可见的选择只有一个：**要不要这个方言**。

| 档位 | 名称 | 含义 | 对应 12 卷 |
|---|---|---|---|
| 基础方言 | `sub`（**默认**，等价于不加旗标） | 无子类型关系；HKT 为扁平 kind 片段、禁嵌套；类型相容走 `≈`/`≡` | §0.5（D-1/D-2/D-3 的基线侧） |
| Fω<: 方言 | `fomega-bound` | 一般 kind 箭头 + 放开 `F[G[Nat]]` 嵌套 + 有界量化 `[X <: τ]` + 算法子类型判定 | §1.2、§2、§4、§5 全卷 |

**内部工程分期 ≠ 用户档位。** 方言的实现工作量大，须分阶段落地（§四），但阶段编号（下称 P0—P3）是**工程内部**的交付切分，不暴露为旗标取值。P1—P3 期间旗标可以只有 `sub` 一个合法值（`fomega-bound` 尚未接通时接受它会导致"以为开了却没开"，比拒绝更糟）；直到 P3 完成才把 `fomega-bound` 加入合法取值。这样任何时刻旗标的语义都是完整的。

设计要点：

1. **默认 `sub`**：不加旗标时行为与引入旗标之前**逐字一致**（总纲 I-7 与 I-9 的硬要求）；
2. **保守扩展是验收标准，不是愿望**：`fomega-bound` 下，基础方言能通过的代码必须照样通过且诊断一致（12 卷 D-1）。§四 的 P0 阶段专为此设基线快照；
3. **不提供 `full` 档**：Full Fω<: 的子类型关系不可判定（Pierce, *Inf. Comput.* 112(1):131—165, 1994，把双计数器机停机问题归约到 F≤ 子类型；Ghelli 进一步证明 F≤ 的类型检查本身发散，年份 ⚠️ 待核）。12 卷 §4.4 已把 (F-SUB-BOUND-FULL) 定为**任何档位都不得启用**的硬约束。旗标设计上根本不给这个值，比给了再拦更可靠；
4. **不提供区间 kind 档**：Stucki & Giarrusso（2021，⚠️ 单源待校验）证明带区间 kind 的高阶子类型理论不可判定（把 SK 组合子项的可转换性归约到子类型关系）。12 卷 §1.3 已禁用。

### 2.2 解析接线

复用 `parseProveFlags` 的既有模式（Main.kt:53—60）。参照 `--target` 的枚举处理，新增：

```kotlin
/** 类型系统方言（boring doc/编译器旗标扩展类型系统指导 §2）。
 *  SUB = 基础方言（无子类型），即引入旗标前的行为；
 *  FOMEGA_BOUND = Kernel Fω<: 方言（12 卷规格，P3 完成后才接通）。 */
enum class TypeLevel { SUB, FOMEGA_BOUND }

private fun parseTypeLevel(args: Array<String>): TypeLevel? {
    val raw = args.firstOrNull { it.startsWith("--types=") }?.substringAfter("=")?.trim()?.lowercase()
    return when (raw) {
        null, "", "sub" -> TypeLevel.SUB
        "fomega-bound" -> TypeLevel.FOMEGA_BOUND
        else -> null   // 未知值：不静默回落，由调用方打印 USAGE 并退出码 2
    }
}
```

**未知值不得静默回落到默认档**。`--types=full`、`--types=hkt`（旧设想的中间档）或 `--types=typo` 若被静默当成 `sub`，用户会以为启用了却没启用，排查成本极高。正确做法是 `parseTypeLevel` 返回 `null` 时打印 `USAGE`（Main.kt:30—46）并以退出码 2 结束——这与 `run` 子命令误输入的回退行为一致（_langfacts §8：没有 `run` 子命令，误输入回退 USAGE、退出码 2）。

两个取值需要**专门的消息文本**，不能只回退 USAGE：

- `--types=full` → 说明凝华采用 Kernel 规则、Full 规则的子类型关系不可判定（编译器可能永不返回），指向 12 卷 §4.4；
- `--types=hkt` → 说明基础方言已包含扁平 HKT、无需旗标；若想要嵌套构造子应用，用 `--types=fomega-bound`，指向 12 卷 §8.1。

`USAGE` 文本需同步追加（照 `--target` 的排版，Main.kt:31—34）：

```
  --types=sub|fomega-bound   类型系统方言（默认 sub，与引入旗标前行为逐字一致）：
             sub=基础方言，无子类型关系（HKT 为扁平 kind 片段、禁嵌套）；
             fomega-bound=Kernel Fω<: 方言，追加一般 kind 箭头、嵌套构造子应用、
                          有界量化 [X <: τ] 与算法子类型判定（Kernel 规则，界须完全相等）
```

### 2.3 透传管线

现有旗标的透传路径是：`parseProveFlags` → `ProveFlags` 数据类（Main.kt:49—51）→ `MultiModule`／`checkFile` → `Checker` 构造器。新增参数须走同一条管线，不另建通道：

| 位置 | 现状 | 改动 |
|---|---|---|
| `Checker` 构造器 | `aggressive: Boolean = false`（:26）等 6 个带默认值的参数 | 追加 `typeLevel: TypeLevel = TypeLevel.SUB`（末位，带默认值，保持既有调用点不破） |
| `MultiModule` 构造器 | `aggressive`/`proveVerbose`/`proveIntervalMs`/`proveDumpPath`/`target`（:25—34），私有字段 `agg`/`pv`/`pim`/`pdp`（:35—38），透传给 Checker（:65、:110） | 追加 `typeLevel` 参数与私有字段，两处透传点（:65、:110）同步 |
| `Main.kt` compile 分支 | `MultiModule(path, aggressive = pf.aggressive, …)`（:261）、`checkFile(ast, aggressive = true, …)`（:313）、:330—331、:341 | 四个调用点补 `typeLevel = tl` |
| `Main.kt` run-script 分支 | `Interpreter(globalInference = …)`（:369、:392—395） | 脚本模式**是否受 `--types` 影响需明确决策**，见 §2.4 |

关键约束：**所有新增参数必须带默认值且置于参数表末位**。`Checker` 与 `MultiModule` 在测试里被大量以位置参数／命名参数混合方式构造（compiler 536 个测试），插入中间位置会击穿这批调用点。`MultiModule.target`（:33）就是按这个规矩加的（注释明确写了"默认 node 向后兼容——-A/SfA 路线不传本参"）。

### 2.4 脚本模式的作用域决策

`--global-inference` 的作用域被明确限定为"**脚本模式专属，编译模式不受影响**"（USAGE :37—38）。`--types` 应当取**相反的口径**：编译模式与脚本模式**都受影响**，理由是子类型判定属于类型检查层，而脚本模式管线同样包含语义检查（总纲 §3.13：词法 → 语法 →〔可选〕全局类型推导 → 语义检查 → 解释求值）。

但有一处必须排除：**`.subs` 每文件独立执行、互不共享、无需 main**（_langfacts §7）。跨文件的类型约束在脚本模式下本就不成立，方言的有界量化在单文件脚本里的价值有限。落地策略是 `fomega-bound` 在脚本模式下**照常生效但降级警告**：遇到依赖跨模块符号的界时报 W-BOUND-UNRESOLVED（新增提示码），不阻断执行。这条须在实现前定稿，登记为 §六 待决项。

## 三、落地路线（工程分期 P0—P3）

分期编号 P0—P3 是**工程内部的交付切分，不是旗标取值**（§2.1）。每阶段独立可交付、独立可回归、独立可回退。**不得跨阶段合并提交**——一旦 P2 出问题，合并提交会让 P1 一起被回退。

关键原则：**P1—P3 期间旗标只有 `sub` 一个合法取值**，`fomega-bound` 直到 P3 完成才接通。P1/P2 的方言代码全部写在 `if (typeLevel == FOMEGA_BOUND)` 分支内，但该分支在 P3 前不可达——这样既保证渐进开发，又保证任何已提交版本里旗标语义都完整（不会出现"接受 `fomega-bound` 却只做了一半"）。

### P0：前置修复（不新增能力，只修不健全点）

12 卷 §9.3 列出的四个既有不健全点中，两个是方言的阻塞项，必须在 P0 修掉：

| 项 | 现状 | 修复 | 验收 |
|---|---|---|---|
| `typeEq` 忽略 `FunType.theory` 位 | Ast.kt:158—161 自述"宽松，后续收紧"；多态函数类型相等判定不健全 | 补齐 `theory` 位比对（逐 `TypeParam` 比 `name`/`arity`，P3 后追加 `bound`） | `typeEq([T](T)=>T, [U](U)=>U)` 为真；`typeEq([T](T)=>T, (Nat)=>Nat)` 为假 |
| `QualifiedType` 折叠为同简单名 `NamedType` | Types.kt:352；01 卷 §7.3 登记的 P0 限制，不同模块同名类型会合并 | 保留模块路径参与 `≡` 判定（折叠仍可作用于显示层） | 两个模块各定义 `Point` 时 `core.Point ≢ util.Point` |

这两项**即使不引入方言也应该修**——它们是当前实现的正确性缺陷。放在 P0 的好处是：修复后的回归可以独立归因，不会与方言的新增行为混在一起。**注意**：这两项修复会改变基础方言自身的判定（多态函数类型不再一律判等、跨模块同名类型不再合并），因此它们**不受**保守扩展 D-1 约束——D-1 只约束"方言 vs 基础方言"，不约束"修复缺陷前 vs 修复缺陷后"。P0 的基线快照须在修复**之后**建立（§4.1）。

另外两项（8 轮定点上限 CallCheck.kt:798—815、`applyKindHead` 补丁 CallCheck.kt:56—62）分别推迟到 P2 与 P3 处理，因为它们只在方言的一般 kind／子类型下才成为问题。

### P1：旗标管线（只接线，不接方言）

**目标**：把 `--types` 旗标解析与透传接通，`fomega-bound` 分支留空（不可达）。

- `TypeLevel` 枚举、`parseTypeLevel`（返回 `null` 触发 USAGE 回退）、`ProveFlags` 同级承载、经 `MultiModule`/`checkFile` 透传至 `Checker` 构造器（§2.2、§2.3 的接线）；
- 此阶段 `parseTypeLevel` **暂不接受 `fomega-bound`**（返回 `null` → USAGE），避免"接受却没实现"；P3 完成时才把它加入合法取值；
- 建立基线快照（§4.1）：P0 修复后，对 examples 全量与 compiler 测试全量跑 `check`，存诊断输出为基线。

**验收**：`--types=sub` 与不加旗标的诊断序列**逐字一致**、且与 P0 基线逐字一致；`--types=fomega-bound` 此时回退 USAGE 退出码 2（因为尚未接通）；`--types=typo` 同样回退。

### P2：方言 kind 层（`fomega-bound` 分支内，仍不可达）

**目标**：在 `if (typeLevel == FOMEGA_BOUND)` 分支内引入一般 kind 箭头、放开嵌套应用禁令。

| 改动 | 落点 | 说明 |
|---|---|---|
| 新增 `Kind` AST 节点 | `frontend/.../ast/Ast.kt` | `KindStar` / `KindArrow(from, to)`；`TypeParam.arity` 保留为派生视图（`arity = 前缀 ★ 的个数`），维持向后兼容 |
| `TypeParam` 增补 `kind: Kind?` | 同上 | `null` 表示沿用 `arity` 推导 |
| 放开 E-NON-PATTERN-HKT | `Symbols.kt:358—362` | 仅 `FOMEGA_BOUND` 分支允许 `F[G[Nat]]`；`SUB` 分支维持禁令 |
| kind 完整比对 | `checkTypeResolvable` | 从计数比对（`\|args\| = arity`）升级为 (F-WF-TAPP) 结构比对；不匹配报 E-KIND-ARROW-MISMATCH（新码） |

**验收**：本阶段 `fomega-bound` 仍不可达，故验收在**单元测试层**直接构造 `typeLevel = FOMEGA_BOUND` 的 Checker 跑用例（不经 CLI）：`F[G[Nat]]` 通过、kind 不匹配报 E-KIND-ARROW-MISMATCH（消息含期望 kind 与实际 kind）、`expand` 深层归一不被深度上限误判为环。**CLI 层验收**：`--types=sub` 与 P1 基线逐字一致（`SUB` 分支未被 P2 改动触及）。

### P3：方言子类型层（接通 `fomega-bound`）

**目标**：引入有界量化与算法子类型判定，并把 `fomega-bound` 加入 `parseTypeLevel` 合法取值。工作量最大、风险最高。

**3.1 AST 与解析**

- `TypeParam` 增补 `bound: Type?`（`null` = 无界，语义上等价于界为 `Top_★`）。这是**最小的必要改动**且完全向后兼容；
- 语法形态 `[X <: τ]` 挂在理论参数位（`FunType.theory`）。**必须先确认不与 `fun f<score <= 100>`（约束形参表，`constraintListAhead` 歧义消解）冲突**——两者都在角表/方括号位，且 `<=` 与 `<:` 词法相近。03 卷已核实 `constraintListAhead` 现有判定明确排除 LT/GT（Parser.kt:315），但引入 `<:` 后须重新确认该排除集是否需扩充（12 卷 §10.6 第一组冲突已排除、剩余两组待核），实现前须先出解析方案；
- `->` 全位非法（lexer 出 ARROW 仅供诊断）、命题蕴含只用 Unicode `→`（writer-contract）。`<:` 是新符号，需在 `Lexer.kt` 增加 token 种类，且确认最长匹配优先级 `<->`(IFF) > `<:` > `<=`(LE) > `<`，不使 `->` 非法约束被绕过。

**3.2 子类型判定器**

新增 `subsumeAlgo`，实现 12 卷 §5.2 的算法规则（F-ASUB-REFL / F-ASUB-BOUND-VAR / F-ASUB-BOT / F-ASUB-TOP / F-ASUB-FUN / F-ASUB-BOUND / F-ASUB-APP）。三条实现纪律：

1. **不实现传递性搜索**。传递性在算法系统里是可容许的元定理（F-ASUB-TRANS-ADMISSIBLE），不是规则。写了传递性搜索就失去确定性，退回声明式系统的回溯爆炸；
2. **每条判断至多一条规则推出**（算法化呈现的定义）。这是 Steffen & Pierce（ECS-LFCS-94-280）消除传递性规则的手法，也是终止性证明（12 卷定理 7.1）的前提；
3. **遇 `MutType` 立即委托 01 卷视图规则**（12 卷 §4.6）。`@mut τ` 与 `τ` 不是子类型关系而是同一结构的两个视图，严格不相等（Types.kt:322 EQ-MUT）。在 Fω<: 层处理可变性会让两套规则打架。

**3.3 与宽松策略的隔离**

(F-ASUB-OPAQUE)（12 卷 §8.3）是硬性隔离条款：子类型判定只在两侧都是**确切类型**时启动，任一侧是合成类型或推导期占位就回落到 `typeLooseEq`（Diffusion.kt:417）。这条不做，宽松策略会把子类型判定整个污染掉，且失效是静默的（12 卷 §0.5 D-2 已点名）。

**3.4 8 轮定点上限的处理**

`CallCheck.kt:798—815` 的定点迭代当前有 8 轮硬上限（防环）。12 卷 §5.5 的结论是：Kernel 系统里终止性由结构归纳保证（定理 7.1），硬上限**不必要且有害**——它会把"未收敛"误报成"类型错误"。

`FOMEGA_BOUND` 分支的正确做法是：把上限替换为**收敛判据**（本轮 `𝕊` 无新绑定即停，现有代码已有这个分支），并保留一个**远高于 8 的保险上限**（如 64）用于防御实现缺陷，触发时发内部错误诊断而非类型错误诊断。`SUB` 分支维持 8 轮不变。

**3.5 诊断码**

12 卷 §8.4 定义的五个新码须全部落地，并同步登记进三处：09 卷码表、`cli explain` 全量表（_langfacts §8）、总纲 §6.3 的"规格预留码"清单（把它们从"预留"移到"现行"）。漏登记会让 `explain E-BOUND-VIOLATED` 返回空。

其中 **E-BOUND-REBINDING** 是凝华特有的诊断：当用户的类型声明**只有在 Full 规则下才成立**时报此码。检测方法是——Kernel 规则判定失败后，用 Full 规则再判一次，若 Full 成功则报 E-BOUND-REBINDING 而非 E-BOUND-VIOLATED。消息文本须明确指出"凝华采用 Kernel 规则，界必须相等"并给出改写建议。这条码把"我们不支持"变成"我们告诉你为什么不支持、以及怎么改"，是旗标门控方案里用户体验的关键一环，也是白话指南与 12 卷 §11 E-3 评估口径依赖的信号。

代价是每次界判定失败多跑一次 Full 判定。**Full 判定可能发散**（定理 7.5、7.6），因此这次探测必须带步数上限（如 32 步），超限即放弃探测、回落报 E-BOUND-VIOLATED。发散风险被上限封住，不传播到编译整体。

**3.6 擦除性**

有界量化**完全擦除**，无运行时表示（总纲 I-6）。这与类型类字典不同——字典是 I-6 的唯一例外（运行时对象，承载方法分派）。`JsCodeGen.kt` 侧只需确认 `theory` 位的 `bound` 不产生任何输出，无需新增擦除逻辑。

**验收**：
- CLI 接通：`--types=fomega-bound` 现在被接受并启用方言；
- Kernel 规则正例：`[X <: Nat](X) => X` 可用 `Nat` 实例化；
- Kernel 规则负例：`∀X<:Top. T` 与 `∀X<:U. T` 之间无子类型关系（即使 `U <: Top`），报 E-BOUND-VIOLATED 或 E-BOUND-REBINDING；
- 界检查：界为 `Nat` 时用 `Any` 实例化报 E-BOUND-VIOLATED；
- 终止性：构造深度嵌套的有界量化类型（如 20 层），确认判定在有限步内返回；
- 隔离性：合成类型参与的比对全部走宽松路径，无 `<:` 判定被触发（日志断言）；
- **保守扩展 D-1**：`--types=sub` 与 P1 基线逐字一致，且 examples 全量在 `fomega-bound` 下无新增诊断。

## 四、回归底线与验收总表

### 4.1 三条不可破的底线

**底线一：默认档逐字一致（总纲 I-7、I-9）。** 同一源文本在 `--types=sub`（或不加旗标）下的诊断序列，必须与 P0 修复后建立的基线**逐字一致**——顺序、内容、位置全部一致。这条用"基线快照对比"验收：P0 修复后、P1 接线前，对 examples 全量与 compiler 测试用例全量跑一遍 `check`，把诊断输出存为基线文件；此后每阶段提交都重跑并 diff。（基线在 P0 之后建立，是因为 P0 的两项修复会正当改变基础方言判定，见 §三 P0 末段。）

`aggressive` 位是这条底线的既有范例：Checker 构造器注释明确写了"默认 false——普通模式行为完全不变"（Checker.kt:25—26），`session` 在 `aggressive=false` 时为 `null`、证明器所有激进分支全部关闭（:37—41）。`typeLevel` 须照此办理：`SUB` 档下所有方言分支**全部不进入**，而不是"进入了但放宽"。

**底线二：preservation 不放松（Progressive Soundness，§1.2）。** 方言只改变"哪些诊断被发出"，不改变"已通过的代码是否类型正确"。具体判据：**`fomega-bound` 下被接受的程序，在 `sub` 下不得出现运行时类型错误**。若方言接受了基础方言会在运行时崩的程序，说明放松了 preservation，属设计缺陷。这与底线一（保守扩展 D-1）方向互补：D-1 保证"基础方言通过的，方言也通过"，底线二保证"方言通过的，不比基础方言更危险"。

**底线三：不引入不可判定路径。** 12 卷 §7.2 的三条定理（Pierce：F≤ 子类型不可判定；Ghelli：F≤ 类型检查发散；Stucki & Giarrusso：区间 kind 的 Fω 子类型不可判定，⚠️ 单源待校验）划定红线。任何档位都不得启用 (F-SUB-BOUND-FULL) 作为**判定依据**，不得引入区间 kind。§3.5 的 E-BOUND-REBINDING 探测虽然会跑一次 Full 判定，但带 32 步上限且结果只用于改善诊断文本、不参与接受/拒绝决策——这不构成"启用 Full 规则"。

### 4.2 分阶段验收总表

| 阶段 | 交付内容 | `fomega-bound` 状态 | 核心验收 | 回归范围 |
|---|---|---|---|---|
| P0 | `typeEq` 补 `theory` 位；`QualifiedType` 保留模块路径 | 不存在 | 两项各有正负例单测 | compiler 536 + frontend 65 全量 |

## 五、风险与回退

| 风险 | 触发形态 | 缓解 | 回退 |
|---|---|---|---|
| 解析歧义：`[X <: τ]` 与 `fun f<score <= 100>` 冲突 | 约束形参表被误解析为有界量化 | 阶段 3 开工前先出解析方案（12 卷 §10.6 待核项）；`<:` 与 `<=` 在 Lexer 层用最长匹配区分 | 换语法形态（如 `[X sub τ]` 关键字形态），不动类型层设计 |
| `theory` 位比对收紧击穿既有代码 | 阶段 0 后大量多态函数类型判定从"相等"变"不等" | 阶段 0 独立提交、独立回归；先跑基线 diff 看击穿面 | 阶段 0 可单独回退，不影响 1/2/3 |
| 子类型判定意外发散 | 实现缺陷导致 (F-ASUB-*) 未按结构递减 | 保险步数上限 + 超限报内部错误诊断（非类型错误）；P3 加终止性压测 | 旗标降回 `sub`（基础方言）；`--types=sub` 不受影响 |
| E-BOUND-REBINDING 探测本身发散 | Full 判定在 32 步内不收敛 | 探测带 32 步上限，超限放弃探测回落 E-BOUND-VIOLATED | 删除探测逻辑，统一报 E-BOUND-VIOLATED（损失诊断质量，不损失正确性） |
| 旗标组合爆炸 | `--types` 与 `--prover=aggressive`／`--global-inference`／`--target` 交互未定义 | 明确正交性：`--types` 作用于类型层，`--prover` 作用于证明器轮次（Checker.kt:41），`--global-inference` 仅脚本模式（USAGE :37—38），`--target` 作用于装载模型（MultiModule.kt:33）。四者互不干预 | — |
| 用户误用方言后无法回退 | 代码依赖了 `fomega-bound` 特性（有界量化、嵌套构造子应用），降回 `sub` 即编译失败 | 每个新诊断码的 explain 文本须说明"该特性需要 `--types=fomega-bound`"；E-BOUND-REBINDING 给出改写建议 | 这是设计意图（特性依赖应当显式），不算缺陷 |

**旗标正交性**值得展开一句：`aggressive` 只影响 `Prover(maxRounds=…)`（Checker.kt:41）与 `ProverSession`（:37—40），`typeLevel` 只影响类型层判定。二者作用于不同子系统，不存在"激进模式下子类型判定也更激进"这种交叉语义——**明确禁止**这类交叉，因为它会让底线三（不引入不可判定路径）变得无法论证：`aggressive` 的既有语义就是"可能很慢甚至不停机"（USAGE :40—41），若让它干预子类型判定，等于给不可判定路径开了后门。

## 六、待决项（实现前必须定稿）

1. **脚本模式下方言的作用域**：§2.4 提出"照常生效但降级警告 + 新增 W-BOUND-UNRESOLVED"，需确认。`.subs` 每文件独立执行、互不共享、无需 main（_langfacts §7），跨模块界约束在脚本模式下本就不成立。
2. **是否需要独立的 `TypeLambda` 节点**：12 卷 §10.1 待核项。透明别名（`Symbols.expand` 消除，Types.kt:352—366）与不透明算子（保留结构、参与 kind 判定）在 (F-SUB-BOUND-KERNEL) 下行为不同——透明别名会让界"意外相等"。若凝华要非透明算子，`TypeAliasDecl` 不够用。
3. **`<:` 的 Lexer token 形态**：新增 token 种类，须确认与 `<=`（LE）、`<->`（IFF）的最长匹配不冲突；同时确认 `->` 全位非法的既有约束（writer-contract）不被新符号绕过。
4. **η 等价是否纳入 `≡`**：12 卷 §4.5 说明当前不纳入是健全方向的保守（拒绝合法程序，不是接受非法程序）。纳入需处理"不同类型的 η 展开带不同域注解"的问题。若不纳入，(F-SUB-BOUND-KERNEL) 的 `≡` 前提会拒绝一部分本应合法的界相等判定。
5. **方差标注**：12 卷 §10.3 待核项。(F-ASUB-APP) 要求构造子各位的方差信息，凝华当前无标注、默认不变。是否引入 `+`/`-` 语法需独立提案——参照极化高阶子类型的方案（极性标记 `+`/`-`、方差为极性集合、基 kind 为 `Ω/V`、箭头 kind 为 `𝕂→𝕂′` 且支持依赖）。**注意该方案的"支持依赖"与 12 卷 §7.3 明确不启用依赖 kind 的取舍冲突**，引入前须重新论证。
6. **`--types` 是否进 `.settings`**：凝华的模块挂载靠 `.settings` 文件的 `mount <路径> [as <别名>]` 指令（_langfacts §2，语言无 import 产生式）。类型档位是工程级配置，逻辑上应当可以写进 `.settings` 而不必每次命令行传参。但多模块工程里各模块档位不一致时的语义未定义（取最严？报错？），需先定这条再实现。
