## 一、规范性质与效力

### 1.1 本规范是什么

本文档是凝华语言的**规范性定义**（normative specification）：它规定语言**应当**如何被解析、如何被检查、如何被求值。任何实现（编译器、解释器、语言服务、代码生成器）都以本规范为符合性判据。

规范用词遵循以下约定：

| 用词 | 含义 |
|---|---|
| **必须**（must）／**不得**（must not） | 强制性要求。违反即为不符合规范的实现或程序 |
| **应当**（should）／**不应当**（should not） | 推荐性要求。偏离须有正当理由 |
| **可以**（may） | 可选项。实现可自由选择 |

### 1.2 效力层级

凝华的设计文档分为若干层级，冲突时按以下顺序裁决：

1. **根文档**（`root doc/`）——最高权威。《上下文系统》《手动证明》《副作用与可变性控制》《模式匹配》《异步》《其他语法糖》《注解处理器》《脚本模式》。
2. **设计文档**（`idea doc/`）——对根文档未覆盖领域的规范性设计：《全局类型推导》《激进模式》《自动类型类》。凡与实现冲突且未裁决的，以实现待修正论。
3. **形式化规范**（`boring doc/`，即本规范）——对前两层的系统性展开与形式化。
4. **实现**（`frontend/`、`compiler/`、`interpreter/` 等）——规范的一个具体实现。与本规范冲突时，以实现待修正论。

**本规范正文以第 1、2 层为语义基准。**凡根文档或设计文档已规定、而当前实现尚未覆盖的语义，本规范一律按已规定语义书写，不作降级描述。

### 1.3 规范的边界

本规范定义语言本身，不定义：

- 具体实现的内部数据结构命名与文件组织（仅在有助于理解规则时以注释形式提及）；
- 标准库 `core` 包中各函数的算法实现（仅定义其类型签名与语义契约，见第九卷）；
- 集成开发环境、构建工具、命令行工具的用户界面细节（仅定义命令行旗标的语义效果）。

## 二、语言概览

### 2.1 定位

凝华是一门**静态类型、带编译期命题证明**的通用编程语言。其核心特征是把类型系统与程序逻辑融合：函数与结构体的签名可以携带**命题**，命题在编译期由证明器验证，验证不通过即为编译错误；命题本身在代码生成阶段被完全擦除，不产生任何运行时开销。

语言名取自物理现象「凝华」——气态不经液态直接凝为固态。与之同构：程序中的命题不经运行时，直接在编译期析出为静态保证。

### 2.2 三条设计公理

以下三条公理贯穿全规范，各分卷的规则均是它们的展开。

**公理一 · 万物皆为表达式。**
语言的每一个语法构造都产出一个值。语句不是独立范畴，而是产出 `Null` 的表达式。因此证明语句（因为-所以语句、分类讨论语句、存在语句、策略语句）均固定返回 `Null`；`return`、赋值、变量声明同样可以在表达式位出现。这一公理的直接后果是：块（`{ … }`）的值由其尾表达式决定，无尾表达式的块值为 `Null`。

**公理二 · 值与命题二分。**
语言存在两个互不相通的世界：

- **值世界**：可求值、可打印、可作为实参传递。 inhabitant 是运行时值。
- **命题世界**：居住于作用域上下文 $\Gamma$，在编译期被证明或否证，**不进入生成代码**。

两个世界的书写形式刻意区分：`x != 0` 是值世界的表达式（类型为 `Bool`，可被求值），`x ≠ 0` 是命题世界的命题（不可求值，只可被证明）。凡值世界的布尔判断不能自动成为命题世界的事实；命题世界的事实也不能被值世界读取。二者之间唯一的桥梁是 `if`／`when` 的分支条件：值世界的条件在分支内被提升为命题世界的事实。

**公理三 · 健全但不完备。**
证明器承诺：凡它证出的命题皆为真（健全性）；它不承诺能证出一切真命题（不完备性）。因此「证不出」不等于「命题为假」。当自动证明失败时，语言提供三条出路：手动证明语句（第四卷）、策略调用（第四卷）、以及唯一的命题逃逸口——公理语句 `axiom`（根文档《手动证明》）。健全性是不可让步的底线：**任何模式下，证明器都不得猜测命题成立、不得启发式近似目标、不得接受未经证明的前提。**

### 2.3 零成本擦除

以下构造在代码生成阶段必须被完全擦除，不产生任何运行时表示：

- 全部类型标注、类型参数（理论参数）、类型类约束；
- 全部命题、上下文（上文／下文）、伴生命题；
- 全部定理函数（`@theorem`）的调用与本体；
- 全部证明语句（`∵`／`∴`／`if[p]`／`when[p ∨ q]`／`∃`／策略）；
- 全部类型别名（`type`）。

**唯一例外**是类型类字典：字典是运行时对象，承载方法实现的分派。

`axiom q` 擦除后应当在生成代码中保留一行注释（形如 `// axiom: q`），以供人工审计。

## 三、编译管线

### 3.1 工程模式

工程模式（`compile`／`check`）的完整阶段顺序：

```
源文本
  → ① 词法分析        Token 流（第一卷）
  → ② 语法分析        抽象语法树 AST（第二卷）
  → ③ 模块树构建      目录扫描、settings 解析、挂载闭包（第八卷）
  → ④ 符号收集（阶段 A）  声明骨架、prelude、纯事实注册
  → ⑤ 注解处理器      AST → AST 变换，多轮至收敛（第八卷 §5）
  → ⑥ 类型可解析性与 impl 完整性（阶段 B）
  → ⑦ 语义检查（阶段 C） 类型、效应、可变性、命题义务（第三至七卷）
  → ⑧ 代码生成        JavaScript（第九卷）
```

阶段 ④⑥⑦ 合称**三阶段检查**。之所以必须分阶段：跨模块的名字解析要求全树符号先齐备，类型可解析性要求符号表完整，而函数体检查依赖前两者的结论。

### 3.2 脚本模式

脚本模式（`run-script`）的管线：

```
源文本 → ① 词法 → ② 语法（scriptMode）→ ③〔可选〕全局类型推导 → ④ 语义检查 → ⑤ 解释求值
```

脚本模式与工程模式的差异（详见第九卷）：顶层允许语句、无模块概念、无产物、依赖仅来自宿主预置。

### 3.3 注解处理器的位置

注解处理器必须运行在**符号收集之后、语义检查之前**。理由：处理器的产出（例如把 `@allMut` 改写为 `@mut`）属于「待合法化的新代码」，变换之后统一送入检查器，才能保证「所有代码都过检查」这一契约——处理器因此无法绕过语言设计。

## 四、元语言与记法约定

### 4.1 词法约定

- 规范正文中的**语言片段**（凝华源码）以 ```subl 代码块给出；
- **元语言片段**（文法产生式、推导规则、算法）以无标注代码块给出；
- 语言中的名字在正文中以 `等宽字体` 标注；
- 诊断码以 `E-`／`W-`／`H-`／`D-` 前缀标注，全大写连字符分隔。

### 4.2 EBNF 约定

文法采用扩展巴科斯范式，元符号如下：

| 记号 | 含义 |
|---|---|
| `x → α` | 产生式：非终结符 `x` 可由 `α` 推导 |
| `α \| β` | 选择 |
| `[ α ]` | 可选（零次或一次） |
| `{ α }` | 重复（零次或多次） |
| `{ α }+` | 重复（一次或多次） |
| `( α )` | 分组 |
| `ε` | 空串 |
| `'tok'` | 终结符（字面词法单元） |
| `Name` | 非终结符（首字母大写） |

产生式**不含**优先级与结合性信息；凝华的表达式解析规则见第二卷 §5，它是文法的一部分而非附录。

### 4.3 判断式

规范的语义部分以**判断式**（judgement）表达。判断式的一般形式为：

$$\frac{\text{前提}_1 \qquad \text{前提}_2 \qquad \cdots \qquad \text{前提}_n}{\text{结论}} \quad (\text{规则名})$$

横线之上是前提（可同时成立的条件），横线之下是结论。规则名置于横线右端括号内，全规范唯一。前提为空时，横线之上留白，该规则为公理式规则。

本规范使用的判断式形式：

| 判断式 | 读法 | 定义卷 |
|---|---|---|
| $\vdash\ \text{src} \Rightarrow \text{toks}$ | 源文本 `src` 词法分析得到 Token 流 `toks` | 第一卷 |
| $\vdash\ \text{toks} \Rightarrow \text{ast}$ | Token 流 `toks` 语法分析得到抽象语法树 `ast` | 第二卷 |
| $\Gamma \vdash e : \tau$ | 在上下文 $\Gamma$ 下，表达式 `e` 具有类型 $\tau$ | 第三卷 |
| $\Gamma \vdash e : \tau\ \langle\!\langle \pi \rangle\!\rangle$ | 在上下文 $\Gamma$ 下，表达式 `e` 具有类型 $\tau$ 且效应为 $\pi$ | 第六卷 |
| $\Gamma \vdash p$ | 在上下文 $\Gamma$ 下，命题 `p` 可证 | 第四卷 |
| $\Gamma \vdash p \Longrightarrow \Gamma'$ | 在上下文 $\Gamma$ 下检查语句，命题义务 discharged 后得到 $\Gamma'$ | 第五卷 |
| $e \Downarrow v$ | 表达式 `e` 求值为值 `v`（大步操作语义） | 第九卷 |
| $\tau \equiv \tau'$ | 类型 $\tau$ 与 $\tau'$ 严格相等 | 第三卷 §3 |
| $\tau \sqsubseteq \tau'$ | 类型 $\tau$ 可隐式转换为 $\tau'$ | 第三卷 §5 |
| $p \equiv_\alpha q$ | 命题 `p` 与 `q` $\alpha$-等价 | 第四卷 §2 |

### 4.4 元变量约定

| 元变量 | 范围 |
|---|---|
| $e$, $e_1$, $e_2$ | 表达式 |
| $\tau$, $\sigma$, $\upsilon$ | 类型 |
| `p`, `q`, `r` | 命题 |
| $\Gamma$, $\Delta$ | 上下文（命题事实集 + 变量类型环境） |
| `x`, `y`, `z` | 变量名 |
| `f`, `g`, `h` | 函数名 |
| `T`, `A`, `B` | 类型名或类型参数名 |
| `C`, `D` | 类型类名 |
| `v`, `w` | 运行时值 |
| $\pi$ | 效应标注（`pure`／`impure`／`async`） |
| $\alpha$, $\beta$ | 类型变量（推导期未知类型） |
| `n`, `m`, `k` | 自然数（元层计数） |
| `K` | 关键表达式池 |
| $\Sigma$ | 符号表 |

### 4.5 上下文 $\Gamma$ 的构成

上下文 $\Gamma$ 是一个二元组 $\Gamma = \langle V, F\rangle$：

- `V`：**变量类型环境**，从变量名到类型的有限映射；
- `F`：**命题事实集**，命题的有限集合（去重，保持注入顺序）。

$\Gamma$ 按作用域嵌套组织为帧（frame）链。$\Gamma \supseteq \Delta$ 表示 $\Gamma$ 的事实集包含 $\Delta$ 的事实集。上下文的操作规则见第五卷。

### 4.6 规则命名前缀

各卷的规则名以卷前缀开头，便于交叉引用：

| 前缀 | 卷 |
|---|---|
| `L-` | 词法（Lexical） |
| `S-` | 语法（Syntactic） |
| `D-` | 脱糖（Desugaring） |
| `T-` | 类型（Typing） |
| `U-` | 合一（Unification） |
| `C-` | 转换（Conversion） |
| `P-` | 命题（Proposition） |
| `R-` | 推理规则（Reasoning） |
| `G-` | 上下文弥散（Gamma / diffusion） |
| `E-` | 效应与可变性（Effect） |
| `M-` | 模式匹配（Matching） |
| `X-` | 模块（eXport / module） |
| `V-` | 求值（Value / evaluation） |

注意：规则名前缀 `E-` 与诊断码前缀 `E-` 含义不同，前者后接大写字母与短名（如 `E-DECL`），后者后接连字符大写词组（如 `E-TYPE-MISMATCH`）。二者不会混淆。

### 4.7 位置与诊断

每个语法节点携带一个**位置**（`行:列`，均从 1 开始计数）。带位置的诊断在输出时必须附带：源码行文本、行号、以及指向出错列的上箭头。诊断分级见第十卷。

## 六、全局不变量

以下不变量对所有实现、所有编译模式（含激进证明模式）恒成立。任何违反它们的行为都是缺陷。

**I-1（健全性）。** 若编译成功，则程序中每一个被编译器接受的命题义务，都在规范定义的推理系统内可证。证明器不得以猜测、近似、或降级为公理的方式通过义务。

**I-2（擦除性）。** 生成代码中不含任何类型、命题、理论参数、定理调用的运行时痕迹（类型类字典除外）。

**I-3（纯度守恒）。** 纯函数体内不得出现不纯表达式；纯函数不得修改其捕获范围外的可变状态；纯函数必须可证停机。

**I-4（不可变默认）。** 变量、结构体字段、函数参数默认不可变；可变性必须显式标注，且必须在类型层可见。

**I-5（检查完整性）。** 进入代码生成的全部抽象语法树，无论是用户书写还是注解处理器产生，都必须完整通过语义检查。

**I-6（诊断确定性）。** 同一源文本在同一编译模式下，产生的诊断序列必须一致（顺序与内容）。

**I-7（普通模式稳定性）。** 开启激进证明模式不得改变普通模式的任何行为。同一份源文本在不加旗标时，诊断输出与产物必须与开启旗标之前完全一致。
