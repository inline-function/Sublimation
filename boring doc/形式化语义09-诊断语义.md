# 形式化语义 · 第 09 卷 · 诊断语义

> **一句话**：编译器对用户说的一切都是「严重级 + 诊断码 + 位置 + 消息」的四元组；本卷规定这个四元组怎么产生、怎么合并、怎么渲染、谁被闸门挡住、怎么查表、以及它如何决定进程退出码。

## 一、本卷的地位与判断系统

### 1.1 判断形式

本卷兑现 00 卷 §3.8 的接口，主判断为：

$$\Phi \vdash \text{prog} \Rightarrow \delta^*$$

读法：在诊断收集环境 $\Phi$（实现为 `DiagBag`，Diag.kt:35）下，程序产生诊断序列 $\delta^*$。围绕该判断，本卷派生四族子判断：

| 子判断 | 读法 | 定义节 |
|---|---|---|
| $\Phi \Rightarrow \delta$ | 单条诊断的产生 | §3 |
| $\textit{render}(\delta, \textit{src}) = \sigma$ | 诊断的输出形态 | §4 |
| $\textit{report}(\Phi, v) = \sigma^*$ | 报告闸门（过滤/去重/排序） | §5 |
| $\textit{EXPLAIN}[c] \mapsto t$ | 码的查表解释 | §7 |

诊断判定不参与类型/命题/效应的推导结果（那些是 01–05 卷的判断），只**观察**它们失败的位置并落袋为安。因此本卷的全部规则都是 Observable 性质：规则左端引用他卷判断的失败（如 $\Gamma \nvdash P$），右端产出一条 $\delta$。

### 1.2 诊断的元组形态

$$\delta = (\textit{sev},\ c,\ \textit{pos},\ m,\ \textit{mp})$$

- $\textit{sev} \in \{\text{ERROR}, \text{WARN}, \text{HINT}, \text{SUPPLEMENT}\}$（Diag.kt:4 的四级枚举）；
- $c$：诊断码，形如 `E-IMMUT-ASSIGN`（码族字母 + 连字符大写词组，00 卷 §6.3）；
- $\textit{pos}$：位置串 `"行:列"`（从 1 计），空串表示无位置（Diag.kt:9）；
- $m$：人话消息（含义 + 修复导向，不含内部决策编号）；
- $\textit{mp}$：归属模块路径 `modulePath`，根模块为 `""`，core 标准库模块为 `"core/..."`（Diag.kt:11；根模块键为空串见 ModuleTree.kt:14/22）。

### 1.3 命名空间裁决（兑现 00 卷 §7 待核 6）

00 卷曾登记待办：效应规则前缀 `E-`（04 卷）与诊断码族 `E-`（本卷）同名异义。本卷正式规定：

1. **位置区分**：诊断码只作为**对象**出现——在判断式的结论中以码字面量出现（如 `E-CANNOT-PROVE@pos`）、在码表中、在 `explain` 的实参中；判断式**规则名**只出现在横线右端的 `(\text{规则名})` 括号内。规则名一律不写成 `E-` 开头的诊断码形态。
2. **本卷规则名一律 `N-` 前缀**（00 卷 §6.2 已分配，此处落实）：`N-EMIT`、`N-RENDER`、`N-DEDUPE` 等。
3. **脱糖规则 `D-`（如 D-5）与补充级码族 `D-`（如 D-BTS）同名异义**：脱糖规则的 `D-` 后接短数字/短名且只在脱糖判断式右端出现；诊断码的 `D-` 后接连字符大写词组且只作为对象出现。
4. 禁止任何规则名与诊断码字面量完全同形地出现在同一位置上下文中；行文中指称码族时一律写「E 族 / W 族 / D 族 / H 族」，不写「E 规则」。

### 1.4 与他卷的接口约定

- 02 卷的证明失败（$\Gamma \nvdash$ 形式的各种形态）→ 本落 \S 9.9 的命题族码；
- 04 卷的效应/可变性闸门违反 → 落 §9.8 的效应族码；
- 08 卷的模块树校验失败 → 落 §9.10 的模块族码；
- 10 卷（注解处理）的诊断按严重级映射进同一 $\Phi$（Main.kt:280/343 的回调），编译后阶段的诊断**只报告不阻断**（Main.kt:284/347）。

## 二、严重级与码族语义

### 2.1 四级枚举与渲染标签

| Severity（Diag.kt:4） | 渲染标签（Diag.kt:15） | 规范码族 | 阻断编译 | 默认输出 |
|---|---|---|---|---|
| `ERROR` | `[错误]` | `E-` | **是** | 是 |
| `WARN` | `[警告]` | `W-` | 否 | 是 |
| `HINT` | `[提示]` | `H-` | 否 | 是 |
| `SUPPLEMENT` | `[补充]` | `D-` | 否 | **否**（仅 `-v`） |

### 2.2 实测计数

对 Main.kt:69–176 的 `EXPLAIN` 表全量抽取（本卷写作时实测，与 wiki/05-工程-诊断码体系.md 一致）：

$$|\textit{EXPLAIN}| = 106 \qquad |E| = 70 \qquad |W| = 10 \qquad |D| = 19 \qquad |H| = 7$$

该计数由 `cli/src/test/.../ExplainCoverageTest.kt` 以 `EXPLAIN.keys == knownCodes` 双向断言强制（§9.5、§7.3）。

### 2.3 码族语义判断式

**E 族 —— 阻断**。语言规范的前提条件被违反；对应他卷判断的**失败**被断言（不是「证不出」，见 W 族）：

$$\frac{\delta = (\text{ERROR},\ c,\ \textit{pos},\ m,\ \_) \in \Phi}{\textit{hasError}(\Phi) = \top \qquad \text{exit} = 1 \qquad \text{compile 拒绝生成 JS}} \quad (\text{N-FAM-E})$$

实现：`hasError = all.any { it.severity == Severity.ERROR }`（Diag.kt:45）；阻断点在 Main.kt:261（目录 check）、:305（单文件 check）、:323（单文件 compile，「拒绝生成 JS」）。

**W 族 —— 证不出，但不敢断言**。程序良构，但编译器**证不出**安全性或用户意图，不敢断言其为错误，只以警告示警（N-SEV-BLOCK 保证它绝不阻断）：

$$\frac{\text{程序良构} \qquad \text{编译器对性质 } P \text{ 既证不出 } \top \text{ 也证不出 } \bot \qquad \neg\,\textit{typeOk}\text{-级失败}}{\Phi \Rightarrow (\text{WARN},\ \texttt{W-}\dots,\ \textit{pos},\ m)} \quad (\text{N-FAM-W})$$

典型：`W-CONSTRAINT-UNPROVEN`（实参是运行时变量，约束表条件证不出，CallCheck.kt:935）、`W-NON-EXHAUSTIVE`（分支可能没走完——穷尽性是运行时性质，编译期只能证「模式集已覆盖构造子集」，证不出就降级为警告）、`W-UNUSED`/`W-UNREACHABLE`（卫生类，不证不成错误）。这与 00 卷 I-1（健全即不猜测）同源：**证不出 ≠ 错误**，故 W 族存在的充要理由是给「证不出」一个不阻断的出口。

**D 族 —— 确认性回声，默认隐藏**。编译器替用户做了一次隐式决定，留下可审计的痕迹：

$$\frac{\text{编译器完成隐式决定 } a \in \{\text{脱糖, 类型推导, 深拷贝, 命题注入, 效应降级}\}}{\Phi \Rightarrow (\text{SUPPLEMENT},\ \texttt{D-}\dots,\ \textit{pos},\ m) \qquad \neg\,\textit{hasError}\ \text{不受影响}} \quad (\text{N-FAM-D})$$

默认不输出（N-GATE-V）；价值是可审计性——用户开 `-v` 即可看到编译器把源码理解成了什么。D 族**永远不阻断**：发射端一律走 `bag.supplement`（Diag.kt:42），严重级恒为 SUPPLEMENT，由 N-SEV-BLOCK 直接免除阻断。

**H 族 —— 教学提示**。程序正确，但存在更佳写法或易误读点：

$$\frac{\text{程序正确} \qquad \exists\ \text{更可读/更安全的等价写法}}{\Phi \Rightarrow (\text{HINT},\ \texttt{H-}\dots,\ \textit{pos},\ m) \qquad \text{不阻断} \qquad \text{默认输出}} \quad (\text{N-FAM-H})$$

典型：`H-ARITH-PRECEDENCE`（语言无运算符优先级，混用 `+`/`*` 时提示加括号，Parser.kt:1134–1143 的 `maybeArithHint` 是解析器 hints 的**唯一**种类，故 Main.kt:300/318 把全部 hints以该码落袋并非误标）、`H-FIELD-SHADOW`、`H-AMBIGUOUS-CTOR`。

### 2.4 阻断性由严重级决定，而非码族字母（N-SEV-BLOCK 与解耦实证）

$$\frac{}{\textit{hasError}(\Phi) \iff \exists \delta \in \Phi.\ \textit{sev}(\delta) = \text{ERROR}} \qquad \text{（与码族字母无关）} \quad (\text{N-SEV-BLOCK})$$

码族字母是**命名约定**（方便 explain 查表与文档分区），阻断性由**发射端选择的严重级**决定。实证：源码中存在若干以 `bag.warn(...)` 发射 `E-` 前缀码的位点，它们**不阻断**：

| 码 | 发射位 | 实际严重级 | 效果 |
|---|---|---|---|
| `E-PROP-UNBOUND` | Checker.kt:742（∃ 消去前提不在已知事实）、CallCheck.kt:907/:914（显式供给不成立 / 命题参数无 0 元供给） | WARN | 不阻断 |
| `E-QUANT-UNPROVEN` | Checker.kt:754（局部函数无体，∀ 引入要求有体） | WARN | 不阻断 |
| `E-THEOREM-SEARCH-DEPTH` | Diffusion.kt:348（定理搜索超深度） | WARN | 不阻断 |

对称地：`E-PROP-AMBIGUOUS`（CallCheck.kt:915）在同一判定族中以 `error` 发射、**阻断**。因此读诊断时**必须以严重级标签 `[错误]/[警告]` 判阻断性，不能以码族字母猜**——这是本卷的第一条操作契约。反向（`W-` 码以 ERROR 发射）当前全库未发现，但 N-SEV-BLOCK 的定义已涵盖该情形。

## 三、诊断的产生与归并

### 3.1 单条诊断的产生

$$\frac{\text{核对位 } \textit{chk} \text{ 判定规则 } r \text{ 被违反} \qquad (\textit{sev}_r, c_r) \text{ 为 } r \text{ 的规范严重级与码} \qquad \textit{pos} = \text{违反点 行:列}}{\Phi \vdash \textit{chk} \Rightarrow \delta(\textit{sev}_r,\ c_r,\ \textit{pos},\ m,\ \textit{mp})} \quad (\text{N-EMIT})$$

四个入口（Diag.kt:39–42）：`error / warn / hint / supplement`，分别固定严重级；`modulePath` 由 `DiagBag.modulePath`（Checker 在构造时设置，根为 `""`）自动携带。发射点分布（实测）：

- 语义层：`Checker.kt`（E-CANNOT-PROVE :651、E-PREMISE-UNPROVEN :640、E-STRATEGY-FAILED :696、E-IMMUT-ASSIGN :612 附近、W-PROP-UNBOUND :662、补充级 :412/:531/:589/:603/:628/:648/:680/:694/:733/:757/:764 等）、`CallCheck.kt`（E-CTX-UNPROVEN :493、E-CONSTRAINT-VIOLATED/W-CONSTRAINT-UNPROVEN :935、E-PROP-AMBIGUOUS :915、E-PROP-UNBOUND :907/:914、D-METHOD-SUGAR :407、D-AUTO-AWAIT :773）、`Diffusion.kt`（E-DEEP-SATURATION :328、E-THEOREM-SEARCH-DEPTH :348）、`WhenCheck.kt`（W-NON-EXHAUSTIVE / E-NON-SEALED-MATCH 等）、`ModuleTree.kt`（E-PARSE-SETTINGS :110、E-CIRCULAR-MOUNT）、`MultiModule.kt:140`（多个模块声明 main → E-DUP-DECL）；
- 解析层 notes 通道：`Parser.kt` 的 `supplements`（D-INFIX :1091、D-TRAILING :1212）与 `hints`（算术优先级 :1139），经 `parseSourceWithNotes`（Parser.kt:1775）返回 `ParseResult`，由 Main.kt:300–301/:318–319 与 MultiModule.kt:52–53 落袋；
- 注解处理器层：`ProcessorApi.kt`（E-PROCESSOR-SCRIPT :292、W-PROCESSOR-SCRIPT :295、H-PROCESSOR-SCRIPT :298、D-PROCESSOR-SCRIPT :301）、`ProcessorPipeline.kt`（E-PROCESSOR-LOAD :41/:44/:56/:117）、结构性编辑失败码 E-PROCESSOR-EDIT。

### 3.2 归并

$$\frac{\Phi_1, \dots, \Phi_n \text{ 为各模块的袋}}{\Phi = \Phi_1 \cup \dots \cup \Phi_n \qquad \text{（序保序拼接）}} \quad (\text{N-ABSORB})$$

实现：`absorb(other)` 直追加 `other.all`（Diag.kt:48）；目录模式在 MultiModule.runPhases（MultiModule.kt:141）把每个 Checker 的袋并入总袋。

### 3.3 解析层失败：异常通道，不是诊断码通道

词法/语法失败（`ParseFailure`、词法异常）在 CLI 的 check/compile 路径上**以异常上抛**，被 main 的 `catch (e: RuntimeException)`（Main.kt:366–368）兜住，输出 `[错误] <消息>`、退出码 1，**不携带诊断码**：

$$\frac{\text{解析失败}}{\text{抛 } \texttt{ParseFailure} \qquad \text{exit} = 1 \qquad \delta^* = \epsilon\ (\text{无码})} \quad (\text{N-PARSE-EXN})$$

`E-LEX` / `E-PARSE` / `E-CHECK` 三码的发射端在 language-service（LspAnalysis.kt:347/:363/:452）；CLI 路径上它们只存在于 EXPLAIN 表中可查。本卷按 00 卷 §7.5 不引用 LSP 行为，仅记录「同码不同通道」的事实。`DiagCoverageTest` 有一条专门测试钉住该划分：`解析失败以异常上抛而非诊断码`（DiagCoverageTest.kt:21–22）。

## 四、渲染形态（render）

### 4.1 基本形态

$$\frac{\delta = (\textit{sev},\ c,\ \textit{pos},\ m,\ \_)}{\textit{render}(\delta) = \text{[标签][}\textit{pos}\text{] } c\text{: } m} \quad (\text{N-RENDER})$$

- 标签：ERROR→`[错误]`、WARN→`[警告]`、HINT→`[提示]`、SUPPLEMENT→`[补充]`（Diag.kt:14–16）；
- $\textit{pos}$ 为空串时 `[$pos]` 段省略（Diag.kt:17）；非空时带双方括号。

### 4.2 源码片段上下文（补充形态）

$$\frac{\textit{source} \neq \text{null} \qquad \textit{pos} = \text{"}l\text{:}k\text{"} \qquad 1 \leq l \leq |\textit{source}|}{\textit{render}(\delta, \textit{source}) = \text{基本形态} \;+\; \begin{array}{l}\text{右对齐 } l \text{ | 源第 } l \text{ 行}\\ \text{对齐空格 | } (k-1) \text{ 个空格加 } \hat{}\ \text{（指到列）}\end{array}} \quad (\text{N-SNIPPET})$$

实现细节（Diag.kt:19–32）：$k-1$ 以 `coerceIn(0, text.length)` 夹逼、箭头只画一个 `^`；行号右对齐宽度取 $|source|$ 行数的十进制位数。以下情形**不追加**片段（Diag.kt:20–25）：`source == null`、`pos` 为空、`pos` 不匹配 `(\d+):(\d+)`、行号越界。

### 4.3 输出通道

| 内容 | 通道 | 位点（Main.kt） |
|---|---|---|
| check 诊断报告（单文件 / 目录） | **stdout** | :304 / :258 |
| compile 诊断报告 | **stderr** | :322 |
| 收尾失败行 `[错误] 语义检查未通过` | stderr | :261 / :305 / :323 |
| JS 产物 | stdout（无 `-o`）或 `-o` 文件 | :272–273 / :333–335 |
| 编译后处理器报告 | stdout；其错误行 `[警告] 注解处理器编译后阶段出错` 走 stderr | :283–284 / :346–347 |
| 脚本模式 inferNotes | stdout | :392 / :404 |
| explain 命中 / 未命中 | stdout / stderr | :190 / :187 |

注意 check 与 compile 对诊断报告的通道选择**相反**（check 走 stdout 使脚本能干净地分离「诊断」与「产物」，compile 走 stderr 使 stdout 只剩 JS 产物）。目录模式（Main.kt:257）调 `report(includeSupplement = verbose)` **不带 source**——即目录模式无源码片段上下文，单文件模式才带。

## 五、报告闸门

报告是三道闸的复合，顺序为「过滤 → 输出」，袋内序列保序。

### 5.1 `-v` 补充级闸门

$$\frac{\neg\,\textit{verbose}}{\{\delta \mid \textit{sev}(\delta) = \text{SUPPLEMENT}\} \notin \textit{report}} \qquad \frac{\textit{verbose}}{\textit{report} = \Phi\ \text{（全族保留）}} \quad (\text{N-GATE-V})$$

实现：`report(includeSupplement)`（Diag.kt:64–66）；`verbose = args.contains("-v")`（Main.kt:194）——**全局旗标**，与子命令位置无关，对 check / compile、单文件 / 目录模式一致生效；对激进证明旗标正交。注意过滤**只作用于输出**，不作用于 `hasError`（N-SEV-BLOCK）：即使补充级被隐藏，阻断行为不变；反之 D 族本来也不阻断。

### 5.2 多模块归属过滤

$$\frac{\textit{sev}(\delta) = \text{SUPPLEMENT} \qquad \delta.\textit{mp} \neq \text{""}}{\delta \notin \textit{report}} \quad (\text{N-GATE-DROP})$$

实现：`dropSupplementsOutside(rootPath)`（Diag.kt:51–53），唯一调用点是 `MultiModule.runPhases` 的 `bag.dropSupplementsOutside("")`（MultiModule.kt:143，v4 诊断决策）。根模块 `modulePath = ""`（ModuleTree.kt:14），故即便 `-v` 也看不到 core 标准库等挂载模块自身的推导/方法糖补充——这是**有意设计**（用户工程的 `-v` 不应被标准库内部噪声淹没）。该闸**只在目录模式存在**：单文件 check/compile 的 Checker 未设 modulePath（默认 `""`），且从不调用本闸。

### 5.3 dedupe 三元组去重

$$\frac{\exists \delta' \in \Phi_{\text{已见}}.\ (\textit{code}, \textit{pos}, m) = (\textit{code}', \textit{pos}', m')}{\delta \text{ 被丢弃（保留首发权威）}} \qquad \frac{(\textit{pos} \neq \textit{pos}' \lor m \neq m')}{\delta, \delta' \text{ 均保留}} \quad (\text{N-DEDUPE})$$

实现：`dedupe()`（Diag.kt:56–61）以 `Triple(code, pos, message)` 为键。两个触发点（都是**重查**场景）：

1. **类型推导定点反推**：泛型调用的 lambda 实参在 ≤8 轮迭代环里重复检查，可能重发同一诊断，循环后 `if (rounds > 1) d.dedupe()` 收敛（CallCheck.kt:804 注、:837）；
2. **注解处理器改写后重查**：处理器改动 AST → 阶段 A/B/C 全部重跑，`if (checked) bag.dedupe() else checked = true`（MultiModule.kt:113）。

推论：**两处同种错误互不吸收**（位置不同即不同键），别误以为只修一处就够。

### 5.4 序

$$\frac{}{\textit{report}\text{ 的序} = \Phi\text{ 的袋内插入序（过滤与去重均不重排）}} \quad (\text{N-ORDER})$$

无任何按严重级或码排序的步骤；补充级「排在最后」只是袋内插入顺序的涌现（补充级往往在检查后段产生），不是排序保证。

## 六、脚本模式 inferNotes 旁路

### 6.1 旁路判断式

脚本模式（`run-script`，含 `--global-inference`）有一条约过 $\Phi$ 的**直通通道**：全局类型推导（GlobalInference）的产物不进 DiagBag，而由解释器暴露为 `inferNotes`（Interpreter.kt:33–34；元素为 `InferNote(severity, code, pos, message)`，GlobalInference.kt:29）：

$$\frac{n \in \textit{interp.inferNotes}}{\text{stdout}:\ \text{[提示] [}n.c\text{] } n.m \qquad \text{不经 } \Phi\text{、不经 render、不受 } \text{-v}\text{ 闸、不受 dropSupplementsOutside、不经 dedupe}} \quad (\text{N-NOTE-BYPASS})$$

实现：Main.kt:392 / :404 的 `interp.inferNotes.forEach { n -> println("[提示] [" + n.code + "] " + n.message) }`。特征：标签**硬编码为 `[提示]`**（与 $n.\textit{sev}$ 无关）；不打印位置与源码片段；只要跑了推导就一定打印（无闸门）。

### 6.2 与标准映射的偏差

- `D-AUTO-IMPURE`：GlobalInference.kt:670 以 `severity = "SUPPLEMENT"` 发射（停机检查失败 → 自动标 @impure 放行），经本通道打印为 `[提示] [D-AUTO-IMPURE] …`——码族字母 `D`（规范对应 `[补充]`）与渲染标签 `[提示]` **双重偏差**，且不受 `-v` 控制（恒打印）；
- `E-TYPE-CONFLICT`：推导冲突（GlobalInference.kt:332/:349/:390）在推导期即抛 `InterpreterError`（Interpreter.kt:206–209，消息形如 `脚本全局类型推导冲突: [E-TYPE-CONFLICT] …`），被 main 的 RuntimeException 兜底（Main.kt:366–368）→ 退出码 1。它永不作为 $\delta$ 出现在 check/compile 的袋里（该码只在脚本模式 + `--global-inference` 下有意义）。

$$\frac{n.\textit{sev} = \text{"ERROR"} \qquad n \in \textit{inferNotes}}{\text{抛 } \texttt{InterpreterError} \qquad \text{exit} = 1} \quad (\text{N-INFER-ERR})$$

### 6.3 旁路的合理性与边界

旁路存在的理由：脚本模式的推导提示是「推导期一次性产物」，不参与编译阻断判定（错误已直接转异常）。代价是两通道码覆盖不一致——`D-AUTO-IMPURE` 与 `E-TYPE-CONFLICT` 只走旁路，工程模式 check 里看不到它们（待核项见 §11）。此外脚本模式下 Checker 的诊断（Interpreter.kt:215–220）若有 ERROR 级，同样抛 InterpreterError → 退出码 1，但**警告及以下被丢弃**（只过滤 ERROR 级拼消息），脚本模式的 W/D/H 级诊断不回显（待核：是否有意为之）。

## 七、explain 查表语义

### 7.1 判断式

`explain <CODE>` 是**纯查表**：不读源码、不跑管线、不做任何分析。

$$\frac{\textit{EXPLAIN}[\textit{upper}(c)] = t}{\text{stdout}:\ \text{"}c\text{ — } t\text{"} \qquad \text{exit} = 0} \quad (\text{N-EXPLAIN-HIT})$$

$$\frac{\textit{upper}(c) \notin \textit{keys}(\textit{EXPLAIN})}{\text{stderr}:\ \text{[错误] 未收录诊断码 } c\text{（现有：}\textit{sorted}(\textit{keys})\text{ 列表）} \qquad \text{exit} = 2} \quad (\text{N-EXPLAIN-MISS})$$

实现：Main.kt:182–192；入参先 `uppercase()`（:184），故终端敲小写也命中，但码的**规范拼写仍是全大写**；无模糊匹配、无别名、无前缀补全。命中路径 `println` 后 `return`（:190–191），退出码 0；失败路径退出码 2（:188），且把全部已收录码按字典序列出（106 条会刷很长一屏——该失败列表本身是「全表目录」的副带入口）。

### 7.2 表项文本约定

EXPLAIN 表项是固定两段式：**含义句**（以「。——」分隔）+ **修复建议**（可操作动作，常用「检查 X / 改成 Y」句式，能给例子的直接给例子）。部分表项仍带「错误：/警告：/补充：/提示：」前缀（如 :130/:135/:137 等），是历史写作遗迹，与实际严重级**无绑定关系**——判断阻断性仍只看 N-SEV-BLOCK。

### 7.3 覆盖不变量

$$\frac{}{\textit{keys}(\textit{EXPLAIN}) = \textit{knownCodes}\ (\text{双向同步，由测试强制})} \quad (\text{N-COVERAGE})$$

`ExplainCoverageTest`（cli/src/test/.../ExplainCoverageTest.kt:124–126）断言 `EXPLAIN.keys.toSortedSet() == knownCodes`：既不缺实码（用户查不到），也无幽灵码（查到一个不存在的码）。但必须注意两点：

1. `knownCodes` 是**人工维护**清单（该测试文件 :14–121），不变量是「表与清单一致」，不是「表与发射点一致」；
2. **表收录 ⇏ 现役发射**。实测四类失配（详见 §9 各表脚注）：
   - 历史预留（无生产发射点）：`W-CANNOT-PROVE`、`D-BECAUSE-PROVED`、`D-THEREFORE`、`D-PLUSBECAUSE-PROVED`（后三者全库仅见于 EXPLAIN 与 knownCodes）；
   - 显式废弃（发射器已删、测试钉住不再触发）：`E-ANY-STRUCT`、`E-ANY-CALL`（Any 已为自动类型类，DiagCoverageTest.kt:123–127）；
   - 通道专属：`E-LEX`/`E-PARSE`/`E-CHECK` 只经 LSP 通道（§3.3），`E-TYPE-CONFLICT` 只经脚本推导通道（§6.2）；
   - 码族/严重级错位发射（§2.4）。

## 八、退出码契约

$$\frac{\neg\,\textit{hasError}(\Phi) \qquad \text{无异常抛出}}{\text{exit} = 0} \quad (\text{N-EXIT-OK})$$

$$\frac{\textit{hasError}(\Phi)}{\text{stderr}:\ \text{[错误] 语义检查未通过} \qquad \text{exit} = 1 \qquad \text{compile 拒绝生成 JS}} \quad (\text{N-EXIT-ERR})$$

$$\frac{\text{用法/前置契约被违反}\ (\text{无源文件、未知子命令、缺参数、-p/-A 缺值、目录接错子命令、explain 未收录})}{\text{stderr}:\ \text{USAGE 或 [错误] 说明} \qquad \text{exit} = 2} \quad (\text{N-EXIT-USAGE})$$

$$\frac{\textit{aggressive} \qquad \text{用户 Ctrl-C} \qquad \text{搜索循环抛 } \texttt{ProverInterrupted}}{\textit{dumpPath}\text{ 写诊断报告} \qquad \text{stderr}:\ \text{[激进证明] 已中断} \qquad \texttt{Runtime.halt}(130)} \quad (\text{N-EXIT-INT})$$

| 退出码 | 语义 | 触发位点（Main.kt） |
|---|---|---|
| **0** | 成功 | check 通过（:306/:264）、compile 产出（:272/:333）、explain 命中（:191）、脚本跑完（:412） |
| **1** | 编译/执行失败 | hasError（:261/:305/:323）；处理器装载失败（:253）；InterpreterError 及任何 RuntimeException（:366–368）；脚本目录无可运行目标（:410） |
| **2** | 用法/契约错误 | 空参数（:179）；explain 缺码/未收录（:183/:188）；缺子命令参数（:193）；-p 缺路径/路径不存在（:208/:210）；-A 缺值（:223）；文件不存在（:241）；目录接非 check/compile 子命令（:246）；未知子命令（:357）；run-script 无目标（:377）或路径不存在（:384） |
| **130** | 激进证明被用户中断 | ProverInterrupted 兜底（:359–365）→ `AggressiveRuntime.writeReport`（Aggressive.kt:140）→ `halt(130)` |

三条操作契约：

1. **halt 而非 exitProcess**：130 路径用 `Runtime.getRuntime().halt(130)`（Main.kt:365）**绕过其余 shutdown 处理立即退出**——包括 :199 为激进模式注册的 `AggressiveRuntime.interrupt()` 钩子；dumpPath 缺省为 `sublimation-prover-dump.md`（:362，仅中断时写）。
2. **1 与 2 的区分是给 CI 用的**：「编译失败」（源码问题，退出 1）与「命令本身用错」（契约问题，退出 2）必须可程序化区分；脚本据此分支重试或告警。
3. **退出码只看 ERROR 级**：W/D/H 任意多条都不改变退出码（N-SEV-BLOCK 直接蕴含）；`hasError` 在报告过滤之前计算，故 `-v` 与否、dropSupplementsOutside 与否均不影响退出码。

## 十、确定性与健全性条款

1. **N-DET（确定性，00 卷 I-8 落地）**：同一源文本、同一编译模式、同一旗标集，$\delta^*$ 的**内容与顺序**都确定。依据：袋为保序插入（N-EMIT/N-ABSORB）、报告只过滤不重排（N-ORDER）、dedupe 保留首发（N-DEDUPE，确定性不受重查次数影响——同一三元组只留首发，重查无论几轮结果一致）、dropSupplementsOutside 不重排。唯一非确定的已知来源是激进模式的搜索调度（受中断时机影响），但那只在 Ctrl-C 时显现为 exit 130 + dump 报告。
2. **N-NOHIDE**：ERROR 级诊断不受任何闸门隐藏——`-v` 闸只过滤 SUPPLEMENT（N-GATE-V）、dropSupplementsOutside 只作用于 SUPPLEMENT（N-GATE-DROP）、dedupe 只吸收三元组全同者（N-DEDUPE）。用户永远不会「看不到阻断错误的全部实例」。
3. **N-SOUND-EXIT**：exit 0 ⟹ 无 ERROR 级诊断（N-EXIT-OK/N-SEV-BLOCK 的逆否）；exit 1 时 stderr 必有可定位的原因（错误行或异常消息）。
4. **N-D-NONBLOCK**：D 族恒不阻断（发射端固定 SUPPLEMENT，N-FAM-D）；D 族的作用是**可审计性**而非正确性——开 `-v` 是用户观察编译器隐式决定的唯一官方窗口。
5. **N-EXPLAIN-CONTRACT**：每个规范码在 EXPLAIN 中恰有一条解释（N-COVERAGE 双向同步）；`explain` 是纯查表，不得有副作用、不需要源文件、失败即退出 2。表项遵循「含义 + 修复建议」两段式（§7.2）。
6. **N-CHANNEL**：诊断有且仅有三条落盘通路——$\Phi$ 袋（check/compile，过 render 与全部闸门）、脚本 inferNotes 旁路（§6，无码闸无渲染）、解析/运行时异常通道（§3.3、N-INFER-ERR，无码）。三条通路的退出码最终统一于 §8 的四值契约。

## 十一、待核与勘误入口

1. **W-CANNOT-PROVE / D-BECAUSE-PROVED / D-THEREFORE / D-PLUSBECAUSE-PROVED 四码无生产发射点**（§7.3/§9）：仅存在于 EXPLAIN 与 knownCodes。本卷按现状登记为「表内留存」——是预留码还是废弃残留，需向语言所有者确认后要么接线、要么从两表中同步移除（注意移除会触发 N-COVERAGE 测试，须同步改 knownCodes）。
2. **码族字母与严重级的错位发射**（§2.4 实证表）：`E-PROP-UNBOUND`/`E-QUANT-UNPROVEN`/`E-THEOREM-SEARCH-DEPTH` 以 WARN 发射。这是有意降级（推导能力边界的温和化）还是命名债，待确认；确认前**一切阻断性判断以严重级标签为准**（N-SEV-BLOCK）。
3. **两通道码覆盖一致性**（承 wiki/05 同款待核）：inferNotes 旁路与 DiagBag 的码集合关系没有形式保证；`D-AUTO-IMPURE` 的 `[提示]` 渲染标签与 D 族规范的 `[补充]` 标签双偏差（§6.2）。
4. **脚本模式 W 级以下诊断不回显**（§6.3）：Interpreter.kt:215–220 仅取 ERROR 级拼消息；脚本用户看不到 W/H/D 级袋内诊断，待确认是否有意。
5. **目录模式无源码片段上下文**（§4.3）：`report` 在目录模式未传 source；多模块下每条诊断的源文本要按 modulePath 回查，当前未实现，待评估。
6. **行号精度**：本卷所引行号均为 _langfacts.md 口径的近似定位（langfacts §9），精确行号待复核；规则以源码语义为准。
7. **LSP 通道**：LspAnalysis 当前由他人重写，本卷仅引用「E-LEX/E-PARSE/E-CHECK 的发射端在 LSP」这一既有事实以划分通道（§3.3），不对其行为做规范。

## 十二、综合示例

一段可运行的工程模式代码，一次触发四个族（`check demo.subl -v`）：

```subl
axiom p                                        // Prop：PAtom("p",[]) 注入模块级作用域

fun main() {
  var n: Nat = 1
  n = 2                                         // E-IMMUT-ASSIGN（E 族：阻断，exit 1）
  ∵ p                                          // 前提已注入，成立（若换成 ∵ q 则 E-PREMISE-UNPROVEN）
  ∴ q                                          // E-CANNOT-PROVE：上下文无 q 的依据
  var x = 1                                    // W-UNUSED（x 从未使用）+ D-TYPE-INFERRED（-v 才可见）
  when (n) {
    0 => print("zero")
    1 => print("one")
  }                                            // W-NON-EXHAUSTIVE：Nat 上的 when 未穷尽（示意）
}
```

输出形态（示意，N-RENDER + N-SNIPPET）：

```
[错误][4:3] E-IMMUT-ASSIGN: 给不可变的变量赋值了。—— n 声明时没标 @mut，不允许重新赋值。……
  4 |   n = 2
    |   ^
[错误][7:3] E-CANNOT-PROVE: 编译器证不出这个命题。……
[警告][8:3] W-UNUSED: 声明后从没用过。……
[警告][10:3] W-NON-EXHAUSTIVE: when 可能没走完所有情况。……
[补充][8:3] D-TYPE-INFERRED: 变量类型是编译器推导出来的。你没写类型标注时，编译器自动推断……（仅 -v）
[错误] 语义检查未通过                          ← stderr；随后 exit 1
```

脚本模式的旁路通道（`run-script demo.subs --global-inference`）：

```subs
fun loop(n: Nat): Nat = loop(n)                // 自递归无递减参数：停机检查失败
print(loop(0))
```
