# 线性作用域 · 白话版

> **文档性质**：设计理念文档，面向语言使用者。对应的实现规范见《线性作用域 · 形式化版》。
> **状态**：尚未实现。本文是对 `idea doc/线性作用域.md` 原始构想的完善与修正。
> **与规范的关系**：本特性一旦落地，将成为《凝华形式化规范》的第十二卷；它主要修订第五卷（上下文系统），并与第六卷（效应与可变性）衔接。

---

## 一、它解决什么问题

上下文系统对可变性的态度是「半死不活」：

```subl
@mut var n = 0
n = n + 1
∴ n = 1          // 证不出
```

证不出的原因是编译器**根本不注入** `n = 1` 这条事实。规范第五卷 §4.2 写得很明白：可变变量、引用变量、可变结构体类型的变量，一律不注入绑定等式。理由是「值会变，等式保不住」。

这个理由是对的，但代价是：**只要程序里有一个可变变量，关于它的一切推理能力就归零。**而现实中的代码大量使用可变变量——计数器、累加器、缓冲区、状态机。于是用户被逼到两条路上：

- 要么改写成纯函数式风格（往往不自然，有时性能更差）；
- 要么用 `unchecked.axiom[n = 1]` 硬塞事实（不安全，等于放弃了编译器保护）。

**线性作用域就是第三条路：让可变变量重新变得可证明，且不牺牲健全性、不增加运行时开销。**

---

## 二、一句话理念

> **把「一个变量随时间变化」展开成「一串不会变化的版本」，每个版本都是不可变的，于是每个版本都能进入上下文系统。**

时间维度被摊平成了空间维度。变量 `n` 被赋值三次，编译器眼里就有三个版本 `n#0`、`n#1`、`n#2`，每个版本绑定一次、永不再改。不可变的东西当然可以证明——问题就此消解。

这个思路在编译器领域有成熟先例：它就是 **SSA**（静态单赋值形式），几乎所有优化型编译器内部都会做。凝华的新意在于：**把 SSA 的版本索引直接用作命题的索引**，让版本化的事实进入证明系统。

### 「线性」是什么意思

需要澄清，避免与学术界的 linear types 混淆：

| 概念 | 含义 | 凝华的线性作用域是否符合 |
|---|---|---|
| 线性类型（linear types / 线性逻辑） | 值**恰好被使用一次**，用完即消耗 | **不符合**——不限制使用次数 |
| 唯一性类型（uniqueness types，如 Clean） | 值**只有唯一所有者**，不可别名 | **符合** |
| 时间线性的状态流转 | 状态沿单条时间线前进，不回头 | **符合** |

所以凝华的「线性」指的是：**域内的可变实体有唯一所有者（不可别名、不可逃逸），且其状态沿单条时间线单向流转。** 使用次数不受限制——你可以读 `n` 一百次。

## 三、基本写法

在块的花括号前加 `%`，这个块就是线性作用域：

```subl
@impure
fun main() %{
    @mut var n = 0
    ∴ n = 0            // 成立
    n = 1
    ∴ n = 1            // 成立
    n = n + 10
    ∴ n = 11           // 成立：11 是常量折叠的结果
}
```

对照普通作用域：

```subl
@impure
fun main() {
    @mut var n = 0
    ∴ n = 0            // 不成立：Γ 里没有 n = 0
    n = 1
    ∴ n = 1            // 不成立
}
```

**同一个 `@mut var`，加不加 `%` 的可证明性完全不同。** 这就是线性作用域的全部价值。

`%` 与 `{` 之间**不得有空格**——因为 `%` 本身是取余运算符，`a % { … }` 需要被解析为「a 取余一个块」而非线性作用域。这与 `<` 的邻接消歧是同一套机制（规范第一卷 §9.2）。

## 四、编译器在背后做了什么

上面的例子，编译器内部看到的是：

```
域入口：Ω = {}
─────────────────────────────────────────────
@mut var n = 0        →  n#0 = 0，Ω = {n ↦ 0}
                         注入 Γ：n#0 : Nat、n#0 = 0、n#0 ≥ 0

∴ n = 0               →  ∴ n#0 = 0
                         （读取点解析到当前版本 0，命中事实）

n = 1                 →  n#1 = 1，Ω = {n ↦ 1}
                         注入 Γ：n#1 = 1

∴ n = 1               →  ∴ n#1 = 1     命中

n = n + 10            →  右侧的 n 解析为 n#1
                         n#2 = n#1 + 10，Ω = {n ↦ 2}
                         注入 Γ：n#2 = n#1 + 10

∴ n = 11              →  ∴ n#2 = 11
                         由 n#2 = n#1 + 10、n#1 = 1 经等量代换得 n#2 = 11
                         线性算术通道判定成立
```

**关键点：版本名 `n#0`、`n#1` 是编译期内部名，用户永远看不见。** 你写的始终是 `n`。诊断消息也会还原成 `n`（必要时附注「第 2 次赋值后」）。

`#` 这个前缀是特意选的：合法标识符不含 `#`，所以 `n#k` 必然不与任何用户名字冲突（规范第四卷 §2.8 已用同一机制生成新鲜常量）。

**运行时什么都不多。** `n#0`、`n#1`、`n#2` 在代码生成时全部映射回同一个 JavaScript 变量 `n`，赋值就是 `n = …`。版本只活在编译期的命题索引里，随命题一起被擦除。这是**零运行时成本**（详见 §十）。

## 五、三条支柱

线性作用域由三条规则支撑，缺一不可。

### 支柱一 · 唯一所有权

域内的可变实体**不得别名、不得逃逸**：

- 不能被 lambda 捕获（`xs.forEach { n = n + 1 }` 里的 `n` 是捕获）；
- 不能声明为 `@ref`（引用别名意味着多个名字指向同一存储）；
- 不能以 `@mut` 视图传给会修改它的函数，除非你接受该调用点之后事实失效（§八）。

为什么必须这样？因为版本化事实 `n#1 = 1` 的含义是「**在这个程序点，n 的值是 1**」。如果别处也能改 `n`，那「在这个程序点」就无法确定——你以为的 `n#1` 可能已经被别的代码改成了 `n#5`。唯一所有权保证了「只有本域能改它」，于是版本与程序点严格对应。

### 支柱二 · 版本化

每次赋值产生新版本，每个读取点解析到**最近的前驱版本**。分支合并时产生合并版本（§七）。

### 支柱三 · 流敏感命题

Γ 不再是「一个作用域一套事实」，而是「**一个程序点一套事实**」。事实随程序点前进而更新：

| 事件 | 事实的变化 |
|---|---|
| 赋值 `x = e` | 产生新版本，注入 `x#k = e` |
| 读取 `x` | 解析到当前版本，不改变 Γ |
| 传入不纯函数 | 该实体的全部版本化事实**失效** |
| 分支合并 | 注入各支的**析取** |
| 域结束 | 全部版本化事实随帧销毁（不回溢，见 §九） |

「流敏感」（flow-sensitive）是程序分析的标准术语，意思是「事实依赖于控制流位置」。凝华的普通作用域是流不敏感的（一个作用域一套固定事实），线性作用域是流敏感的。

## 六、结构体字段

字段的修改是**就地修改**，同样可以版本化：

```subl
struct Point(x : Nat, y : Nat)

@impure
fun main() %{
    var p : @mut Point = Point(0, 0)
    ∴ p.x = 0                  // 成立
    p.x = 5
    ∴ p.x = 5                  // 成立
    ∴ p.y = 0                  // 成立：y 没被改过
}
```

字段版本化与变量版本化同理：`p.x#0 = 0`、`p.x#1 = 5`。因为 `p` 是本地的、唯一所有权的，就地修改是安全的。

注意：这**放宽了**规范第六卷 §5.3 的字段写入条件——在普通作用域里，`p.x = 5` 要求字段本身标注 `@mut`；在线性作用域里，域本身提供了唯一所有权保证，因此只要求接收者持有 `@mut` 视图。这是线性作用域带来的第二重便利（第一重是可证明性）。

结构体的伴生命题在域内同样按版本化后的字段值验证：

```subl
struct PosPoint(x : Nat) <x > 0>

@impure
fun demo() %{
    var p : @mut PosPoint = PosPoint(1)     // 构造时证明 1 > 0
    ∴ p.x > 0                                // 成立
    // p.x = 0                               // 若允许，则伴生命题被破坏
}
```

**伴生命题怎么处理**：就地修改字段可能让结构体的伴生命题对新值不再成立。规定是——**旧版本的伴生命题保留**（它说的是历史，仍然为真），**新版本不自动获得伴生命题**，除非赋值右侧代入后能重新证明。

```subl
struct PosPoint(x : Nat) <x > 0>

@impure
fun demo() %{
    var p : @mut PosPoint = PosPoint(1)     // 构造时证明 1 > 0，注入 p.x#0 > 0
    ∴ p.x > 0                                // 成立：解析为 p.x#0 > 0
    p.x = 0                                  // 注入 p.x#1 = 0；p.x#1 > 0 不注入
    // ∴ p.x > 0                             // 不成立：解析为 p.x#1 > 0，Γ 里没有
    ∴ p.x = 0                                // 成立
    p.x = 5                                  // 右侧 5 > 0 可证，重新注入 p.x#2 > 0
    ∴ p.x > 0                                // 又成立了
}
```

这里有个关键的安全保证，也是它比「一破坏就报错」更好的地方：**证明器不会误用旧版本的伴生命题去证明新版本的命题**。因为 `p.x#0` 和 `p.x#1` 是两个不连通的名字，Γ 里不存在 `p.x#0 = p.x#1` 这样的等式，等量代换无从下手（严格论证见形式化版 §9.4）。

那如果这个「不变式已被破坏」的结构体流到需要该不变式的地方呢？由**既有的上文检查**拦下，不需要线性作用域额外做什么：

```subl
fun usePos(p : PosPoint) <p.x > 0> : Null {}     // 上文要求 p.x > 0

@impure
fun demo2() %{
    var p : @mut PosPoint = PosPoint(1)
    p.x = 0
    usePos(p)          // E-PRE-UNPROVEN：p.x#1 > 0 证不出——调用点自然拦下
}
```

所以修改字段破坏伴生命题，不会报错，只是让相关命题回到「需要重新证明」的状态。想恢复就用 `∵`／`by` 补，或赋一个满足伴生命题的新值，或调用一个下文能保证它的函数。

## 七、分支

分支是版本化的第一个难点：两个分支各自赋值，合并点的值是哪个？

```subl
@impure
fun classify(flag : Bool) %{
    @mut var n = 0
    if (flag) {
        n = 1
        ∴ n = 1          // 分支内：成立
    } else {
        n = 2
        ∴ n = 2          // 分支内：成立
    }
    ∴ n = 1 ∨ n = 2      // 合并点：成立
    // ∴ n = 1            // 合并点：不成立，正确
}
```

编译器做的事：

```
域入口            n#0 = 0
then 分支         n#1 = 1，注入 n#1 = 1
else 分支         n#2 = 2，注入 n#2 = 2
合并点            产生 n#3，注入 n#3 = n#1 ∨ n#3 = n#2
```

合并点注入的是**析取**，因此 `n = 1 ∨ n = 2` 可证，而单独的 `n = 1` 不可证。这与直觉一致：合并点确实不知道走了哪个分支。

如果两个分支赋的是**同一个值**：

```subl
if (flag) { n = 7 } else { n = 7 }
∴ n = 7          // 成立：析取 n#3 = 7 ∨ n#3 = 7 即 n#3 = 7
```

如果只有一个分支赋值：

```subl
if (flag) { n = 1 }
// 合并点：n#2 = n#0 ∨ n#2 = n#1，即 n#2 = 0 ∨ n#2 = 1
∴ n = 0 ∨ n = 1     // 成立
```

`when` 分支同理，各支的析取在合并点合成。这与第七卷的穷尽性判定天然配合——穷尽的 `when` 覆盖全部情况，合并点的析取就是完整的值域描述。

## 八、逃逸、别名与失效

### 8.1 禁止的情形

以下写法在线性作用域内**报错**：

```subl
%{
    @mut var n = 0
    xs.forEach { n = n + 1 }        // E-LINEAR-ESCAPE：lambda 捕获并修改
}

%{
    @ref var a : @mut T = T(0)      // E-LINEAR-ALIAS：@ref 别名
    @ref var b : @mut T = a
}

%{
    @mut var n = 0
    return n                        // E-LINEAR-RETURN：提前返回
}
```

**lambda 捕获为什么必须禁止**：lambda 是值，它的执行时机与次数不受定义点控制（可能被调用零次、一次、多次，也可能被存起来稍后调用）。如果 lambda 能改域内变量，那「程序点」与「版本」的对应关系就崩了——你无法静态确定 `n#3` 对应哪个时刻。

这也解释了规范第五卷 §3.4「lambda 帧隔离」的深层理由：隔离不只是防止事实外泄，更是防止**跨帧的状态修改**。

**提前返回为什么必须禁止**：域结束时要做版本化的收尾（§九）。中途 `return` 会跳过收尾，使域内累积的事实处于未定义状态。这个限制比原始构想宽松——原始构想因为链式脱糖的 `actNow()` 而必须禁止返回，本方案的禁止理由更单纯，且**只禁止带值的提前返回；`return`（裸返回，用于 `Null` 函数）在域的最后一条语句位置是允许的**。

### 8.2 允许但会失效的情形

把可变实体传给**不纯函数**是合法的，但该调用点之后，关于它的事实全部失效：

```subl
@impure
fun main() %{
    @mut var n = 0
    n = 5
    ∴ n = 5                // 成立
    someImpureFn(n)        // n 作为不可变值传入：不失效（传的是值，不是可变视图）
    ∴ n = 5                // 仍成立

    var p : @mut Point = Point(0, 0)
    ∴ p.x = 0              // 成立
    mutatePoint(p)         // p 以 @mut 视图传入：p 的全部字段事实失效
    // ∴ p.x = 0            // 不再成立
    ∴ p.x ≥ 0              // 仍成立：类型不变量不失效
}
```

失效的范围：

| 事实种类 | 是否失效 |
|---|---|
| 版本化等式（`p.x#k = v`） | **失效** |
| 类型归属（`p : Point`、`p.x : Nat`） | 不失效 |
| 类型不变量（`p.x ≥ 0`，来自 `Nat`） | 不失效 |
| 结构体伴生命题 | **失效**（除非函数下文重新保证） |

失效会发 `D-LINEAR-INVALIDATED` 补充级诊断，告诉你哪些事实被丢掉了、在哪个调用点。

**恢复事实的办法**：给那个不纯函数写下文。

```subl
@impure
fun resetOrigin(p : @mut Point) : Null <p.x = 0, p.y = 0>
```

调用 `resetOrigin(p)` 之后，事实失效，但函数下文立即注入 `p.x = 0`、`p.y = 0`——于是又能证明了。这正是上下文系统的既有机制（规范第五卷 §5.5），线性作用域只是让它对可变实体也生效。

### 8.3 逃逸分析是保守的

编译器判定「是否逃逸」时，**有疑问就当作逃逸**。例如通过字典分派的方法调用（无法静态确定被调方）、通过 `Any` 类型的传递、通过高阶函数的间接调用，一律视为逃逸并触发失效。

保守意味着「不会漏掉真实的修改」，代价是「有时会失效得比必要的更多」。健全性优先。

## 九、域的边界

### 9.1 事实不回溢

线性作用域内产生的版本化事实**不回溢到父帧**：

```subl
@impure
fun main() {
    %{
        @mut var n = 0
        n = 5
        ∴ n = 5          // 域内成立
    }
    // ∴ n = 5           // 域外：n 不存在（它是域内声明的）
}
```

这与普通块的事实回溢（规范第五卷 §3.3）**不同**。理由：版本化事实是流敏感的，出了域就没有「程序点」的语境，事实失去意义。而且域内变量在域外也不可见，事实无从引用。

但如果变量是**域外声明、域内修改**的：

```subl
@impure
fun main() {
    @mut var n = 0
    %{
        n = 5
        ∴ n = 5          // 域内成立
    }
    // ∴ n = 5           // 域外不成立：版本化事实不回溢
}
```

域外要恢复事实，只有两条路：显式写下文，或在域外重新用不可变变量承接（`var snapshot = n`，规范第五卷 §10.3 的建议）。

**这是有意的设计**：让线性作用域成为一个明确的「可证明区间」，区间的边界清晰，不产生跨边界的隐式推理。

### 9.2 域可以嵌套

```subl
%{
    @mut var n = 0
    %{
        n = 1
        ∴ n = 1          // 内层可见外层变量，版本继续递增（n#1）
    }
    ∴ n = 1              // 内层域结束后……不成立（事实不回溢）
}
```

内层域可以读写外层的线性变量，版本序号在整个「线性域族」内连续递增。但内层的事实不回溢到外层，所以外层在内层之后看不到内层的赋值事实——尽管**运行时的值确实改了**。

这个行为初看反直觉，但它是健全的：外层若要在内层之后使用 `n`，应当显式承接。若你觉得这太严格，替代方案是让内层域结束时把「最终版本」的等式回溢一层——但这会破坏「事实不回溢」的一致性，第一版不采用。

## 十、运行时成本：零

这是本方案与原始构想最大的区别，也是它可行的关键。

| 方面 | 原始构想（链式结构体脱糖） | 本方案（编译期版本化） |
|---|---|---|
| 运行时产生的结构 | `Main$state` 结构体、`actions` 列表、闭包链 | **无** |
| 副作用执行时机 | 延迟到 `actNow()`，输出顺序错乱 | 就地执行，顺序正确 |
| 每次赋值的开销 | `copy(…)` 构造新结构体 | 一次普通赋值 |
| 容器的开销 | 每次 `copy$listAnd` 深拷贝 | 无额外拷贝 |
| 命题层 | 擦除 | 擦除 |
| 版本名 | 出现在运行时结构里 | 编译期擦除 |

生成的 JavaScript 与普通 `@mut` 代码**逐字节相同**：

```subl
@impure
fun main() %{
    @mut var n = 0
    n = 1
    print(toStr(n))
}
```

生成：

```javascript
function main() {
    let n = 0;
    n = 1;
    print(String(n));
}
```

版本化、命题注入、事实失效——全部发生在编译期，全部随命题层擦除（规范总纲不变量 I-2）。线性作用域是**纯静态的分析增强**，不是运行时机制。

## 十一、当前限制（诚实声明）

第一版明确**不支持**以下场景，遇到时报错或降级，绝不猜测。

| 限制 | 原因 | 应对 |
|---|---|---|
| **lambda 内修改域内变量** | lambda 执行时机不定，版本与程序点无法对应 | 改写为顺序代码，或把 lambda 提到域外 |
| **域内累加器循环** | 凝华的循环只能靠递归或高阶函数，两者的帧都隔离 | 把循环写成递归函数，用函数的下文表达不变量 |
| **`@ref` 别名** | 别名使「唯一所有权」失效 | 域内不使用 `@ref` |
| **域内声明自递归函数** | 递归调用点使版本化事实的时序无法静态确定 | 把递归函数提到域外 |
| **循环出口的版本化事实** | 需要归纳证明（规范第四卷 §9.10 明确暂不做归纳） | 用递归函数的下文表达不变量 |
| **跨域的事实传递** | 事实不回溢（§9.1） | 域外用不可变变量承接 |
| **容器内容的深度推理** | `list = (1,2,3)` 涉及列表字面量等式，线性算术通道不覆盖 | 逐元素用 `elementAt` 取出后推理，或等待容器推理通道 |

关于最后一条，需要特别说明。原始构想的核心示例是：

```subl
var list : @mut List = mutableListOf(1,2)
∴ list = (1,2)          // 期望成立
list += 3
∴ list = (1,2,3)        // 期望成立
```

第一版**不能**证明这两条命题——不是因为版本化机制不行，而是因为证明器缺少「列表字面量的结构等式」判定通道。版本化会正确产生 `list#0 = mutableListOf(1,2)` 与 `list#1 = list#0 + 3`，但从这里推到 `list#1 = (1,2,3)` 需要列表代数的重写规则，那是第四卷 §8 算术判定之外的新通道。

**本方案对此的处理**：版本化机制先落地（它对所有类型通用），列表内容推理作为独立的后续工作。落地后你能立刻得到的是：

```subl
%{
    @mut var list = listOf(1, 2)
    ∴ list = listOf(1, 2)                        // 成立：Γ 中就有这条版本化等式
    list = list.append(listOf(3))
    ∴ list = listOf(1, 2).append(listOf(3))      // 成立：旧版本值可归约为字面表达式
    // ∴ list = listOf(1, 2, 3)                  // 不成立：需要列表代数通道
}
```

即**赋值右侧原样可证**，而**需要对容器做代数化简的等式**需要新通道。诚实地说清楚这条边界，比承诺一个做不到的能力更好。

**一处待实现期核实的点**：上面第二条命题依赖「旧版本的值可归约为字面表达式」，进而由线性算术通道判定 `list = listOf(1,2).append(listOf(3))`。数值型实体（`Nat`／`Int`／`Rat`）的这类归约由既有通道覆盖（第四卷 §5.1 的常量归约与 §8.1 的线性算术）；但**容器类型的归约是否落在既有通道的判定片段内，需在实现期实测确认**。若不在，第一版对容器的可证范围仅限「赋值右侧结构相同」这一种情形。

另外，`+=` 的定义也需要明确。标准库容器是**不可变**的（规范第三卷 §2.9：`put`/`add`/`remove` 返回新容器）。因此线性作用域内的 `list += 3` 应当定义为**重新绑定**（`list = list + 3`，`+` 对 List 返回新列表），而非就地修改。这与原始构想的 `copy$listAnd { list => list += 3 }`（就地修改 + `@ref @mut` 形参 + `unchecked` 逃逸）不同——重新绑定是纯函数式的版本流转，不需要别名分析，也不需要逃逸。

## 十二、与既有机制的关系

### 12.1 与 `@mut` 的关系

线性作用域**不替代** `@mut`，而是与它协作：

| 场景 | 用什么 |
|---|---|
| 不需要证明的可变状态 | `@mut var`（普通作用域） |
| 需要证明的可变状态 | `%{ @mut var … }` |
| 完全不需要可变 | 普通 `var`（最佳选择） |

域内仍需写 `@mut`——这不是冗余。`@mut` 声明的是**运行时的可变性**（代码生成用 `let` 而非 `const`），`%` 声明的是**编译期的可追踪性**。两者职责不同。

不过可以考虑一个便利：域内的 `var` 默认允许赋值（隐式 `@mut`），因为「线性」本身已经蕴含了受控的可变性。这个便利待作者裁决，本方案**保守地要求显式写 `@mut`**。

### 12.2 与 `unchecked` 的关系

线性作用域是 `unchecked` 的**安全替代品**：

```subl
// 旧办法：不安全
@mut var n = 0
n = 1
unchecked.axiom[n = 1]       // 你在骗编译器，如果实际是 2 就完了

// 新办法：安全
%{
    @mut var n = 0
    n = 1
    ∴ n = 1                  // 编译器验证过，错不了
}
```

`unchecked` 仍然是逃逸口（总有编译器分析不了的场景），但线性作用域把「需要逃逸」的场景大幅缩小了。

### 12.3 与深拷贝的关系

规范第六卷 §6.6 规定：涉及 `@mut` 视图的绑定默认深拷贝。线性作用域内的版本化**不改变这条规则**——`var m = n`（n 是 `@mut T`）仍然深拷贝，且 `m` 是独立的新变量，有自己的版本序列。

深拷贝点会发 `D-DEEP-COPY`，版本化会发 `D-LINEAR-VERSION`，两者独立。

### 12.4 与 `pure<f>` 的关系

线性作用域内的代码若含赋值，其所在函数**仍然是不纯的**（`@impure`）——版本化不改变效应。`pure<f>` 命题的注册规则不变（规范第六卷 §2.1）。

换句话说：线性作用域让你**证明关于可变状态的事实**，但不让可变状态变成纯的。这是正确的——可变性本身就是效应。

## 十三、为什么不采用原始构想的脱糖方式

原始构想把 `%{ … }` 脱糖成一个状态结构体的链式调用：

```subl
Main$state(n = 0)
    .then { n => … }
    .set$n(1)
    .then { n => … }
    .actNow()
```

这个方案有六个问题：

1. **副作用被延迟**。`then{}` 把动作累积进 `actions` 列表，`actNow()` 才执行。域内写的 `print` 全部跑到最后，输出顺序与源码顺序不符。这是可观测的语义错误。

2. **闭包固化了旧值**。`.curry(n).curry(list)` 在构造 `then` 的时刻就把当时的 `n`、`list` 值固化进闭包。而 `set$n(1)` 返回的是**新状态**，累积在 `actions` 里的闭包仍持有旧值。延迟执行时读到的是旧值——与「状态流转」的意图直接矛盾。

3. **用 `unchecked` 逃逸**。`copy$listAnd` 的体内是 `list.mutable().also{ unchecked f(_) }`。为了支持就地修改而逃逸检查，这与「让可变性可被证明」的初衷冲突。

4. **运行时开销非零**。产生状态结构体、动作列表、闭包链、末尾遍历执行。违反零成本擦除（规范总纲不变量 I-2）。

5. **命名规则未定义**。`Main$state` 从函数名 `main` 生成，但同一函数有多个线性作用域、或作用域嵌套时怎么办？`$` 又与既有的「返回值指代」语义（规范第五卷 §7.3）混淆。

6. **三条约束是实现副产物**。「不得提前返回」「固定返回空」「修改必须在同域」都不是设计意图，而是链式脱糖做不到别的选择。本方案里，前两条放宽（允许末尾裸 `return`；域的返回值可以是末表达式），第三条保留但理由更清晰（唯一所有权）。

**本方案的取舍**：放弃「脱糖成可见的语言构造」，改为「纯编译期的分析变换」。代价是变换过程无法用凝华源码表达（它是编译器内部的一步），收益是零开销、语义正确、约束更少。

考虑到凝华的核心哲学是「零成本擦除」——命题不进运行时、类型不进运行时——把版本化也做成不进运行时的编译期机制，与这个哲学是一致的。原始构想的链式结构体反而在运行时留下了痕迹。

## 十四、效应系统与异步：为什么拆出去

原始构想把四件事捆在一起：线性作用域、效应系统（`@effect`/`IO`）、效应器委托（`by`）、异步（`yield`）。**本方案只做第一件。**

拆分的理由：

### 14.1 耦合度低

线性作用域解决的是「可变状态的命题追踪」；效应系统解决的是「副作用的组合与延迟执行」。前者是静态分析，后者是运行时机制。两者可以独立设计、独立实现、独立验证。

### 14.2 效应方案有根本缺陷

原始构想的效应脱糖：

```subl
@effect @root fun readFile(name : Str) : Str
```
脱糖为
```subl
fun readFileByName($readFile : @impure (Str) => Str = default$readFile, name : Str) : IO
    = io{ $readFile(name) }
```

四个问题：

- **形参默认值违反语言规则**。凝华的函数形参不允许默认值（`E-DEFAULT-PARAM`，规范第二卷 §3.2），只有结构体字段允许。
- **`IO` 类型与 `io{}` 构造全语言未定义**。规范第九卷 §2.1 的值域里没有 IO。
- **形参顺序错位**。效应器插在首位，所有既有调用点的实参都要跟着改。
- **效应着色问题**（function coloring）。`readFileByName` 返回 IO，调用它的函数也要返回 IO，一路传染到 `main`。「在非线性作用域调用非纯函数会立即 `actNow()`」这个补丁破坏了组合性——IO 值无法被传递、存储、批处理。

### 14.3 凝华已有一套效应机制

规范第六卷已经定义了完整的效应体系：`@impure` 标注 + `pure<f>` 命题 + 纯度传染 + 上下文放行。这套机制的特点是**效应是标注而非类型**——函数不会「返回 IO」，它只是被标注为不纯，调用它需要不纯上下文或 `pure<f>` 证据。

这个选择避开了着色问题，代价是不能把效应作为值来组合（无法写「先做 A 再做 B」的效应组合子）。要不要补上这个能力，是一个独立的设计问题，值得单开一轮讨论——但**不应当与线性作用域捆绑**。

### 14.4 异步已有 Flow

`yield` 效应器与规范第六卷 §8.6 的 `Flow`/`emit` 功能重叠：两者都是「产出一串值供外部消费」。凝华已经有 `Flow { emit(1); emit(2) }` 与 `collect`/`map`。新增 `yield` 效应器需要说明它与 `Flow` 的关系——是替代、是语法糖、还是不同层次的机制。这也应当独立讨论。

**结论**：本方案只交付线性作用域。效应系统与异步生成器留作后续独立设计。

## 十五、小结

| 维度 | 结论 |
|---|---|
| 解决什么 | 可变变量在上下文系统里不可证明 |
| 核心机制 | 版本化（SSA）+ 流敏感命题 + 唯一所有权 |
| 运行时成本 | 零（版本名与命题一起擦除） |
| 健全性 | 可证：唯一所有权保证版本与程序点对应（见形式化版 §9） |
| 主要限制 | lambda 内不可修改域内变量；无循环追踪；列表内容推理待补 |
| 语法 | `%{ … }`（`%` 紧贴 `{`，靠邻接与取余运算符消歧） |
| 域内 var | 仍须显式写 `@mut`（`@mut` 管运行时可变、`%` 管编译期可追踪，职责不同） |
| lambda 只读捕获 | 快照语义：读到的是捕获时刻的版本，不随后续赋值前进 |
| 伴生命题破坏 | 不报错；旧版本保留、新版本不自动注入，靠既有上文检查（`E-PRE-UNPROVEN`）拦截流出 |
| 新增诊断 | 错误级 `E-LINEAR-ESCAPE`、`E-LINEAR-ALIAS`、`E-LINEAR-RETURN`、`E-LINEAR-REC`；补充级 `D-LINEAR-VERSION`、`D-LINEAR-INVALIDATED`、`D-LINEAR-MERGE`、`D-LINEAR-PROP-LOST` |
| 修订的规范卷 | 第一卷（`%` 邻接）、第二卷（产生式与脱糖）、第五卷（流敏感 Γ）、第六卷（字段写入放宽）、第九卷（版本名映射）、第十卷（诊断码） |
| 不在本方案内 | 效应系统（`@effect`/`IO`）、效应器委托、`yield` 异步 |
