## 一、本卷的地位与读法

### 1.1 本卷定义什么

注解处理是编译管线中**唯一以 AST 为对象、以 AST 为产物**的阶段。本卷固定五样东西：

1. **注解分类**（§2）：语言层注解按消费方分四层（类型层 / 行为层 / 生成层 / 目标层），外加处理器层（APT 引入名）；
2. **扫描语义**（§3）：AnnotationScanner 如何把 AST 上的注解扁平化为挂载点序列；
3. **装载语义**（§4）：处理器=Sublimation 脚本，文件名=处理器名=关注注解，-p 附加、目录装载、-A key=value 传参；
4. **多轮改写语义**（§5、§6）：ProcessorEngine 的轮次、跳过、变化判定、重查与收敛；脚本侧编辑指令如何不可变地作用回 AST；
5. **管线时序**（§7）：处理器先于 B/C 检查跑、处理器产出视为新代码、postCompile 收尾阶段。

### 1.2 判断形式

本卷主判断沿用 00 卷 §3.1 总表第 10 行，规则前缀固定为 **H-**：

$$\frac{}{\Pi \vdash A \looparrowright A'} \quad (\text{H-...})$$

读法：**注册序为 Π = p₁…pₙ 的处理器集合把 AST A 变换为 A′**。本卷新增的从属判断：

| 判断 | 读法 | 定义节 |
|---|---|---|
| $A \triangleright s^*$ | AST A 扫描得挂载点序列 s* | §3 |
| $p \vdash A \Rightarrow (A', \delta^*)$ | 处理器 p 单次执行把 A 变为 A′ 并产诊断 δ* | §6 |
| $\textit{load}(\Pi_c) = (\Pi, \varepsilon^*)$ | CLI 处理器路径表 Πc 装载得处理器集 Π 与装载错误 ε* | §4 |
| $\Pi \vdash A \looparrowright A'$ | 整条流水线（多轮）的变换 | §5、§7 |

元变量：`A, A′` 为 FileAst；`ν` 为注解名（string）；`s_i` 为挂载点（AnnotatedNode）；`p` 为处理器、`Π` 为其注册序；`K` 为编译参数映射（`-A`）；`k ⇒ v` 为其中一对；`r` 为轮次、`R = 5` 为轮次上限；`δ` 为单条诊断、`Φ` 为诊断袋；`Σ` 为符号表；`D` 为目录、`F` 为文件。

### 1.3 与他卷的接口

- 04 卷定义所有权标签 μ（`@mut`/`@ref`）与拷贝四规则；本卷只引用其**载体位置**（类型位 / var 位 / 字段位），不重述规则。

- 11 卷定义宿主与脚本模式；本卷 §4.6 只点出 ProcessorHost 这一宿主对接点，不展开。

## 二、注解的分类学（语言层判断）

### 2.1 注解的语法载体

解析器 `parseAnnotations()`（Parser.kt:261）只读 `@IDENT` 名字序列、不读实参：

$$\frac{\textsf{cur} = \texttt{@} \qquad \textsf{next} = \text{IDENT}}{\textsf{annos} := \textsf{annos} \cdot \nu} \quad (\text{H-LEX-ANNO})$$

可挂注解的 AST 节点（`annotations: List<String>` 字段）共五类：

$$\frac{n \in \{\texttt{FunDecl}, \texttt{StructDecl}, \texttt{ClassDecl}, \texttt{VarStmt}, \texttt{VarExpr}\}}{\text{可挂}(n)} \quad (\text{H-CARRIER})$$

补充两条载体事实：`Param`（函数形参/结构体字段）也带 `annotations`，但它**不实现 Node、不参与扫描**（其注解面向 checker，见 §3.4）；`EnumDecl / ImplDecl / TypeAliasDecl / PropDefDecl` 无注解字段，天然扫不到。类型位另有专用语法（Parser.kt:506-521）：

$$\frac{\nu = \texttt{mut} \quad | \quad \nu = \texttt{atomic}}{\tau := \texttt{@}\nu\ \tau'} \quad (\text{H-POS-TY-1}) \qquad \frac{\nu = \texttt{impure} \qquad \tau' \ \text{为函数类型}}{\tau := \tau'.\textsf{purity} := \texttt{impure}} \quad (\text{H-POS-TY-2})$$

$$\frac{\nu \notin \{\texttt{mut}, \texttt{atomic}, \texttt{impure}\} \qquad \text{位置} = \text{类型位}}{\textsf{ParseFailure}(\text{「类型位注解只支持 @mut / @atomic / @impure」})} \quad (\text{H-POS-TY-ERR})$$

**关键事实**：`@ref` 在类型位不可写——它不是类型构造子，而是变量级注解（`"ref" in s.annotations`，Frame.refs 登记；00 卷 §2.2 同一定论）。`@ref @mut T` 的真实含义是「变量标 `@ref`、类型为 `@mut T`」。

### 2.2 四层分类

按**核心编译器在何处消费注解**分四层；各注解的实际消费点见 §2.3 表。

$$\frac{\nu \in \{\texttt{mut}, \texttt{ref}\}}{\textsf{层}(\nu) = \text{类型层（所有权）}} \quad (\text{H-ANN-TY})$$

$$\frac{\nu \in \{\texttt{impure}, \texttt{theorem}, \texttt{classic}, \texttt{simp}, \texttt{axiom}\}}{\textsf{层}(\nu) = \text{行为层（检查义务）}} \quad (\text{H-ANN-BEH})$$

$$\frac{\nu \in \{\texttt{root}, \texttt{atomic}\}}{\textsf{层}(\nu) = \text{生成层（代码形态）}} \quad (\text{H-ANN-GEN})$$

$$\frac{\nu \in \{\texttt{android}, \texttt{view}\}}{\textsf{层}(\nu) = \text{目标层（平台桥接）}} \quad (\text{H-ANN-TARGET})$$

$$\frac{\nu \in \{\texttt{allMut}, \texttt{composable}, \texttt{host}, \texttt{async}, \texttt{list}, \dots\}}{\textsf{层}(\nu) = \text{宿主/处理器层}} \quad (\text{H-ANN-SCRIPT})$$

未知注解名不作核心校验：

$$\frac{\nu \notin \text{内建名集} \qquad \nu \notin \bigcup_p \textsf{int}(p)}{\text{核心放行}\ \nu\ (\text{无 E-ANNOTATION 类诊断})} \quad (\text{H-ANN-UNKNOWN})$$

即：注解名字空间由宿主与处理器联合决定（interpreter/Annotation.kt 头注「用户不能自定义注解名——注解名字空间由宿主提供」），编译器核心对未知名既不报错也不消费；未匹配任何处理器的注解静默保留在 AST 上。

### 2.3 各注解的消费点（事实表）

| 注解 | 层 | 载体位 | 消费点（源码） | 语义 |
|---|---|---|---|---|
| `@mut` | 类型 | 类型位 / var 位 / 字段位 / 声明位 | Parser.kt:511（MutType）；Checker.kt:327（函数标 @mut → 接收者持 @mut 视图）；:526/:582（var）；:870（字段写闸 E-NOT-MUT） | 唯一所有权可变视图 |

### 2.4 分类判断式示例

对一段声明做分层标注：

```subl
@allMut struct Point(x: Nat, y: Nat)          // 处理器层（@allMut，由 allMut.subs 消费）

@android @impure fun log(msg: Str): Null      // 目标层 + 行为层（声明位）

fun step(p: @mut Point) : Nat {               // 类型层（类型位 @mut）
  var alias : @ref @mut Point = p             // 类型层（var 位 @ref + 类型位 @mut）→ 别名
  alias.x = 3
  alias.x
}

@theorem fun addOk(a: Nat, b: Nat) : Nat = a + b   // 行为层（证明义务函数）

fun main() { print(step(Point(1, 2))) }
```

层级之间**正交**：同一声明可同时携带多层注解（`@android @impure` 即目标层＋行为层）。分层的判断价值在于诊断义务的归属——行为层注解改变检查器闸门，目标层注解改变代码生成形态，处理器层注解核心完全不消费（只在流水线阶段被脚本读取）。

## 三、扫描语义（AnnotationScanner）

### 3.1 扫描判断

$$\frac{A = \textsf{FileAst}(e_1, \dots, e_m) \qquad \forall i: e_i \triangleright s_i^*}{A \triangleright s_1^* \cdots s_m^*} \quad (\text{H-SCAN-FILE})$$

每个 `DeclEntry` 走声明步、`StmtEntry` 走语句步。多文件形态（`scan(List<FileAst>)`）按文件序合并，挂载点保持**源码顺序**。

### 3.2 拆分规则（一注解一条）

$$\frac{n.\textsf{annotations} = [\nu_1, \dots, \nu_k] \qquad \text{可挂}(n)}{n \triangleright \langle (\nu_1, n), \dots, (\nu_k, n) \rangle} \quad (\text{H-SCAN-SPLIT})$$

一个注解产生一条 AnnotatedNode；同一节点 k 个注解拆成 k 条。挂载点记录：`annotation: Annotation(ν, args=[])`、`node`（只读引用）、`kind: NodeKind`、`file`（多文件定位；单文件合并时为 null）、`nodeName`、`pos`。

### 3.3 遍历规则

声明步：先发射自身，再下钻函数体 / 类型类成员体 / impl 成员体。语句步覆盖全语句族——var/赋值/表达式语句/unchecked（递归 inner）/函数内声明/return/`axiom`/`by`/`∵∴`/命题 when/策略/if-命题/∃ 引入与消去。表达式步递归下钻全部复合表达式（含 when 的模式 `walkPattern`、尾随 lambda 体、BlockExpr 内的语句）。不可达的叶子（字面量、名字、命题原子）停止。

$$\frac{s = \texttt{unchecked}\ s'}{s \triangleright (s' \ \text{的挂载点})} \quad (\text{H-SCAN-UNCHECKED}) \qquad \frac{\text{节点无 annotations 字段}}{\text{该节点零挂载点}} \quad (\text{H-SCAN-NULL})$$

### 3.4 扫描覆盖事实（不变量）

- **可挂集合** = {FunDecl, StructDecl, ClassDecl, VarStmt, VarExpr}；`Param` 的注解（`@tuple`/`@mut`/`@list` 等）**不独立展开**——它不实现 Node；处理器需要时通过 SymbolsView 拿完整声明。
- `NodeKind` 为处理器提供按种类过滤：FUN / STRUCT / CLASS / ENUM / IMPL / TYPE_ALIAS / PROP_DEF / VAR_STMT / VAR_EXPR / UNKNOWN（后五位在实际扫描中不会出现——ENUM/IMPL 等无注解字段，UNKNOWN 是兜底）。
- `Annotation.args` 当前**恒为空**：解析器只读 `@IDENT`。扫描时把 `List<String>` 升格为 `Annotation(name, args = emptyList())`（AnnotatedNode.kt 头注：不改 AST 的约 30 处构造点，是既定的接口边界）。

$$\frac{s \in \textsf{scan}(A) \qquad s.\textsf{annotation}.\textsf{name} = \nu}{\nu \in A\ \text{的注解名集}} \quad (\text{H-SCAN-SOUND}) \qquad \frac{\nu\ \text{在不可挂节点上}}{\nu\ \text{对扫描不可见}} \quad (\text{H-SCAN-BLIND})$$

H-SCAN-BLIND 是**陷阱规则**：写在枚举、impl、类型别名、自定义命题（`def`）、形参上的注解，处理器永远看不到；这类意图必须改挂在可挂节点上，或经符号表查询（`fieldAnnotations` 等）读出。

## 四、处理器=脚本（装载判断）

### 4.1 装载约定

一个 `.subs` 文件 = 一个处理器（root doc/注解处理器.md 11「第二版」，BuiltinProcessors.kt:9-14）：

$$\frac{F = \texttt{<}\nu_p\texttt{>.subs} \qquad \textsf{src} = \textsf{read}(F)}{\textsf{proc}(F) = \langle \textsf{name} = \nu_p,\ \textsf{int} = \{\nu_p\} \cup \textsf{extra}(\textsf{src}),\ \textsf{src} \rangle} \quad (\text{H-LOAD-NAME})$$

**文件主名 = 处理器名 = 默认关注的注解名**：`allMut.subs` → 名 `allMut`、关注 `allMut`。引擎据此跳过无关 AST（§5）。脚本本身是 Sublimation 脚本模式（顶层语句直接执行、无需 main、由解释器解释执行），脚本约定：抛异常 → E-PROCESSOR-ERROR 且 AST 不变；编辑幂等（§6）。

### 4.2 脚本内指令

$$\frac{\textsf{src}\ \text{含}\ \texttt{@interested}\ \nu_1, \dots, \nu_k}{\textsf{extra}(\textsf{src}) = \{\nu_1, \dots, \nu_k\}} \quad (\text{H-LOAD-INTERESTED})$$

`@interested` 用正则 `@interested\s+([A-Za-z0-9_, ]+)` 从源码任意位置（实践中写在注释行）提取，用于**跨注解纪律**——如 `composable.subs` 声明 `@interested view`：只要工程里有 `@view` 结构体，该处理器就运行（视图构造纪律跨注解校验）。

$$\frac{\textsf{src}\ \text{含}\ \texttt{@postcompile}\ f}{\textsf{postEntry}(p) = f} \quad (\text{H-LOAD-POST})$$

`@postcompile <函数名>` 声明编译后阶段入口（V2，安卓 APT 构建 APK 用，见 §7.4）。

### 4.3 内建处理器目录（cwd 相对——拼写陷阱）

$$\frac{\textsf{DEFAULT\_DIR} = \texttt{annotation processer} \qquad \textit{相对 cwd}}{\text{内建集} = \textsf{loadFrom}(\textsf{DEFAULT\_DIR})} \quad (\text{H-LOAD-BUILTIN})$$

$$\frac{\neg\ \textsf{isDir}(\texttt{annotation processer})}{\text{内建集} = \emptyset \qquad \text{静默，不报错}} \quad (\text{H-LOAD-BUILTIN-MISS})$$

**陷阱**：目录名是 `annotation processer`（"processer" 是项目既定拼写，不是 "processor"），且是 **cwd 相对路径**——换工作目录即静默失效（langfacts §8）。同一陷阱有第二层：处理器脚本的解释器标准库目录是 `File("core")`（BuiltinProcessors.kt:22），同样 cwd 相对。目录装载按**文件名排序**保证注册序稳定；目录不存在 → 空列表（无内建处理器也是一种合法环境）。

### 4.4 目录装载的递归性（待核）

`loadFrom(D)` 用 `dir.listFiles { f -> f.isFile && f.name.endsWith(".subs") }`——只收**直接子文件**；而 ProcessorPipeline.loadProcessorFiles 的注释称「目录递归收全部 .subs」。以代码为准：**非递归**。注释/代码分歧 待核。

$$\frac{D\ \text{为目录}}{\textsf{load}(D) = \text{sortedByName}(\texttt{*.subs}\ \in\ \text{直接子文件})} \quad (\text{H-LOAD-DIR})$$

### 4.5 CLI `-p` 与 `-A`

$$\frac{\texttt{-p}\ F \qquad F\ \text{存在} \wedge F.\textsf{name}\ \texttt{endswith .subs}}{\Pi := \Pi \cdot \textsf{proc}(F)} \quad (\text{H-LOAD-P-FILE})$$

$$\frac{\texttt{-p}\ D \qquad D\ \text{为目录}}{\Pi := \Pi \cdot \textsf{load}(D)} \quad (\text{H-LOAD-P-DIR}) \qquad \frac{\texttt{-p}\ X \qquad X\ \text{既非 .subs 文件也非目录}}{\varepsilon^* := \varepsilon^* \cdot \text{「注解处理器路径无效」}} \quad (\text{H-LOAD-P-ERR})$$

$$\frac{\texttt{-A}\ k \quad | \quad \texttt{-A}\ k\texttt{=}v \qquad (\text{可多次})}{K := K[k \mapsto v] \qquad (\text{无}\ \texttt{=}\ \text{则}\ v = \texttt{''})} \quad (\text{H-LOAD-OPT})$$

CLI 细节（Main.kt:201-230）：`-p`/`--processor`、`-A`/`--processor-arg` 均可多次；`-p` 路径不存在直接退出码 2；`-A` 后无参退出码 2。注册序：

$$\frac{\Pi = \textsf{sortedByName}(\textsf{loadFrom}(\texttt{annotation processer})) \cdot \Pi_{\texttt{-p}}}{\text{注册序} = \Pi \qquad \text{同名处理器先注册者胜（putIfAbsent）}} \quad (\text{H-LOAD-ORDER})$$

### 4.6 装载诊断与宿主对接

$$\frac{\varepsilon^* \neq \emptyset}{\Phi \vdash A \Rightarrow \texttt{E-PROCESSOR-LOAD}@\textsf{path}} \quad (\text{H-LOAD-DIAG})$$

目录模式下装载错误先于处理跑（`loadErrorsToBag`，有错退出码 1）；单文件模式下装载错误汇入处理器诊断袋（E-PROCESSOR-LOAD）。

`ProcessorHost` 是**宿主外壳**（11 卷接口）：向脚本模式解释器注入 `loadProject / processAnnotations / writeGenerated / annotatedCount / diagnosticReport / hasErrors` 六个宿主函数，把工程装载、管线执行、生成代码写出一站对接；`@host` 声明的无体函数由宿主运行时注入（`Interpreter.register`）。本卷不展开宿主语义。

## 五、引擎多轮判断（ProcessorEngine）

### 5.1 一轮流程

引擎持有注册表 `LinkedHashMap<名, 处理器>`，`run(A, Σ, typeOf, emit, recheck, K)` 的每轮：

1. 扫描当前 AST → 挂载点序列（实现按处理器逐个重扫，ProcessorEngine.kt:88——同一轮内后位处理器看到前位处理器的改写）；
2. 按注册序逐处理器：挂载点无该处理器关注注解 → 跳过；否则构建 ProcessorInput 调 process()；
3. 输出 AST ≠ 当前 AST → 更新当前 AST；
4. 本轮有变化 → 调 recheck 重查（可选）；无变化 → 退出；超 5 轮 → E-PROCESSOR-LOOP。

判断式（r 为轮次计数，初始 `changed := 真` 故第一轮必跑）：

$$\frac{\textsf{sites}(A) \cap \textsf{int}(p) = \emptyset}{\Pi; A \looparrowright_r A \qquad p\ \text{跳过}} \quad (\text{H-SKIP})$$

$$\frac{\textsf{sites}(A) \cap \textsf{int}(p) \neq \emptyset \qquad p \vdash A \Rightarrow (A', \delta^*)}{\delta^*\ \text{入}\ \Phi \qquad A' \neq A \Rightarrow \textsf{current} := A'} \quad (\text{H-PROC})$$

$$\frac{p.\textsf{process()}\ \text{抛异常}}{\Phi \vdash \texttt{E-PROCESSOR-ERROR} \qquad A\ \text{不变，继续下一处理器}} \quad (\text{H-PROC-THROW})$$

### 5.2 变化判定

$$\frac{p \vdash A \Rightarrow (A', \delta^*) \qquad A' \neq A\ (\text{FileAst 结构相等})}{\textsf{roundChanged} := \text{真}} \quad (\text{H-CHANGE})$$

FileAst 是 data class，`output.ast != current` 是**结构相等**比较（非引用比较）。这决定了收敛契约：处理器产出的 AST 与输入逐字段相等即视为「无变化」，注解编辑的幂等性（§6.2）正是靠这条停机。

### 5.3 重查

$$\frac{\textsf{roundChanged} \qquad \textsf{recheck} \neq \textsf{null}}{\textsf{recheck}(A) \Rightarrow (\Phi_{\text{rc}}, \Sigma') \qquad \Sigma := \Sigma'} \quad (\text{H-RECHECK})$$

重查保证**「所有代码都过检查」——处理器产出视为新代码，不可绕过语言设计**（ProcessorEngine.kt:21 头注；00 卷 I-3）。两种管线的重查强度不同：

- **单文件**（ProcessorPipeline.run）：recheck = 独立 Checker 每轮跑全量（`Checker(newAst).run()`，拿回新符号表）；
- **多模块**（moduleTransformer）：**模块内不重查**（recheck = null），交给 compiler 侧 MultiModule 在全部模块变换后统一重跑 A/B/C——模块间交叉引用的重新检查只在模块层做才完整。

### 5.4 收敛与停机保护

$$\frac{\neg\ \textsf{roundChanged}}{\Pi \vdash A \looparrowright A} \quad (\text{H-LOOP-EXIT}) \qquad \frac{r \geq 5 \wedge \textsf{changed}}{\Phi \vdash \texttt{E-PROCESSOR-LOOP}\ (\text{「N 轮内未收敛，可能产生触发自己的代码」})} \quad (\text{H-LOOP-BOUND})$$

零开销快门：

$$\frac{\Pi = \emptyset\ \vee\ \bigcup_p \textsf{int}(p) = \emptyset}{\Pi \vdash A \looparrowright A \qquad \text{原引用返回（不跑引擎）}} \quad (\text{H-ZERO})$$

即：工程无任何关注注解时，处理器阶段引用不变、诊断袋为空（ProcessorPipeline.run 的 interestedAnnotationNames 判空；「无关注注解则整轮跳过」亦逐处理器生效）。

### 5.5 处理器输入（ProcessorInput）

| 字段 | 语义 | 限制 |
|---|---|---|
| `ast` | 当前 AST（只读引用） | 变换只能通过返回新 FileAst |
| `symbols` | SymbolsView 只读符号表 | findFunction/allStructs/implsOfTrait 等查询；**不能写**——加声明要走 AST 变换，由重查重新登记 |
| `annotated` | 本轮扫描的挂载点 | H-SCAN-SPLIT 的产物 |
| `options` | `-A key=value` 编译参数 | 单文件 check 不传（§7.1 陷阱） |
| `typeOf` | 类型查询 | V1 限制：类型在 Checker 弥散上下文而非 AST 节点，**大部分返回 null**，视为尽力查询 |
| `annotationsOf` | 声明的注解列表 | 等价于扫描升格 |
| `emit` | 生成代码发射器 | 累积片段供宿主 writeGenerated 写出；**不是 AST 变换的替代** |

## 六、编辑语义（脚本 API → AST 重建）

### 6.1 累积契约

脚本执行期**不改 AST**：脚本通过宿主函数只累积编辑指令，由 ScriptProcessor.process 收尾时以「保持 AST 不可变」（data class copy 重建）的方式作用回去：

$$\frac{p \vdash A \Rightarrow (A', \delta^*)}{A' = \textsf{applyAnnEdits}(\textsf{applyAstEdits}(A, \textsf{astEdits}^*), \textsf{annEdits}^*)} \quad (\text{H-EDIT-ORDER})$$

**应用顺序：先结构性编辑（体替换/语句注入/声明增删/视图原语）、后注解编辑**——两者按声明名匹配，互不干扰。

### 6.2 注解编辑（AnnotationEdit）

指令六条：`addStructAnnotation` / `removeStructAnnotation` / `addFieldAnnotation(s, f, a)` / `removeFieldAnnotation` / `addFunAnnotation` / `removeFunAnnotation`。编辑目标 = STRUCT（声明级 field=null / 字段级 field≠null）与 FUN（仅声明级）。

$$\frac{\textsf{ed} = \textsf{add}(\nu) \qquad \nu\ \text{已在目标注解表}}{\textsf{apply}(\textsf{ed}) = \text{无变化} \qquad \text{幂等}} \quad (\text{H-EDIT-ANN-IDEM})$$

$$\frac{\textsf{ed}\ \text{的目标（结构体/函数/字段名）不存在}}{\Phi \vdash \texttt{W-PROCESSOR-EDIT}\ (\text{「目标不存在？」}) \qquad \text{其余编辑继续}} \quad (\text{H-EDIT-ANN-MISS})$$

$$\frac{\textsf{annEdits}^* = \emptyset\ \vee\ \text{无编辑命中}}{A' = A\ (\text{引用相等，引擎据此跳过重查})} \quad (\text{H-EDIT-ANN-NOOP})$$

H-EDIT-ANN-IDEM 是收敛机制的核心：第二轮起注解已存在 → 不产生变化 → 引擎判定无变化 → 停机。

### 6.3 结构性编辑（AstEdit）

四条通用指令 + 两条视图原语：

| 指令 | 语义 | 失败处理 |
|---|---|---|
| `setFunBody(name, src)` | 函数体整体替换（块体/表达式体） | 片段解析失败 → E-PROCESSOR-EDIT（错误级，该条**丢弃**） |
| `prependStmts(name, [src…])` | 语句插到块体最前 | 目标不存在/无体函数 → W-PROCESSOR-EDIT |
| `addDecl(src)` | 文件末尾追加新声明 | 同名已存在 → 跳过（幂等） |
| `replaceDecl(name, src)` | 整体替换命名声明 | 目标不存在 → W-PROCESSOR-EDIT；ImplDecl 无名不参与按名替换 |
| `rewriteViewCtors(views)`（原语） | 视图构造点改写为 `X(..., children = listOf(子视图), recomposion = recomposion$X$N)`，body 擦除 | 已改写的构造点不再匹配（幂等） |
| `injectViewStruct(name)`（原语） | 给结构体追加 `children: List[Any]` + `recomposion: (Any) => Null` | 字段已存在则无变化（幂等） |

$$\frac{\textsf{src}\ \text{片段解析失败（ParseFailure）}}{\Phi \vdash \texttt{E-PROCESSOR-EDIT}\ (\text{「源码片段解析失败，编辑被丢弃」}) \qquad \text{其余编辑继续}} \quad (\text{H-EDIT-AST-PARSE})$$

$$\frac{\textsf{prependStmts}(f, \cdot) \qquad f.\textsf{body}\ \text{为表达式体}}{\textsf{body} := \textsf{Block}(\textsf{prep} + [\textsf{return}\ b]) \quad (\text{脱糖})} \quad (\text{H-EDIT-PREPEND-DESUGAR})$$

$$\frac{\textsf{addDecl}(\textsf{src}) \qquad \text{同名声明已存在}}{\text{跳过} \qquad \text{幂等}} \quad (\text{H-EDIT-ADDDECL-IDEM})$$

结构性编辑的**幂等须脚本自守**：同一轮重复发同体替换天然幂等（结构相等），`prependStmts` 需配注解标记自守（否则每轮注入一次直至 5 轮上限报 E-PROCESSOR-LOOP）。

### 6.4 视图原语为什么在框架侧

`rewriteViewCtors` / `injectViewStruct` / `collectViewCtorSites` 是表达式位的 AST 遍历+重建（AndroidViewEdits.kt），声明级的脚本 API 表达不了，故框架提供原语、编排在脚本里完成（view.subs 的三段编排见 §8.3）。构造点识别：`CallExpr(StructCtorExpr(X, …), [bodyLambda])`（Parser 尾随 lambda 脱糖形态），按源码序为每个视图名分配递增 ordinal。

## 七、编译管线时序（处理器先于 B/C 检查）

### 7.1 单文件（check / compile）

$$\frac{\textsf{cmd} \in \{\texttt{check}, \texttt{compile}\} \qquad A = \textsf{parse}(\textsf{src})}{A_1: \Pi \vdash A \looparrowright A' \qquad A_2: \textsf{Checker}(A') \Rightarrow \Phi} \quad (\text{H-TIME-SINGLE})$$

注释原文（Main.kt:295/311）：「注解处理器（脚本模式解释执行）先跑：变换后的 AST 才是检查对象（如 @allMut 引入的 @mut）」。**陷阱事实**：单文件 `check` 走两参 `runBuiltin(ast, extraProcessors)`——**不传 K**，`-A` 参数在该路径对处理器不可见（`option(k)` 恒返回空串）；`compile` 与目录模式才传 K。此不对称 待核 是否有意。

### 7.2 多模块（目录即模块）

$$\frac{\text{阶段 A（init：collectPrelude + collectDecls，符号收集）已完成}}{\forall\ \text{模块}\ m: \Pi \vdash A_m \looparrowright A_m'} \quad (\text{H-TIME-MODULE-A})$$

$$\frac{\exists m: A_m' \neq A_m}{\text{重建每模块 Checker（阶段 A 重跑）} \Rightarrow \text{统一重跑阶段 B（finishCollect）+ C（checkAllBodies）}} \quad (\text{H-TIME-MODULE-RECHECK})$$

$$\frac{\forall m: A_m' = A_m}{\text{runPhases（B/C）一次}} \quad (\text{H-TIME-MODULE-PLAIN})$$

即「**处理器先于 B/C 检查跑**」（Main.kt:250-251 注、langfacts §8）：阶段 A 后、B/C 前。处理器产出（如 @allMut 引入的 @mut）是要被合法化的代码——**先变换再统一检查**；已检查过的情形也兼容（重跑 B/C，重复诊断经袋内去重吸收）。入口唯一性（多个 main 的 E-DUP-DECL）在 runPhases 内检查。

### 7.3 处理器产出视为新代码（健全性条款）

$$\frac{p \vdash A \Rightarrow (A', \delta^*) \qquad A'\ \text{含非法形态}}{A'\ \text{在后续/重查 Checker 中被拒（E-…）} \qquad \text{处理器无豁免}} \quad (\text{H-LEGIT})$$

处理器没有绕过语言设计的通道：所有闸门（纯度、可变性、类型、穷尽、证明义务）在重查阶段对处理器产物与用户代码一视同仁。`unchecked` 也不能由处理器注入（它是源码语句形态，经解析产生）。

### 7.4 编译后阶段（postCompile，V2）

$$\frac{\textsf{cmd} = \texttt{compile} \qquad \text{JS 生成成功}}{\forall p \in \Pi: p.\textsf{postCompile}(\textsf{ctx}) \Rightarrow \delta^*} \quad (\text{H-TIME-POST})$$

ctx = PostCompileContext `{finalAst, js, outputPath?, projectDir, options: K, report}`。用途：需要构建额外产物的处理器——安卓 APT 的 APK（aapt2/d8/zipalign/apksigner 由 `-A` 传入的工具路径驱动；脚本侧 `buildAndroidApk(appDir, jsPath, outDir, sdkDir)`）。只做 AST 变换的处理器默认 no-op。

$$\frac{p.\textsf{postCompile}\ \text{抛异常}}{\Phi \vdash \texttt{E-POSTCOMPILE-ERROR}} \qquad \frac{\textsf{postEntry}\ \text{的脚本重跑抛异常}}{\Phi \vdash \texttt{E-POSTCOMPILE-SCRIPT}} \quad (\text{H-POST-ERR})$$

**关键事实**：postCompile 诊断**只报告不阻断**——即使出错，CLI 只打印「[警告] 注解处理器编译后阶段出错」，编译退出码不变（Main.kt:284/347）。脚本约定：postCompile 入口调用作为顶层语句执行一次（`fun __dshPostGuard() : Null = entry()` + 脚本体 + 调用），处理器常规处理语句须自行幂等或由 `option("__post_compile__")` 分支守卫。

## 八、@allMut：APT 引入注解机制

### 8.1 引入判断

`@allMut` 是**处理器层注解**：编译器核心完全不消费它，它的全部语义由 `annotation processer/allMut.subs` 实现：

$$\frac{\texttt{@allMut struct}\ S(f_1: T_1, \dots, f_k: T_k)}{\textsf{allMut} \vdash A \looparrowright A' \quad \text{其中}\ S' = \texttt{@mut struct}\ S(\texttt{@mut}\ f_1: T_1, \dots, \texttt{@mut}\ f_k: T_k)} \quad (\text{H-ALLMUT})$$

脚本实现（20 行，递归处理结构体表与字段表）：`processStructs(structsWithAnnotation("allMut"))` → 每个结构体 `addStructAnnotation(s, "mut")` + 对每个字段 `addFieldAnnotation(s, f, "mut")`。可运行示例：

```subl
@allMut struct Acc(total: Nat)              // 等价于 @mut struct Acc(@mut total: Nat)

fun bump(a: @mut Acc, n: Nat) : Nat {
  a.total = a.total + n                    // 字段写：@mut 字段 + @mut 视图（已持）
  a.total
}

fun main() { print(bump(Acc(0), 3)) }
```

### 8.2 引入的注解先于 B/C 合法化

$$\frac{\textsf{allMut} \vdash A \looparrowright A' \qquad A'\ \text{含}\ \texttt{@mut struct}/\texttt{@mut 字段}}{A'\ \text{进入阶段 B/C 检查} \qquad \texttt{@mut}\ \text{在使用点已被引入（合法化）}} \quad (\text{H-ALLMUT-LEGIT})$$

这是「APT 引入注解先于 B/C 检查」的范式：若处理器在检查后才跑，`@mut` 字段写会先撞 E-NOT-MUT / E-IMMUT-ASSIGN；时序保证引入先于检查（H-TIME-*）。反过来，这也说明 @allMut 的语义**完全由流水线承担**——不跑处理器的环境（parse / tokens / run-script 子命令）里 `@allMut` 不产生任何 @mut。

### 8.3 内建处理器链（注册序 = 文件名序）

注册序 `allMut < android < composable < view`（sortedBy 文件名）：

| 处理器 | 关注 | 行为 | AST 变化 | 收敛 |
|---|---|---|---|---|
| `allMut.subs` | {allMut} | 展开结构体+字段 @mut | 有 | 幂等（H-EDIT-ANN-IDEM） |
| `android.subs` | {android} | 白名单/缺 @impure 告警/无体检查；`@postcompile build` 构建 APK | 无（仅诊断） | 天然零变化 |
| `composable.subs` | {composable, view}（@interested view） | 视图构造纪律：@view 只能在 @composable 函数里构造，否则 processorError | 无（仅诊断） | 天然零变化 |
| `view.subs` | {view} | 注入 children/recomposion 字段；每构造点 `addDecl(recomposion$X$N)`；rewriteViewCtors | 有 | 三重幂等（字段无变化/同名跳过/无匹配构造点） |

视图生成函数形态（view.subs 生成）：

```subl
@android @impure fun recomposion$X$N(v: Any): Null = androidRecompose("X", 3, v)
```

多轮协作事实：composable 的纪律校验跨注解生效（@interested view），即使工程没有任何 @composable 函数，只要有 @view 结构体构造点就会触发校验——这是「关注注解」机制超越文件名约定之处。

## 十、健全性不变量（本卷 H 族）

**H-1（扫描忠实）。** 挂载点序列 = 可挂节点的注解原样升格：扫描不解释、不过滤、不合并注解；一个注解一条，保源码序。Param 与无注解字段节点对扫描不可见（H-SCAN-BLIND），这是既定边界而非缺陷。

**H-2（检查不绕过）。** 处理器产出的每一份 AST 都进 Checker：单文件每轮重查 + CLI 侧全量检查；多模块模块内不重查但模块层统一重跑 A/B/C。无任何「处理器产物免检」通道（H-LEGIT；00 卷 I-3）。

**H-3（停机保护）。** 引擎轮次有界（R = 5）；超限报 E-PROCESSOR-LOOP 而非挂起或静默接受。收敛的手段是幂等（注解编辑天然幂等；结构性编辑须脚本自守）。

**H-4（变换不可变）。** 处理器拿到的是 AST 只读引用；变换只能通过返回新 FileAst（data class copy 重建），符号表只读。脚本运行期累积编辑、收尾统一应用（H-EDIT-ORDER）。

**H-5（装载可观测与 cwd 依赖）。** 装载失败产 E-PROCESSOR-LOAD（可观测）；但内建处理器目录 `annotation processer/`（注意拼写）与处理器标准库目录 `core/` 均为 **cwd 相对**——换工作目录即静默退化为无内建处理器环境（H-LOAD-BUILTIN-MISS）。这条是部署陷阱：仓库根执行 CLI 才有内建处理器。

**H-6（诊断分级正确）。** 处理器诊断经 bagOf 逐级映射保留严重级别；postCompile 诊断只报告不阻断（H-TIME-POST）——APK 构建失败不改编译退出码。

## 十一、待核与勘误入口

1. **目录装载递归性**：ProcessorPipeline 注释称目录「递归收全部 .subs」，BuiltinProcessors.loadFrom 用 listFiles（仅直接子文件）。本卷按代码记为非递归（§4.4）；待裁定注释是遗留还是需改实现。
2. **单文件 check 不传 -A**：Main.kt:296 调两参 runBuiltin（options 空），compile 与目录模式传。待核是否有意；若有意，-A 文档应注明只在 compile 生效。
3. **每轮每处理器重扫描**：ProcessorEngine.kt:88 在处理器循环内调用 AnnotationScanner.scan，而非每轮一次（其头注流程图称每轮一次）。语义等价（同轮内后位看见前位改写），性能事实以代码为准。待核。
