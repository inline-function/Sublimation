# 第八卷 · 模块系统

> 本卷规定凝华的工程组织：目录即模块、settings 文件、挂载、可见性、core 标准库、多模块编译的三阶段，以及注解处理器管线。

---

## 1. 模块

### 1.1 目录即模块

**一个目录 = 一个模块。**目录树即模块树：

```
MY_PROJECT/
  main.subl                  ← 根模块的源文件
  core/                      ← core 标准库包（隐式自动挂载）
  users/                     ← 子模块目录
    users.subl               ← 模块源码
    users.settings           ← 模块声明（mount 依赖）
  billing/
    billing.subl
```

规则：

- 编译入口（一个目录）是**根模块**；
- 同目录下所有 `.subl` 文件**共享一个符号表**；
- 模块的标识是**绝对路径** `absPath`：相对根以 `/` 连接的路径；根的 `absPath` 是空串（唯一键）；
- `fun main()` 写在任意模块里都可以。

### 1.2 模块扫描

```
scan(root)：递归扫描目录树
────────────────────────────────────────  (X-SCAN)
① 每个目录构成一个 ModuleNode(name, absPath, dir)
② 目录内文件按名字排序处理，只收集 .subl 文件
③ 子目录的 absPath = 父 absPath + "/" + 目录名（父为根时即目录名）
④ 忽略隐藏目录（名字以 . 开头）与构建产物目录
```

**忽略目录集**：

```
build   out   target   node_modules   .git   .gradle   .idea   .kotlin
```

外加一切以 `.` 开头的隐藏目录。

### 1.3 根模块的限制

**根模块没有 settings 文件**——它的模块名为空，装载 settings 时直接跳过（历史限制）。

这不影响可见性：`core` 对根模块同样隐式挂载，子目录按限定名可达。

## 2. settings 文件与挂载

### 2.1 settings 文件

每个模块可以有一个 `<模块名>.settings` 文件（模块名 = 目录名），逐行声明依赖。

**文法**：

```
Settings → { Line }
Line     → 'mount' Path [ 'as' Alias ]     挂载指令
         | '#' { 任意字符 }                 注释
         | 空行
```

`mount <路径> [as <别名>]` 是 settings 支持的**唯一**指令；别的写法报 `E-PARSE-SETTINGS`。

### 2.2 挂载语义

**挂载**（mount）是「在当前模块的命名空间里加一条指针」，**不复制代码**。

```
mount billing                    # 挂兄弟模块
mount core.math                  # 挂标准库的 math 子包（点分完整包名）
mount core.collection as coll    # 挂到本地别名 coll
```

```
MountDecl = ⟨ targetAbsPath : String, alias : String? ⟩
```

规则：

- **路径写法两等价**：斜杠形 `core/math` 与点分形 `core.math`（目录名按约定不含点）；
- **多段目标的前缀包一并隐式挂载**：`mount core.math` 之后，短名 `math.gcd(…)` 即可达；
- 挂载目标必须存在，否则报 `E-UNBOUND-NAME`（消息形如「模块 users 的 settings 挂载了不存在的模块路径 'nothere'」）；
- 挂载目标的**本地名**若与子目录名或别的挂载名相撞，报 `E-DUP-DECL`——因此一个模块没法挂自己的直接子目录（目标名字已被子目录占用）；
- 挂载链成环报 `E-CIRCULAR-MOUNT`（只报第一个环）。

### 2.3 别名

```
mount core.collection as coll
```

挂载后 `coll` 成为该模块在当前模块命名空间中的本地名。

## 3. 可见性

### 3.1 可见性是计算出来的集合

可见性**不是查表的布尔值**，而是**计算出来的集合**：每次符号查找都要携带当前模块的完整可见路径集合 `visiblePaths`。

### 3.2 可见性方向

```
────────────────────────────────────────  (X-VISIBILITY)
父 → 子：可见（限定名，且传递）
子 → 父：不可见
兄弟之间：默认不可见，靠挂载建立
祖先的挂载：向下流淌，对后代可见
挂载目标的符号：经传递可达
```

引用路径一律**相对当前模块视角**：`project/data/x.subl` 引用标准库同样写 `core.math.gcd`（`core` 经挂载传递可见）。

### 3.3 裸名可见集

$$\text{裸名可见集} = \text{本模块} \cup \text{core 整包（默认导入）} \cup \text{自身及祖先挂载的传递闭包}$$

**子模块的函数在父模块里裸调不到**——必须写限定名或挂载它。

### 3.4 三种调用形式

以挂载了 `mount core.math` 的模块为例，三种写法都对：

```subl
core.math.gcd(12, 8)    // 全限定名
math.gcd(12, 8)         // 短名（挂载目标的前缀包）
gcd(12, 8)              // 裸名（默认导入）
```

在根模块里直接写 `dbl(21)`（不加限定也不挂 `util`）会被拒：

```
E-UNBOUND-NAME: 没找到函数 dbl——拼写错了？还是没 mount 它所在的模块？
```

### 3.5 跨模块解析

构造子（`Ok`／`Err`、`Some`／`None`）、结构体、枚举、函数、类型类方法都会在可见模块（自己 + 后代 + 挂载闭包 + core）里**依次查找**。

类型类的 `impl` 也随模块可见性走：想用别的模块的 `impl Show for Point`，把那个模块挂载过来即可。

**跨模块同名构造子**取末者，可能导致静默覆盖——书写跨模块代码时应当用 `枚举::构造子` 消歧。

## 4. core 标准库

### 4.1 标准库的形态

标准库是名为 **core** 的**包**：目录下只含子包目录、**没有直接的 `.subl` 源文件**。

```
core/
  math/math.subl + math.settings       算术：gcd/lcm/isEven/sq …
  collection/*.subl                    List/Set/Map/Optional/Result 与类型类
  string/string.subl                   concat/length/charAt/parseNat …
  logic/logic.subl                     定理：rangeLowerBound、natNonNeg …
  classic/                             经典逻辑定理（需 @classic 挂载）
  io  json  time  async  random  net  regex  encoding  real  number
```

**判定「是不是标准库包」看形态**：目录里只有子包、没有直接 `.subl`。用户自己建一个 `core/` 并往里直接放源文件，它就是普通模块，不会被当作标准库、也不触发隐式挂载。

### 4.2 标准库的识别布局

编译器按两种布局识别标准库（相对编译入口根，按优先级）：

```
① 入口目录下有 core/ 子目录
      —— 最常见的自包含写法：把仓库根 core/ 复制一份进工程
② 根下没有 core/ 而存在 test/core/，且 test/core 是标准库包形态
      —— 嫁接：重挂为根的 core 子树，absPath 重算为 core/…
```

### 4.3 隐式挂载

```
M 是非 core 的模块
────────────────────────────────────────  (X-IMPLICIT-CORE)
编译器为 M 注入标准库挂载：core 根及其全部子包按名字挂入
（等价于自动写了 mount core + mount core.math + mount core.collection + …）
```

用户模块**无需任何 settings** 即可：

- **裸名**调用标准库符号：`gcd(12, 8)`、`Some(3)`、`size(xs)`；
- **限定名**调用：`core.math.gcd(12, 8)`、`core.collection.size(xs)`。

**本地优先**：用户模块自带的同名子目录优先。`proj/core/` 存在时，`proj` 的 `core.xxx` 指自己的子模块，编译器跳过对标准库子包的注入（本地名 `core` 已被占用，其余子包照常注入）。

### 4.4 prelude

无论何种模式，编译器注入一组**prelude** 实体：

- 基本类型（第三卷 §2.1）；
- `Bool`、`Null`、`Optional` 的枚举注册；
- 内建函数表（`@root` 白名单，第九卷 §4）。

### 4.5 跨模块定理搜索

证明时，定理搜索同样沿可见路径跨模块展开：

```subl
∵ n ∈ (0..30)
∴ n ≥ 0            // 命中 core/logic/logic.subl 的 rangeLowerBound 与 natNonNeg
```

## 5. 多模块编译

### 5.1 三阶段

```
阶段 A（init）           prelude + 符号收集；全模块先落全局符号表
      ↓
阶段 A′（注解处理器）     AST → AST 变换，多轮至收敛（§6）
      ↓
阶段 B（finishCollect）  类型可解析性 + impl 完整性 + pure 事实 + 子类型类父链
      ↓
阶段 C（checkAllBodies） 声明体 + 顶层语句检查
```

**为何必须分阶段**：

| 阶段 | 前置依赖 |
|---|---|
| A | 无——纯收集 |
| B | 全树符号齐备后才能做跨模块的类型可解析性与 impl 检查 |
| C | B 阶段的类型、impl、pure 信息 |

### 5.2 全局符号表

```
allSymbols : Map<absPath, Symbols>
```

每个模块一个符号表；跨模块查找携带 `visiblePaths`。

### 5.3 main 入口

$$\frac{\text{整个工程有且仅有一个零参 fun main()}}{\begin{gathered}\text{多个模块声明 main} \Rightarrow \text{E-DUP-DECL（消息列出全部位置）} \\\text{main 带形参或类型参数} \Rightarrow \text{E-MAIN-PARAMS}\end{gathered}} \quad (\text{X-MAIN})$$

`main()` 自动作为入口调用（代码生成尾部追加 `main();`）。`main` 天然是 `@impure` 允许的异步上下文（第六卷 §8.1）。

### 5.4 命令与产物

```
check   <目录>            类型检查整个工程
compile <目录> -o out.js  语义通过后生成 JS
```

`check`／`compile` 传**目录**即走模块系统（目录模式只支持这两个命令；脚本目录用 `run-script`）。

编译产物是**单个 JavaScript 文件**。跨模块同名符号靠名字前缀隔离：

```
mangle(absPath, name)：
────────────────────────────────────────  (X-MANGLE)
absPath 的 '/' 换成 '_' 再做合法化，前缀于名字
core/math 的 gcd → core_math__gcd
util 的 dbl      → util__dbl
根模块符号        → 不加前缀
```

### 5.5 目录编译的诊断过滤

目录编译时：

- `core` 标准库自身的 `H-ROOT-BUILTIN`、`W-UNUSED` 等提示和警告会出现在输出里（不阻断编译）；
- **补充级诊断只保留根模块的**——挂进来的模块的推导过程被视为噪声，自动过滤；
- 模块层错误（挂载目标缺失、settings 语法、挂载成环）在树校验阶段**最先**报出。

## 6. 注解处理器

### 6.1 定位

注解处理器是**编译期的用户扩展点**：它是一段**用凝华自己写的程序**（`.subs` 脚本），由解释器解释执行。它读注解、输出两类编辑——**注解编辑**（加／删注解）与**结构性编辑**（改函数体、插语句、增删声明，即真正的 AST → AST 变换）——编译器在语义检查前统一应用，让注解真正改变代码的语义。

**模型是 AST 变换管道**，接近 Babel 插件、PostCSS 插件——处理器是「AST → AST」的变换函数，链式执行。区别于 Java APT（只能生成新文件，不能改 AST）和 Rust proc-macro（只能生成 token，不能改已解析的 AST）。

**为什么解释执行**：处理器跑在解释器上，能调用语言本身的 `when`／递归／`List`，与被处理的代码同源，不需要为处理器单独设计 DSL。

### 6.2 管线位置

```
解析 → 符号收集(阶段 A) → [注解处理器] → 语义检查(阶段 B/C) → 代码生成
```

处理器**先于**语义检查跑：处理器的产出（如 `@allMut` 引入的 `@mut`）是「要被合法化的代码」，变换后再统一进检查器——**「所有代码都过检查」的契约仍然成立，处理器不能绕过语言设计**（总纲不变量 I-5）。

### 6.3 核心契约

| 维度 | 规定 |
|---|---|
| AST 不变性 | AST 保持不可变，处理器返回**新** AST（节点是不可变数据类，只能创建新实例；深度变换需递归重建整棵树） |
| 处理后检查 | **重新跑语义检查** |
| 处理器顺序 | 按注册顺序（装载顺序）执行 |
| 输入 | AST + 符号表 + 类型查询（均**只读**） |
| 重新检查时机 | 改完 AST 后重新跑检查器 |

**为什么必须重新检查**：处理器能改 AST——加 `impl`、改函数返回类型、删声明。如果不重新检查，处理器能产生「非法代码」绕过检查。重新检查保证：所有代码都过检查（无论谁产生的）；处理器不能绕过语言设计。

**处理器产出的合法性**：处理器返回的 AST 可能不符合语言规则（比如函数没有函数体）。重新检查会捕获这些——走现有的诊断通道。**处理器不需要保证产出合法**；处理器产出视为新代码。

### 6.4 处理器文件

处理器脚本以 `.subs` 文件存在：

- **默认目录 `annotation processer/`**（相对**工作目录**，编译器从哪里启动就从哪里找）——内建 `@allMut` 脚本就在这里；目录不存在时**静默跳过**（适合打包发布）；
- **文件主名 = 处理器名 = 关注的注解名**：`allMut.subs` → 处理器 `allMut`，只对 `@allMut` 起反应；引擎据此跳过无关 AST，零开销；
- 文件里是**普通脚本**：顶层语句直接执行，用 `//` 写注释（`#` 不是注释，会报语法错），遍历列表用 `when(Nil/Cons)`，lambda 与 `when` 臂的 `=>` 与普通程序相同。

因为默认目录相对工作目录，随身携带的工程往往没有它——这正是 `-p` 的用途。

### 6.5 装载

```
sublimation compile demo/app -p "annotation processer"   :: 装载默认目录
sublimation compile demo/app -p myprocs/mine.subs         :: 单文件
sublimation check demo/app -p procsA -p procsB -v         :: 可多次、可与 -v 并用
```

规则：

- `-p` 可多次附加；目录参数收入其**直接**下的全部 `.subs`（不递归子目录；按文件名排序，注册序稳定）；
- 路径不存在 → `[错误] 注解处理器路径不存在: <路径>`；
- 存在但不是 `.subs` 文件或目录 → `E-PROCESSOR-LOAD`（装载失败，编译立即终止）;
- 无论是否传 `-p`，默认目录的处理器总会装载；
- `check`／`compile` 在**单文件与目录模式**下都跑处理器；
- **顺序即注册顺序**：处理器 A 在 B 之前执行，A 的产出是 B 的输入。依赖关系由用户负责，编译器不猜、不做自动拓扑排序。

### 6.6 宿主 API

处理器脚本通过一组**宿主函数**只读查询声明、累积注解编辑、报告诊断（脚本里直接调用，不需要声明）：

**查询**：

| 宿主函数 | 作用 |
|---|---|
| `structNames()` | 全部结构体名（声明序） |
| `structsWithAnnotation(a)` | 带注解 `a` 的结构体名 |
| `structAnnotations(n)` / `structHasAnnotation(n, a)` | 结构体的注解列表 / 是否有注解 `a` |
| `structFields(n)` / `fieldAnnotations(s, f)` | 字段名（声明序）/ 字段的注解列表 |
| `funNames()` / `funsWithAnnotation(a)` / `funAnnotations(n)` | 函数族查询 |

**注解编辑**：

| 宿主函数 | 作用 |
|---|---|
| `addStructAnnotation(n, a)` / `removeStructAnnotation(n, a)` | 结构体注解增删 |
| `addFieldAnnotation(s, f, a)` / `removeFieldAnnotation(s, f, a)` | 字段注解增删 |
| `addFunAnnotation(n, a)` / `removeFunAnnotation(n, a)` | 函数注解增删 |

**结构性编辑**：

| 宿主函数 | 作用 |
|---|---|
| `setFunBody(name, src)` | 把函数的体替换为 `src` 解析出的块体或表达式 |
| `prependStmts(name, stmts)` | 把语句片段插到函数块体最前；表达式体自动脱糖成 return 块 |
| `addDecl(src)` | 追加一条新声明（fun/struct/enum/class/impl/type） |
| `replaceDecl(name, src)` | 整体替换名为 `name` 的声明 |

**诊断**：

| 宿主函数 | 诊断码 |
|---|---|
| `processorError(m)` | `E-PROCESSOR-SCRIPT` |
| `processorWarn(m)` | `W-PROCESSOR-SCRIPT` |
| `processorHint(m)` | `H-PROCESSOR-SCRIPT` |
| `processorInfo(m)` | `D-PROCESSOR-SCRIPT`（仅 `-v` 显示） |

**已知接口瑕疵**：0 参宿主函数（`structNames`、`funNames`）在脚本里被注入了一个占位形参，调用时得传一个任意实参，例如 `structNames(0)`——直接写 `structNames()` 会报 `E-ARITY`。

### 6.7 编辑的应用方式

脚本执行期**不改 AST**：编辑函数只**累积指令**，引擎收尾时以不可变方式重建 AST。

结构性编辑以**源码片段**的形式发出——引擎收尾时把片段解析成 AST 节点再不可变地嫁接回去，产物仍整体过重查。

**注解编辑的幂等性**：注解已存在不重复加，删不存在的注解也不报错——配合引擎多轮自然收敛。

**结构性编辑的幂等性**（必须自己保证，否则引擎判定「每轮都有变化」最终 `E-PROCESSOR-LOOP`）：

| 编辑 | 幂等性 |
|---|---|
| `setFunBody` / `replaceDecl` | 每轮发同样的片段 → 产物深度相等 → 停机 |
| `addDecl` | 同名声明已存在则跳过（引擎内建幂等） |
| `prependStmts` | 每轮都会真正改变语句序列——**必须自己守**，最方便的是配注解标记 |

幂等守卫示例：

```subs
// trace.subs —— 给标了 @trace 的函数体最前插入一行跟踪打印（注解标记守，幂等）
fun containsFun(f : Str) : Bool = contains(funAnnotations(f), "traced")

fun run(xs : List[Str]) : Null = when(xs) {
    Nil => null
    is Cons(f, rest) => {
        if (containsFun(f)) { null } else {
            prependStmts(f, listOf("print(toStr(111))"))
            addFunAnnotation(f, "traced")
        }
        run(rest)
    }
}
run(funsWithAnnotation("trace"))
```

### 6.8 执行模型与收敛

引擎按注册序逐处理器跑，一轮结束后若 AST 变化则进入下一轮：

```
────────────────────────────────────────  (X-PROCESSOR-LOOP)
① 跑全部处理器（按注册序）
② AST 无变化 → 收敛退出
③ AST 有变化 → 重新跑检查器，回到 ①
④ 超过最大轮数（5 轮）仍有变化 → E-PROCESSOR-LOOP
```

- **最大轮数 5**（可配置）；超轮数报错——处理器可能陷入「产生触发自己的代码」的循环。典型写法是「翻转」型脚本：有注解 `flip` 的结构体删掉、没有的加上——每轮都变，永不收敛；
- 脚本抛异常（类型检查失败／运行时错误）→ `E-PROCESSOR-ERROR`（附处理器名与原因），AST 不变。不因一个处理器出错而中断整个编译，但报错后继续其他处理器，最终编译仍失败；
- 片段解析失败 → `E-PROCESSOR-EDIT`（错误级；该条编辑被丢弃，同批其他编辑照常生效）；
- 编辑目标不存在（名字拼错）→ `W-PROCESSOR-EDIT`（警告级），其余编辑继续生效；
- **产物整体过重查**：替换出的体若是非法代码（如类型不匹配），`E-TYPE-MISMATCH` 等正常编译错误会拦截整次编译。

**跳过优化**：处理器声明其关注的注解（文件名即注解名）；AST 里没有任何处理器关注的注解时跳过该处理器。

### 6.9 能力边界

**处理器只扩展，不改语言语义。**

| 允许 | 不允许 |
|---|---|
| 加新诊断（如 `@Lint` 报风格问题） | 改类型系统规则 |
| 生成新代码（如 `@derive Show` 生成 impl） | 改命题检查逻辑 |
| 收集信息（如 `@Route` 收集路由表） | 绕过纯度检查 |
| 改注解 | 改 AST 节点类型 |
| 加新声明 | 删已有声明（如果检查器依赖它） |
| 改函数体、插语句、替换声明 | 改符号表（符号表由重新检查重建） |
| — | 撤销编译器产生的诊断 |
| — | 访问编译器内部状态（只能通过宿主 API） |

这个边界是规范的一部分——否则处理器会变成「绕过语言设计的手段」。

**违反边界的处理**：技术上，接口只暴露只读信息，处理器无法改符号表；语义上，违反边界的处理器是「用户的错」，编译器不兜底。

**当前查询范围限制**：查询只覆盖**结构体与函数**（字段注解可查）；enum／class／impl 不在脚本 API 里。`typeOf` 类型查询固定返回 null（类型信息在检查器的弥散上下文里，不在 AST 节点上）。settings 里注册第三方处理器（`processor` 行）仍未支持，扩展点目前是 `-p` 路径。

### 6.10 内建处理器：@allMut

标在结构体上，表示**结构体可变、全部字段也可变**。处理器把它等价改写为：

```subl
@allMut
struct Point(x : Nat, y : Nat)

// 处理器变换为：
@mut struct Point(@mut x : Nat, @mut y : Nat)
```

变换之后，下面的代码才合法（没有 `@allMut` 时同一个赋值被 `E-NOT-MUT` 拒绝）：

```subl
@allMut
struct Point(x : Nat, y : Nat)

@impure
fun main() {
    var p : @mut Point = Point(1, 2)
    p.x = 5
    print(toStr(p.x))          // 5
}
```

### 6.11 宿主外壳

`AnnotationProcessorHost` 把处理器包成可从脚本驱动的宿主：脚本模式里用 `@host` 声明工程能力函数，即可加载工程、跑处理器、写出产物：

```subs
@host fun loadProject(path : Str) : Null
@host fun processAnnotations() : Null
@host fun writeGenerated(path : Str) : Null

loadProject("myproject/")
processAnnotations()
writeGenerated("out.subl")
```

另有 `annotatedCount()`／`diagnosticReport()`／`hasErrors()` 查询函数。

**脚本不自带工程，但宿主可以给它工程**——与宿主-脚本模型一致，一切能力来自宿主（第九卷 §5）。

### 6.12 处理器示例

给标了 `@twice` 的函数逐个报警告：

```subs
// twice.subs
fun warnAll(xs : List[Str]) : Null = when(xs) {
    Nil => null
    is Cons(s2, rest) => {
        processorWarn(concat("twice hits ", s2))
        warnAll(rest)
    }
}
warnAll(funsWithAnnotation("twice"))
```

被处理的工程与命令：

```subl
// demo/cproc/main.subl
@twice
fun helper() : Nat = 1

@impure
fun main() : Null {
    print(toStr(helper()))
}
```

```
sublimation check demo/cproc -p demo/cproc
# [警告] W-PROCESSOR-SCRIPT: twice hits helper
# [完成] 模块检查通过
```

## 8. 模块系统的诊断

| 码 | 等级 | 触发条件 |
|---|---|---|
| `E-PARSE-SETTINGS` | 错误 | settings 文件出现 `mount` 以外的指令或格式错 |
| `E-CIRCULAR-MOUNT` | 错误 | 挂载链成环，只报第一个环 |
| `E-UNBOUND-NAME` | 错误 | 挂载目标不存在；裸名／限定名在可见模块里找不到 |
| `E-DUP-DECL` | 错误 | 挂载的本地名与子目录／其他挂载冲突；多个模块声明 `main`；同模块重复声明 |
| `E-MAIN-PARAMS` | 错误 | `main` 有形参或类型参数 |
| `E-PROCESSOR-LOAD` | 错误 | 处理器路径存在但不是 `.subs` 文件或目录 |
| `E-PROCESSOR-SCRIPT` | 错误 | 处理器脚本主动调 `processorError` |
| `E-PROCESSOR-ERROR` | 错误 | 处理器脚本执行失败 |
| `E-PROCESSOR-LOOP` | 错误 | 处理器 5 轮内未收敛 |
| `E-PROCESSOR-EDIT` | 错误 | 结构性编辑的片段解析失败 |
| `W-PROCESSOR-SCRIPT` | 警告 | 脚本调 `processorWarn` |
| `W-PROCESSOR-EDIT` | 警告 | 编辑的注解目标不存在 |
| `H-PROCESSOR-SCRIPT` | 提示 | 脚本调 `processorHint` |
| `D-PROCESSOR-SCRIPT` | 补充 | 脚本调 `processorInfo` |
