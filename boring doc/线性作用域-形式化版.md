## 1. 动机与问题陈述

### 1.1 现有规则的缺口

规范第五卷 §4.2 规定，`var x = e` 注入等式事实 `x = e` 的条件为：

```
e 是纯表达式
x 未标注 @mut
x 未标注 @ref
x 的类型不是可变结构体类型
────────────────────────────────────────  (G-VAR-EQ)
inject(F, x = e)
```

其否命题即：对任意 `@mut` 变量 `m`，在任何程序点都**不注入** `m = e`。第六卷 §4.3 亦规定可变变量「除自反外不承认它与其他表达式的相等命题」。

由此产生的缺口：设程序含 `@mut var m`，则对任意值 `v`，命题 `m = v` 在 Γ 中不可证（除非经 `unchecked.axiom` 逃逸或函数下文注入）。

### 1.2 缺口的根源

规则 `G-VAR-EQ` 的否定分支是正确的，其理由为：Γ 是**作用域级**的事实集（第五卷 §2.1），而可变变量的值随**程序点**变化。以作用域级的 Γ 承载程序点级的事实必然不健全——若在作用域入口注入 `m = 0`，则该事实在 `m = 1` 之后仍留在 Γ 中，证明器会据以证出假命题。

**结论**：缺口不能靠放宽 `G-VAR-EQ` 解决，必须使 Γ 具备流敏感性。

### 1.3 本卷的目标与非目标

**目标**：

- G1. 为受限语法片段（线性作用域）引入流敏感的 Γ，使可变实体的等式命题可证；
- G2. 保持健全性（总纲不变量 I-1）：任何被接受的命题义务在推理系统内可证；
- G3. 零运行时成本（总纲不变量 I-2）：本机制的全部产物在代码生成阶段被擦除；
- G4. 与既有机制兼容：不修改 `@mut`、深拷贝、纯度、`pure<f>` 的既有语义。

**非目标**：

- N1. 效应系统（`@effect`、`IO` 类型、效应器委托）——原始构想的一部分，本卷不涉及，理由见 §12；
- N2. 基于 `yield` 的异步生成器——与第六卷 §8.6 的 `Flow`／`emit` 重叠，另行设计；
- N3. 归纳证明——第四卷 §9.10 明确暂不实现，故循环出口的版本化事实不在本卷范围；
- N4. 线性类型（linear types）意义上的「恰好使用一次」——本卷不限制使用次数，见 §2.3。

## 2. 定义

### 2.1 线性作用域

**定义 2.1（线性作用域）** 线性作用域是带 `%` 前缀标记的块表达式：

```
LinearBlock → '%' BlockExpr
```

`%` 与 `{` 之间**不得存在空白**（邻接规则，见 §3.2）。

**定义 2.2（线性域族）** 设 `B` 是一个线性作用域。`B` 的**线性域族** `family(B)` 定义为：`B` 自身，加上 `B` 内所有嵌套的线性作用域（递归）。

线性域族是版本序号的分配单位：同一域族内共享版本计数器。

### 2.2 线性实体

**定义 2.3（线性实体）** 称一个变量或字段路径为**线性实体**，当且仅当：

- 它在线性域族内被声明，或在线性域族内被赋值；且
- 它标注了 `@mut`（变量）或持有 `@mut` 视图（字段路径）；且
- 它未标注 `@ref`；且
- 它未被任何 lambda 捕获（§8.1）。

线性实体的集合记为 `Lin`。

**定义 2.4（字段路径）** 字段路径是形如 `x.f₁.f₂…fₖ`（k ≥ 1）的表达式，其中 `x` 是变量名。字段路径的版本化以**整个路径**为单位。

### 2.3 关于「线性」的术语澄清

本机制所称「线性」指以下两条性质的合取，**不**指线性逻辑／线性类型中的「资源恰好使用一次」：

| 性质 | 形式化表述 |
|---|---|
| **唯一所有权**（uniqueness） | 线性实体在其生命周期内不存在别名，且不被任何逃逸出域的值引用 |
| **时间线性**（temporal linearity） | 线性实体的状态沿单一控制流时间线单向演进，每个程序点至多一个当前版本 |

对照学术术语：本机制接近 Clean 的 uniqueness types 与 Rust 的 `&mut` 借用，而非 Girard 的 linear logic。使用次数不受限制。

## 3. 语法

### 3.1 产生式

对第二卷 §5.6 的后缀表达式产生式作如下扩充：

```
Postfix → Primary { PostfixOp }

PostfixOp → … （既有产生式）
          | '%' '{' Block '}'                 ⟶ LinearBlock
```

对第二卷 §4.2 的语句产生式，线性作用域可作为语句：

```
Stmt → … （既有产生式）
     | '%' BlockExpr                          ⟶ ExprStmt(LinearBlock)
```

抽象语法节点：

```
LinearBlockExpr ⟨ block : BlockExpr, pos : String ⟩ : Expr
```

`LinearBlockExpr` 的类型是其内层 `BlockExpr` 的类型（§6.4）。

### 3.2 词法与邻接消歧

`%` 在凝华中已是 `PERCENT` 单元（取余运算符，第一卷 §4.4）。消歧规则：

```
'%' 之后紧跟 '{' 且二者之间无空白
────────────────────────────────────────  (L-LINBLOCK)
解析为线性作用域起始

其他情形
────────────────────────────────────────  (L-MOD)
'%' 解析为取余运算符
```

该规则与 `<` 的邻接消歧（第一卷 §9.2）同源：紧贴为特殊语法，带空格为运算符。

**歧义分析**：`a % { … }` 在语法上是「a 取余一个块」。由于块的类型通常不是数值类型，该表达式必然在类型检查期失败；而 `a %{ … }`（紧贴）不可能是取余。故消歧规则无实际歧义。

### 3.3 版本名的内部表示

版本名 `x#k`（k 为自然数）是**编译期内部标识**，不经过词法分析器。理由：

- `#` 在词法层是 `HASH` 单元，用于量词的类型参数标记（第二卷 §5.8）；
- 版本名不出现在源文本中，用户不可书写；
- 版本名不出现在生成代码中（§10）。

在实现中，版本名应当表示为「变量名 + 版本序号」的**结构体对**而非字符串拼接，以避免与用户标识符的任何可能冲突，并使版本比较成为整数比较。

形式化时记作 `⟨x, k⟩`，渲染为 `x#k` 仅用于诊断输出与本文档表述。

## 4. 版本化上下文

### 4.1 版本映射

**定义 4.1（版本映射）** 版本映射 `Ω` 是从线性实体到版本序号的有限映射：

```
Ω : Lin → ℕ
```

`Ω(x) = k` 读作「实体 `x` 的当前版本是 `k`」。

**定义 4.2（版本化事实）** 版本化事实是形如 `PAtom("=", [NameRef(x#k), e])` 的命题，其中 `x#k` 是版本名。

**约定**：以下将 `x#k` 视为一个原子名字（`NameRef`），其内部结构（变量名 + 序号）由符号表维护。

### 4.2 线性帧

**定义 4.3（线性帧）** 线性帧是在第五卷 §2.1 的 `Frame` 基础上扩充的结构：

```
LinearFrame = Frame ∪ ⟨
    omega       : Map<Lin, ℕ>            版本映射
    linVars     : Set<Lin>               本域族的线性实体集
    versionCtr  : Ref<ℕ>                 域族共享的版本计数器
    invalidated : Set<Prop>              已失效的版本化事实（供诊断）
⟩
```

其中 `versionCtr` 在整个线性域族内**共享**（引用语义），使嵌套域的版本序号连续递增。

**注**：`omega` 与 `linVars` 是**流敏感状态**，随程序点前进而更新；它们不是 Γ 的一部分，而是 Γ 的**索引器**——决定「名字 `x` 在当前程序点解析为哪个版本名 `x#k`」。

### 4.3 名字解析

**定义 4.4（版本解析）** 设 `F` 是线性帧，`x` 是名字。版本解析函数 `resolve` 定义为：

```
x ∈ F.omega 的域
────────────────────────────────────────  (LV-RESOLVE-LIN)
resolve(F, x) = x#(F.omega[x])

x ∉ F.omega 的域
────────────────────────────────────────  (LV-RESOLVE-PLAIN)
resolve(F, x) = x          （普通名字，不版本化）
```

**规则 LV-RESOLVE-PLAIN 的意义**：非线性的名字（不可变变量、函数名、类型名）保持原样。因此线性作用域内的不可变代码与普通作用域完全一致——版本化只对线性实体生效。

对字段路径递归应用：

```
resolve(F, x.f₁…fₖ) = resolve(F, x).f₁…fₖ
                                                          (LV-RESOLVE-FIELD)
```

即版本索引附着在**根变量**上，字段路径整体随之版本化。

### 4.4 命题的版本化改写

**定义 4.5（版本化改写）** 设 `p` 是命题表达式，`F` 是线性帧。`versionize(F, p)` 定义为对 `p` 的语法树自底向上应用 `resolve`：

```
versionize(F, PAtom(h, [t₁…tₙ])) = PAtom(h, [resolve′(F,t₁) … resolve′(F,tₙ)])
versionize(F, PNot(q))  = PNot(versionize(F, q))
versionize(F, PAnd(a,b)) = PAnd(versionize(F,a), versionize(F,b))
…（其余命题构造同理）

其中 resolve′(F, e) 对表达式 e 内的全部名字应用 resolve(F, ·)
```

**关键性质**：版本化改写是**纯语法替换**，不改变命题的逻辑结构。因此第四卷的全部推理规则对版本化后的命题同样适用——这是本机制能复用既有证明器的根本原因。

## 5. 流敏感的 Γ

### 5.1 核心判断式

普通作用域的类型判断是 `Γ ⊢ e : τ`（第三卷 §10.1），其中 Γ 在整个作用域内固定。线性作用域引入**带输出的判断式**：

```
Γ ; Ω ⊢ S ⟹ Γ′ ; Ω′
```

读作：在上下文 Γ 与版本映射 Ω 下检查语句序列 `S`，得到更新后的 Γ′ 与 Ω′。

对表达式：

```
Γ ; Ω ⊢ e : τ ; Ω′
```

读作：在 Γ、Ω 下 `e` 具有类型 τ，且求值过程中 Ω 更新为 Ω′（表达式内的赋值，如 `VarExpr`）。

### 5.2 赋值规则

```
Γ ; Ω ⊢ e : τ ; Ω₁        e 是纯表达式
x ∈ Lin     k = fresh(F)     Ω₂ = Ω₁[x ↦ k]
────────────────────────────────────────  (LV-ASSIGN)
Γ ; Ω ⊢ x = e ⟹ Γ ∪ {x#k = e′, x#k : τ} ; Ω₂

其中 e′ = versionize(F, e)，fresh(F) 递增 F.versionCtr 并返回其值
```

**规则要点**：

- 新版本的等式事实注入 Γ；
- `Ω` 更新为指向新版本，因此后续对 `x` 的读取解析到 `x#k`；
- **旧版本的事实保留在 Γ 中**（`x#(k-1) = …` 不删除）。这是必要的：证明可能需要引用历史版本（例如 `x#2 = x#1 + 10` 与 `x#1 = 1` 联合推出 `x#2 = 11`）。

**旧版本事实保留的健全性**：旧版本事实是关于**过去的程序点**的，它们不描述当前值，因此不会导致假证明。当前值由 `Ω[x]` 唯一确定（§9.2 定理）。

### 5.3 声明规则

```
Γ ; Ω ⊢ e : τ ; Ω₁     x 标注 @mut     x 未标注 @ref     x 未被 lambda 捕获
k = fresh(F)     Ω₂ = Ω₁[x ↦ k]     x 的类型不是可变结构体类型
────────────────────────────────────────  (LV-DECL)
Γ ; Ω ⊢ @mut var x : τ = e ⟹ Γ ∪ {x#k = e′, x#k : τ} ; Ω₂

x 的类型是可变结构体类型 S，S 的字段为 f₁…fₘ
────────────────────────────────────────  (LV-DECL-STRUCT)
Γ ; Ω ⊢ @mut var x : S = e ⟹ Γ ∪ {x#k = e′, x#k : S, x.fᵢ#k = e.fᵢ′} ; Ω₂
```

**与 `G-VAR-EQ` 的对比**：规则 `LV-DECL` 是 `G-VAR-EQ` 在线性域内的**受控放宽**——`@mut` 变量也注入等式，但注入的是**版本化**等式。`G-VAR-EQ` 在非线性域内保持原样。

### 5.4 字段赋值规则

```
Γ ; Ω ⊢ e : τ ; Ω₁     x.f₁…fₖ ∈ Lin     j = fresh(F)     Ω₂ = Ω₁[x.f₁…fₖ ↦ j]
x 持有 @mut 视图     x ∈ Ω₁ 的域
────────────────────────────────────────  (LV-FIELD-ASSIGN)
Γ ; Ω ⊢ x.f₁…fₖ = e ⟹ Γ ∪ {x.f₁…fₖ#j = e′} ; Ω₂
```

**对第六卷 §5.3 的放宽**：规则 `E-FIELD-WRITE` 要求「字段标注 `@mut`」且「接收者持有 `@mut` 视图」。在线性域内，第一条要求**免除**：

```
赋值 x.f = e 位于线性域内     x 持有 @mut 视图     x ∈ Lin
────────────────────────────────────────  (LV-FIELD-WRITE-RELAX)
免除「f 标注 @mut」的要求
```

**放宽的正当性**：`E-FIELD-WRITE` 的第一条要求（字段标 `@mut`）的目的是防止「通过不可变字段路径引入可变性」。在线性域内，`x` 有唯一所有权（§8.1），修改 `x.f` 不可能被域外观察到，因此该要求的目的已达成。

**伴生命题的版本化处置**（作者裁决：仅失效，不做后续流跟踪）：

```
S 的伴生命题为 [p₁…pₘ]     x : S     x.f 被赋值为 e     j = fresh(F)
────────────────────────────────────────  (LV-PROP-VERSION)
① 旧版本的伴生命题事实 pᵢ(x.f#(j-1)) 保留在 Γ 中（它关于历史版本，为真，见引理 9.2）
② 新版本的伴生命题 pᵢ(x.f#j) **不自动注入**
③ 若 versionize(F, pᵢ)[f := e] 在当前 Γ 下可证，则注入 pᵢ(x.f#j)
```

即：修改字段后，伴生命题对**新版本**不再是既得事实，必须重新获得证明——由赋值右侧代入验证（③），或由用户经 `∵`／`by` 注入，或由后续函数调用的下文注入。

**这一处置不削弱健全性**，其论证见 §9.4。

```subl
struct Pos(x : Nat) <x > 0>

@impure
fun demo() %{
    var p : @mut Pos = Pos(1)     // 注入 p.x#0 = 1、p.x#0 > 0
    ∴ p.x > 0                      // 成立：解析为 p.x#0 > 0，命中事实
    p.x = 0                        // 注入 p.x#1 = 0；p.x#1 > 0 未注入
    // ∴ p.x > 0                   // 不成立：解析为 p.x#1 > 0，Γ 中无此事实
    ∴ p.x = 0                      // 成立
}
```

### 5.5 读取规则

```
resolve(F, x) = x#k
────────────────────────────────────────  (LV-READ)
Γ ; Ω ⊢ x : τ ; Ω          （Ω 不变）
```

读取不改变版本映射。类型来自 `Γ` 中 `x#k : τ` 的事实，或符号表的变量环境。

### 5.6 分支规则

设 `if (c) B₁ else B₂` 位于线性域内，`c` 是条件，进入分支前状态为 `Γ ; Ω`。

```
Γ ; Ω ⊢ B₁ ⟹ Γ₁ ; Ω₁        Γ ; Ω ⊢ B₂ ⟹ Γ₂ ; Ω₂
∀x ∈ dom(Ω₁) ∪ dom(Ω₂). 
    k = fresh(F)，Ωₘ = Ω₁ ⊔ Ω₂ 在 x 上取 max(Ω₁[x], Ω₂[x])，Ωₘ[x] := k
Γₘ = (Γ₁ ∩ Γ₂) ∪ {x#k = x#(Ω₁[x]) ∨ x#k = x#(Ω₂[x]) | x ∈ dom(Ω₁) ∩ dom(Ω₂), Ω₁[x] ≠ Ω₂[x]}
────────────────────────────────────────  (LV-MERGE)
Γ ; Ω ⊢ if (c) B₁ else B₂ ⟹ Γₘ ; Ωₘ
```

**规则解读**：

- 两个分支各自演进版本；
- 合并点为每个在**至少一个**分支中被赋值的实体产生一个**新的合并版本** `k`；
- 注入的事实是该实体的**析取**：`x#k = x#(左支版本) ∨ x#k = x#(右支版本)`；
- 两个分支都有的事实（`Γ₁ ∩ Γ₂`）直接保留。

**特例一（两支赋同值）**：若 `Ω₁[x] ≠ Ω₂[x]` 但两支注入的等式右侧 α-等价，则析取 `x#k = v ∨ x#k = v` 经第四卷 §5.2 的合取展平与去重后等价于 `x#k = v`。故 `∴ x = v` 可证。

**特例二（仅一支赋值）**：设仅 `B₁` 赋值 `x`，则 `Ω₂[x] = Ω[x]`（未变），合并事实为 `x#k = x#(Ω₁[x]) ∨ x#k = x#(Ω[x])`。故可证「新值或旧值」的析取。

**特例三（两支都未赋值）**：`Ω₁[x] = Ω₂[x] = Ω[x]`，不产生合并版本，`Ωₘ[x] = Ω[x]`，Γ 直接取交集。

**`when` 分支**：`LV-MERGE` 推广到 n 个分支，合并事实为 n 元析取：

```
x#k = x#(Ω₁[x]) ∨ x#k = x#(Ω₂[x]) ∨ … ∨ x#k = x#(Ωₙ[x])
                                                          (LV-MERGE-N)
```

与第七卷 §4 的穷尽性判定天然配合：穷尽的 `when` 覆盖全部构造子，故合并点的析取构成对值域的完整描述。

### 5.7 域的进入与退出

```
F 是父帧     B 是线性块
────────────────────────────────────────  (LV-ENTER)
创建 F′ = LinearFrame(F)，F′.omega 初始化为 {}
F′.versionCtr 与同域族共享（若 F 是线性帧则复用，否则新建）
对 B 内声明或赋值的每个 @mut 实体登记入 F′.linVars

F′ ; Ω′ ⊢ B.stmts ⟹ Γ_B ; Ω_B
────────────────────────────────────────  (LV-EXIT)
F′ 销毁；Γ_B 中的版本化事实（含 x#k 形式的一切命题）**不回溢**到 F
B 的类型 = 尾表达式类型（无尾表达式则为 Null）
```

**与第五卷 §3.3 的对比**：普通块的事实回溢父帧（`nf.facts.forEach { f.inject(it) }`）。线性块的版本化事实**不回溢**。

**不回溢的理由**：版本化事实 `x#k = v` 的含义是「在域内第 k 次赋值后，x 的值是 v」。「第 k 次」的语境随域销毁而消失，域外无法解释 `x#k`。

**例外**：不含版本名的普通事实（例如域内对不可变变量证明的命题）**照常回溢**，与普通块一致。回溢的判据：

```
p 的语法树中不含任何版本名 x#k
────────────────────────────────────────  (LV-SPILL)
p 回溢到父帧
```

### 5.8 域外声明、域内修改

```
x 在父帧声明为 @mut     x 在线性域内被赋值
────────────────────────────────────────  (LV-OUTER-MUT)
域内产生 x#k 版本化事实；域结束后全部销毁，父帧不获得任何关于 x 的新事实
```

因此域外若要在域之后使用 `x` 的值，必须显式承接（第六卷 §4.4、第五卷 §10.3）：

```subl
@mut var n = 0
%{ n = 5 }
var snapshot = n        // snapshot 是不可变的，其等式按 G-VAR-EQ 注入
∴ snapshot = 5          // 成立（若 snapshot 的初值可归约）
```

## 6. 类型规则

### 6.1 线性块的类型

```
Γ ; Ω ⊢ B : τ ; Ω′
────────────────────────────────────────  (LV-BLOCK-TYPE)
Γ ; Ω ⊢ %{ B } : τ ; Ω′
```

线性块的类型即其内层块的类型。依总纲公理一，无尾表达式的线性块类型为 `Null`。

**对原始构想的修正**：原始构想规定线性作用域「固定返回空」。本规则**放宽**为「返回尾表达式的类型」——因为版本化是编译期机制，不约束值层。

### 6.2 提前返回的限制

```
return e 位于线性域内     e 不是 null     该 return 不是域的末尾语句
────────────────────────────────────────  (LV-NO-RETURN)
报错 E-LINEAR-RETURN

return（裸）或 return null 位于域的末尾语句位
────────────────────────────────────────  (LV-RETURN-OK)
允许
```

**限制的理由**：带值的提前返回使域的「值」在多个程序点产生，而版本化事实只在域的正常出口有意义。放宽到「末尾裸 return」是因为它与「无尾表达式的块」语义等价（都返回 `Null`）。

**对原始构想的修正**：原始构想完全禁止提前返回（链式脱糖的必然结果）。本规则给出更精确的边界。

### 6.3 纯度不变

```
线性域内出现赋值语句
────────────────────────────────────────  (LV-IMPURE)
包含该域的函数仍须标注 @impure
```

版本化**不改变效应**。可变性本身是效应（第六卷 §2.5：参数类型可变时函数必须标 `@impure`）。线性作用域使可变状态**可证明**，但不使其变纯。

### 6.4 与 `unsealedT` 的交互

线性块内含非穷尽 `when` 时，其类型按第七卷 §5.2 退化为 `(未密封)`，规则不变。线性化不影响密封性判定。

## 7. 与证明系统的接口

### 7.1 证明义务的提出

线性域内的证明义务（`∴`、函数下文、结构体伴生命题等）在**提出时刻**的 Γ 与 Ω 下判定：

```
义务 p 在程序点 P 提出     F 是 P 处的线性帧
────────────────────────────────────────  (LV-OBLIGATION)
判定 versionize(F, p) 是否在 F.allFacts() 下可证
```

**关键**：义务先经 `versionize` 改写，再送入证明器。因此用户写 `∴ n = 1`，证明器看到的是 `∴ n#1 = 1`。

### 7.2 复用既有证明器

由 §4.4 的关键性质（版本化改写是纯语法替换），第四卷的全部推理规则无需修改即可作用于版本化命题：

| 通道 | 对版本化命题的作用 |
|---|---|
| 结构相等（`P-REFL-PURE`） | `n#1 = n#1` 平凡成立 |
| 等式图可达（`R-EQ-TERM`） | `n#2 = n#1 + 10` 与 `n#1 = 1` 构成等式图，`n#2` 与 `11` 可达 |
| 线性算术（第四卷 §8.1） | 版本名作为独立变量参与线性约束求解 |
| 常量归约（第四卷 §5.1 通道 8） | `n#1 = 1` 使含 `n#1` 的目标归约为常量 |
| 饱和闭包（第四卷 §5.3） | 版本名是 ground 项，进入关键表达式池 |

**无需新增证明通道**——这是版本化方案相对原始构想的重要优势。

**限定（容器类型）**：上表对数值型实体（`Nat`／`Int`／`Rat`）成立，其版本化等式可由常量归约与线性算术通道判定。对容器类型（`List`／`Set`／`Map`），版本化机制**本身**照常工作（正确产生 `list#0 = …`、`list#1 = list#0.append(…)` 等事实），但「把版本化事实归约到容器字面量并判定代数等式」需要第四卷 §8 之外的**容器推理通道**。在该通道落地前，容器实体的可证范围限于「赋值右侧结构相同」（`P-REFL-PURE`）。此边界须在第一波实现的测试中实测确认。

### 7.3 关键表达式池的影响

版本名 `x#k` 是 ground 项，会进入关键表达式池 `K`（第四卷 §5.3）。池规模的约束：

```
线性域内每个实体的版本数 ≤ 该域内的赋值次数 + 分支合并次数
```

由于域内赋值次数是源码可数的，版本数**有界**，不会导致池爆炸。这与第四卷 §5.3「池一次性收集、此后固定」的规则一致——版本名在收集时刻已全部存在于 Γ 的事实中。

### 7.4 诊断输出

版本名在诊断消息中**还原为用户名**：

```
内部：n#2 = 11
输出：n = 11（第 2 次赋值后）
```

还原规则：诊断消息渲染时，`x#k` 渲染为 `x`，并在消息尾部附注版本序号（仅当 k > 0 且域内有多次赋值时附注）。

## 8. 唯一所有权与逃逸

### 8.1 逃逸的判定

**定义 8.1（逃逸）** 称线性实体 `x` 在程序点 P **逃逸**，当且仅当在 P 之前存在以下任一情形：

```
① x 被 lambda 捕获且该 lambda 内出现对 x 的赋值
② x 被声明为 @ref
③ x（或其 @mut 视图）作为实参传入一个可能修改它的函数
④ x 的地址／引用被存入逃逸出域的数据结构（容器、结构体字段、全局）
⑤ x 经由字典分派的方法调用传递，且被调方无法静态确定
⑥ x 以 Any 类型传递
```

**判定原则：保守。**有疑问即判定为逃逸。

### 8.2 lambda 捕获的禁止

```
lambda L 位于线性域内     L 捕获 x ∈ Lin     L 内出现对 x 的赋值
────────────────────────────────────────  (LV-NO-LAMBDA-MUT)
报错 E-LINEAR-ESCAPE
```

**理由（形式化）**：版本化的健全性依赖「版本序号与程序点一一对应」（§9.2 定理）。lambda 是值，其调用次数 `c` 满足 `c ∈ {0, 1, 2, …}` 且 `c` 静态不可知。若 `c ≥ 2`，则同一条赋值语句执行多次，版本序号无法在编译期确定；若 `c = 0`，则版本序号递增但值未变，注入的等式事实为假。两种情形都破坏健全性。

**只读捕获是允许的**：

```
lambda L 捕获 x ∈ Lin     L 内不出现对 x 的赋值
────────────────────────────────────────  (LV-LAMBDA-READ)
允许，但 L 体内 x 解析为捕获时刻的版本 x#k（快照语义）
```

**快照语义的理由**：L 可能在任意后续时刻被调用，届时 `x` 的当前版本可能已前进。若 L 内解析为「调用时刻的版本」，则 L 的行为依赖调用时机，无法静态验证。固定为捕获时刻的版本使 L 成为纯函数式的快照读取。

### 8.3 `@ref` 的禁止

```
x 位于线性域内     x 标注 @ref
────────────────────────────────────────  (LV-NO-REF)
报错 E-LINEAR-ALIAS
```

**理由**：`@ref` 是别名语义（第六卷 §6.4），意味着存在另一个名字指向同一存储。这与定义 2.3 的唯一所有权直接冲突。

### 8.4 不纯调用的事实失效

```
调用 g(a₁…aₙ)     g 标注 @impure     aᵢ 是线性实体 x（或以 @mut 视图传递）
────────────────────────────────────────  (LV-INVALIDATE)
Ω[x] := fresh(F)（版本前进，但**不注入**等式事实）
x 的全部历史版本化事实标记为 invalidated（从后续推理的可用集移除）
发 D-LINEAR-INVALIDATED
```

**失效的精确范围**：

| 事实种类 | 是否失效 | 理由 |
|---|---|---|
| `x#k = v`（版本化等式） | **失效** | g 可能修改了 x |
| `x#k : τ`（类型归属） | 不失效 | 类型不因副作用改变 |
| `x#k ≥ 0`（`Nat` 类型不变量） | 不失效 | 类型不变量恒成立 |
| 结构体伴生命题（新版本） | **不注入** | g 可能破坏了不变式；处置同 `LV-PROP-VERSION` ②，可由 g 的下文重新注入（`LV-RESTORE`） |
| 结构体伴生命题（历史版本） | **失效** | 其断定的字段值可能已被 g 改写 |
| 关于**其他**实体的事实 | 不失效 | 唯一所有权保证 g 改不到它们 |

最后一行是关键：**唯一所有权使失效范围可精确限定**。若 `x` 无别名，则 `g(…)` 只能修改 `x`（及其可达的字段），不可能修改域内其他线性实体 `y`。故 `y` 的事实完好。

**失效的实现方式**：不删除 Γ 中的事实（删除会破坏 `allFacts` 的单调性），而是在证明入口处过滤：

```
proveInLinear(F, goal) = proveOrDeep(F.allFacts() ∖ F.invalidated, goal)
                                                          (LV-PROVE-FILTER)
```

**过滤不影响健全性论证**：`invalidated` 只做减法，可用事实集是 `allFacts()` 的子集。命题 9.3 断言的是「Γ 中不存在跨版本等式」，在子集上同样成立；推论 9.4 穷举的证明路径只会因过滤而更少。故 §9 的全部结论在过滤后依然有效——过滤使系统**更弱但更安全**，属不完备性一侧（§9.3），非健全性一侧。

### 8.5 通过下文恢复事实

```
g 的下文为 [q₁…qₘ]     调用 g(x) 成功
────────────────────────────────────────  (LV-RESTORE)
按规则 LV-INVALIDATE 失效，随后按第五卷 §5.5 注入 qᵢ（经 versionize 改写）
```

因此为不纯函数书写下文即可恢复推理能力。这是既有机制（第五卷 §5.5）在线性域内的直接应用。

### 8.6 自递归函数的禁止

```
线性域内声明 fun f     f 的体内出现对 f 自身的调用
────────────────────────────────────────  (LV-NO-REC)
报错 E-LINEAR-REC
```

**理由**：递归调用点使控制流形成环，版本序号在环上无法单调递增（每次递归都递增则版本无上界，池爆炸；不递增则同一版本对应多个程序点，破坏 §9.2）。

**替代方案**：把递归函数提到域外，用函数的下文表达循环不变量。这是凝华既有的惯用法（第六卷 §3.2 的结构递归）。

## 9. 元理论

### 9.1 健全性陈述

**定理 9.1（健全性）** 设线性域 `B` 通过检查，且检查过程中接受了证明义务 `p₁…pₘ`。则对每个 `pᵢ`，在其提出时刻的程序点 `Pᵢ` 处，`pᵢ` 在规范定义的推理系统内可证，且 `pᵢ` 关于运行时状态为真。

### 9.2 证明的核心引理

**引理 9.2（版本-程序点对应）** 设 `x ∈ Lin`，`Ω` 是程序点 `P` 处的版本映射，`Ω[x] = k`。则运行时执行到 `P` 时，变量 `x` 的存储单元中的值等于 Γ 中事实 `x#k = v` 所断定的 `v`（若该事实存在且未失效）。

**证明思路**（对 `P` 的结构归纳）：

- **基例**（域入口）：`Ω` 为空，无线性实体，命题平凡成立。
- **声明**（规则 `LV-DECL`）：`x` 首次绑定，`Ω[x] = 0`，注入 `x#0 = e`。运行时 `x` 的存储被初始化为 `e` 的值。对应成立。
- **赋值**（规则 `LV-ASSIGN`）：`Ω[x]` 从 `j` 前进到 `k = j+1`，注入 `x#k = e`。运行时 `x` 的存储被写为 `e` 的值。对应成立。
- **读取**（规则 `LV-READ`）：`Ω` 不变，运行时存储不变。对应保持。
- **分支**（规则 `LV-MERGE`）：运行时只走一支。设走了 `B₁`，则到达合并点时存储值等于 `Ω₁[x]` 对应的值；合并版本 `k` 的事实是析取 `x#k = x#(Ω₁[x]) ∨ x#k = x#(Ω₂[x])`，其**左支**为真。故析取为真，对应成立（以析取形式）。
- **不纯调用**（规则 `LV-INVALIDATE`）：版本前进但**不注入**等式事实。故引理的前提「该事实存在」不满足，命题平凡成立（无断言可被违反）。
- **嵌套域**：内层域共享版本计数器，故版本序号在内层继续单调递增，不与外层冲突。归纳假设适用。

**引理成立的前提**：唯一所有权（§8）。若 `x` 有别名，则「运行时执行到 `P` 时 `x` 的存储值」可能被别名的写入改变，而 `Ω` 不感知该写入，对应关系被破坏。这正是 §8.2、§8.3 禁止 lambda 修改与 `@ref` 的形式化理由。∎

**定理 9.1 的证明**：由引理 9.2，Γ 中每个未失效的版本化等式事实在其断定的程序点为真。Γ 中其余事实（类型归属、类型不变量、非版本化命题）由既有机制保证为真（第五卷、第四卷的健全性）。第四卷的推理系统健全（总纲公理三），故由其推出的 `pᵢ` 为真。∎

### 9.3 不完备性

本机制**不完备**，且不完备性是固有的：

| 不可证的情形 | 原因 |
|---|---|
| 循环出口的版本化事实 | 需要归纳（第四卷 §9.10 暂不实现） |
| 不纯调用后的值 | 事实已失效，除非函数有下文 |
| lambda 内读取的「当前值」 | 快照语义固定为捕获时刻版本（§8.2） |
| 容器内容的代数等式 | 需要容器推理通道（第四卷 §8 之外） |

依总纲公理三，不完备不构成缺陷；「证不出」不等于「假」。

### 9.4 伴生命题处置的健全性

规则 `LV-PROP-VERSION`（§5.4）采用「仅失效、不做后续流跟踪」的处置。本节论证该处置健全，并说明为何**不需要**在赋值点报错。

**命题 9.3（版本隔离）** 设 `x.f` 被赋值 `m` 次（`m ≥ 1`），产生版本 `x.f#0 … x.f#m`。则对任意 `i ≠ j`，Γ 中不存在等式 `x.f#i = x.f#j`，除非该等式由 `LV-ASSIGN`／`LV-DECL`／`LV-MERGE` 显式注入。

**证明**：三条注入规则的形式分别为：

- `LV-DECL`／`LV-ASSIGN`：注入 `x.f#k = e`，其中 `e` 是赋值右侧表达式，不含版本名 `x.f#i`（若含，则 `e` 中的 `x.f` 已按 `LV-READ` 解析为读取时刻的版本，此时 `i < k` 且等式确实成立）；
- `LV-MERGE`：注入 `x.f#k = x.f#i ∨ x.f#k = x.f#j`，是析取而非等式，且 `k` 是新分配的合并版本；
- 版本名 `x.f#k` 不出现在源文本中，用户不可书写，故无法经 `unchecked.axiom` 或 `by` 直接注入跨版本等式。

因此跨版本等式只能来自赋值右侧的真实数据流，而这类等式为真（引理 9.2）。∎

**推论 9.4（伴生命题不被误用）** 设结构体 `S` 的伴生命题为 `p(x.f)`，构造 `S(v)` 时注入 `p(x.f#0)`。若后续 `x.f = w` 且 `¬p(w)`，则命题 `p(x.f#k)`（`k ≥ 1`）在 Γ 中不可证。

**证明**：由 `LV-PROP-VERSION` ②，`p(x.f#k)` 未被自动注入。要证出它，证明器需要 Γ 中的其他事实。可用路径穷举：

| 路径 | 是否可行 | 理由 |
|---|---|---|
| 事实直接匹配 | 否 | `p(x.f#k)` 不在 Γ 中 |
| 由 `p(x.f#0)` 经等式代换 | 否 | 需 `x.f#0 = x.f#k`，由命题 9.3 不存在 |
| 由 `x.f#k = w` 与 `∀y. p(y)` | 否 | 前提 `∀y. p(y)` 与 `¬p(w)` 矛盾，不可能同时在 Γ 中 |
| 由 `x.f#k = w` 与 `w` 满足 `p` | — | 此时 `p(w)` 为真，证出真命题，无害 |
| 由 `unchecked.axiom`／`by` 注入 | 是 | 用户显式逃逸，责任自负（总纲公理三） |

故除用户显式逃逸外，`p(x.f#k)` 不可证。∎

**因此**：版本化机制本身已经隔离了新旧版本，证明器无法「误用」旧版本的伴生命题去证明新版本的命题。这使在赋值点报错（原方案的 `E-LINEAR-PROP-BROKEN`）成为**冗余**的保护——它拒绝的程序中，有一部分实际上是健全的（例如「先破坏、后重建」：`p.x = 0` 之后再 `p.x = 5`，第二个赋值点 `p.x#2 > 0` 可由 ③ 代入验证注入）。

**取舍说明**：「仅失效不追踪」的代价是，携带已破坏不变式的结构体可以流入要求该伴生命题的位置——但流入时，该位置的**上文义务**（第五卷 §5.4 的 `G-PRE`）会要求证明 `p(x.f#当前版本)`，而该命题按推论 9.4 不可证，于是报 `E-PRE-UNPROVEN`。**保护由既有的上文检查机制承担，无需新增流跟踪。** 这是本方案优于原方案的第二处：它复用既有机制而非引入新机制。

```subl
struct Pos(x : Nat) <x > 0>
fun usePos(p : Pos) <p.x > 0> : Null {}     // 上文要求 p.x > 0

@impure
fun demo() %{
    var p : @mut Pos = Pos(1)
    p.x = 0
    usePos(p)          // E-PRE-UNPROVEN：p.x#1 > 0 不可证——既有机制拦下
}
```

## 10. 擦除与代码生成

### 10.1 擦除规则

```
────────────────────────────────────────  (LV-ERASE-VERSION)
版本名 x#k 在代码生成阶段映射为运行时变量名 x

────────────────────────────────────────  (LV-ERASE-BLOCK)
%{ B } 生成与 B 相同的代码（% 标记不留痕迹）

────────────────────────────────────────  (LV-ERASE-FACT)
全部版本化事实随命题层擦除（总纲不变量 I-2）
```

### 10.2 变量名冲突的处理

多个版本 `x#0`、`x#1`、`x#2` 映射到同一个运行时变量 `x`。这在代码生成层是**正确的**，因为：

- 每个版本的赋值语句在源码中对应一条真实的赋值，按顺序生成即可；
- 版本序号只用于索引命题，不用于区分存储位置。

**推论**：线性作用域生成的 JavaScript 与等价的普通 `@mut` 代码**逐字节相同**：

```subl
@impure
fun main() %{ @mut var n = 0; n = 1; print(toStr(n)) }
```
生成
```javascript
function main() { let n = 0; n = 1; print(String(n)); }
```

### 10.3 与深拷贝的交互

版本化**不改变**第六卷 §6.6 的深拷贝判定。域内 `var m = x`（`x` 是 `@mut T`）仍触发深拷贝并发 `D-DEEP-COPY`；`m` 是独立的新变量，若 `m` 也是 `@mut` 则获得自己的版本序列。

### 10.4 不变量 I-7 的保持

线性作用域是新增语法。不含 `%` 的源文本，其解析、检查、生成路径完全不变，故不变量 I-7（普通模式产物逐字节不变）自动保持。

## 11. 算法

### 11.1 检查流程

```
checkLinearBlock(B, parentFrame):
  1. F ← LinearFrame(parentFrame)
     若 parentFrame 是线性帧，F.versionCtr ← parentFrame.versionCtr（共享）
     否则 F.versionCtr ← new Ref(0)
  2. 预扫描 B：收集全部 @mut 声明与赋值目标，
     对每个候选执行逃逸分析（§8.1）
     发现 lambda 修改捕获 / @ref / 自递归 → 立即报错，不进入后续步骤
  3. Ω ← {}
  4. 逐语句检查 B.stmts，维护 (Γ, Ω)：
       声明      → LV-DECL / LV-DECL-STRUCT
       赋值      → LV-ASSIGN / LV-FIELD-ASSIGN（字段赋值附带 LV-PROP-VERSION 处置）
       分支      → LV-MERGE（递归处理各支）
       不纯调用  → LV-INVALIDATE
       证明义务  → LV-OBLIGATION（versionize 后送 proveOrDeep，过滤 invalidated）
       return    → LV-NO-RETURN / LV-RETURN-OK 判定
  5. 域出口：按 LV-SPILL 回溢不含版本名的普通事实；销毁 F
  6. 返回尾表达式类型
```

### 11.2 预扫描的必要性

步骤 2 必须在步骤 4 之前完成。理由：逃逸分析的结果影响「哪些实体属于 `Lin`」，而 `Lin` 决定版本化的范围。若边检查边分析，已注入的版本化事实可能因后续发现逃逸而需要撤销——撤销会破坏 Γ 的单调性。

预扫描的代价是遍历语法树两次。由于线性域通常是函数体的一小部分，代价可接受。

### 11.3 版本序号的分配

```
fresh(F):
  k ← F.versionCtr.value
  F.versionCtr.value ← k + 1
  return k
```

**注意**：版本计数器是**域族共享**的，不是每实体独立。这使得 `n#0`、`m#1`、`n#2` 这样的交错序号成为可能。

**替代设计**：每实体独立计数（`n#0`、`n#1`；`m#0`、`m#1`）。两种设计都健全。域族共享的优点是序号全局唯一，便于诊断输出定位程序点；每实体独立的优点是序号更小、更可读。**本规范采用域族共享**，与第四卷 §2.8 新鲜常量 `#vg{d}_{i}` 的双重索引风格一致。

### 11.4 复杂度

设域内语句数 `s`、线性实体数 `v`、分支深度 `d`：

| 阶段 | 复杂度 |
|---|---|
| 预扫描 | O(s) |
| 版本分配 | O(赋值次数) ≤ O(s) |
| 名字解析 | O(1) 每次（哈希查找） |
| 分支合并 | O(v) 每个合并点，合计 O(s·v) |
| 关键池增量 | O(v·s)（版本名数量上界） |

主导项是分支合并与关键池增量。由于 `v` 与 `s` 都是源码规模，整体是**多项式**的，不引入指数级开销。

## 12. 效应系统与异步：为何不在本卷

原始构想 `idea doc/线性作用域.md` 把四件事捆绑：线性作用域、效应系统（`@effect`/`IO`）、效应器委托（`by`）、`yield` 异步。本卷只做第一件。理由如下。

### 12.1 耦合度分析

| 机制 | 层次 | 依赖线性作用域？ |
|---|---|---|
| 版本化 + 流敏感 Γ | 编译期静态分析 | — |
| 效应系统（`IO` 类型、效应器） | 运行时机制 + 类型系统扩充 | 否 |
| 效应器委托 `by` | 语法糖，依赖效应系统 | 否 |
| `yield` 异步生成器 | 运行时机制 | 否 |

后三者互相依赖，但与线性作用域**无依赖关系**。捆绑实现会使任一子问题的困难阻塞全部进度。

### 12.2 原始效应方案的技术缺陷

原始构想的脱糖：

```subl
@effect @root fun readFile(name : Str) : Str
```
脱糖为
```subl
fun readFileByName($readFile : @impure (Str) => Str = default$readFile, name : Str) : IO
    = io{ $readFile(name) }
```

逐条问题：

| # | 问题 | 违反的规范条款 |
|---|---|---|
| 1 | 形参带默认值 `= default$readFile` | 第二卷 §3.2：函数形参不允许默认值（`E-DEFAULT-PARAM`） |
| 2 | 返回类型 `IO` 未定义 | 第三卷 §2.1 的基本类型集与 §2.6 的异步内建泛类型均无 `IO` |
| 3 | `io{ … }` 构造未定义 | 第二卷 §5.6：只有 `Task{ … }` 与 `Flow{ … }` 触发块构造 |
| 4 | 效应器插在形参首位 | 破坏全部既有调用点的实参位置；且 `$readFile` 中的 `$` 与第五卷 §7.3 的返回值指代语义冲突 |
| 5 | 「非线性作用域调用即 `actNow()`」 | 破坏组合性：IO 值无法被传递、存储、批处理；这是效应着色问题的典型症状 |

### 12.3 凝华已有效应机制

规范第六卷已定义完整的效应体系：

```
@impure 标注  +  pure<f> 命题  +  纯度传染  +  上下文放行
```

其特点是**效应是标注而非类型**：函数不「返回 IO」，只是被标注为不纯；调用它需要不纯上下文，或 Γ 中持有 `pure<f>` 证据（第六卷 §2.3）。

该选择避开了效应着色（function coloring）问题，代价是效应不能作为值组合。是否补上组合能力，是独立的设计问题——若要做，应当评估三条路线：

| 路线 | 代价 |
|---|---|
| 引入 `IO[T]` 类型 + `do` 记法 | 效应着色：所有调用链都要改 |
| 代数效应 + handler | 实现复杂度高；与 JS 目标的兼容性需论证 |
| 保持现状，用 `Task`/`Flow` 表达组合 | 无新增；但组合能力受限于异步机制 |

三条路线都**不依赖**线性作用域，故不应捆绑。

### 12.4 `yield` 与既有 `Flow` 的重叠

原始构想：

```subl
@effect @async @root fun yield[T](a : T)
@impure @async fun gen() ^ yield %{ (1..3).forEach { yield(_) } }
```

规范第六卷 §8.6 已有：

```subl
var fl = Flow { emit(1); emit(2); emit(3) }
fl.collect(fun(x : Nat) { print(toStr(x)) })
var doubled = fl.map({ x => x * 2 })
```

两者语义高度重叠：都是「产出一串值供外部消费」，都惰性、都在异步上下文、都支持组合（`map`／`collect`）。

引入 `yield` 效应器需要回答：

1. 它与 `Flow`/`emit` 是替代、语法糖，还是不同层次的机制？
2. `^ yield` 这个「效应签名」语法的解析规则是什么？`^` 已是幂运算符（第一卷 §4.4），如何消歧？
3. 效应器委托 `by yield : { … }` 与 `Flow.collect(f)` 的区别是什么？后者已经能注入任意消费逻辑。

这些问题都独立于线性作用域，且第 2 条与 §3.2 的 `%` 消歧属同类问题（运算符重载为语法标记），可一并设计。

**结论**：`yield` 异步生成器留作后续独立议题。

### 12.5 拆分后的收益

| 收益 | 说明 |
|---|---|
| 独立可验证 | 线性作用域的健全性证明（§9）不依赖效应系统的任何性质 |
| 渐进落地 | 版本化机制对所有类型通用，可先落地；容器内容推理、效应系统各自独立推进 |
| 风险隔离 | 若效应方案需要重新设计（§12.3 的三路线评估），不阻塞线性作用域 |
| 符合既有哲学 | 凝华的效应是「标注 + 命题」而非「类型」；本卷的版本化事实同样是命题层机制，与之同构 |
