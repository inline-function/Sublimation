# 第十卷 · 诊断

> 本卷规定凝华的诊断分级体系、诊断输出格式，以及诊断码全集。
> 诊断码是编译器与用户之间的契约：每个码对应一个确定的触发条件，不得复用，不得静默发出。

---

## 1. 诊断分级

### 1.1 四级

| 等级 | 标记 | 前缀 | 含义 | 是否阻断编译 |
|---|---|---|---|---|
| 错误 | `[错误]` | `E-` | 编译阻断，必须修 | **是** |
| 警告 | `[警告]` | `W-` | 能编译但有风险 | 否 |
| 提示 | `[提示]` | `H-` | 建议改进，可忽略 | 否 |
| 补充 | `[补充]` | `D-` | 编译器替你做了某事 | 否 |

### 1.2 各级的语义边界

**错误**：程序不符合语言规范，无法产出正确产物。语义检查未通过时，代码生成不启动。

**警告**：程序合法但很可能不是用户本意。典型是 `when` 非穷尽、不可达代码、命题没证出但不影响类型正确性。

**提示**：程序正确，但有更好的写法，或存在容易误读的地方。典型是算术优先级提示、参数遮蔽字段、构造子歧义。

**补充**：编译器**替用户做了某件事**的留痕——推导出的类型、注入的自然命题、发生的深拷贝、展开的语法糖。**默认不输出**，加 `-v` 后显示。

补充级诊断的价值在于可审计性：用户能看到编译器的每一个隐式决定。

### 1.3 分级准确性的要求

诊断消息的措辞必须与其等级一致。错误级的消息中不得出现「警告」字样，反之亦然。

---

## 2. 诊断输出

### 2.1 格式

每条带位置的诊断输出如下形态：

```
[等级][行:列] 诊断码: 消息
  行号 | 源码行文本
       | ……^
```

实例：

```
[错误][1:16] E-TYPE-MISMATCH: 函数 f 声明返回 Nat，但函数体是 Str，两边不一致
  1 | fun f(): Nat = "s"
    |                ^
```

### 2.2 三件套原则

每条诊断必须做到：

| 要素 | 内容 |
|---|---|
| ① 哪里错 | 位置（自动附源码片段、行号、上箭头） |
| ② 为什么错 | 用平实语言说明违反的规则 |
| ③ 怎么改 | 给出具体改法或正确写法的示例 |

**说人话**：消息中不得引用内部编号（如「决策 59」「root doc 第 39 行」「CH-4」）——用户看不到也看不懂。

**给例子**：能给出正确写法的，直接写进消息。

### 2.3 输出通道

| 内容 | 通道 |
|---|---|
| 诊断文本 | **标准输出** |
| 检查未通过的收尾行 `[错误] 语义检查未通过` | **标准错误** |
| 编译产物（JavaScript） | 标准输出（未给 `-o` 时）或文件 |
| 激进证明的进度 | **标准错误**（不污染产物） |

进程退出码：成功为 0；检查或编译失败为非 0；激进证明被 `Ctrl-C` 中断为 **130**。

### 2.4 收尾行

| 命令 | 通过时 |
|---|---|
| `check <文件>` | `[完成] 语义检查通过` |
| `check <目录>` | `[完成] 模块检查通过` |
| `compile` | `[完成] 已生成 out.js（N 字节）` |

### 2.5 诊断归属过滤

目录（多模块）编译时：

- 挂进来参与编译的 `core` 标准库会露出它自己的提示和警告（如 `H-ROOT-BUILTIN`、`W-UNUSED`），它们**不阻断编译**；
- **补充级诊断只保留根模块的**——其余模块的推导过程被视为噪声，自动过滤；
- 模块层错误（挂载目标缺失、settings 语法、挂载成环）在树校验阶段**最先**报出。

### 2.6 explain 子命令

```
explain <CODE>
```

打印诊断码的含义与修复建议，不区分大小写（`w-unused` 亦可）。未收录的码会列出全部现有码，便于翻阅：

```
explain E-NOPE
# [错误] 未收录诊断码 E-NOPE（现有：D-AUTO-AWAIT / D-BECAUSE-PROVED / … / W-UNUSED）
```

## 3. 错误级诊断码（E-）

### 3.1 词法与语法

| 码 | 触发条件 |
|---|---|
| `E-LEX` | 源码里有编译器不认识的字符或 Token：写错的符号、未闭合的字符串或插值、混入的全角标点、未闭合或跨行的反引号标识符 |
| `E-PARSE` | 代码不符合语言文法：缺失的括号、缺失的关键字、语句或声明的位置错误、抽象语法树状态不合法 |
| `E-CHECK` | 语义分析内部错误——编译器在类型检查时抛出了意外异常。这通常是编译器自身的缺陷，应当保留源码并反馈 |

### 3.2 类型

| 码 | 触发条件 |
|---|---|
| `E-TYPE-MISMATCH` | 表达式类型与预期不符：返回类型、实参类型、变量标注与初值、结构体构造、lambda 体、if 分支、区间端点、`is` 模式、`@list` 变长实参异构、`in` 右侧不是区间 |
| `E-KIND-MISMATCH` | 类型构造子用错：`List` 这类类型必须带类型参数（`List[Nat]`），不能裸用；参数个数也要对 |
| `E-NON-PATTERN-HKT` | 类型参数嵌套了类型构造子（如 `F[G[Nat]]`）。类型构造子的实参必须是具体类型 |
| `E-TYPE-MISSING` | 类型推导不出来，需要显式标注：`Channel` 创建缺类型参数等 |
| `E-ANY-CALL` | 涉 `Any` 的调用推导不出具体类型。手动标注类型 |
| `E-ANY-STRUCT` | 结构体里有 `Any` 类型成员，必须用 `unchecked` 才能创建。更好的做法是给该成员标注具体类型 |
| `E-TYPE-CONFLICT` | 全局类型推导的构造点类型冲突：同一个参数或字段在多个构造点给出了不同的具体类型。冲突就是承诺失败 |
| `E-TUPLE-DESTRUCT` | 解构的初值不是元组 |
| `E-TUPLE-ARITY` | 解构的分量个数和元组元素个数不一致 |
| `E-DESTRUCT` | 参数解构失败：解构只支持元组或结构体，且分量个数要对上 |

### 3.3 名字与作用域

| 码 | 触发条件 |
|---|---|
| `E-UNBOUND-NAME` | 名字没定义：拼写错误、忘了声明、在别的模块里而未 `mount`、挂载目标不存在 |
| `E-DUP-DECL` | 重复声明：同模块内名字声明了不止一次；挂载的本地名与子目录或其他挂载冲突；多个模块声明 `main` |
| `E-FUTURE-FUN` | 引用了尚未定义的函数（前向引用）；类型类方法引用暂不支持 |
| `E-MAIN-PARAMS` | 入口函数 `main` 有形参或类型参数 |
| `E-NO-METHOD` | 类型上找不到这个方法 |
| `E-NO-SELF` | 方法调用缺接收者：应写成 `接收者.方法(…)` 或 `方法(接收者, …)` |
| `E-PARAM-REF` | 匿名函数参数引用越界：函数只有 N 个形参，却引用了第 N+1 个 |
| `E-PARAM-REF-IN-BODY` | 函数体里用了非法的匿名参数引用。用参数名代替 |

### 3.4 函数与控制流

| 码 | 触发条件 |
|---|---|
| `E-FUN-NO-BODY` | 函数缺函数体：只有编译器内建的名字才允许无体（用 `@root` 声明） |
| `E-ROOT-NOT-ALLOWED` | `@root` 只能用于编译器内建名字，你写的名字不在白名单里 |
| `E-MISSING-RETURN` | 块体函数必须显式写 `return`（若只需一个值，用表达式体 `= 值`） |
| `E-RETURN-TYPE` | `return` 后面表达式的类型跟函数声明的返回类型不一样 |
| `E-RETURN-OUTSIDE` | `return` 用在了非法位置：只能出现在具名函数体或 lambda 体的语句流里 |
| `E-ARITY` | 实参个数跟声明的不一样（多了或少了） |
| `E-NAMED-ARG` | 命名实参冲突：同一个参数既按位置传又按名字传；或函数没有这个参数名；或方法不支持命名参数 |
| `E-DEFAULT-PARAM` | 函数或方法的形参不允许默认值。只有 struct 字段支持默认值 |
| `E-DUP-FIELD` | 构造结构体时同一个字段传了两次 |
| `E-FIELD-MISSING` | 构造结构体时少了某个字段，且它没有默认值 |
| `E-ASSIGN-TARGET` | 赋值目标不是变量：赋值号左边必须是变量名或可变字段 |

### 3.5 模式匹配

| 码 | 触发条件 |
|---|---|
| `E-NON-SEALED-MATCH` | `when` 用作表达式但分支不穷尽，值可能是 `Null`，却流向了非 `Null` 上下文 |

### 3.6 类型类与 impl

| 码 | 触发条件 |
|---|---|
| `E-NO-INSTANCE` | 类型类实例缺失：类型没有实现对应的类型类；子类型类未先实现父类 |
| `E-AMBIGUOUS-INSTANCE` | 一个类型对同一方法有多个 impl，编译器分不清用哪个 |
| `E-IMPL-INCOMPLETE` | `impl C for T` 没有实现类型类 C 的全部方法 |
| `E-IMPL-MISMATCH` | impl 方法的签名和类型类声明的不一致 |
| `E-IMPL-EXTRA` | impl 里实现了一个类型类里没有的方法，且未标 `@new` |
| `E-BY-UNBOUND` | `impl … by 字段` 委托引用了一个不存在的字段 |

### 3.7 纯度、可变性与效应

| 码 | 触发条件 |
|---|---|
| `E-IMPURE-CALL` | 纯函数里调了有副作用的函数，且 Γ 中无 `pure<f>` |
| `E-IMPURE-REQUIRED` | 函数的参数类型带有 `@mut T`，函数声明必须加 `@impure` |
| `E-IMMUT-ASSIGN` | 给不可变的变量赋值：声明时没标 `@mut` |
| `E-NOT-MUT` | 字段修改需要可变视图：字段须标 `@mut`，且变量类型前须加 `@mut T`；可变方法缺 `@mut` 视图 |
| `E-STRUCT-MUT-PROP` | 结构体声明了伴生命题，但命题引用了 `@mut` 可变字段，无法保证恒成立 |
| `E-NON-STRUCTURAL-REC` | 纯函数自递归时没有一个参数在「变小」（结构递归或数值递减） |
| `E-NEED-ASYNC` | 异步调用需要在异步上下文：只能在 `@async` 函数、`Task` 体或 `main` 里用 |
| `E-NOT-STARTED` | Task 未 `start()` 就 `join()` |
| `E-CHANNEL-CLOSED` | Channel 已 `close()`，之后的 `send`／`receive` 无效 |

### 3.8 命题与证明

| 码 | 触发条件 |
|---|---|
| `E-PRE-UNPROVEN` | 函数调用的前置条件（上文）没证明。可用 `∵` 注入事实，或换调用参数让编译器能自动证出 |
| `E-POST-UNPROVEN` | 函数体的后置条件（下文）没证明：函数体结束时 Γ 不蕴含下文 |
| `E-PREMISE-UNPROVEN` | 因为-所以语句的前提没证出 |
| `E-CANNOT-PROVE` | 因为-所以语句的结论证不出。消息会列出已试的定理与当前 Γ |
| `E-DEEP-SATURATION` | 证明义务太复杂，自动证明器走到最深也没证出。把大结论拆成小步骤 |
| `E-THEOREM-SEARCH-DEPTH` | 定理搜索超过深度限制（默认两跳）。把大结论拆成小步骤 |
| `E-PROP-UNBOUND` | 前提命题不在当前已知事实里；命题参数无供给；`∃` 消去的前提缺失 |
| `E-PROP-AMBIGUOUS` | 命题参数有多个候选，编译器无法唯一确定 |
| `E-QUANT-UNPROVEN` | `∃` 引入的实例满足不了目标性质；`∀` 引入（局部函数）无体 |
| `E-STRATEGY-FAILED` | 策略（`@simp`／`@subst` 等）证明失败 |
| `E-NEED-CLASSIC` | `if[p]` 需要先挂载排中律：在文件里任一声明加 `@classic` 注解 |
| `E-IF-CONCLUSION-MISMATCH` | `if[p]` 的两支推导出的结论不一致。排中律要求两支结论相同 |
| `E-STRUCT-PROP-UNPROVEN` | 结构体的伴生命题在构造时证不出来。检查构造实参是否满足性质 |
| `E-CTX-UNPROVEN` | 函数值调用时，其类型携带的上下文命题未证出 |
| `E-CONSTRAINT-VIOLATED` | 调用违反了函数的约束表：编译器已反证实参不满足声明的约束 |

### 3.9 模块

| 码 | 触发条件 |
|---|---|
| `E-PARSE-SETTINGS` | settings 文件语法错：只支持 `mount <路径> [as <别名>]`，一行一个指令 |
| `E-CIRCULAR-MOUNT` | 模块挂载成环：settings 里的 `mount` 链形成了循环。只报第一个环 |

### 3.10 注解处理器

| 码 | 触发条件 |
|---|---|
| `E-PROCESSOR-LOAD` | 处理器路径存在，但不是 `.subs` 文件或目录（装载失败，编译立即终止） |
| `E-PROCESSOR-SCRIPT` | 处理器脚本主动调了 `processorError(msg)` |
| `E-PROCESSOR-ERROR` | 处理器脚本执行时抛出异常（脚本类型检查失败或运行时错误），AST 不变 |
| `E-PROCESSOR-LOOP` | 处理器在 5 轮内未收敛（可能产生触发自己的代码） |
| `E-PROCESSOR-EDIT` | 结构性编辑的源码片段解析失败：`setFunBody`／`prependStmts`／`addDecl`／`replaceDecl` 给的片段不是合法的函数体／语句／声明。该条编辑被丢弃，其余照常生效 |

## 4. 警告级诊断码（W-）

| 码 | 触发条件 |
|---|---|
| `W-NON-EXHAUSTIVE` | `when` 可能没走完所有情况：枚举或构造子类型的 `when` 少了分支；区间 `when` 的端点未无缝衔接。作为表达式时值类型退化为 `Null` |
| `W-CANNOT-PROVE` | `∵`／`∴` 里的命题在当前已知事实下推不出（**不阻断**）。检查是否漏了前提，或换个能自动证的写法 |
| `W-PROP-UNBOUND` | 分类讨论语句 `when[p ∨ q]` 的析取前提不在 Γ 中 |
| `W-WHEN-NO-COMMON` | 分类讨论语句的各支没有共同结论 |
| `W-CONSTRAINT-UNPROVEN` | 函数约束表的条件编译器没证出：实参是运行时才确定的变量时只给警告。换成字面量或先注入事实可消除 |
| `W-UNUSED` | 变量或参数声明后从没用过。删掉它，或改名加 `_` 前缀表示故意不用 |
| `W-UNREACHABLE` | 不可达代码：`Nothing` 或 `return` 之后的语句永远执行不到 |
| `W-DIV-ZERO` | 字面量除以零 |
| `W-PROCESSOR-SCRIPT` | 处理器脚本调了 `processorWarn(msg)`。这是处理器给作者的提示，不影响编译通过 |
| `W-PROCESSOR-EDIT` | 处理器的注解编辑没命中目标：按名字找不到结构体／函数／字段。检查脚本里的名字是否拼错（其余编辑照常生效） |

## 5. 提示级诊断码（H-）

| 码 | 触发条件 |
|---|---|
| `H-ARITH-PRECEDENCE` | 语言不做运算符优先级（一律左结合）。混用 `+` 和 `*` 这类不同优先级的运算符时，实际计算顺序可能与直觉不同。给想要的子表达式加括号明确本意 |
| `H-AMBIGUOUS-CTOR` | 构造子名有歧义，多个枚举都有这个构造子。用 `枚举::构造子` 明确指定 |
| `H-FIELD-SHADOW` | 参数名遮蔽了 `self` 的同名字段。函数体内裸写这个名字时指向参数而不是字段 |
| `H-PARAM-REF` | 函数签名里用 `$数字` 引用参数——直接用参数名更可读 |
| `H-ROOT-BUILTIN` | 你写的名字是编译器内建名，可以用 `@root` 声明成无体内建函数 |
| `H-EMPTY-DECL` | 这个声明是空的（无构造子枚举、无字段结构体、无成员类型类），可以省略花括号写得更简洁 |
| `H-PROCESSOR-SCRIPT` | 处理器脚本调了 `processorHint(msg)` |

## 6. 补充级诊断码（D-）

补充级默认不输出，加 `-v` 后显示。

### 6.1 推导与脱糖留痕

| 码 | 触发条件 |
|---|---|
| `D-TYPE-INFERRED` | 变量类型是编译器推导出来的（未写类型标注时） |
| `D-METHOD-SUGAR` | 方法糖展开：`.f(…)` 是自由函数 `f(o, …)` 的简写 |
| `D-INFIX` | 中缀糖展开：`a f b` 与 `f(a, b)` 等价 |
| `D-TRAILING` | 尾随 lambda：`f(a) { … }` 等价 `f(a, { … })` |
| `D-AUTO-AWAIT` | 异步调用自动 await：编译器检测到 `@async` 函数调用，自动等待其完成 |
| `D-DEEP-COPY` | 发生了深拷贝：绑定或赋值涉及 `@mut` 类型时，编译器自动复制一份，新变量是独立副本 |
| `D-AUTO-IMPURE` | 全局类型推导自动标注 `@impure`：脚本模式下某函数自递归但找不到递减的参数（停机检查失败），已降级为 `@impure` 放行，效应向上传播 |

### 6.2 上下文与证明留痕

| 码 | 触发条件 |
|---|---|
| `D-NAT-PROP` | 注入了自然命题：`Nat` 类型的变量自动成立 `n ≥ 0` |
| `D-BECAUSE-PROVED` | 命题成立、已注入上下文：`∵ …` 引入的事实进入后续证明的上下文 |
| `D-THEREFORE` | 命题证明成立：`∴ …` 求证成功，结果注入后续上下文 |
| `D-BTS` | 因为-所以语句成立，结论已注入 Γ |
| `D-WHEN-PROP` | 分类讨论语句得出共同结论，已注入 Γ |
| `D-STRATEGY` | 策略（`@simp`／`@subst`）证出目标 |
| `D-EXIST-INTRO` | `∃` 引入成立：给出了满足性质的实例，编译器确认存在性 |
| `D-LOCAL-FUN` | 局部函数登记为全称引入（块内定理） |
| `D-BY` | 用了 `by` 辅助策略：编译器按给的中间命题注入 Γ |
| `D-AXIOM-POST` | `@axiom` 函数的下文签名即公理，免除自动证明 |
| `D-RANGE-INFER` | `when(n in _)` 的 `_` 被推断为具体区间 |
| `D-DEFAULT-VAL` | 结构体构造时字段取了默认值 |
| `D-CTOR-RESOLVE` | 跨模块构造子解析到了具体模块 |
| `D-DICT-HIT` | 扩展方法解析到了类型类字典 |

### 6.3 注解处理器留痕

| 码 | 触发条件 |
|---|---|
| `D-PROCESSOR-SCRIPT` | 处理器脚本调了 `processorInfo(msg)` |

## 7. 诊断码索引

### 7.1 按场景查

**看不懂类型错误**：`E-TYPE-MISMATCH` → `E-KIND-MISMATCH` → `E-ANY-CALL` → `E-TYPE-CONFLICT`。

**找不到名字**：`E-UNBOUND-NAME`（检查拼写、作用域、`mount`）→ `E-DUP-DECL` → `E-FUTURE-FUN`。

**证明失败**：`E-PRE-UNPROVEN`（调用点的上文）→ `E-POST-UNPROVEN`（函数体的下文）→ `E-CANNOT-PROVE`（因为-所以的结论）→ `E-PREMISE-UNPROVEN`（因为-所以的前提）→ `E-DEEP-SATURATION`（推理太深）→ `E-THEOREM-SEARCH-DEPTH`（定理搜索超限）。

**可变性受阻**：`E-IMMUT-ASSIGN`（变量不可变）→ `E-NOT-MUT`（字段缺可变视图）→ `E-IMPURE-REQUIRED`（`@mut` 形参须 `@impure`）→ `E-STRUCT-MUT-PROP`（伴生命题引用可变字段）。

**纯度受阻**：`E-IMPURE-CALL`（纯函数调不纯函数）→ `E-NON-STRUCTURAL-REC`（递归停机存疑）。

**when 相关**：`W-NON-EXHAUSTIVE`（分支没盖全）→ `E-NON-SEALED-MATCH`（非密封值流向具体类型）→ `W-PROP-UNBOUND`（分类讨论前提缺失）→ `W-WHEN-NO-COMMON`（分类讨论无公共结论）。

**类型类相关**：`E-NO-INSTANCE` → `E-AMBIGUOUS-INSTANCE` → `E-IMPL-INCOMPLETE` → `E-IMPL-MISMATCH` → `E-IMPL-EXTRA` → `E-NO-METHOD` → `E-NO-SELF`。

**异步相关**：`E-NEED-ASYNC` → `E-NOT-STARTED` → `E-CHANNEL-CLOSED`。

**模块相关**：`E-PARSE-SETTINGS` → `E-CIRCULAR-MOUNT` → `E-UNBOUND-NAME`（挂载目标缺失）。

**处理器相关**：`E-PROCESSOR-LOAD` → `E-PROCESSOR-SCRIPT` → `E-PROCESSOR-ERROR` → `E-PROCESSOR-LOOP` → `E-PROCESSOR-EDIT` → `W-PROCESSOR-EDIT`。

### 7.2 排错流程

1. 读带箭头的源码行，**先修第一个错误**（后面的错误常是它的连锁反应）；
2. 看不懂码 → `explain <CODE>`；
3. 想看推导过程 → 加 `-v`；
4. 涉及跨模块名字 → 先查 `mount` 与模块可见性（第八卷 §3）；
5. 涉及证明失败 → 查当前 Γ（错误消息会列出），判断是缺前提还是缺定理；
6. 仍怀疑是编译器问题 → 用 `parse`／`tokens` 单独看语法树与 Token 流定位；`E-CHECK` 是编译器内部异常，保留源码反馈。

## 8. 码的统计与一致性

### 8.1 码总数

本卷 §3–§6 定义的诊断码统计：

| 等级 | 数量 |
|---|---|
| 错误 `E-` | 70 |
| 警告 `W-` | 10 |
| 提示 `H-` | 7 |
| 补充 `D-` | 22 |
| **合计** | **109** |

### 8.2 一致性要求

诊断码集合必须满足双向一致性：

```
编译器实际发出的码集合 = explain 表收录的码集合 = 本卷清单
```

- **不缺码**：编译器发出的每个码都必须在 `explain` 表中有解释，并在本卷清单中登记；
- **无幽灵码**：`explain` 表与本卷清单不得收录编译器从不发出的码。

该一致性由测试保证（诊断码覆盖面体检）。

### 8.3 设计码与预留码

**设计码**是本规范依据设计文档定义、当前实现尚未接线的码。它们在本卷中按已定义语义登记，实现应当逐步补齐：

| 码 | 语义 | 出处 |
|---|---|---|
| `D-DEFAULT-VAL` | 结构体构造时字段取了默认值 | 《诊断信息设计文档》K10 |
| `D-CTOR-RESOLVE` | 跨模块构造子解析到了具体模块 | 《诊断信息设计文档》K11 |
| `D-DICT-HIT` | 扩展方法解析到了类型类字典 | 《诊断信息设计文档》K12 |
| `D-RANGE-INFER` | `when(n in _)` 的 `_` 被推断为具体区间 | 《诊断信息设计文档》K13 |

**预留码**是已收录进 `explain` 表但当前**不触发**的码，用于锁定未来行为的语义位置。预留码必须在测试中显式断言其「当前不触发」，以防实现意外接线。当前唯一的预留码是 `E-ANY-INFER`（「涉 `Any` 推导失效」的语义由 `E-ANY-CALL`／`E-ANY-STRUCT` 落地）。

### 8.4 码的稳定性

诊断码是**公开接口**：

- 已发布的码不得改含义；
- 废弃的码不得复用给新语义；
- 新增码必须同时进入 `explain` 表与本卷清单。
