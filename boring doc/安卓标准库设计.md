## 〇、摘要

凝华当前的 JavaScript 产物是一个**自执行、不导出任何东西的 IIFE**，并硬编码了六处 Node.js 桌面假设（`require('fs')`、`Buffer`、`process.argv`）。这两点决定了安卓支持不是"加一个标准库"那么局部的事，而是需要先引入**编译目标（target）**这一层抽象，把平台假设从代码生成的字符串里抽出来。

本文的结论概要：

| 议题 | 结论 |
|---|---|
| UI 渲染路线 | 采**方案 B：JS 侧持有视图树，原生渲染原生控件**（即草稿的意图），但视图树必须**不可变**，草稿的 `recomposition` 描述需修正 |
| 入口与生命周期 | 产物改为返回导出对象的 IIFE，`main` 在 `--target=android` 下**不自执行**，由原生在 `onCreate` 时调用 |
| 状态与视图更新 | **复用《线性作用域》的版本化机制**承载"直觉主义的可变修改"：语法上就地修改，语义上版本化 + 路径拷贝 + 增量下发 |
| 桥接协议 | 请求-应答 + 事件推送双通道，全部走 JSON 字符串；原生回调统一由 `dispatch` 单入口派发 |
| 标准库组织 | `core/android/` 新建子模块，隐式挂载机制无需改动 |
| 平台内建重定向 | `readFile` 等六个函数按 target 分派实现，不改函数签名 |

草稿与现行语言规则有 **7 处冲突**，见 §12。其中两处（结构体变长参数、`layout` 未声明）是硬性语法冲突，必须调整草稿写法或扩展语言。

## 一、目标与非目标

### 1.1 目标

1. 使凝华能够编写**完整的安卓应用**（不仅是计算逻辑，含 UI、生命周期、权限、持久化）。
2. 应用打包为 APK，凝华代码编译为 JavaScript，在 APK 内的 WebView 中执行。
3. APK 内含原生支持器（Kotlin/Java），负责 JS 与原生的双向交互，以及原生控件的创建与更新。
4. 保持凝华的核心纪律：不可变优先、纯度显式、零成本擦除、健全性可证。
5. 桌面端（Node）与安卓端**共用同一套前端与检查器**，差异收敛在代码生成的目标层。

### 1.2 非目标

1. **不做跨平台 UI 抽象**。本文只针对安卓；不设计一套同时映射到 iOS/桌面/Web 的通用视图模型。
2. **不做 AndroidX/Compose 绑定**。不生成 Kotlin 侧的 Compose 代码，原生侧是经典 View 体系。
3. **不在第一版做多活动**。草稿规定应用仅一个活动，本文沿用；多活动支持留作后续。
4. **不做 JS 引擎替换**。不考虑 V8/Hermes/QuickJS 直跑，仅 WebView。

### 1.3 与草稿的关系

草稿《安卓标准库》是根文档，其确立的四项决策本文全部沿用：

| 草稿决策 | 本文态度 |
|---|---|
| 编译为 JS，APK 内 WebView 运行 | 沿用 |
| 应用仅一个活动，`android.activity` 管理生命周期 | 沿用，并补全生命周期事件集（§7） |
| 声明式 DSL 构建布局，`@view` 结构体，编译器特殊优化 | 沿用意图，**修正机制**（§8） |
| `log` 函数输出到应用日志，可被 adb/shizuku 获取 | 沿用，并补全等级枚举与实现路径（§9.2） |

草稿中与现行语言规则冲突之处，本文在 §12 逐条列出并给出修正方案。

## 二、平台约束：必须考虑的硬事实

这一节是全文的基础。安卓与 WebView 的以下性质不是设计选择，而是**外部强加的约束**；任何方案都必须满足它们。

### 2.1 Activity 会被销毁重建

草稿说"应用仅由一个活动构成，因此只需要管理这一个活动的生命周期"。单活动是对的，但**单活动不等于单实例**。以下情形会导致 Activity 实例被销毁并重建：

| 触发情形 | 是否默认重建 |
|---|---|
| 屏幕旋转 | 是 |
| 深色/浅色模式切换 | 是 |
| 系统语言切换 | 是 |
| 分屏/折叠屏形态变化 | 是 |
| 系统内存不足回收后台进程 | 是（进程级） |
| 开发者选项"不保留活动" | 是 |

重建意味着 **WebView 内的 JavaScript 全局状态全部丢失**。因此：

- `onSaveInstanceState` / `onRestoreInstanceState` 不是可选特性，是**必需机制**；
- 应用状态必须可序列化，或可从持久化存储恢复；
- 若原生侧配置了 `android:configChanges`，可以拦截部分重建，但**进程被杀无法拦截**。

**对设计的影响**：视图树本身不需要保存（重建后 `onStart` 会重新构建），但**应用状态**（用户数据、页面栈、表单内容）必须有明确的保存通道。见 §7.4。

### 2.2 三个不同的线程

WebView 场景下至少涉及三个执行上下文，混淆它们是最常见的错误来源：

| 线程 | 运行什么 | 约束 |
|---|---|---|
| **UI 线程（主线程）** | 原生控件的创建与修改、`evaluateJavascript` 调用 | 所有视图操作必须在此线程；阻塞它会导致 ANR |
| **JavaBridge 线程** | `@JavascriptInterface` 标注方法的执行 | **不是 UI 线程**；在此线程碰视图会崩溃或行为未定义 |
| **WebView JS 线程** | 凝华编译出的 JavaScript | 单线程、事件循环驱动；与 JavaBridge 线程不同 |

关键推论：

1. JS 调用 `@JavascriptInterface` 方法时，该方法在 JavaBridge 线程执行；若它要改 UI，必须 `runOnUiThread { … }` 或 `view.post { … }`。
2. 原生调用 `evaluateJavascript` **必须在 UI 线程**，否则抛异常。
3. JS 侧是单线程事件循环，凝华的 `Task`/`Channel` 是**协作式并发**，没有真并行。因此第六卷 §8 的异步模型在安卓端语义不变，但"并行"的直觉需要修正：`runBoth` 不会让两段代码真正同时跑。

### 2.3 桥接接口的类型限制

`@JavascriptInterface` 方法的参数与返回值只支持：

- Java 基本类型及其包装类（`int`/`long`/`double`/`boolean` 等）
- `String`
- 不支持：自定义对象、对象数组、泛型集合

原生 → JS 方向，`evaluateJavascript(script, callback)` 的 `script` 是字符串，回调只能收到字符串结果。

**对设计的影响**：所有跨边界数据必须**序列化为字符串**。凝华侧已有 `Json` 类型与 `jsonParse`/`jsonToStr` 等内建函数（第三卷 §6.3），这是天然的序列化通道。桥接协议应当直接构建在 JSON 之上，而不是另设一套编码。

另一个限制：`@JavascriptInterface` 方法调用是**同步阻塞**的（JS 侧等待返回）。这意味着耗时操作绝不能放在这些方法里，否则 JS 线程被挂起。所有耗时操作必须走"发起请求 → 立即返回 → 异步回调"模式（§10）。

### 2.4 WebView 的版本碎片

`Android System WebView` 是独立更新的系统组件，但：

- Android 5–6 上的 WebView 版本可能很旧（ES5 时代）；
- 部分设备（尤其某些定制 ROM）的 WebView 被替换或禁用；
- 用户可能未更新 WebView。

凝华代码生成使用 `async function`、`Promise`、`class`、箭头函数、`for await`（第六卷 §8、第九卷 §10）。这些要求 **ES2017+**，实际上需要 Chrome 55+ 内核的 WebView（Android 7+ 基本满足，Android 5–6 需要用户手动更新）。

**候选方案**：

| 方案 | 说明 | 取舍 |
|---|---|---|
| **B-1 设定最低系统版本** | `minSdkVersion = 24`（Android 7.0） | 简单；牺牲少量老旧设备 |
| **B-2 降级产物** | 代码生成增加 ES5 目标，async/await 转 Promise 链 | 产物体积与复杂度显著上升，且 `for await`（Flow）难以降级 |
| **B-3 打包 JS 引擎** | APK 内置 V8/Hermes/QuickJS，不用 WebView 跑逻辑 | 摆脱碎片化，但 APK 增大 5–15MB，且失去 WebView 的调试工具链 |

**推荐 B-1**，并把 WebView 版本检测作为启动检查项（§11.3）。

### 2.5 权限是异步的、可能被拒

安卓 6.0（API 23）起，危险权限必须运行时申请，用户可能拒绝，且可能勾选"不再询问"。权限种类包括相机、麦克风、定位、通讯录、存储、通知等。

**对设计的影响**：权限申请的结果必须在**类型层面**可见，否则用户会写出"假定已授权"的代码。凝华已有现成的表达手段：`Result[T, E]`（core 容器）与函数的下文（第五卷 §5.5）。

因此权限 API 的返回类型应当是 `Result[Null, PermissionDenial]`，而不是 `Bool`——拒绝原因（首次拒绝 / 永久拒绝）需要区分，因为二者的后续处理完全不同（永久拒绝只能引导用户去系统设置）。

### 2.6 生命周期与后台限制

Android 8+ 对后台服务、后台定位、通知渠道有严格限制；Android 12+ 限制前台服务启动。若应用需要后台能力，必须走前台服务 + 通知，这不是 WebView 内部能解决的事，必须由原生支持器实现。

**第一版建议不纳入后台服务**，只做前台应用。

### 2.7 ANR 与看门狗

UI 线程被阻塞超过 5 秒触发 ANR 对话框。凝华代码跑在 WebView JS 线程，理论上不直接阻塞 UI 线程，但：

- `@JavascriptInterface` 的同步调用会阻塞 JS 线程，若该调用又 `runOnUiThread` 并等待结果，形成死锁；
- 大量 `evaluateJavascript` 调用会挤占 UI 线程。

**对设计的影响**：桥接层必须**严格避免同步等待 UI 线程**；批量更新要合并（§8.5）。

### 2.8 输入与手势

触屏没有 hover 状态，手势包括点击、长按、双击、拖动、捏合、滑动、多指。草稿只提到 `onClick`。完整的视图模型需要覆盖这些手势，否则做出来的应用"不像安卓应用"。

### 2.9 尺寸、密度与适配

屏幕密度（ldpi–xxxhdpi）、刘海/挖孔、导航栏、折叠屏、平板、横竖屏。尺寸单位必须用 dp/sp 而非 px。这些应当体现在布局 DSL 的单位设计上（§8.7）。

### 2.10 键盘与焦点

软键盘弹出会改变可视区域，可能遮挡输入框。需要 `WindowInsets` 处理。表单类应用无法回避。

### 3.2 必须改造的部分

| 缺口 | 现状 | 改造 |
|---|---|---|
| **产物是自执行 IIFE，不导出任何东西** | `JsCodeGen.kt:235, 355-363`：`(() => { … main(); })();` | 宿主无法主动调用 JS 函数，生命周期回调无从触发。必须改为返回导出对象（§4.1） |

### 3.3 `core/` 现状

15 个子模块、25 个 `.subl` 文件，按功能域组织：`collection`（7 个文件）、`async`（5）、`string`、`io`、`json`、`time`、`math`、`real`、`number`、`logic`、`classic`、`random`、`net`、`regex`、`encoding`。

命名惯例：每个子目录一个 `.settings` 文件 + 若干 `.subl`；`.settings` 内容多为注释（同模块内互见无需 mount）。

新增安卓标准库应当遵循此惯例：`core/android/android.settings` + `core/android/{activity,view,log,io,permission,…}.subl`。

## 四、编译目标与产物结构

### 4.1 产物结构的改造

现状（第九卷 §10.1）：

```javascript
"use strict";
(() => {
  /* 声明与运行时片段 */
  main();
})();
```

安卓端需要宿主能够：

1. 在 WebView 加载完成后调用 `main`；
2. 在生命周期事件发生时调用对应回调；
3. 在原生异步操作完成时派发结果；
4. 在系统事件（返回键、权限结果、配置变更）发生时通知 JS。

**候选方案**：

| 方案 | 产物形态 | 取舍 |
|---|---|---|
| **S-1 返回导出对象的 IIFE** | `globalThis.__subl = (() => { …; return { main, dispatch }; })();` | 保持封装性（内部符号不泄漏到全局），同时提供明确的导出面。**推荐** |
| **S-2 逐个挂全局** | IIFE 内部执行 `globalThis.__subl_main = main; …` | 简单，但污染全局命名空间，且导出面分散 |
| **S-3 不导出，靠 console 通信** | 原生通过 `WebChromeClient.onConsoleMessage` 截获 JS 输出，JS 通过 `prompt()` 调用原生 | 无需改产物结构，但通信带宽极低、无法传结构化数据、性能差。仅适合日志 |

**推荐 S-1**。导出对象的最小接口：

```javascript
globalThis.__subl = (() => {
  "use strict";
  /* … 全部声明与运行时片段 … */
  return {
    main: main,                        // 由原生在 WebView 加载完成后调用
    dispatch: function (payload) { … }, // 原生 → JS 的统一入口（JSON 字符串）
    version: 1
  };
})();
```

**单一入口 `dispatch`** 是关键设计：原生侧只需知道一个函数名，所有回调、事件、应答都通过它进入 JS，由 JS 侧的桥接运行时按 payload 内的标签分派。这样原生支持器代码极少，且协议演进不需要改原生侧。

### 4.2 引入编译目标 `--target`

现状是平台假设散落硬编码。引入显式目标后：

| 目标 | `main` 自执行 | 文件系统 | 产物结构 | 桥接层 |
|---|---|---|---|---|
| `node`（默认，兼容现状） | 是 | `require('fs')` | 纯 IIFE | 无 |
| `browser` | 是 | 不可用（或 IndexedDB） | S-1 导出 | 无 |
| `android` | **否** | 走桥接 | S-1 导出 | 注入 |

实现要点：

1. 代码生成器持有一个 `Target` 枚举，`call()` 里的平台相关分支按 target 分派（§5）；
2. `Target.Android` 时额外注入安卓桥接运行时片段（§10）；
3. `Target.Android` 时抑制 `main()` 的自动调用（`JsCodeGen.kt:355-361` 处按 target 判断）。

这一层抽象同时解决了工程审查报告 P2-6「桌面假设硬编码」的问题，是有独立价值的重构。

### 4.3 单文件产物

现状是多模块编译合成**单个 JS 文件**（`MultiModule.kt:193`）。这对安卓端是**优点**：APK 内只需一个 asset 文件，加载简单，无跨文件请求。沿用。

## 五、平台内建函数的重定向

六个 IO 函数与两个环境函数依赖 Node.js API，在 WebView 中不可用。原则：**函数签名不变，实现按 target 分派**。这样同一份凝华源码在桌面与安卓上都能编译，语义一致。

| 函数 | 桌面实现 | 安卓实现 | 语义差异 |
|---|---|---|---|
| `print(v)` | `console.log(…)` | `console.log(…)`（原生经 `WebChromeClient` 捕获）**或**直接走桥接到 `log` | 无 |
| `readFile(p)` | `require('fs').readFileSync` | 桥接到原生，读应用私有目录 | **变为异步**；路径解释不同（§5.1） |
| `writeFile(p,s)` | `writeFileSync` | 桥接到原生 | **变为异步** |
| `appendFile(p,s)` | `appendFileSync` | 桥接到原生 | **变为异步** |
| `fileExists(p)` | `existsSync` | 桥接到原生 | **变为异步** |
| `readDir(p)` | `readdirSync` | 桥接到原生 | **变为异步** |
| `readLine()` | `fs.readSync(0, Buffer…)` | **无对应物**（安卓无 stdin） | 需处理（§5.2） |
| `getArgs()` | `process.argv.slice(2)` | 由原生在启动时注入（Intent extras） | 语义扩展 |

**关键矛盾**：桌面版是同步的（返回 `Result[Str,Str]`），安卓版天然异步（跨桥接必须等待原生）。若签名不变，则安卓实现只能同步阻塞 JS 线程等原生返回——而 §2.3 已说明 `@JavascriptInterface` 同步调用不能做耗时操作，否则有 ANR 风险。

**候选方案**：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **R-1 IO 函数标注 `@async`** | 安卓目标下这六个函数要求 `@async` 上下文，返回 `Task[Result[…]]` | 语义诚实，与第六卷 §8 一致；但同一函数在两个 target 下异步性不同，**破坏"同一份源码两种目标"** |
| **R-2 统一改为异步** | 桌面目标下也用 Promise 包装（`awaited(…)` 机制已存在，`JsCodeGen.kt:927`） | 两目标语义一致；桌面端现有代码需要加 `@async`，**是破坏性变更** |
| **R-3 安卓侧提供独立的异步 IO 模块** | `core/io` 保持同步（桌面专用），新增 `core/android/io` 提供异步版本 | 无破坏性变更，职责清晰；代价是两套 IO API，跨平台代码要分支 |

**推荐 R-3**，理由：凝华的哲学是效应显式，同步 IO 与异步 IO 本就是不同的效应，用不同函数名表达比用编译目标隐式改变同一函数的效应更诚实。`core/io` 的六个函数在 `--target=android` 下应当**编译期报错**（`E-PLATFORM-UNAVAILABLE`），提示改用 `android.io` 的异步版本，而不是静默生成会崩的代码。

这是本设计新增的诊断码，需入第十卷。

### 5.1 路径语义

安卓应用没有自由文件系统访问。可用位置：

| 位置 | 原生 API | 特点 |
|---|---|---|
| 应用私有内部存储 | `context.filesDir` | 无需权限，应用卸载即删除 |
| 应用私有缓存 | `context.cacheDir` | 系统可能清理 |
| 应用私有外部存储 | `context.getExternalFilesDir(null)` | 无需权限（API 19+），卸载即删除 |
| 公共媒体 | `MediaStore` | 需分区存储 API，Android 10+ 强制 |
| 任意路径 | SAF（`ACTION_OPEN_DOCUMENT`） | 需用户选择器交互，返回 URI 而非路径 |

**设计**：`android.io` 的路径参数应当是**相对于应用私有目录的相对路径**，或一个显式的存储域枚举：

```subl
enum StorageScope { Internal, Cache, External }

@root @async @impure
fun androidRead(scope : StorageScope, path : Str) : Task[Result[Str, Str]] {}
```

直接暴露绝对路径会诱导用户写出在其他设备上失效的代码。

### 5.2 `readLine` 与 `getArgs`

- `readLine`：安卓无 stdin。方案是在 `--target=android` 下报 `E-PLATFORM-UNAVAILABLE`；若需要用户输入，走 UI（文本框）。
- `getArgs`：安卓的对应物是 Intent extras 与启动参数。方案是原生在调用 `main` 前注入 `__subl.args`，`getArgs()` 读取它。这让"从通知点击进入特定页面"这类深链接成为可能。

### 5.3 `timeNow` 与 `rand`

`Date.now()` 与 `Math.random()` 在 WebView 中可用，**无需改造**。

但注意：`Math.random()` 不是密码学安全的。若应用需要安全随机数，应当桥接到 `java.security.SecureRandom`。这是 `android.random` 的存在理由。

## 六、UI 渲染架构：三条路线

这是本设计最重要的决策。

### 6.1 方案 A：纯 WebView（DOM/CSS）

JS 直接操作 DOM，用 HTML/CSS 呈现界面，安卓侧只提供能力（相机、传感器、文件）。

| 维度 | 评价 |
|---|---|
| 实现成本 | **最低**。无需原生视图桥接，浏览器 API 完备 |
| 视觉与触感 | 不像原生应用；滚动惯性、点击反馈、字体渲染有差异 |
| 性能 | 复杂列表滚动性能弱于 RecyclerView |
| 与凝华的契合 | 需要一整套 DOM 绑定标准库，且 DOM 是**可变**的，与不可变纪律冲突 |
| 跨平台潜力 | 最高（同一份代码可跑桌面浏览器） |

### 6.2 方案 B：JS 描述视图树，原生渲染原生控件

JS 侧持有视图树的描述，通过桥接层告知原生创建/更新真实的安卓控件（`TextView`、`Button`、`LinearLayout` 等）。这是 React Native 与草稿所选的路线。

| 维度 | 评价 |
|---|---|
| 实现成本 | **最高**。需要完整的视图桥接、属性映射、事件回传、diff 机制 |
| 视觉与触感 | 原生控件，触感正确 |
| 性能 | 桥接调用是瓶颈；批量更新与 diff 粒度决定体验 |
| 与凝华的契合 | **最好**。视图树是不可变数据结构，符合语言哲学；且可用线性作用域承载状态 |
| 跨平台潜力 | 中（视图模型可复用到 iOS，但需另写桥接） |

### 6.3 方案 C：混合

WebView 承载主体 UI，原生控件只在必要时（地图、视频、WebView 无法胜任的组件）以叠加层出现。

| 维度 | 评价 |
|---|---|
| 实现成本 | 中 |
| 一致性 | 差——两套 UI 体系混合，层级与事件穿透复杂 |

### 6.4 决策

采**方案 B**。理由：

1. 草稿已明确此意图（`Box`/`Button` 是结构体，编译为原生视图，APK 内有原生支持器）；
2. 与凝华的不可变哲学契合度最高——视图树天然是不可变数据结构；
3. 草稿的 `@view` 与 `recomposition` 概念只在方案 B 下有意义。

代价是工作量最大。§13 的分阶段路线据此安排：先做**极小的控件集**（文本、按钮、纵向/横向容器）打通全链路，再逐步扩充。

## 七、生命周期 API

### 7.1 事件集

安卓 Activity 生命周期的完整事件，以及应用可能需要关心的系统事件：

| 事件 | 何时触发 | 应用典型处理 |
|---|---|---|
| `onCreate` | 实例创建 | 初始化（凝华侧对应 `main` 的执行） |
| `onStart` | 即将可见 | 恢复订阅 |
| `onResume` | 可交互 | 启动动画、传感器 |
| `onPause` | 失去焦点 | 暂停动画、保存草稿 |
| `onStop` | 不可见 | 释放资源 |
| `onDestroy` | 即将销毁 | 清理 |
| `onSaveInstanceState` | 系统可能杀进程前 | **序列化应用状态** |
| `onRestoreInstanceState` | 重建后 | 恢复状态 |
| `onBackPressed` | 返回键/返回手势 | 页面栈回退 |
| `onConfigurationChanged` | 配置变更（若已拦截） | 重新布局 |
| `onRequestPermissionsResult` | 权限申请返回 | 继续被挂起的操作 |
| `onNewIntent` | 单实例模式下新 Intent | 深链接处理 |

草稿只写了 `onStart`。完整的支持需要覆盖上述事件，但**第一版可以只做 5 个**：`onStart`、`onResume`、`onPause`、`onStop`、`onSaveInstanceState`。

### 7.2 API 形态

草稿：

```subl
fun main() {
    onStart {
        log("it works!")
    }
}
```

这里 `onStart { … }` 是内建函数 + 尾随 lambda（第二卷 §7.2 的脱糖规则适用）。语义是**注册回调**，而非立即执行。

**需要注意的三点**：

1. **`main` 执行完就返回了**，但回调要在未来触发。这要求 JS 全局状态在 `main` 返回后继续存活——§4.1 的导出对象结构保证了这一点。
2. **lambda 捕获**：回调 lambda 捕获 `main` 作用域的变量。按第五卷 §2.2，lambda 帧隔离，捕获的变量类型可见、事实不传播。这对生命周期回调是**正确的语义**（回调在未来执行，那时的上下文与注册时不同）。
3. **纯度**：`log` 是 `@impure`，所以回调 lambda 按第六卷 §5.2 会被推导为不纯（`Checker.kt:685-688` 的 `curLambdaImpure` 机制）。这正确，但要求 `onStart` 的形参类型标注为 `@impure () => Null`（第三卷 §1.4 的纯度标注），否则把一个不纯函数值传给纯函数类型形参会触发 `E-TYPE-MISMATCH`。

**修正后的签名**：

```subl
@root @impure
fun onStart(handler : @impure () => Null) : Null {}
```

### 7.3 `layout` 的归属

草稿写：

```subl
onStart { layout = mainLayout() }
```

`layout` 未声明。这在凝华中是 `E-UNBOUND-NAME`（第九卷 §2.1）。**必须修正**。候选方案：

| 方案 | 写法 | 取舍 |
|---|---|---|
| **L-1 显式函数调用** | `setLayout(mainLayout())` | 最符合凝华风格（无隐式全局）；动词明确表达这是效应 |
| **L-2 活动对象属性** | `activity.layout = mainLayout()` | 面向对象直觉；但 `activity` 需要是可变对象，且属性赋值触发第六卷 §5.3 的字段写入规则 |
| **L-3 隐式全局变量** | `layout = mainLayout()` | 草稿原意；违反"无隐式全局"，且 `layout` 的可变性无从表达 |

**推荐 L-1**：

```subl
@root @impure
fun setLayout(root : View) : Null {}
```

配合 §8 的视图更新机制，后续更新走视图自身的更新通道（§8.4）。

### 7.4 状态保存

`onSaveInstanceState` 需要一个可序列化的载荷。方案：

```subl
@root @impure
fun onSaveState(handler : @impure (Json) => Json) : Null {}
```

语义：原生在系统可能杀进程前调用该回调，传入上次的状态（首次为 `Null` 的 Json），回调返回新状态，原生把它放进 `Bundle`。

用 `Json` 而非自定义类型，是因为 `Bundle` 只能装基本类型与 `String`，且凝华已有完整的 Json 内建（第三卷 §6.3）。

**与 §2.1 的关系**：这是应对 Activity 重建的唯一手段。若不实现，旋转屏幕就会丢失全部应用状态。

### 7.5 事件循环与程序存活

桌面端 `main` 返回即进程退出。安卓端 `main` 返回后应用**必须继续存活**等待事件。

实现上这不是问题：JS 全局对象存活，注册过的回调由原生通过 `dispatch` 触发。但需要明确：

- `main` 返回后若有未完成的 `Task`，它们继续跑（Promise 链挂在事件循环上）；
- 应用退出由原生决定（`finish()`），凝华侧可提供 `androidFinish()`。

## 八、视图模型：`@view` 结构体与 recomposition

这是草稿中问题最集中、也最需要重新设计的部分。

### 8.1 草稿方案及其内在矛盾

草稿原文：

> 这种结构体标注了 `@view`，称它们为视图结构体，编译器对它们有特殊优化。视图结构体会被编译器加上一个属性 `recomposition`，当视图被修改的时候，视图会调用这个属性，然后把修改好的视图传给他，而原来的视图依然不变。

三处矛盾：

1. **"布局是更直觉主义的可变修改"** vs **"原来的视图依然不变"**——前半句说可变，后半句说不可变。
2. **`recomposition` 是运行时属性**——"编译器加上一个属性"意味着每个视图对象都携带一个函数引用，这是运行时开销，与零成本擦除（总纲 §3）冲突。
3. **修改如何传播未定义**——修改一个深层叶子节点，根视图如何知道？`recomposition` 只挂在被修改的那个视图上，父链无感知。

另外草稿示例本身有语法冲突（§12.1、§12.2）。

### 8.2 修正方案：不可变视图树 + 版本化更新

**核心决定**：视图结构体是**不可变**的。所谓"直觉主义的可变修改"由**语法层**提供，语义层是不可变更新。

这正是《线性作用域》的机制。用户写：

```subl
fun main() {
    onStart { setLayout(mainLayout()) }
}

@impure
fun mainLayout() : View = %{
    var @mut theButton = Button(text = "text1")
    theButton.onClick = { theButton.text = "text2" }
    Box(theButton)
}
```

编译器内部：

- `theButton` 被版本化为 `theButton#0`、`theButton#1`、…；
- `theButton.text = "text2"` 不就地修改，而是产生新版本（结构体是不可变的，字段赋值触发路径拷贝）；
- 版本名在代码生成时擦除，产物是普通的 JS 变量重赋值。

**`recomposition` 因此不需要作为运行时属性存在**——它是编译期的版本化机制，产物中不出现。这消除了矛盾 2。

矛盾 3（修改如何传播）由 §8.4 的提交机制解决。

### 8.3 视图标识

diff 需要知道"新树的这个节点对应旧树的哪个节点"。候选方案：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **I-1 位置 + 类型** | 同一父节点下、同一位置、同一类型的节点视为同一 | 无需用户标注；但插入/删除一个元素会导致后续全部错位重建 |
| **I-2 显式 key** | 视图结构体带可选 `key : Str` 字段 | 精确；但要求用户在列表场景手动标注 |
| **I-3 原生侧对象标识** | 每个视图创建时分配 `viewId`，JS 侧持有 | 需要 JS 侧保存 viewId 映射，且 viewId 与不可变视图树的对应关系复杂 |

**推荐 I-1 + I-2 组合**：默认按位置+类型，用户可显式提供 `key` 覆盖。这与 React 的 key 机制一致，是业界验证过的方案。

### 8.4 更新的提交时机

修改产生新树后，何时把变化下发给原生？

| 方案 | 做法 | 取舍 |
|---|---|---|
| **C-1 每次修改立即下发** | 每个字段赋值都产生一条桥接命令 | 实现最简单；但一次交互可能产生几十条命令，桥接成为瓶颈（§2.7） |
| **C-2 微任务批量提交** | 修改只更新 JS 侧树，在 Promise 微任务末尾统一 diff + 下发 | 一次交互一帧一次提交，桥接调用数最小化。**推荐** |
| **C-3 显式提交** | 用户调用 `commit()` | 控制权最大；但违背"直觉主义"的初衷 |

**推荐 C-2**。实现：桥接运行时维护一个"脏标记"，首次修改时 `Promise.resolve().then(flush)` 排入微任务；`flush` 时 diff 新旧树，生成变更集，序列化为一条 JSON 命令下发。

这与浏览器的渲染时机天然对齐，也与安卓的 VSYNC 节奏兼容。

### 8.5 diff 与变更集

变更集是一组操作：

```json
{
  "ops": [
    { "op": "create", "id": 7, "type": "Button", "parent": 3, "index": 0, "props": { "text": "text2" } },
    { "op": "update", "id": 5, "props": { "text": "text1" } },
    { "op": "delete", "id": 6 },
    { "op": "move", "id": 4, "parent": 3, "index": 2 }
  ]
}
```

属性名与值的映射由**视图结构体的字段名**决定，无需额外配置——这是 `@view` 结构体的关键价值：字段名就是原生属性名（或经一张映射表转换）。

深拷贝的成本：视图树是持久化数据结构，修改叶子只需拷贝从根到叶子的路径，成本 O(深度)，不是 O(节点数)。**这要求视图结构体的子节点字段是不可变的**——第六卷 `C-COPY-3` 的深拷贝规则在此不适用，因为不存在 `@mut` 视图。

### 8.6 事件回调

草稿的 `onClick = { theButton.text("text2") }` 有两个需要修正的问题：

1. `text` 既是字段名又当方法用（§12.3）；
2. lambda 捕获正在初始化的 `theButton`（自引用）。

**已核实与现行规则兼容的部分**：lambda 内修改外部捕获的可变变量**不报错**，只是把该 lambda 推导为不纯（`Checker.kt:685-688`）。这正是事件回调需要的语义，详见 §12.4。

**修正**：事件回调的类型是 `@impure () => Null`，回调体内对视图变量的赋值走 §8.2 的版本化路径。自引用问题由 lambda 的延迟执行天然解决（回调触发时 `theButton` 已完成初始化），但**必须在规范中明确捕获语义**。

若采用线性作用域，按《线性作用域·形式化版》§8.2 的 `LV-LAMBDA-READ`，lambda 捕获的是**快照版本**——这对事件回调是**错误的语义**：用户期望回调读到点击时刻的当前值，而非注册时刻的快照。

**候选方案**：

| 方案 | 语义 | 取舍 |
|---|---|---|
| **E-1 回调不捕获视图变量** | 视图更新通过独立的状态变量驱动，回调整体重建视图树 | 语义清晰（这就是 Compose/React 模式）；但草稿明确不想要这种写法 |
| **E-2 回调读当前版本** | 事件回调特殊处理，读到触发时刻的版本 | 符合"直觉主义的可变修改"；但破坏 `LV-LAMBDA-READ` 的快照语义，需要为视图域单开例外 |
| **E-3 视图变量按引用捕获** | 视图变量在事件回调中解析为一个"当前值读取器" | 实现上等价于 E-2，但表述为引用而非版本 |

**推荐 E-2，并把例外限定在 `@view` 结构体变量上**。理由：视图状态是**长寿命的应用状态**，与线性作用域针对的"函数内局部计算状态"不是同一类东西；线性作用域的快照语义是为健全性证明服务的（形式化版 §9.2），而事件回调的执行时机由用户交互决定，本就不可静态确定，强行快照会得到反直觉的结果。

这个例外需要在《线性作用域·形式化版》§8.2 补一条限定，并在健全性论证中说明：**视图域不参与 `∴` 证明的版本追踪**（视图状态用于渲染，不用于命题证明），因此例外不损害 §9 的健全性定理。

这是一个**需要拍板的设计决策**（§15 决策 9）。

### 8.7 布局与尺寸单位

草稿只给了 `Box`。安卓的布局体系至少需要：

| 视图 | 对应安卓 | 说明 |
|---|---|---|
| `Box` | `FrameLayout` | 层叠 |
| `Column` | `LinearLayout(vertical)` | 纵向排列 |
| `Row` | `LinearLayout(horizontal)` | 横向排列 |
| `Text` | `TextView` | 文本显示 |
| `Button` | `Button` | 按钮 |
| `TextInput` | `EditText` | 输入框 |
| `Image` | `ImageView` | 图片 |
| `Scroll` | `ScrollView` | 滚动容器 |
| `Spacer` | `Space` | 占位 |
| `LazyColumn` | `RecyclerView` | 长列表虚拟化（性能关键） |

尺寸单位必须是 **dp**（密度无关像素）与 **sp**（可缩放像素，用于字体）。凝华侧的表达方式候选：

- 裸数字默认 dp（`padding = 16`）；
- 引入单位构造函数（`16.dp`、`14.sp`），但这需要中缀或后缀语法支持；
- 引入枚举（`Dp(16)`）。

**推荐裸数字默认 dp + 字体尺寸单独用 `fontSizeSp` 字段名区分**，避免引入新的语法机制。

### 8.8 变长子视图

容器视图（`Box`/`Column`/`Row`）需要接受**任意数量**的子视图。草稿写 `Box(var theButton = Button(...))`，依赖结构体的变长参数——而**结构体字段不支持 `@list`**（§3.2、§12.1）。

候选方案：

| 方案 | 写法 | 取舍 |
|---|---|---|
| **V-1 扩展 `@list` 到结构体字段** | `struct Box(@list children : List[View])` → `Box(a, b, c)` | 语法最自然，正是草稿的意图；需要改 `JsCodeGen.kt:226-228` 的收集逻辑与 `CallCheck` 的构造检查 |
| **V-2 显式列表** | `Box(listOf(a, b, c))` | 无需改语言；但嵌套层次多时括号冗长 |
| **V-3 尾随块语法** | `Box { a; b; c }` | 最接近 Compose 的写法，可读性最好；需要新的语法产生式 |

**推荐 V-1**，因为它是语言层面的通用改进（不只服务安卓），且改动量可控（`@list` 的打包逻辑已存在，只需放开到 `StructDecl`）。V-3 可作为后续的语法糖叠加。

### 8.9 `@view` 结构体的检查规则

需要为 `@view` 增加的规则：

1. **字段类型限制**：只能是 `Nat`/`Int`/`Rat`/`Real`/`Str`/`Bool`/`View`/`List[View]`/回调类型/`Json`。禁止 `@mut` 类型（视图必须不可变）、禁止 `@ref`。
2. **不可变性**：`@view` 结构体不得标注 `@mut`，其字段不得标注 `@mut`。违反报 `E-VIEW-MUTABLE`。
3. **回调纯度**：回调类型字段（如 `onClick`）必须是 `@impure` 的函数类型——因为改视图必然产生效应。
4. **伴生命题**：`@view` 结构体**不得声明伴生命题**。理由：视图字段会被频繁更新，伴生命题在每次更新时都需要重新证明，这与 §8.6 的版本化更新节奏冲突，且视图属性（颜色、尺寸）很少需要进入命题推理。
5. **不参与 `∴` 证明**：视图变量的版本事实不注入 Γ（或注入但标记为不可用于证明）。这是 §8.6 例外的配套措施。

这些规则需要新增诊断码：`E-VIEW-MUTABLE`、`E-VIEW-FIELD-TYPE`、`E-VIEW-PROP`。

```
core/android/

```

依赖 `core/collection`（`Result`/`Optional`/`List`）、`core/async`（`Task`/`Channel`）、`core/json`。`.settings` 中 mount 这三个包。

**与 `core/` 其他模块的区别**：`core/android` 只在 `--target=android` 下可用。若在 node 目标下 import，应报 `E-PLATFORM-UNAVAILABLE`。这需要 ModuleTree 或 Checker 增加 target 感知——是本设计对模块系统（第八卷）的唯一改动。

### 9.2 日志（草稿的 `log`）

草稿规定：`log` 输出到应用自带日志，可被 adb 与 shizuku 获取；第一参数 `Str` 为内容，第二参数为等级，默认 `Info`。

**补全**：

```subl
enum LogLevel { Verbose, Debug, Info, Warn, Error, Assert }

@root @impure
fun log(message : Str, level : LogLevel = Info) : Null {}
```

六个等级对应安卓 `Log.v/d/i/w/e` 与 `Log.wtf`（`Assert`）。

默认值 `Info` 依赖函数形参默认值机制——而**函数形参默认值被 `E-DEFAULT-PARAM` 禁止**（第三卷 §7.3、第九卷 §4.3；`Parser.kt:389` 的注释明确写"仅 struct 字段允许"，`DiagCoverageTest.kt:177-178` 有测试锁定）。

这是草稿与现行规则的**一处冲突**（§12.6）。候选方案：

| 方案 | 做法 |
|---|---|
| **G-1 重载** | 提供 `log(msg : Str)` 与 `logLevel(msg : Str, level : LogLevel)` 两个函数 |
| **G-2 放开函数形参默认值** | 修订 `E-DEFAULT-PARAM`，允许函数形参有默认值（代码生成已支持 JS 默认参数语法，见 `JsCodeGen.kt:434-440`） |
| **G-3 用 Optional** | `log(msg : Str, level : Optional[LogLevel])`，调用写 `log("x", Some(Warn))` 或 `log("x", None)` |

**推荐 G-2**。理由：结构体字段允许默认值而函数形参不允许，这个不对称缺乏充分理由——函数形参默认值是无害的语法便利，且安卓 API 大量需要它（几乎每个视图属性都该有默认值，靠重载会产生组合爆炸）。放开它是一项通用改进，实现成本极低（删除一处检查）。

若采纳 G-2，需要同步修订：第三卷 §7.3、第九卷 §4.3、第十卷删除 `E-DEFAULT-PARAM`，以及 `Parser.kt:389` 的注释与两处测试。

**实现路径**：`log` 生成一条桥接调用，原生侧转发到 `android.util.Log`。这样 adb logcat 与 shizuku 类工具都能获取——正是草稿的要求。等级通过独立参数传递，不要用消息前缀（避免原生侧解析字符串）。

### 9.3 活动控制

```subl
@root @impure fun onStart(handler : @impure () => Null) : Null {}
@root @impure fun onResume(handler : @impure () => Null) : Null {}
@root @impure fun onPause(handler : @impure () => Null) : Null {}
@root @impure fun onStop(handler : @impure () => Null) : Null {}
@root @impure fun onDestroy(handler : @impure () => Null) : Null {}
@root @impure fun onSaveState(handler : @impure (Json) => Json) : Null {}
@root @impure fun onRestoreState(handler : @impure (Json) => Null) : Null {}
@root @impure fun onBackPressed(handler : @impure () => Bool) : Null {}
@root @impure fun setLayout(root : View) : Null {}
@root @impure fun androidFinish() : Null {}
```

`onBackPressed` 的回调返回 `Bool`：`true` 表示应用已处理，原生不做默认回退；`false` 表示交还系统。这个"是否消费"的模式是安卓事件处理的标准约定。

### 9.4 权限

```subl
enum Permission { Camera, Microphone, FineLocation, CoarseLocation, Notifications, ReadContacts }
enum PermissionDenial { Denied, PermanentlyDenied }

@root @async @impure
fun requestPermission(p : Permission) : Task[Result[Null, PermissionDenial]] {}

@root @impure fun hasPermission(p : Permission) : Bool {}
@root @impure fun openPermissionSettings() : Null {}
```

`PermanentlyDenied` 时唯一的出路是 `openPermissionSettings()` 引导用户去系统设置——这正是 §2.5 要求区分两种拒绝的原因。

`hasPermission` 是同步的（原生侧查询 `checkSelfPermission` 很快，可在 `@JavascriptInterface` 中同步返回）。

### 9.5 异步文件 IO

```subl
@root @async @impure fun androidRead(scope : StorageScope, path : Str) : Task[Result[Str, Str]] {}
@root @async @impure fun androidWrite(scope : StorageScope, path : Str, content : Str) : Task[Result[Null, Str]] {}
@root @async @impure fun androidExists(scope : StorageScope, path : Str) : Task[Bool] {}
@root @async @impure fun androidList(scope : StorageScope, path : Str) : Task[Result[List[Str], Str]] {}
```

### 9.6 键值持久化

对应安卓 `SharedPreferences`（或 DataStore）：

```subl
@root @impure fun prefsGet(key : Str) : Optional[Str] {}
@root @impure fun prefsPut(key : Str, value : Str) : Null {}
@root @impure fun prefsRemove(key : Str) : Null {}
@root @impure fun prefsKeys() : List[Str] {}
```

同步实现（`SharedPreferences` 的读是内存操作，写是异步落盘但不需等待）。这是保存少量应用状态最便捷的方式，与 §7.4 的 `onSaveState` 互补：`prefs` 适合持久数据，`onSaveState` 适合临时 UI 状态。

### 9.7 设备与资源

```subl
struct ScreenInfo(widthDp : Nat, heightDp : Nat, density : Rat, isLandscape : Bool)

@root @impure fun screenInfo() : ScreenInfo {}
@root @impure fun resourceStr(name : Str) : Str {}
```

`resourceStr` 读 `res/values/strings.xml`，是**国际化**的基础：应用不应硬编码界面文案，而应从资源读取，由系统按语言环境选择。这一点在草稿中缺失，但对真实应用是必需的。

### 9.8 传感器与通知

第二阶段。传感器天然是**流**，凝华的 `Flow`（第六卷 §8.6）与之完美契合：

```subl

@root @impure fun accelerometer() : Flow[Vec3] {}
```

这是 `Flow` 在安卓端的最佳用武之地，也回应了 §2.8 的手势与传感器需求。

## 十、桥接协议

### 10.1 双向通道

| 方向 | 机制 | 特点 |
|---|---|---|
| **JS → 原生** | `@JavascriptInterface` 标注的方法 | 同步阻塞 JS 线程；只能传基本类型与 String；**在 JavaBridge 线程执行** |
| **原生 → JS** | `webView.evaluateJavascript(script, null)` | 必须在 UI 线程调用；异步；script 是字符串 |

### 10.2 JS → 原生的两种调用

**同步调用**（适用于原生侧能立即返回的操作）：

```javascript
// 凝华的 hasPermission(p) 生成：
__sublBridge.sync("hasPermission", JSON.stringify({ p: "Camera" }))
```

原生侧 `sync` 方法解析 JSON、执行、返回 JSON 字符串。**必须保证原生侧不做耗时操作**（§2.3、§2.7）。

**异步调用**（适用于耗时操作）：

```javascript
// 凝华的 androidRead(scope, path) 生成：
__sublAwait(__sublBridge.async("readFile", JSON.stringify({ … })))
// async 立即返回 requestId，__sublAwait 返回 Promise
```

原生侧完成后调用：

```kotlin
webView.evaluateJavascript("__subl.dispatch({\"kind\":\"resolve\",…})", null)
```

### 10.3 原生 → JS 的统一入口

所有原生发起的通信都走 `__subl.dispatch(payload)`，payload 是 JSON 字符串，按 `kind` 字段分派：

| kind | 载荷 | 用途 |
|---|---|---|
| `resolve` | `{ id, value }` | 异步调用的成功应答 |
| `reject` | `{ id, error }` | 异步调用的失败 |
| `lifecycle` | `{ event: "onResume" }` | 生命周期事件 |
| `event` | `{ viewId, name: "click", args }` | 视图事件 |
| `system` | `{ type: "backPressed" \| "configChanged" \| … }` | 系统事件 |

单一入口的好处：原生支持器代码极少（一个 `dispatch` 调用点），协议演进只需改 JS 侧桥接运行时，**不需要重新编译 APK**。这对开发迭代速度影响很大。

### 10.4 请求-应答的配对

JS 侧桥接运行时维护 `requestId → { resolve, reject }` 的映射：

```javascript
const __sublPending = new Map();
function __sublAwait(id) {
  return new Promise((res, rej) => __sublPending.set(id, { res, rej }));
}
```

`dispatch` 收到 `resolve`/`reject` 时取出并调用。这与现有 `Channel` 的 senders 队列（`JsCodeGen.kt:291`）是同一模式，可复用实现思路。

**超时处理**：原生侧崩溃或忘记应答会导致 Promise 永久挂起。方案：桥接层为每个请求设超时（如 30 秒），超时后 reject 并 `log` 一条错误。

### 10.5 事件回传与 viewId

视图事件（点击等）需要知道是哪个视图触发的。原生侧为每个创建的视图分配 `viewId`（整数），事件回传时携带。JS 侧维护 `viewId → 回调` 的映射。

这个映射是**运行时状态**，不参与命题系统。`viewId` 的分配由 diff 算法在 `create` 操作时决定（§8.5）。

### 10.6 序列化约定

统一用 JSON。凝华侧已有 `jsonToStr`/`jsonParse`（第三卷 §6.3），原生侧用 `org.json` 或 Gson。

**视图属性值的类型映射**：

| 凝华类型 | JSON | 原生 |
|---|---|---|
| `Str` | string | `String` |
| `Nat`/`Int` | number | `Int`/`Long` |
| `Rat`/`Real` | number | `Double` |
| `Bool` | boolean | `Boolean` |
| 颜色 | string（`"#RRGGBB"`）或 number | `Int`（`Color.parseColor`） |
| 枚举 | string（构造子名） | 映射表 |

### 10.7 桥接运行时的注入

按 §3.1 的按需注入机制，新增标志位 `androidBridgeUsed`，在 `--target=android` 且源码 import 了 `core.android` 时置位，注入桥接运行时代码（约 100–200 行 JS）。

## 十一、原生支持器

### 11.1 职责边界

原生侧（Kotlin）只做四件事：

1. **宿主 WebView**：创建、配置、加载产物 JS、提供 `@JavascriptInterface` 对象；
2. **实现桥接命令**：按 `sync`/`async` 的命令名分派到安卓 API；
3. **渲染视图树**：按变更集创建/更新/删除原生控件；
4. **转发生命周期与系统事件**：调用 `__subl.dispatch`。

**不做**：业务逻辑、布局计算、状态管理。这些全在 JS 侧。这个边界保证了原生支持器代码量小且稳定——理想情况下，写完一次就不需要再改，所有应用开发都在凝华侧进行。

### 11.2 视图渲染器

原生侧需要一张"视图类型 → 安卓控件"的映射表，以及"属性名 → setter"的映射表。

```kotlin
when (type) {
  "Box"    -> FrameLayout(ctx)
  "Column" -> LinearLayout(ctx).apply { orientation = VERTICAL }
  "Text"   -> TextView(ctx)
  "Button" -> Button(ctx)
  // …
}
```

属性应用：

```kotlin
when (prop) {
  "text"       -> (view as TextView).text = value.asString()
  "fontSizeSp" -> (view as TextView).setTextSize(TypedValue.COMPLEX_UNIT_SP, value.asFloat())
  "padding"    -> view.setPadding(dp(value), dp(value), dp(value), dp(value))
  // …
}
```

这张表是安卓标准库的**另一半实现**，与 `core/android/view.subl` 的结构体定义必须一一对应。建议在仓库中维护一份映射清单文档，作为两侧的契约。

### 11.3 启动流程

```
1. Application.onCreate     → 初始化全局（日志、崩溃处理）
2. Activity.onCreate        → 创建 WebView → 配置设置 → 加载产物 JS（assets 内）
3. WebView onPageFinished   → evaluateJavascript("__subl.main()")
4. JS main 执行             → 注册生命周期回调与初始布局 → 返回
5. Activity.onStart         → dispatch({kind:"lifecycle", event:"onStart"})
6. JS 回调执行              → setLayout(...) → diff → 下发变更集 → 原生渲染
```

**WebView 版本检查**应在步骤 2 之前：读取 `WebView.getCurrentWebViewPackage()`，若版本低于要求则显示提示页。

### 11.4 WebView 配置要点

```kotlin
settings.javaScriptEnabled = true
settings.domStorageEnabled = true          // localStorage
settings.databaseEnabled = true
settings.allowFileAccess = false           // 安全：禁止 file:// 访问
settings.allowContentAccess = false
settings.mediaPlaybackRequiresUserGesture = false

webView.addJavascriptInterface(bridge, "__sublBridge")
webView.webChromeClient = …                // 捕获 console 消息 → android.util.Log
webView.webViewClient = …                  // onPageFinished → 调用 main
```

**安全**：`addJavascriptInterface` 在 Android 4.2 以前有远程代码执行漏洞（API 17+ 已通过 `@JavascriptInterface` 注解限制）。设定 `minSdkVersion ≥ 24` 后无此风险，但仍应只暴露必要的方法。

### 11.5 崩溃处理

JS 异常不会崩溃 APK，但会让应用进入不一致状态。方案：

- `window.onerror` 捕获 JS 异常 → `dispatch` 到原生 → 写日志 + 可选的重启策略；
- 原生侧 `Thread.setDefaultUncaughtExceptionHandler` 捕获 Java 异常。

## 十二、草稿与现行语言规则的冲突

这一节是**需要你拍板**的部分。每条给出冲突、原因、候选方案。

### 12.1 结构体变长参数（硬性冲突）

**草稿**：「`Box` 和 `Button` 是一个结构体，结构体也可以声明变长参数与默认值」

**现状**：默认值 ✅ 支持（`JsCodeGen.kt:434-440` 生成 JS 默认参数）；**变长参数 ❌ 不支持**——`@list` 的打包位置只在 `FunDecl` 分支收集（`JsCodeGen.kt:226-228`），`StructDecl` 不走该逻辑，`CallCheck` 也无对应处理。

**候选**：见 §8.8 的 V-1（扩展 `@list` 到结构体，推荐）／V-2（显式 `listOf`）／V-3（尾随块语法）。

### 12.2 `layout` 未声明（硬性冲突）

**草稿**：`onStart { layout = mainLayout() }`

**现状**：`layout` 不是任何已声明的变量或全局，赋值触发 `E-UNBOUND-NAME`（第九卷 §2.1）。凝华无隐式全局变量。

**候选**：见 §7.3 的 L-1（`setLayout(...)`，推荐）／L-2（`activity.layout = ...`）／L-3（引入隐式全局，不推荐）。

### 12.3 `text` 既作字段又作方法

**草稿**：`Button(text = "text1", …)` 与 `theButton.text("text2")`

**现状**：结构体字段与 impl 方法处于不同命名空间，技术上可以同名共存。但同一名字同时用作字段（构造时）与方法（调用时）在可读性上是灾难，且 `theButton.text("text2")` 若无返回值定义则语义不明。

**候选**：

- 统一为**字段赋值**：`theButton.text = "text2"`（配合 §8.2 的版本化）。**推荐**，与"直觉主义的可变修改"最契合。
- 或统一为**方法**：`theButton.setText("text2")`，返回新视图。

### 12.4 lambda 内修改捕获的变量（已核实：无冲突）

**草稿**：`onClick = { theButton.text("text2") }`

**现状**（已核实源码）：lambda 体内给外部捕获的可变变量赋值**不报错**。`Checker.kt:685-688` 的处理是：当前帧未声明该名字、且沿父链判定为 `@mut` 时，置 `curLambdaImpure = true`，使该 lambda 的函数值类型标为 `FunType.purity = "impure"`（第六卷 §5.2）。后果是：这个函数值**不能在纯上下文中被调用**，否则报 `E-IMPURE-CALL`。

也就是说，语言已经允许"事件回调修改外部可变变量"，代价是回调被推导为不纯——这正是安卓事件回调需要的语义。**草稿此处与现行规则兼容，无需修改语言。**

需要注意的只有一点：`onClick` 字段的类型必须声明为 `@impure () => Null`（第三卷 §1.4 的纯度标注），否则把一个不纯的函数值赋给纯函数类型字段会触发 `E-TYPE-MISMATCH`。

**候选**：

- **保持现状**（推荐）：视图变量标注 `@mut`，回调内直接修改，lambda 自动不纯。
- 或改为回调返回新视图、由框架合并（Compose 模式，即 §8.6 的 E-1），这与草稿的"直觉主义可变修改"意图相悖。

> **勘误说明**：本节初稿曾断言此处触发一个名为 `E-MUTABLE-OUTER-VAR` 的错误码。经核实源码，**该诊断码不存在**，实际行为如上（推导为不纯，不报错）。特此更正。

### 12.5 事件回调的版本捕获语义

**冲突**：《线性作用域·形式化版》§8.2 的 `LV-LAMBDA-READ` 规定 lambda 捕获**快照版本**；事件回调需要**当前版本**。

**候选**：见 §8.6 的 E-1／E-2（推荐）／E-3。

若采 E-2，需在《线性作用域》两份文档中补一条限定，并说明为何不损害健全性定理（理由：视图域不参与命题证明）。

### 12.6 函数形参默认值被禁止

**草稿**：`log` 的第二个参数「默认值是 `Info`」

**现状**：`E-DEFAULT-PARAM` 禁止函数形参默认值（第三卷 §7.3、第九卷 §4.3、`Parser.kt:389` 注释、`DiagCoverageTest.kt:177`），但**结构体字段允许**。代码生成器已实现 JS 默认参数语法。

**候选**：见 §9.2 的 G-1（重载）／G-2（放开禁令，推荐）／G-3（`Optional`）。

**说明**：安卓 API 几乎每个属性都需要默认值（视图有几十个可选属性），若靠重载会产生组合爆炸。放开它是一项通用改进，且实现成本极低。

### 12.7 `recomposition` 作为运行时属性

**草稿**：「编译器给视图结构体加上一个属性 `recomposition`」

**现状**：这与零成本擦除（总纲 §3）冲突——每个视图对象携带一个函数引用是运行时开销，且该属性对用户可见（可被读取、被 diff 误当作数据字段）。

**候选**：见 §8.2——用编译期版本化替代运行时属性。**推荐**。

### 12.8 视图结构体的可变性

**草稿**：「布局是更直觉主义的可变修改」

**现状**：若视图结构体标注 `@mut`，则 `@mut` 类型不能进函数签名（第六卷 §4.1），而 `mainLayout() : View` 的返回类型必然是视图类型 → 触发 `E-IMPURE-REQUIRED`；且每次绑定触发深拷贝（第六卷 §6.1 `C-COPY-3`），视图树深拷贝成本不可接受。

**候选**：视图结构体**不可变**（不加 `@mut`），"可变修改"由语法层的版本化提供（§8.2）。**推荐**，这也是唯一能同时满足性能与语言纪律的方案。

## 十三、分阶段实现路线

### 第一阶段：编译目标与产物结构（不涉及 UI）

1. 代码生成器引入 `Target` 枚举，CLI 增加 `--target=node|browser|android`（默认 `node`，保持向后兼容）；
2. `Target.Android` 下产物改为 §4.1 的 S-1 结构（返回导出对象的 IIFE），抑制 `main()` 自执行；
3. 新增诊断码 `E-PLATFORM-UNAVAILABLE`：在 node 目标下 import `core.android`、或在 android 目标下调用 `core/io` 的六个同步 IO 函数时报出；
4. 建立 `AndroidSDK/` 的最小原生工程：单 Activity + WebView + `@JavascriptInterface` 桥 + `dispatch` 通道；
5. 打通 `log`：`core/android/log.subl` + 桥接命令 + `android.util.Log`，验证 adb logcat 可见；
6. 打通生命周期：`onStart`/`onResume`/`onPause`/`onStop` 的注册与派发；
7. 端到端测试：一个只调用 `log` 与生命周期回调的凝华应用跑在真机/模拟器上。

**验收标准**：草稿里的那个例子（`onStart { log("it works!") }`）能在安卓设备上输出日志。

### 第二阶段：视图渲染

8. 放开 `E-DEFAULT-PARAM`（§12.6 的 G-2），同步修订第三、九、十卷与两处测试；
9. 扩展 `@list` 到结构体字段（§12.1 的 V-1）；
10. 实现 `@view` 结构体的检查规则（§8.9），新增 `E-VIEW-MUTABLE` 等诊断码；
11. 实现最小控件集：`Text`、`Button`、`Column`、`Row`、`Box`、`Spacer`；
12. 实现 `setLayout` 与全量下发（先不做 diff，每次重建整棵树）；
13. 原生侧视图渲染器与属性映射表；
14. 事件回传：`onClick` 的 viewId 映射与派发；
15. 端到端测试：草稿的按钮改文字例子跑通。

**验收标准**：草稿的 `mainLayout` 例子（修正语法后）能渲染出按钮，点击后文字改变。

### 第三阶段：更新机制与状态

16. 实现版本化更新（对接《线性作用域》第一、二波，或独立实现视图域的版本化）；
17. 实现 §8.4 的微任务批量提交与 §8.5 的 diff 算法；
18. 实现 §8.6 的事件回调版本语义（E-2 例外）；
19. 实现 `onSaveState`/`onRestoreState` 与 `prefs` 持久化；
20. 实现权限 API；
21. 实现异步 IO（`androidRead` 等）；
22. 扩充控件集：`TextInput`、`Image`、`Scroll`、`LazyColumn`；
23. 手势：长按、拖动、滑动。

### 第四阶段：完善

24. 传感器（`Flow` 承载）；
25. 通知；
26. Intent 与深链接；
27. 资源与国际化（`resourceStr`）；
28. 远程调试与 sourcemap（§14.1）；
29. 性能剖析工具；
30. 打包工具链：一条命令从凝华源码产出可安装的 APK。

### 依赖关系

第二阶段依赖第一阶段的桥接通道；第三阶段的 16–18 依赖《线性作用域》的实现（或独立实现一套视图域版本化——两者机制相同，可共用代码）；第四阶段各项彼此独立，可并行。

**关键路径**：第一阶段 1–7 → 第二阶段 8–15 → 第三阶段 16–18。

## 十四、开发期工程问题

### 14.1 调试手段

| 手段 | 说明 |
|---|---|
| **Chrome 远程调试** | `WebView.setWebContentsDebuggingEnabled(true)`（仅 debug 构建），桌面 Chrome 访问 `chrome://inspect` 可断点调试 JS、查看视图树、看 console。**最高优先级**，没有它开发效率极低 |
| **logcat** | `log` 输出转发到 `android.util.Log`，`adb logcat` 可见 | 草稿已要求 |
| **sourcemap** | 代码生成器输出 sourcemap，使 JS 断点能映射回 `.subl` 行号 | 现有 codegen 无此能力，需新增 |
| **变更集可视化** | 桥接层可选地把每次下发的变更集 `log` 出来 | 排查 UI 不更新问题的利器 |
| **模拟器 vs 真机** | 模拟器便于自动化测试，真机才能验证触感、性能、厂商 ROM 差异 | 两者都需要 |

### 14.2 测试策略

| 层次 | 方法 |
|---|---|
| 凝华侧类型检查 | JUnit + `.subl` 测试探针（沿用 `prove_matrix` 的模式，可新建 `android_matrix/`） |
| 代码生成产物 | 逐字节快照测试——工程审查报告 P1-3 已指出 codegen 缺此测试，安卓端更应有 |
| 桥接协议 | 用 mock 的 `__sublBridge` 在 Node 中跑产物 JS，验证协议正确性（**不需要设备**，可进 CI） |
| 原生渲染 | Android Instrumented Test（Espresso） |
| 端到端 | 模拟器 + 截图对比 |

**关键洞察**：桥接协议层可以在 **Node 环境中用 mock 测试**，不需要安卓设备。这让大部分逻辑能进 CI，只有原生渲染与真机行为需要设备。这大幅降低了开发门槛。

### 14.3 与既有测试基线的关系

工程审查报告 §1.1 记录源码实测 762 处 `@Test`。安卓端的每一阶段都应当增加测试并更新该数字，避免文档与代码脱节（审查报告 P2-1）。

### 14.4 仓库位置

草稿自称根文档。建议的落位：

| 内容 | 位置 |
|---|---|
| **根文档**（不可修改的原始构想） | `root doc/安卓标准库.md`——即你的草稿原文 |
| **设计文档**（本文） | `boring doc/安卓标准库设计.md` |
| **实现规范**（落地后） | 《凝华形式化规范》第十二卷 |

| **测试探针** | `android_matrix/`（类比 `prove_matrix/`） |

## 十六、本文未覆盖但应当考虑的议题

1. **导航与页面栈**：多页面应用如何组织？返回键如何与页面栈联动？草稿与本文都只涉及单页面。
2. **主题与样式**：颜色、字体、间距的统一管理；深色模式适配（§2.1 提到它会触发重建）。
3. **列表性能**：`LazyColumn` 的虚拟化实现，长列表的内存与滚动性能。
4. **动画**：属性动画、过渡动画、手势跟随动画。桥接调用频率是瓶颈（§2.7），动画可能需要原生侧驱动。
5. **无障碍（a11y）**：`contentDescription`、TalkBack 支持。这是上架 Google Play 的隐性要求。
6. **应用图标、启动画面、应用名称**：打包元数据。
7. **多语言**：§9.7 的 `resourceStr` 只是入口，完整的 i18n 需要复数规则、日期格式化、RTL 布局。
8. **网络**：`core/net` 在安卓端如何实现？HTTP 请求需要桥接到 `OkHttp` 或 `HttpURLConnection`，且需要 `INTERNET` 权限（安装时权限，无需运行时申请）。
9. **WebView 与原生视图的层级混合**：若某些组件（地图、视频播放器）必须是原生控件叠加在 WebView 上，层级与触摸事件穿透如何处理。
10. **安全**：`addJavascriptInterface` 的暴露面、WebView 加载本地资源的策略、敏感数据在 JS 侧的驻留。
11. **应用体积**：APK 内含 WebView 无关（系统提供），但产物 JS 与原生支持器的大小；ProGuard/R8 混淆。
12. **上架合规**：Google Play 的数据安全表单、隐私政策、目标 API 级别要求（每年提升）。

## 十七、结语

安卓端支持的工作量分布大致是：**原生支持器 30%、桥接协议与代码生成 30%、视图模型与 diff 25%、标准库 API 15%**。其中视图模型是唯一需要修改语言本身的部分（§15 的决策 6–9），其余都是在既有机制上的扩展。

现有的三项资产显著降低了成本：按需注入的运行时片段机制（§3.1）、基于 Promise 的异步模型（天然适配原生回调）、`core/` 的隐式挂载（新模块零配置）。最大的障碍是产物结构（自执行 IIFE 不导出）与六处 Node.js 假设，而这两者都由"引入编译目标"这一项改造统一解决，且该改造对桌面端也有独立价值。

草稿确立的四项决策（WebView 运行、单活动、声明式 DSL、`log`）全部保留。需要修正的是 `recomposition` 的实现机制与示例代码的语法细节——修正后的方案在保住"直觉主义的可变修改"这一核心意图的同时，与凝华的不可变纪律、零成本擦除不变量以及《线性作用域》的版本化机制完全一致。
