## 0. 总览

凝华**没有源码级 import 语句**：Parser 无 ImportStmt 产生式，模块挂载不是源码语句（_langfacts.md §2）。跨模块引用由三件事支撑：

1. **目录即模块**——编译入口的目录树被扫描成模块树（§1）；
2. **.settings 挂载**——每个模块用 `mount <路径> [as <别名>]` 指令声明依赖（§2），可见性是**计算出来的集合**而非查表的布尔（I-20，§3）；
3. **限定引用与裸名回退**——`a.b.c` 沿模块链解析（§5），裸名在可见集合内依次查找（§6）。

本卷用判断式（LaTeX）给出各条规则；规则名统一以 X- 前缀编号，诊断码沿用实现。

## 1. 模块树：目录即模块

### 1.1 模块与扫描

每个**目录**（含编译入口根）是一个模块；同模块内所有 `.subl` 文件共享一个 `Symbols`（ModuleTree.kt:10-18）。模块树节点：

$$\text{ModuleNode} = \langle \text{name},\ \text{absPath},\ \text{dir},\ \text{children},\ \text{files},\ \text{settings} \rangle$$

其中 `name` 为目录名（根为空串）、`absPath` 为相对根以 `/` 连接的路径（根为空串，作全树唯一键）、`children` 按目录名索引、`files` 为目录内排序后的 `.subl` 文件、`settings` 为挂载声明。

$$\frac{d \text{ 是目录} \qquad \neg d.\text{name}.\text{startsWith}(".") \qquad d.\text{name} \notin \text{IGNORED\_DIRS}}{\text{scan}(d) = \text{ModuleNode}(\ldots) \quad \text{且} \quad d \text{ 的子目录递归入 } \text{children}} \quad (\text{X-SCAN})$$

- 目录内文件按名字排序处理，**只收集 `.subl` 文件**（ModuleTree.kt:63-71）；
- 忽略集 `IGNORED_DIRS` = `build, out, target, node_modules, .git, .gradle, .idea, .kotlin`，外加一切以 `.` 开头的隐藏目录（ModuleTree.kt:43-46）。

$$\frac{}{\text{absPath}(\text{根}) = "" \qquad \text{absPath}(\text{子}) = \text{absPath}(\text{父}) + "/" + \text{name}(\text{子})\ (\text{父为根时即目录名})} \quad (\text{X-ABSPATH})$$

### 1.2 标准库包的嫁接

标准库模块名为 `core`（STDLIB_MODULE，ModuleTree.kt:49）。候选布局相对编译入口根、按优先级：`core/` 与 `test/core/`（ModuleTree.kt:56）。若根下无 `core` 子目录而 `test/core` 存在且为标准库包形态，则将其**重挂为根的 `core` 子树并重算 absPath**：

$$\frac{"core" \notin \text{root}.\text{children} \qquad \text{root}.\text{children}["test"].\text{children}["core"] = c \qquad \text{isStdlibPackage}(c)}{\text{root}.\text{children}["core"] = \text{repath}(c,\ "core")} \quad (\text{X-GRAFT})$$

其中**标准库包形态**判定为：只含子包目录、无直接 `.subl` 源文件（`isStdlibPackage`：`files.isEmpty() ∧ children.isNotEmpty()`，ModuleTree.kt:93-94）。用户自建的普通 `core/`（目录下直接有源文件）保持普通模块语义，不被劫持。

### 1.3 根模块的限制

$$\frac{\text{node}.\text{name} = ""}{\text{loadSettings}(\text{node}) = \text{ModuleSettings}(\emptyset)} \quad (\text{X-ROOT-NO-SETTINGS})$$

**根模块没有 settings 文件**（P0 限制，ModuleTree.kt:105）：根模块的依赖只能靠子目录与「祖先挂载向下流淌」获得，且根模块符号不加 mangle 前缀（用户拍板 Q4a，见 §9）。

## 2. settings 文件与挂载声明

### 2.1 文法

每个模块可有一个 `<模块名>.settings` 文件（模块名 = 目录名，ModuleTree.kt:106），逐行声明依赖。`mount` 是 settings 支持的**唯一**指令：

```
Settings → { Line }
Line     → 'mount' Path [ 'as' Alias ]     挂载指令（唯一指令）
         | '#' { 任意字符 }                 注释
         | 空行
```

$$\frac{\ell \neq "" \qquad \ell \text{ 不以 } \# \text{ 开头} \qquad \ell \neq \text{'mount'}\ \pi\ [\text{'as'}\ a]\ (\pi \text{ 非空、无空段})}{\text{E-PARSE-SETTINGS}：\text{"settings 语法错：…"}\ \ell} \quad (\text{X-SETTINGS-PARSE})$$

别名形态固定为四段（`mount <路径> as <别名>`）；缺少路径、段数不是 4、第三段不是 `as` 均抛错并报 E-PARSE-SETTINGS（ModuleTree.kt:128-137）。解析结果为记录：

$$\text{MountDecl} = \langle \text{targetAbsPath} : \text{String},\ \text{alias} : \text{String}? \rangle$$

**路径写法两等价**：斜杠形 `core/math` 与点分完整包名形 `core.math`；点分形在解析期归一化为斜杠形（目录名按约定不含点，ModuleTree.kt:131-132）：

$$\frac{\pi = \pi'.\text{replace}('.',\ '/')}{\text{MountDecl}(\pi,\ a) \equiv \text{MountDecl}(\pi',\ a)} \quad (\text{X-PATH-NORM})$$

### 2.2 挂载校验

校验在 `ModuleTreeDriver.validate()` 中按固定次序执行（ModuleTree.kt:197-218）：装载全部 settings → 完整包名展开（§2.3）→ 逐模块本地名检查 → core 隐式注入（§4）→ 环检测（§7）。

挂载是「在当前模块的命名空间里加一条指针」，**不复制代码**。

$$\frac{m.\text{settings} \vdash \text{mount}\ p\ [\text{as}\ a] \qquad p \notin \text{dom}(\text{nodesByPath})}{\text{E-UNBOUND-NAME}：\text{"模块 } m \text{ 的 settings 挂载了不存在的模块路径 '}p\text{'"}} \quad (\text{X-MOUNT-MISSING})$$

$$\frac{\ell = a \lor (a = \bot \land \text{node}(p).\text{name}) \qquad \ell \in \text{localNames}(m)}{\text{E-DUP-DECL}：\text{"模块 } m \text{ 内本地名 '}\ell\text{' 冲突"}} \quad (\text{X-MOUNT-DUP})$$

`localNames(m)` 初始含 m 的全部子目录名（描述「子目录」），再逐条并入挂载目标名（别名优先）。推论：**一个模块没法挂自己的直接子目录**——目标的目录名已被子目录占用，必报 E-DUP-DECL。

### 2.3 完整包名展开

目标为多段路径的挂载，其**前缀包一并隐式挂载**（`expandPackageMounts`，ModuleTree.kt:223-245）：写 `mount core.math` 后 `core` 也成为本地可见模块名，限定调用 `core.math.gcd(...)` 与按目录名的 `math.gcd(...)` 等价。

$$\frac{m \vdash \text{mount}\ p \qquad p = s_1/\cdots/s_k\ (k \geq 2) \qquad s_1/\cdots/s_i \in \text{nodesByPath} \qquad \text{node}(s_1/\cdots/s_i).\text{name} \notin \text{occupied}(m)}{m \mathrel{+}= \text{mount}\ s_1/\cdots/s_i} \quad (\text{X-PKG-EXPAND})$$

`occupied` 初始为子目录名加既有挂载本地名；**前缀本地名已被占用（子目录/别名/其他挂载目标）则跳过**（不报错）。

示例：

```
# users/users.settings
mount billing              # 挂兄弟模块（斜杠形）
mount core.math            # 挂标准库 math 子包；core 前缀随之隐式可见
mount core.collection as coll   # 挂到本地别名 coll
```

## 3. 可见性计算

### 3.1 可见路径集合（I-20）

可见性**不是查表的布尔值**，而是**计算出来的集合**：每次符号查找都携带当前模块的完整可见路径集合 `visiblePaths`（ModuleTree.kt:17、Checker.kt:136-137）。

$$\frac{}{\text{visiblePaths}(m) = \text{desc}(m) \cup \bigcup\limits_{a \in \{m\} \cup \text{anc}(m)}\ \bigcup\limits_{\text{mount}\ p \in a.\text{settings}} \text{mountReach}(p)} \quad (\text{X-VIS})$$

- `desc(m)`：m 自身与全部后代子树（预序，含 m 自己的 absPath）；
- `anc(m)`：m 的祖先链（不含 m，含根）；
- `mountReach`：挂载图的**传递闭包**——「收编即全收」（用户拍板 Q2，ModuleTree.kt:292-304）：

$$\frac{}{\text{mountReach}(t) = \{t\} \cup \bigcup\limits_{\text{mount}\ p \in t.\text{settings}} \text{mountReach}(p)} \quad (\text{X-MOUNT-REACH})$$

### 3.2 向下流淌与兄弟不可见

$$\frac{a \in \text{anc}(m) \qquad a \vdash \text{mount}\ p}{p \in \text{visiblePaths}(m)} \qquad \textbf{(挂载向下流淌)} \quad (\text{X-DOWNFLOW})$$

$$\frac{s_1, s_2 \text{ 为兄弟模块} \qquad s_1 \nvdash \text{mount}\ s_2 \qquad \text{anc}(s_1) \nvdash \text{mount}\ s_2}{s_2 \notin \text{visiblePaths}(s_1)} \quad (\text{X-SIBLING})$$

三条方向性约束（ModuleTree.kt:316-318：挂载只向下流淌，不上溯）：

| 方向 | 可见性 | 条件 |
|---|---|---|
| 父 → 子 | 可见 | 限定名，且传递（desc 闭包） |
| 子 → 父 | 不可见 | 无例外 |
| 兄弟 ↔ 兄弟 | 默认不可见 | 靠挂载建立 |

引用路径一律**相对当前模块视角**：深层模块 `project/data` 引用标准库同样写 `core.math.gcd`——`core` 经挂载传递可见（ModuleTree.kt:361-364）。

**注意裸名与限定名的差别**：限定解析（§5）走 visiblePaths（含后代），裸名函数回退（§6）走 bareVisibleOf（**不含后代**），二者是不同的集合。

### 3.3 限定子模块解析 visibleChild

`visibleChild(from, name)` 从 from 模块视角解析「名字 → 直接可达的子模块」，三段顺序（ModuleTree.kt:365-392）：

$$\frac{name \in \text{from}.\text{children}}{\text{visibleChild}(\text{from},\ name) = \text{from}.\text{children}[name]} \qquad \textbf{(1. 自身子目录，一层)} \quad (\text{X-VCHILD-DIR})$$

$$\frac{a \in \{\text{from}\} \cup \text{anc}(\text{from}) \qquad a \vdash \text{mount}\ p\ [\text{as}\ \ell] \qquad \ell = name \lor (\ell = \bot \land \text{node}(p).\text{name} = name)}{\text{visibleChild}(\text{from},\ name) = \text{node}(p)} \quad (\text{X-VCHILD-MOUNT})$$

$$\frac{\text{Visible} = \text{visiblePaths}(\text{from}) \qquad \exists p \in \text{Visible}：p \neq \text{from} \land p \in \text{desc}(\text{from}) \land \text{node}(p).\text{name} = name}{\text{visibleChild}(\text{from},\ name) = \text{node}(p)} \quad (\text{X-VCHILD-TRANS})$$

第一阶段/第二阶段未命中时，再查可见集合中**非后代、非已直接挂载**的按目录名匹配项（P28：先精确后代、再挂载传递——同名时后代优先，结果不依赖集合构建序）。「排除已直接挂载者」防止绕过别名定名。**不查祖先的子目录**——兄弟默认不可见（M3）。

### 3.4 裸名可见集

$$\frac{}{\text{bareVisible}(m) = \{m\} \cup \text{corePkgs} \cup \bigcup\limits_{a \in \{m\} \cup \text{anc}(m)}\ \bigcup\limits_{\text{mount}\ p \in a.\text{settings}} \text{mountReach}(p)} \quad (\text{X-BARE})$$

（`bareVisibleOf`，ModuleTree.kt:339-356；`corePkgs` 为 core 根 + 全部子包，见 §4。）

与 X-VIS 的差别：**不含后代子树**。语义是 Kotlin 默认导入只在 core/挂载间透传——根模块裸调子模块函数仍不可见（M3 兄弟/子不可见约束保持）。**子模块的函数在父模块里裸调不到**，必须写限定名或挂载它。

## 4. core 隐式挂载与默认导入

### 4.1 标准库包形态

$$\frac{\text{node}.\text{files} = \emptyset \qquad \text{node}.\text{children} \neq \emptyset}{\text{isStdlibPackage}(\text{node})} \quad (\text{X-STDLIB-SHAPE})$$

目录里只有子包、没有直接 `.subl` 的才算标准库包（ModuleTree.kt:93-94）。用户自己建 `core/` 并往里直接放源文件，它就是普通模块，不触发隐式挂载。

### 4.2 隐式挂载

$$\frac{\text{corePkg} = \text{nodesByPath}["core"] \qquad \text{isStdlibPackage}(\text{corePkg}) \qquad m \neq \text{core} \land m \notin \text{subtree}(\text{core}) \qquad n \in \text{corePkg}.\text{allModules()} \qquad \text{name}(n) \notin \text{localNames}(m)}{m \mathrel{+}= \text{mount}\ \text{absPath}(n)} \quad (\text{X-IMPLICIT-CORE})$$

（`injectCoreMounts`，ModuleTree.kt:254-267。）为所有非 core 自身的模块追加 `mount core` 及其全部子包——等价于自动写了 `mount core + mount core.math + mount core.collection + …`。要点：

- **core 自身与子包不注入**（自挂会成环：core 的子包经 core.settings 互引）；
- **注入的挂载不经本地名冲突检查**：本地同名（子目录名优先于挂载名）时**仅跳过对应子包挂载**（visibleChild 先查子目录）；
- 注入发生在环检测**之前**（ModuleTree.kt:216-217）。

### 4.3 三种调用形式

以挂载了 `mount core.math` 的模块为例，三种写法都对：

```subl
core.math.gcd(12, 8)    // 全限定名（X-VCHILD-MOUNT + X-QCHAIN）
math.gcd(12, 8)         // 短名（前缀包经 X-PKG-EXPAND 隐式挂载）
gcd(12, 8)              // 裸名（core 默认导入 + X-FN-BARE）
```

在根模块里直接裸写另一个用户模块的函数会被拒：

```subl
// 根模块 main.subl——未挂载 util 时
dbl(21)                 // E-UNBOUND-NAME: 没找到函数 dbl——拼写错了？还是没 mount 它所在的模块？
```

用户模块**无需任何 settings** 即可裸名调用标准库符号（`gcd`、`Some`、`size`）与限定调用（`core.collection.size(xs)`）。

## 5. 限定引用 a.b.c

### 5.1 名字链解析

`a.b.c`（表达式层为嵌套 FieldExpr）由 `resolveQChain` 解析（ModuleTree.kt:421-442）：

$$\frac{\text{链} \Rightarrow [a, b, c] \qquad \text{链长} \geq 2 \qquad f.\text{lookupVar}(a) = \bot \qquad \text{node}_0 = \text{node}(\text{modulePath}) \qquad \text{node}_i = \text{visibleChild}(\text{node}_{i-1},\ s_i)\ (i < \text{链长}-1) \qquad \text{node}_{k-1}\ \text{ 存在}}{\text{resolveQChain} = \langle \text{node}_{k-1},\ \text{qualifyIn}(\text{syms}(\text{node}_{k-1}),\ s_k) \rangle} \quad (\text{X-QCHAIN})$$

- 首段是**局部变量则回落值层**（O2 字段优先：`f.lookupVar(segs[0]) != null` → 返回 null，交回原值层逻辑）；
- 链含非名字节点（如数字、调用）→ 不是模块限定；
- 每一段都经 `visibleChild` 相对**当前模块**视角解析——可见性是前提，不是解析后检查。

### 5.2 符号定性

目标模块符号表内按名字定性，**顺序固定**（`qualifyIn`，ModuleTree.kt:406-414）：

$$\frac{}{\text{kind}(s,\ n) = \begin{cases} \text{FUN} & n \in s.\text{funs} \lor s.\text{findFun}(n) \neq \bot \\ \text{CTOR} & n \in s.\text{ctors} \\ \text{STRUCT} & n \in s.\text{structs} \\ \text{ENUM} & n \in s.\text{enums} \\ \text{CLASS} & n \in s.\text{classes} \\ \text{METHOD} & n \in s.\text{methods} \lor n \in s.\text{traitMethods} \\ \text{MISSING} & \text{否则} \end{cases}} \quad (\text{X-QUALIFY-KIND})$$

FUN 的判定含内建函数表（`findFun` 覆盖 print/emptyTuple 等）。

### 5.3 限定调用

`checkQualifiedCall`（CallCheck.kt:1015-1048）按定性分派，走与普通调用**完全相同的公共检查段**：

$$\frac{\text{kind} = \text{MISSING}}{\text{E-UNBOUND-NAME}：\text{"调用模块 } \text{node} \text{ 中未定义符号 } n\text{"}} \quad (\text{X-QCALL-MISSING})$$

$$\frac{\text{kind} = \text{FUN}}{\text{moduleHits}(\text{callee}) = \text{jsOverloadName}(\text{node},\ f) \qquad \text{按目标模块符号表 + 首实参类型挑重载（findCallableIn）}} \quad (\text{X-QCALL-FUN})$$

限定调用 `core.collection.filter(xs, f)` 必须按目标模块重载路由到 List 版（而非先注册的 Set 版），否则误报类型不符（CallCheck.kt:1024）。

$$\frac{\text{kind} = \text{CTOR}/\text{STRUCT}}{\text{checkCtorCall}/\text{checkStructCall}\ \text{以 node.absPath 为模块路径}} \quad (\text{X-QCALL-CTOR})$$

$$\frac{\text{kind} = \text{METHOD} \qquad \text{args} = \emptyset}{\text{E-NO-SELF}：\text{"方法 } n \text{ 缺接收者"}} \quad (\text{X-QCALL-NOSELF})$$

$$\frac{\text{kind} = \text{METHOD} \qquad \text{args} \neq \emptyset \qquad \text{resolveDict}(n,\ \text{type}(\text{args}[0])) = r}{\text{dictHits} = r.\text{dictName} \qquad \text{moduleHits}(\text{callee}) = \text{MODULE\_METHOD\_MARKER} \qquad \text{首实参即接收者，其余实参配形参}} \quad (\text{X-QCALL-METHOD})$$

限定方法调用（`core.show(p)`）在 codegen 走**字典分发**：遇到 MODULE_METHOD_MARKER（ModuleTree.kt:180）时，首实参作 `__self`、剩余实参为真实参数（JsCodeGen.kt:1390、1418）。

限定名作**值**引用（非调用位）同样解析：缺失报 E-UNBOUND-NAME（「模块 X 中无符号 Y」），命中则记 moduleHits 并给出函数类型 / 枚举构造子多态类型 / 合成类型（Checker.kt:953-972）。

### 5.4 限定类型

`c.Point` 形态的 QualifiedType 由 `resolveTypeModule` 解析（ModuleTree.kt:445-451；检查在 Symbols.kt:337-348）：

$$\frac{\text{resolveTypeModule}(t) = \bot \qquad \textbf{(a)}}{\text{E-UNBOUND-NAME}：\text{"未知模块限定类型 } t\text{（模块不可见或不存在）"}} \quad (\text{X-QTYPE})$$

$$\frac{\text{resolveTypeModule}(t) = \text{node} \qquad \text{syms}(\text{node}).\text{baseOf}(\text{namedT}(t.\text{name})) = \bot \qquad \textbf{(b)}}{\text{E-UNBOUND-NAME}：\text{"模块 } \text{node} \text{ 中无类型 } t.\text{name}}} \quad (\text{X-QTYPE-MISS})$$

（a）模块不可见或不存在、（b）模块内无该 struct/enum/class/别名/基类型，分别报错。

## 6. 跨模块构造子裸名回退

### 6.1 回退顺序

裸名调用（`NameRef` 位 callee）且**无接收者**（`selfT == null`）时，构造子/结构体按下列顺序查找（CallCheck.kt:170-181）：

$$\frac{\text{selfT} = \bot \qquad n \in \text{syms}(\text{modulePath}).\text{ctors}}{\text{checkCtorCall(local,}\ n)} \qquad \textbf{(1. 本模块)} \quad (\text{X-CTOR-LOCAL})$$

$$\frac{\text{selfT} = \bot \qquad n \in \text{syms}(\text{modulePath}).\text{structs}}{\text{checkStructCall(local,}\ n)} \qquad \textbf{(2. 本模块)} \quad (\text{X-STRUCT-LOCAL})$$

$$\frac{\text{selfT} = \bot \qquad \text{moduleTree} \neq \bot \qquad \exists p \in \text{visiblePaths}：n \in \text{syms}(p).\text{ctors}}{\text{checkCtorCall(syms}(p),\ n)\ \text{（顺序取可见路径）}} \quad (\text{X-CTOR-FALLBACK})$$

$$\frac{\text{selfT} = \bot \qquad \text{moduleTree} \neq \bot \qquad \exists p \in \text{visiblePaths}：n \in \text{syms}(p).\text{structs}}{\text{checkStructCall(syms}(p),\ n)\ \text{（顺序取可见路径）}} \quad (\text{X-STRUCT-FALLBACK})$$

注释（#4 修复，CallCheck.kt:174）明言：「构造子/结构体跨模块可见——裸名 Ok/Err/… 也查可见模块（含 core 标准库）」。**注意此处走的是 `visiblePaths`（含后代子树），而非 bareVisibleOf**——构造子的裸名回退集合比函数的更宽（待核：这是否为有意的对称差异）。

为何方法路径（selfT 已知）不参与此回退：O2 决策——避免同名截胡（CallCheck.kt:171）。

**已知边界（P0 限制）**：多模块同名构造子取**末者**，可能导致静默覆盖——书写跨模块代码时应当用限定引用消歧。

### 6.2 函数裸名回退

自由函数的裸名解析是另一条路径（`findCallable`，CallCheck.kt:523-531）：

$$\frac{\text{findCallableIn}(\text{syms}(\text{modulePath}),\ n,\ \text{argTypes}) = f}{\text{findCallable} = \langle f,\ \text{modulePath} \rangle} \qquad \textbf{(1. 本模块优先)} \quad (\text{X-FN-LOCAL})$$

$$\frac{\textbf{(1) 未命中} \qquad \exists p \in \text{bareVisible}(\text{modulePath}) \setminus \{\text{modulePath}\}：\text{findCallableIn}(\text{syms}(p),\ n,\ \text{argTypes}) = f}{\text{findCallable} = \langle f,\ p \rangle} \quad (\text{X-FN-BARE})$$

v3.0 语义：Kotlin 默认导入只在 core/挂载间透传——裸名可直接调用 core 函数，但**根模块裸调子模块函数不可见**（M3 兄弟/子不可见约束保持，ModuleTree.kt:337-338）。`findCallableIn` 按实参首类型从重载组挑选匹配项（CallCheck.kt:535-547）。

### 6.3 示例

```subl
// 根模块 main.subl——未经任何挂载
@impure
fun main() : Null {
    var o : Optional[Nat] = Some(3)      // Some 走 X-CTOR-FALLBACK 命中 core/collection
    print(toStr(o))                      // print 是内建（findFun 命中，无模块前缀）
}
```

```subl
// billing/billing.subl
fun total(c : Nat) : Nat = c * 2
```

```subl
// 根模块 main.subl——根不能写 settings（X-ROOT-NO-SETTINGS），且 billing 是子目录
billing.total(7)        // 限定调用：X-VCHILD-DIR 命中子目录 → X-QCHAIN → X-QCALL-FUN
total(7)                // 裸名：X-FN-BARE 不含后代 → E-UNBOUND-NAME
```

## 7. 环形挂载

### 7.1 环检测

挂载图 DFS 三色标记（0=未访问、1=栈中、2=完成）在**全部模块的挂载声明**（含 core 隐式注入）上跑（ModuleTree.kt:270-290）：

$$\frac{\text{dfs}(p)\ \text{遇到}\ q \qquad \text{state}(q) = 1\ (\text{栈中})}{\text{E-CIRCULAR-MOUNT}：\text{"挂载链成环："}\ \text{stack}[\text{indexOf}(q)..] + [q]\ \text{以 " -> " 连接}} \quad (\text{X-CYCLE})$$

**只报第一个环**（`cycleReported` 标志，ModuleTree.kt:280-284）；不在 nodesByPath 中的挂载目标跳过（已由 X-MOUNT-MISSING 报告）。环检测在整个 validate 的最后一步，因此 E-CIRCULAR-MOUNT 与 E-UNBOUND-NAME / E-DUP-DECL 可能同袋并存。

### 7.2 闭包截断

`mountReach` 对环做了独立保护：遇正在访问的路径直接返回空集截断（ModuleTree.kt:294），避免 visiblePathsOf / bareVisibleOf 的递归死循环——环已另行报错，可见性计算不卡死。

$$\frac{t.\text{absPath} \in \text{visiting}}{\text{mountReach}(t) = \emptyset} \quad (\text{X-CYCLE-REACH})$$

示例（users.settings 含 `mount billing`、billing.settings 含 `mount users`）：

```
E-CIRCULAR-MOUNT: 挂载链成环：users -> billing -> users
```

## 8. 多模块三阶段检查

### 8.1 阶段划分

`MultiModule` 是目录模式的编译驱动（MultiModule.kt:23-67）：

| 阶段 | 内容 | 前置依赖 |
|---|---|---|
| 解析 | 每个模块的全部 .subl 按序合并为**一个** FileAst（同模块共享一个 Symbols） | 无 |
| A | prelude + 符号收集；全模块先落全局符号表 allSymbols | 解析完成 |
| A′ | 注解处理器：AST → AST 变换（可选，§8.5） | A |
| B | finishCollect：类型可解析性 + impl 完整性 + pure 事实 + 子类型类父链 | **全树符号齐备** |
| C | checkAllBodies：声明体 + 顶层语句检查 | B 的类型/impl/pure 信息 |

**为何必须分阶段**：B 的跨模块类型可解析性与 impl 检查需要全树符号齐备——单模块顺序检查无法引用尚未收集的兄弟模块符号。

### 8.2 阶段 A：全局符号表

$$\frac{\text{node} \in \text{tree}.\text{allModules()} \qquad \text{ast} = \text{merge}(\text{node}.\text{files})}{\text{Checker}(\text{ast},\ \text{modulePath} = \text{node}.\text{absPath},\ \text{allSymbols},\ \text{moduleTree})\ \text{collectPrelude} \to \text{collectDecls} \to \text{allSymbols}[\text{absPath}] = \text{syms}} \quad (\text{X-PHASE-A})$$

`allSymbols : Map<absPath, Symbols>` 是全局符号表；每个 Checker 持有 `modulePath`、`allSymbols`、`moduleTree` 三件套，`visiblePaths` 即由 moduleTree 计算（Checker.kt:18-22、136-137）。单文件模式（`Checker(file)`）不受影响：modulePath 为空、moduleTree 为 null、visiblePaths 为空集。

### 8.3 阶段 B/C

$$\frac{\forall \text{chk} : \text{chk}.\text{finishCollect}(\text{ast}_{\text{module}})}{\textbf{(B)}} \qquad \frac{\forall \text{chk} : \text{chk}.\text{checkAllBodies()}}{\textbf{(C)}} \quad (\text{X-PHASE-BC})$$

B 检查类型可解析性（含 X-QTYPE 的限定类型）、impl 完整性与 pure 事实；C 检查声明体与顶层语句。所有模块的 Checker 独立跑 B、再独立跑 C——跨模块引用经 allSymbols + visiblePaths 在各自模块的视角下解析。

### 8.4 main 全树唯一

$$\frac{|\{ p : \text{ast}(p) \vdash \text{DeclEntry}(\text{FunDecl}(\text{"main"},\ \emptyset,\ \text{body} \neq \bot)) \}| \geq 2}{\text{E-DUP-DECL}：\text{"多个模块声明了入口 main："}\ p_1,\ p_2,\ \ldots} \quad (\text{X-MAIN})$$

（MultiModule.kt:129-140。）`main` 可位于**任意模块**，但整个工程**有且仅有一个零参 fun main()**；全局唯一性在阶段 C 之后于模块层检查（JsCodeGen.kt:407 注释）。此外单模块内 main 带形参或类型参数报 E-MAIN-PARAMS（Symbols.kt:245）：

$$\frac{\text{FunDecl}(\text{"main"}) \land (\text{params} \neq \emptyset \lor \text{theory} \neq \emptyset)}{\text{E-MAIN-PARAMS}：\text{"入口函数 main 不能有形参或类型参数。写成 fun main() { … }"}} \quad (\text{X-MAIN-PARAMS})$$

### 8.5 注解处理器插桩与重查

`processModules`（MultiModule.kt:85-119）把注解处理器插在 A 与 B/C 之间：对每个模块跑一次处理器（输入模块路径 / 合并 AST / 符号表 / 诊断汇入闭包），返回变换后的 AST。

$$\frac{\exists p : \text{processor}(p) \neq \text{ast}(p)}{\textbf{重跑阶段 A（重建每模块 Checker 与符号表）} \to \textbf{重跑 B/C} \qquad \text{袋内去重吸收重复诊断}} \quad (\text{X-PROCESSOR-RERUN})$$

处理器产出视为**新代码**：模块间交叉引用的重新检查只在模块层做才完整；已检查过的情形也兼容（重跑 B/C）（MultiModule.kt:82-84）。处理器自身的诊断单独成袋返回，不污染主袋。

### 8.6 诊断合并与过滤

$$\frac{\text{bag}.\text{absorb}(\text{chk}.d)\ (\forall \text{chk}) \qquad \text{bag}.\text{dropSupplementsOutside}("")}{\textbf{补充级诊断只保留根模块的}} \quad (\text{X-DIAG-FILTER})$$

（MultiModule.kt:142-144。）挂进来的模块（core 标准库等）内部的推导/方法糖是噪声，补充级诊断自动过滤；模块层错误（挂载目标缺失、settings 语法、挂载成环）在树校验阶段**最先**报出——validate() 在 MultiModule 构造期即完成。

### 8.7 命令与产物

```
sublimation check   <目录>            类型检查整个工程（扫全树）
sublimation compile <目录> -o out.js  语义通过后生成合并 JS
```

check/compile 传**目录**即走模块系统；目录模式只支持这两个命令，其它命令回退「目录模式仅支持 check / compile（脚本目录请用 run-script）」并退出码 2（Main.kt:243-247）。【CLI 无 `run` 子命令——误输入回退 USAGE、退出码 2；工程执行走 run-script 目录回退或 compile + node。】

## 9. JS mangle 与合并编译

### 9.1 名字改编

$$\frac{}{\text{mangleModule}(\text{absPath}) = \text{absPath}.\text{trim}('/').\text{replace}('/',\ '\_').\text{replace}(\text{非法字符},\ '\_')} \quad (\text{X-MANGLE})$$

$$\frac{}{\text{moduleJsName}(\text{absPath},\ n) = \begin{cases} \text{jsMangle}(n) & \text{absPath} = ""\ (\text{根，无前缀}) \\ \text{mangleModule}(\text{absPath}) + "\_\_" + \text{jsMangle}(n) & \text{否则} \end{cases}} \quad (\text{X-JSNAME})$$

（ModuleTree.kt:146-167；根无前缀为用户拍板 Q4a。）

`jsMangle` 处理 JS 保留字（前缀 `$`，如 `\$in`）与符号名（转 `op_` + 十六进制码点序列）；`$` 在 JS 标识符里合法，安卓注解处理器生成的合成名（`recomposion$Box$1`）直接保留（ModuleTree.kt:150-160）。

### 9.2 重载标签

v2.0 决策 92 配套：同名重载按**首参类型基名**加 JS 后缀标签区分（ModuleTree.kt:169-177）：

$$\frac{}{\text{fnTag}(f) = \begin{cases} \text{"v0"} & f.\text{params} = \emptyset \\ \text{类型基名} & \text{首参为 NamedType} \\ \text{"tup"} & \text{首参为 TupleType} \\ \text{"fn"} & \text{首参为 FunType} \\ \text{"v0"} & \text{否则} \end{cases}} \quad (\text{X-FNTAG})$$

重载注册已保证首参 render 不同，故基名在重载组内唯一；声明侧与调用侧（moduleHits）共用同一规则。带重载时调用点留痕为 `moduleJsName + "$" + fnTag`（`jsOverloadName`，CallCheck.kt:415），如 `util__dbl$v0`。

### 9.3 合并产物与入口调用

$$\frac{}{\text{generateJs}() = \text{JsCodeGen}.\text{generateUnits}(\text{asts.toList()},\ \bigcup \text{hits})} \quad (\text{X-MERGE-JS})$$

`MultiModule.generateJs()` 先把全树各 Checker 的调用留痕（dictHits / moduleHits / consHits / sugarHits / asyncAwaitHits / rangeHits / deepCopyHits / listMethodHits 等，MultiModule.kt:152-196）合并，再调用 `generateUnits` 生成**单个 JavaScript 文件**——全部模块合成一份输出，顶层名字靠模块前缀隔离（M8）：

| 模块 | 符号 | JS 名 |
|---|---|---|
| 根 `""` | `main` | `main` |
| `core/math` | `gcd` | `core_math__gcd` |
| `util` | `dbl` | `util__dbl` |

入口调用追加在产物尾部（JsCodeGen.kt:402-413）：根模块顶层语句（StmtEntry）先生成，随后找到首个零参 main 的模块、输出其 mangled 全名加 `()` 的调用行；`main` 天然生成 `async function`（JsCodeGen.kt:718-719），是 @impure 允许的异步上下文。

限定调用的 moduleHits 留痕把 callee 位直接替换为目标的 JS 全名（Checker.kt:961、CallCheck.kt:1027）；限定方法走 MODULE_METHOD_MARKER 字典分发（§5.3）。

### 9.4 内建例外

$$\frac{n \in \{\text{"Some"},\ \text{"None"},\ \text{"null"},\ \text{"true"},\ \text{"false"}\}}{\text{moduleHits}\ \text{不加模块前缀——JS 根作用域函数/字面量}} \quad (\text{X-BUILTIN-NO-PREFIX})$$

（CallCheck.kt:632-635。）否则 core 标准库模块内 `Some(x)` 会被错生成成 `core_collection__Some`。

另：`listMethodHits` 把 core/collection 的 List 方法调用（map/size/…）标记映射到 JS 原生数组方法（P9，CallCheck.kt:420-424）——仅 `core/collection` 模块 + 首形参为 List 才算，用户自定义 List 函数不误中。

## 10. 脚本模式与多脚本隔离

### 10.1 多脚本隔离

$$\frac{s_1, s_2 \in \text{targets} \qquad s_1 \neq s_2}{\text{interp}.\text{runScript}(s_1) \perp \text{interp}.\text{runScript}(s_2)\ \textbf{（互不共享符号/状态，各自独立运行，无需 main）}} \quad (\text{X-SCRIPT-ISO})$$

（Main.kt:29、372-401。）`run-script <file.subs> [<file2.subs> …]` 接受多条脚本路径：每个 `.subs` 文件经 Checker 类型检查后由解释器直接求值，**顶层语句直接运行**，多条脚本互不共享（Main.kt:350-356）。每个脚本一次 `[脚本] <文件名>` 提示、一次 `[完成] 脚本执行结束`；`--global-inference` 旗标开启全局类型推导（省略类型/可变性/效应标注时自动填充）。

### 10.2 目录回退

$$\frac{f \text{ 是目录} \qquad \text{subsIn}(f) \neq \emptyset}{\forall s \in \text{subsIn}(f) : \text{独立运行}\ s} \qquad \frac{f \text{ 是目录} \qquad \text{subsIn}(f) = \emptyset}{\text{interp}.\text{runDir}(f)\ \textbf{（按 .subl 工程、fun main() 入口解释执行）}} \quad (\text{X-SCRIPT-DIR})$$

（Main.kt:386-401。）目录下有 `.subs` 时逐个独立运行；没有 `.subs` 时按 `.subl` 工程以 `fun main()` 为入口解释执行——run-script 目录回退是**工程执行的入口**（CLI 无 run 子命令，_langfacts.md §8）。

### 10.3 与工程模式的分界

| 维度 | 脚本模式（.subs） | 工程模式（目录 = 模块） |
|---|---|---|
| 入口 | 无需 main，顶层语句直接运行 | 全树唯一零参 fun main() |
| 符号共享 | 每文件独立，互不共享 | 同目录 .subl 共享一个 Symbols |
| 模块系统 | 不适用（单文件检查） | 目录树 + settings 挂载 + 可见性 |
| 命令 | run-script | check / compile（目录模式仅此二者） |
| 执行 | 解释器直接求值 | compile 生成合并 JS（run-script 目录回退亦可解释执行） |
| 代码生成 | 无 JS 产物 | 单个 JS 文件，模块前缀隔离 |

## 13. 已知边界与待核

- **根模块无 settings**（P0 限制）：根模块只能靠子目录与向下流淌获得依赖；若工程需要根模块显式挂载，目前只能在子模块内挂载后经 X-DOWNFLOW 透传（待核：是否有计划解除）。
- **多模块同名构造子取末者**（P0 限制）：静默覆盖风险，需限定引用消歧。
- **构造子回退用 visiblePaths、函数回退用 bareVisibleOf**：前者的裸名可见集合更宽（含后代子树）——这与「子模块函数在父模块裸调不到」的口径不对称（待核：确认为有意设计还是历史遗留）。
- **注入挂载不经本地名冲突检查**：core 隐式挂载与本地同名子目录并存时跳过对应子包，不报 E-DUP-DECL（ModuleTree.kt:251-253）。
- **fnTag 重载标签按首参基名**：首参 render 不同的前提由重载注册保证（ModuleTree.kt:172）；运行时 JS 名与声明侧的一致性由声明/调用共用同一规则维持。
