## 〇、严重度汇总

| 严重度 | 判据 | 数量 |
|---|---|---|
| **高** | 会误导用户写出编译不过的代码、导致两种执行模式行为分裂、或动摇证明系统健全性 | 8 |
| **中** | 数字／引用／术语错误，功能缺口，健壮性隐患，但不破坏核心语义 | 21 |

最紧急的三项：

1. **根文档三篇的 `when` 示例全部使用已废弃的 `->` 分隔符**，用户照抄必然编译失败，而根文档是最高权威（§3.1）；

3. **代码生成无逐字节快照测试**，重构后端时无法检测产物回归（§2.8）。

## 二、代码层问题

### 2.1 陈旧注释与代码行为矛盾【高】

**问题**：`Symbols.theorems` 字段的注释与实际登记判据直接矛盾。

- 注释（`Types.kt:364-365`）：「无 @theorem 注解——判据即登记；有体定理照常生成运行时代码」
- 实际（`Diffusion.kt:335`）：`isTheoremFun(d) = "theorem" in d.annotations`，**必须有 `@theorem` 才登记**

这与规范第四卷 §7.2「只有 `@theorem` 显式标注的函数才是定理函数」一致，代码是对的，**注释是错的**。注释描述的是早期「纯 + 返回 Null 即定理」的旧判据。误导后来者以为无需标注即可进定理空间。

**同类**：`Evaluator.kt:476` 注释写「@vararg 可变元组名字特判」，但语言已无 `@vararg` 注解（术语表附录：`@vararg` 被 `@list` 取代）。注释应改为「`listOf`/`setOf` 内建特判」。

**修复**：改正 `Types.kt:364-365` 与 `Evaluator.kt:476` 两处注释。

### 2.2 死代码与不可达分支【低】

| 位置 | 问题 |
|---|---|
| `Kind.IN` | Lexer 的 keywords 表无 `"in"`（`in` 已去关键字化为普通 IDENT，`Lexer.kt:44`），故 `Kind.IN` 从不被产出。但 `Parser.kt:65` 的 `defNameKinds` 与 `LspAnalysis.kt:926` 仍引用它——两处消费永不可达 |
| `Kind.BACKSLASH` | Lexer 产出 `\` → BACKSLASH（`Lexer.kt:129`），但 Parser 不再消费（旧 `\x => …` lambda 已移除，`Parser.kt:1662` 注释自承）。词法每遇 `\` 都产 token，语法层永不消费 |
| `Lexer.kt:138` 的 `'∵' -> BECAUSE`／`'∴' -> THEREFORE` | 注释自承「实际被 isSymbolStart 分支先收——单分支不可达，仅为文档保留」。`∵`/`∴` 在 `Lexer.kt:101` 已被拦截 |

**修复**：清理死枚举或在注释中统一标注「保留但不可达」，避免 LSP 高亮逻辑引用死枚举。

### 2.3 占位文件【低】

`compiler/.../checker/Purity.kt` 全文仅 KDoc 注释（`Purity.kt:1-10`），无任何逻辑；纯度检查实际分散在 `Symbols.kt`／`CallCheck.kt`／`Checker.kt`。规范第六卷的纯度规则因此没有单一实现落点。属已知技术债，注释说明「待类型级纯度／代数效应落地后再行拆入」。

**建议**：要么把分散的纯度逻辑收拢进 `Purity.kt`，要么删除该空文件以免误导。

### 2.4 深拷贝判定的双实现偏差【高】

**问题**：绑定／赋值是否触发深拷贝，在编译模式与脚本模式由两套独立逻辑判定，且**判据不同**：

- 编译模式 `Checker.binderNeedsCopy`（`Checker.kt:832-834`）：目标或源为 `MutType` **或** `@ref` 时拷贝，双 `@ref` 时别名——与规范第六卷 §6.6 一致；
- 脚本模式 `Evaluator.bindCopy`（`Evaluator.kt:106-107`）：**仅看 `@ref` 标记，不看 `MutType`**。

`Evaluator.kt:102-104` 的注释自承这是「M5 已知偏差」。后果：一个普通 `@mut T` 变量（无 `@ref`）在编译模式绑定会深拷贝，在脚本模式却是别名共享——**同一份代码两种模式行为分裂**，违反规范不变量（值语义应一致）。

**修复**：以规范第六卷 §6.6 的判定表为准，统一 `Evaluator.bindCopy` 与 `Checker.binderNeedsCopy`，最好抽出单一共享函数供两侧调用。

### 2.5 `E-ANY-CALL` 与 `E-ANY-STRUCT` 的逃逸不对称【中】

- `E-ANY-STRUCT`（`CallCheck.kt:28,660`）有 `uncheckedDepth == 0` 守卫，可被 `unchecked` 逃逸；
- `E-ANY-CALL`（`CallCheck.kt:751-753`）**无**该守卫，即使包在 `unchecked` 内仍报错。

规范第三卷 §2.4 已如实记录这一不对称。**需作者确认这是有意设计还是遗漏**：若「涉 Any 的调用推导失效」是不可逃逸的硬约束，则当前行为正确，规范也已如此写；若应当可逃逸，则 `E-ANY-CALL` 缺守卫是缺陷。

### 2.6 全局类型推导仅存在于解释器【中】

`GlobalInference.kt` 完整实现了返回类型推导、SCC 假设-验证、效应推断，但**只有解释器路径调用**（`Interpreter(globalInference=true)`），编译器 `Checker` 无对应能力。后果：脚本模式能自动推导返回类型的函数，切到编译模式可能报 `E-TYPE-MISMATCH`。

这与规范第九卷 §6.1「全局类型推导是脚本模式专属」一致——是**有意的设计边界**，非缺陷。但风险在于：用户可能误以为脚本里验证过的代码可直接编译。建议在文档中强化「脚本模式专属，编译模式标注必须显式」的提示。

### 2.7 `listOf`/`setOf` 双通道维护【中】

解释器 `Evaluator.kt:477-478` 直接构造 `ListV`/`SetV`；代码生成 `JsCodeGen.kt` 按同名特判打包为 JS 数组。两处独立维护，一方改动另一方未同步即行为分裂。与 §2.4 同属「同一语义两处实现」的系统性风险。

### 2.8 代码生成无逐字节快照测试【高】

端到端测试（`E2ETest.kt:33`、`DailyScriptsE2ETest.kt:31`）只断言 `node` 退出码与 stdout，**不对比生成的 JS 文本**。后果：`JsCodeGen` 重构时无法检测产物回归，规范不变量 I-7「普通模式产物逐字节不变」缺乏自动化保障。

**修复**：为代表性源文件建立 JS 产物快照测试（golden file），重构时逐字节比对。

### 2.9 解释器健壮性缺口【中】

| 缺口 | 证据 | 后果 |
|---|---|---|
| 无递归深度限制 | `Evaluator.kt` 全文无 depth/maxDepth | 用户写无限递归触发 JVM `StackOverflowError`，而非友好运行时错误 |
| 整数除零无诊断 | `Evaluator.kt:250,281` Double 除法得 Infinity/NaN 不抛异常；Long 路径 `res.toLong()` 丢精度 | 除零静默产生错误值，无 `W-DIV-ZERO` 之外的运行时保护 |

编译模式有 `W-DIV-ZERO`（字面量除零警告），但运行时的非常量除零在两种模式下都无保护。

### 2.10 JS 字符串转义不完整【中】

`JsCodeGen.q()`（`JsCodeGen.kt:1580-1581`）只转义 `\`、`"`、`\n`、`\r`、`\t`。若源码字符串含 U+0000–U+001F 的其他控制字符，或 U+2028/U+2029（JS 中是行终止符），生成的 JS 会语法错误或语义异常。

**修复**：对 U+0000–U+001F 全范围及 U+2028/U+2029 做 `\uXXXX` 转义。

### 2.11 标识符 mangling 命名空间未隔离【低】

`ModuleTree.kt:156-157` 把非 ASCII 标识符转为 `op_XXXX` 十六进制序列。`op_` 前缀不与用户标识符命名空间隔离：用户若定义名为 `op_0041` 的函数，会与 `A` 的 mangle 结果冲突。

**修复**：mangle 前缀改用不可能出现在合法标识符中的形式，或维护冲突检测。

### 2.12 性能：注解查找线性扫描【低】

`Checker.kt:291,593,821,859` 等多处 `"impure" !in fn.annotations`，`annotations` 是 List，每次 O(n)。注解数量通常很少，实际影响可忽略。`Diffusion.kt` 的 facts 已从 ArrayList 改为 LinkedHashSet（`Diffusion.kt:12-13`），此前的 O(n²) 隐患已修复。

### 2.13 激进模式池构造的健全性——已核实合规【无问题】

子审查曾担忧激进模式从目标（goals）收集项会引入无约束新项（规范第四卷 §9.3 禁止）。经核实：

- `Prop.kt:428` 的 `extraTerms = extraGoals.flatMap { groundTerms(it) }` 与 `Diffusion.kt:247` 的 `buildKeyPool(gamma, listOf(goal), …)` 中，**目标项只进入实例化候选池 `keyTerms`，不进入事实集 `facts`**（`facts` 仅来自 `normalizeFacts(gamma)`）。

这与规范第四卷 §5.3「额外目标只贡献实例化候选、不加入事实」及 §9.7 池边界完全一致。**合规，无需修改。**

## 六、总体评价

工程的**核心语义实现扎实**：证明系统的健全性底线（目标项不作事实、合成类型恒放行、非密封类型只与 Null 相容）经核实均与规范一致；激进模式的三维池构造未违反「新项须有约束来源」的规范约束（§2.13）；模块系统、类型类字典、上下文弥散的块回溢／lambda 隔离等关键机制实现正确。

主要问题集中在三类：

1. **文档滞后于代码**——测试数、诊断码数、废弃术语、根文档示例普遍过时，且根文档因「不得修改」约束而积重难返；
2. **两套并行实现的一致性风险**——深拷贝、`listOf`/`setOf`、全局推导在编译与脚本两模式各有实现，缺乏共享与一致性测试；
3. **诊断体系的双向一致性未达成**——源码发出 106 码，而两张 explain 表分别为 93、89，13 个码（含 3 个错误级）无处可查。

建议下一开发回合优先处理第一梯队四项，并以本规范十一卷为符合性基准，逐步收敛文档与实现的偏差。
