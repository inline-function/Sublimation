## 一、基础方言没有子类型是什么体验

凝华的基础方言里，类型之间只有两种关系：严格相等（≡）和宽松相容（≈）。这两种关系回答的都是"这两个类型是不是同一个"，不回答"这个类型是不是那个类型的子集"。

这意味着你无法写出"接受任何满足某条件的类型"这样的声明。举一个具体场景：你想写一个函数，接受任何"可以比较大小"的值并返回较大者。在基础方言里你有两条路：

**路线 A：用类型类约束。**

```subl
class Ord[a] {
    fun compare(x: a, y: a): Int
}

impl Ord for Nat {
    fun compare(x: Nat, y: Nat): Int = { => /* ... */ }
}

fun max[T: Ord](x: T, y: T): T {
    if (compare(x, y) >= 0) x else y
}
```

这条路能走通，但代价是：你必须为每个需要的类型写 impl，而且运行时存在一份类型类字典用于方法分派。如果你只需要"类型层面上的约束"而不需要方法分派，这份开销就是多余的。

**路线 B：用 Any 放宽。**

```subl
fun max(x: Any, y: Any): Any {
    // 体内必须手动 is 判别或 unchecked
    // ...
}
```

Any 只在期望位（形参、返回类型、默认值）放宽——实参是 Any 而期望是具体类型时仍然严格。所以这条路的代价是：你丢失了类型信息，体内要么手动判别，要么进 unchecked 块放弃检查。

这两条路各自有合理的使用场景，但中间有一个缺口：**纯类型层的约束、零运行时开销、不需要方法分派**。这正是 Kernel Fω＜: 方言要填补的位置。

基础方言里还有三处带方向性的类型关系，但它们都不是子类型：

1. **视图转换**：@mut T 可以隐式转为 T，但转换点就是深拷贝点；反向恒不成立。这是所有权语义，不是包含关系。
2. **数值升格**：Nat/Int/Rat 在宽松相容下按 rank 放行，但这个放行不传递到名义类型——两个不同的 struct 不会因为字段恰好是数值类型就合并。
3. **变体入联合**：T 可以流向 T | U，但这只在赋值和返回位生效，不构成一般的判定关系。

理解这三点很重要：启用方言后，这三处关系的处理方式**不变**。方言不会把它们重新解释为子类型。

再举一个更具体的例子来说明缺口的形状。假设你在写一个容器库，想表达"这个函数接受任何元素类型为 Nat 子类型的列表"：

```subl
// 基础方言：你只能写成这样
fun sum[T: Numeric](xs: List[T]): Nat {
    // 需要 Numeric 类型类提供 add 和 zero
    // 即使你根本不关心 T 的具体身份，只要它是 Nat 就行
}
```

这里 `Numeric` 类型类同时承担了两个职责：约束 T 的类型范围（它必须是数值类型），以及提供运算方法（add、zero）。如果你只需要前者——"T 是 Nat 的子类型就够了，我不需要在体内调用任何方法"——类型类就是过重的机制。有界量化正是为了把这两个职责分开而存在的。

## 二、方言引入的三样东西

启用 --types=fomega-bound 旗标后，你在基础方言之上获得三样新能力。以下代码示例标注为"方言目标形态"的，均为**尚未实现**的规格描述，当前编译器不接受。

### 2.1 有界量化

基础方言的类型参数是无界的：[T] 表示"T 可以是任何类型"。方言允许你给类型参数加上界：

```subl
// 方言目标形态（尚未实现）
fun first[X <: Pair[Nat, Nat]](p: X): Nat = p.first
```

[X <: Pair[Nat, Nat]] 的意思是：X 可以是 Pair[Nat, Nat] 本身，或者它的任何子类型（如果有的话）。调用时，编译器会检查你传入的类型实参是否满足这个界。

在基础方言里，要达到类似效果只能用类型类：

```subl
// 基础方言写法
class HasFirst[a] {
    fun first(x: a): Nat
}

fun first[T: HasFirst](p: T): Nat = p.first(p)
```

有界量化把"类型层约束"从类型类的运行时字典机制中分离出来，变成纯粹的编译期检查，完全擦除、零运行时开销。

### 2.2 真正的 kind

基础方言的 kind 是一个数字（arity）：List 的 kind 是 ★ → ★（接受 1 个真类型、返回真类型），Pair 的 kind 是 ★ → ★ → ★。这足以支撑 List[Nat]、Optional[T] 这类单层应用，但**禁止嵌套**：

```subl
// 基础方言：报错 E-NON-PATTERN-HKT
fun compose[F[_], G[_]](x: F[G[Nat]]): F[G[Nat]] = x
```

F[G[Nat]] 里 G 本身是一个 arity > 0 的构造子形参，嵌套在另一个构造子形参 F 的应用里——基础方言明令禁止这种写法。

方言把 kind 从扁平的 ★ⁿ → ★ 升级为一般的 𝕂₁ → 𝕂₂，于是嵌套应用合法了：

```subl
// 方言目标形态（尚未实现）
fun compose[F[_[_]], G[_]](x: F[G[Nat]]): F[G[Nat]] = x
```

这里 F 的 kind 是 (★ → ★) → ★——它接受的不是一个真类型，而是一个类型构造子。这种表达力在基础方言里不存在。

### 2.3 子类型判定 <:

基础方言的 ≈ 和 ≡ 都是对称的：A ≈ B 成立当且仅当 B ≈ A 成立。方言引入了一个**有方向的**判定 <:，读作"是……的子类型"。

<: 只在三个新增位置启动：有界量化的界检查、显式子类型化、方言新增构造子之间的比较。基础方言既有的 ≈ 路径一条也不会被 <: 取代或收紧。

这三样东西是互相支撑的：有界量化需要 `<:` 来检查界是否满足；真正的 kind 让有界量化的界可以包含嵌套构造子应用；`<:` 本身又依赖 kind 系统来确定哪些类型可以参与比较。它们是一个整体，不能单独启用其中某一个——这也是为什么旗标只有两档（基础的 `sub` 与方言的 `fomega-bound`），而不是把这三样做成独立开关的组合。

## 三、最反直觉的一点：界必须完全相等

这是整份指南最重要的一节，请仔细阅读。

### 3.1 规则是什么

方言采用 Kernel 规则来比较有界量化类型。这条规则要求：**两个有界量化类型只有在界完全相等时才可以比较子类型关系**。

具体来说，要判断 ∀X<:τ₁. σ₁ 是否是 ∀X<:τ₂. σ₂ 的子类型，前提是 τ₁ ≡ τ₂（β 归一后的结构相等）。如果界不相等，无论它们之间的子类型关系多么"显然"，判定直接失败。

所以即使 U <: Top 显然成立，∀X<:Top. T 和 ∀X<:U. T 之间也**没有**子类型关系。

### 3.2 这不是偷懒，是刻意取舍

这个限制是用表达力换可判定性。

更强的 Full 规则允许在推导过程中"重绑定"界——比较 ∀X<:τ₁. σ₁ 和 ∀X<:τ₂. σ₂ 时，可以把 σ₂ 中 X 的界从 τ₂ 换成 τ₁，然后继续推导。这看起来更自然，但 Pierce（1992/1994）证明了带 Full 规则的 System F≤ 的子类型关系**不可判定**——他把双计数器机的停机问题归约到了子类型问题上。Ghelli（1995）进一步证明 F≤ 的**类型检查本身**也会发散。

翻译成工程语言：**编译器可能永远不返回**。对一门要用的语言来说，这是不可接受的。

凝华同样不引入区间 kind。Stucki & Giarrusso（2021）证明了带区间 kind 的高阶子类型理论的子类型关系不可判定——他们把 SK 组合子项的可转换性归约到了子类型关系上。

凝华也不引入交集类型。理由有三条：凝华已有联合类型承担"多形态"表达需求；命题层已有 ∧，类型层再引入会在解析上产生歧义；Compagnoni 的可判定性结论对无交集片段同样成立，不引入交集不损失可判定性保证。

### 3.3 你会遇到什么

当你写出一个类型声明，它在 Full 规则下成立但在 Kernel 规则下不成立时，编译器会报 **E-BOUND-REBINDING**。诊断消息会明确告诉你："凝华采用 Kernel 规则，界必须相等"，并给出改写建议——通常是把两个界改成同一个，或者引入显式类型算子来避免界的重绑定需求。

这不是 bug，也不是编译器不够聪明。这是语言设计者在"更强的表达力"和"保证编译器一定停机"之间选择了后者。

### 3.4 如果未来需要更强的表达力怎么办

Kernel 规则不是唯一可判定的选择。如果试验中发现 Kernel 的表达力损失确实不可接受，以下是已知仍可判定的替代方案（按与凝华的契合度排序）：

- **Strong Kernel**（Hu & Lhoták, 2020）：用双上下文避免重绑定，比 Kernel F<: 更具表达力且仍可判定。对凝华的适配代价中等，需要改 Frame 结构。
- **Positive Subtyping**（Hofmann & Pierce, 1995）：弱于标准有界量化但足以建模对象。可判定，适配代价低，但表达力可能不够。
- **F≤µ**（Zhou 等, 2023）：为 Kernel F≤ 添加等递归类型。可扩展 Kernel F≤ 的框架，适配代价中等，但凝华当前没有递归类型需求。

注意有一个看似诱人的方案是**不可用的**：Castagna & Pierce（1994）的"忽略量词变量的界做子类型比较"虽然子类型可判定，但缺乏最小类型属性。缺最小类型的系统会把"该报什么类型的错"变成不确定的，直接违反凝华的诊断确定性原则。

这些替代方案都不在本卷范围内，列出它们只是为了说明：选择 Kernel 规则不是终局，如果评估结果表明需要调整，有已知的退路。

## 四、什么变了、什么没变

这一节直接回答"启用方言后我的代码会怎样"。

### 4.1 没变的

**既有代码全部照常通过。** 这是保守扩展约定（12 卷 D-1）：凡在基础方言下通过检查的程序，在方言下必须同样通过，且诊断序列一致。升级旗标不会让你既有代码突然报错。如果你观察到既有代码的行为变了，那不是收益，那是保守扩展被破坏的 bug，应该报告。

**@mut/@ref 仍然不是子类型关系。** 方言遇到 @mut 一律交回基础方言的视图转换规则处理，不在 <: 层发明新语义。@mut T 与 T 之间的隐式转换仍然是深拷贝语义，反向仍然恒不成立。

**Any 仍然只在期望位放宽。** Any **不等于**方言里的 Top。Top 是子类型判定内部使用的语义对象（作为无界量词的隐含上界），不进入用户可见语法。把 Any 当成 Top 使用会在实参位踩坑——实参是 Any 而期望是具体类型时仍然严格。

**基础方言的 ≈ 路径一条也不被 <: 取代。** 宽松相容判定仍然走原来的逻辑，不会因为启用了方言就变得更严或更松。

### 4.2 变了的

- 能写出有界的类型参数 [X <: τ]。
- 能写嵌套的构造子应用 F[G[Nat]]（不再报 E-NON-PATTERN-HKT）。
- 类型之间有了 <: 判定。
- 新增 5 个诊断码（见第六节）。

### 4.3 对照表

| 能力 | 基础方言 | 方言 |
|---|---|---|
| 无界类型参数 [T] | 支持 | 支持 |
| 有界类型参数 [X <: τ] | 不支持 | 支持 |
| 单层构造子应用 F[Nat] | 支持 | 支持 |
| 嵌套构造子应用 F[G[Nat]] | 禁止（E-NON-PATTERN-HKT） | 允许 |
| 类型算子抽象 | 不支持 | 支持 |
| 类型间 <: 判定 | 无 | 有 |
| ≈ 宽松相容 | 有 | 有（不变） |
| @mut 视图转换 | 深拷贝语义 | 深拷贝语义（不变） |
| Any 期望位豁免 | 有 | 有（不变） |
| 类型类约束 | 有 | 有（不变） |
| 上下文命题 <p> | 有 | 有（不变） |

## 五、方言与既有泛型通道的分工

凝华现在有三条独立的泛型约束通道，各有明确的适用场景。混淆它们是常见的错误来源。

### 5.1 三条通道

**通道 A：类型类（class C[a] + impl C for T）。** 需要方法分派时用。运行时存在类型类字典，承载方法分派。这是总纲"擦除性"的唯一例外。

**通道 B：有界量化（[X <: τ]）。** 只要类型层约束时用。完全擦除，零运行时开销。方言新增。

**通道 C：上下文命题（函数签名里的 <p>）。** 约束的是命题不是类型，走证明器。属于命题域，不属于类型域。

### 5.2 决策表

| 你的需求 | 用哪条 | 例子 |
|---|---|---|
| "X 必须有 map 方法" | 通道 A（类型类） | fun fmap[F: Functor, A, B](fa: F[A], f: (A) => B): F[B] |
| "X 必须是 Nat 的子类型" | 通道 B（有界量化） | fun clamp[X <: Nat](x: X): X （方言目标形态） |
| "X 必须是 Optional[Y] 形态" | 通道 B + 一般 kind | 需要构造子级约束（方言目标形态） |
| "X 必须满足命题 p" | 通道 C（上下文命题） | fun safe_div(x: Nat, y: Nat) <y ≠ 0>: Rat |
| "X 必须有 show 方法且是 Nat 子类型" | A + B 组合 | 类型类提供方法，有界量化提供类型约束 |

关键边界：凝华的命题层与类型层是二分的（设计公理"值与命题二分"）。有界量化属于类型层，不得把命题当界写（[X <: p] 非法），也不得把类型当命题证。

### 5.3 一个容易混淆的场景

假设你想写"X 必须是 Show 的子类型，且 X 必须有 show 方法"。这看起来像是一个需求，但实际上是两个不同的需求叠在一起：

- "X 必须是 Show 的子类型"——这是类型层约束，走通道 B（有界量化）。
- "X 必须有 show 方法"——这需要方法分派，走通道 A（类型类）。

在基础方言里，你只能用类型类同时承担这两个职责（`class Show[a] { fun show(x: a): Str }` + `impl Show for T`）。方言让你可以把它们拆开：用 `[X <: ShowBase]` 约束类型范围，用 `Show` 类型类提供方法。但前提是 `ShowBase` 作为一个纯类型标记存在——如果 `Show` 本身既是类型又是类型类，拆分就没有意义。

这个例子说明：有界量化和类型类的分工不是语法层面的，而是语义层面的。你需要想清楚自己的约束到底是"类型是什么"还是"类型能做什么"。前者走有界量化，后者走类型类。

## 六、代价与风险

### 6.1 界必须相等带来的表达力损失

以下是你会踩到的具体场景：

**场景 1：想写"对所有 Top 的子类型都成立的函数"。** 你可能想写 ∀X<:Top. (X) => X，然后希望它能用在 ∀X<:U. (X) => X 的位置上（因为 U <: Top）。不行。两个界不相等，子类型判定直接失败。改写方式：把两处界统一为同一个类型，或者去掉外层量化改用具体类型。

**场景 2：层层嵌套的有界量化。** 你可能写了 ∀X<:A. ∀Y<:X. σ，然后想把它传给期望 ∀X<:A. ∀Y<:A. σ 的位置。虽然 Y<:X 且 X<:A 蕴含 Y<:A，但内层界 X 和 A 不相等，判定失败。改写方式：把内层界显式写成 A，在体内用额外的子类型证据弥补。

**场景 3：类型别名展开后的界不等。** 你可能定义了 type MyBound = SomeStruct，然后用 [X <: MyBound] 和 [X <: SomeStruct] 分别声明了两个函数，期望它们互通。别名展开后两者结构相同，但如果 β 归一后的结构相等判定因 η 等价暂不纳入而拒绝某些形态，这两个界可能被判为不等。这是当前规格的已知保守方向——拒绝合法程序，但不接受非法程序。

### 6.2 新增诊断码

| 诊断码 | 什么时候出现 | 看到该怎么办 |
|---|---|---|
| E-BOUND-VIOLATED | 类型实参不满足形参的界 | 换一个满足界的类型实参，或放宽形参的界 |
| E-KIND-ARROW-MISMATCH | 构造子应用的 kind 不匹配（不止 arity 计数） | 检查构造子的 kind 签名，确认实参的 kind 正确 |
| E-BOUND-REBINDING | 源码试图依赖 Full 规则的界重绑定语义 | 按诊断建议改写：统一界，或引入显式类型算子 |
| W-BOUND-TRIVIAL | 界是 Top 或与被约束变量等价（无信息量的界） | 考虑去掉界（改为无界参数），或换成有意义的界 |
| D-BOUND-SUBSUME | 发生了隐式子类型化（提示级别） | 无需处理，仅作信息记录 |

### 6.3 尚未定论的设计问题

以下问题在 12 卷中标记为"待核"，意味着规格本身还没有最终答案：

1. **η 等价暂不纳入 ≡。** 这意味着 λX. τ X 和 τ（当 X 不在 τ 中自由出现时）不会被判为相等。后果是某些界相等判定会被拒——这是健全方向的保守（拒绝合法程序），不是不健全方向（接受非法程序）。纳入 η 需要处理"不同类型的 η 展开带不同域注解"的问题，是 Fω 元理论中最麻烦的部分。

2. **方差标注还没有。** 构造子默认不变（invariant）。这意味着 List[Nat] 不是 List[Int] 的子类型，即使 Nat <: Int。要获得协变或逆变行为，需要等待方差标注语法的独立提案。

3. **TypeLambda 是否需要独立于类型别名还没定。** 类型别名是透明的（会被展开消除），而不透明类型算子保留结构、参与 kind 判定。两者在 Kernel 规则下行为不同——透明别名会让界"意外相等"。是否需要一个独立的不透明类型算子节点，取决于实际使用中是否真的需要非透明算子。

4. **有界量化与 @mut 视图的交互。** 规格规定遇到 MutType 立即委托基础方言的视图规则。但界本身带可变性的形态（如 ∀X <: @mut T. σ）是否合法，还没有定论。

5. **有界量化与上下文命题 <p> 的解析歧义。** 凝华的后缀角表已经承载了三种含义（实例化、显式供给、上下文约束），再加 [X <: τ] 形态需要确认不与现有的约束形参表语法冲突。

## 七、怎么评估这个方言值不值得采纳

作者本人还没有决定是否采纳这个方言。以下是评估时应该问的问题。

### 7.1 一条推论

由于保守扩展约定，**方言的收益只可能来自"新写出的、基础方言写不出的类型声明"**，不可能来自"既有代码变得更好"。既有代码在方言下的行为必须与基础方言下逐字一致。

所以评估的核心问题是：你新写的那些声明，是不是真的比原来用类型类或 Any 的写法更好？

### 7.2 一条警戒信号

如果试验中观察到**既有代码的行为变了**（原本通过的代码开始报错、诊断消息变了、产物不同了），那不是收益，那是保守扩展被破坏的 bug，应该立即报告。

### 7.3 具体的评估问题

1. **有多少处原来只能用类型类绕的地方，现在能直接写界？** 统计试验代码中从 class C[a] + impl 改写为 [X <: τ] 的数量。如果数量为零或极少，说明方言填补的缺口在实际代码中并不存在。

2. **界必须相等的限制在实际代码里触发了多少次 E-BOUND-REBINDING？** 如果频繁触发，说明 Kernel 规则的表达力损失对你的代码库影响显著。如果从未触发，说明你的使用场景恰好在 Kernel 规则的舒适区内。

3. **触发 E-BOUND-REBINDING 时，诊断给出的改写建议是否够用？** 如果改写后的代码比原来的类型类写法更复杂、更难读，那方言在这个场景下不是改进。

4. **嵌套构造子应用（F[G[Nat]]）在实际代码中有多少需求？** 如果基础方言的扁平 HKT（单层应用）已经覆盖了所有实际需求，那么方言的一般 kind 就没有需求侧拉动，可以无限期推迟——方言本就是可撤销的试验，不采纳也不影响基础方言。

5. **新增的 5 个诊断码是否在试验中全部出现过？** 如果某些码从未出现，要么是试验覆盖不足，要么是这些码对应的场景在实际代码中不存在。前者需要补充试验，后者可以简化实现。

6. **待核项中哪些阻塞了你的实际使用？** 如果某个待核项（比如 η 等价、方差标注）的缺失导致你写不出想要的声明，那它应该从"待核"提升为"优先解决"。如果所有待核项都不影响你的试验代码，那它们可以继续挂着。
