## 1. 本轮目标与范围

### 1.1 目标（一句话）

把编译器从**单文件**升级为**多文件 + 目录即模块 + 显式挂载**，让 stdlib 可以开始自举。

### 1.2 本轮做什么

- **M1 目录即模块**：编译器扫描目录树，按目录组织符号表
- **M2 同模块内文件互相可见**：`a/b.subl` 和 `a/c.subl` 互相可访问，无需声明
- **M3 父→子可见（传递）**：父模块能访问任意深度的后代
- **M4 子→父不可见、兄弟默认不可见**
- **M5 挂载**：`<模块名>.settings` 文件声明 `mount`，引用式挂载，可多父
- **M6 impl 也挂载**：`d` 想用 `c` 的 impl，必须挂载 `c`
- **M7 编译入口 = 根 `/`**：`compile` 默认从根扫全树
- **M8 合并编译**：所有模块合并成一个 JS 文件，名字加模块前缀 mangle

### 1.3 本轮**不做**什么（碰了算违规）

- ❌ 成员级可见性（`@pub`/`private`）——**当前全 public**，本轮不加修饰符
- ❌ 每模块独立 IIFE/JS 文件的产物分割——**本轮所有模块合并成一个 JS**
- ❌ 包管理器（下载依赖）
- ❌ prelude 迁移到 stdlib 模块（**prelude 仍是编译器注入**）
- ❌ 命题层跨模块的特殊规则（命题里的符号按普通可见性走，**不加额外规则**）
- ❌ 循环依赖检测的高级形态（本轮只做基础的挂载链环检测）
- ❌ 公理跨模块传播（**默认不传播**，保持模块内部信任）

### 1.4 与决策日志的对应

本轮落地决策 **76（新增，本轮归档）**：模块系统。你完成后要按 §8 归档。

## 2. 术语与语义

### 2.1 目录结构示例

```
/                          ← 唯一根模块
├── project
│   ├── project.settings   ← 模块清单（声明挂载）
│   ├── main.subl
│   ├── data/
│   │   ├── stringData.subl
│   │   └── numberData.subl
│   └── processor/
│       ├── formatter.subl
│       └── printer.subl
├── core
│   ├── core.settings
│   └── math.subl
└── other
```

### 2.2 可见性矩阵

| 从 \ 到 | 同模块 | 父模块 | 子模块 | 兄弟模块 | 挂载目标 |
|---|---|---|---|---|---|
| 同模块 | ✅ | ❌ | ✅ | ❌ | ✅（挂载后） |
| 父 | ✅ | — | ✅ | ❌ | 视挂载情况 |

具体规则：

- **同模块**：完全互相可见
- **父→子**：可见，且**传递**（父看孙子也可见）
- **子→父**：不可见
- **兄弟→兄弟**：默认不可见；通过**挂载**建立可见性
- **根 `/`**：可访问所有后代

### 2.3 挂载语义

`project` 挂载 `core` 后：
- `project` 及其**所有后代**都能访问 `core`
- `project` 里写 `core.math.gcd(...)`，**不写** `project.core.math.gcd(...)`
- `core` 的代码不复制，是同一份符号
- `core` 也被 `other` 挂载时，是同一份代码

**引用式挂载的必然推论**：一个模块在不同命名空间下是同一份符号。编译器按模块的**绝对路径**做唯一标识。

### 2.4 impl 装配语义

`impl Show for Point` 定义在模块 `c`。`d` 模块想用 `show(p)`：

- **必须挂载 `c`**
- 不挂载 → `show(p)` 报 `E-NO-INSTANCE`
- 挂了 → 编译期解析到 `c` 的字典

**这是"显式装配"，不是"隐式发现"**。文档和错误提示都要说清楚。

**impl 冲突**：`d` 同时挂载 `c` 和 `e`，两者都提供 `impl Show for Point` → 编译期报 `E-AMBIGUOUS-INSTANCE`（模块版本）。同一条 impl 通过两条挂载路径到达则**去重**（按绝对路径识别同一份符号）。

### 2.5 settings 文件语法

`<模块名>.settings`，模块目录下：

```
# project/project.settings
mount core
mount lib/parser
mount core/math as math
mount someuser/json as json
```

规则：

- 一行一个 `mount`
- 路径**从根 `/` 起**（绝对路径），例如 `mount core` 指 `/core`
- `as <别名>` 可选。挂载后别名成为本地可见名
- 空行和 `#` 开头的行忽略
- 未在 settings 中声明的模块不可访问

**待确认项**（按本文倾向实现，用户可否决）：路径是否允许相对？**本轮只支持绝对路径**（从 `/` 起），简单可测。

### M1：目录即模块（符号表按目录组织）

#### 3.1.1 改动点

**新增 `checker/ModuleTree.kt`**：

```kotlin
package sugared.functor.checker

import java.io.File

/**
 * 模块树（第 5 轮，决策 76）：目录即模块。
 * - 每个目录 = 一个模块，目录名即模块名
 * - 根 = 编译入口目录
 * - 同模块内的所有 .subl 文件共享一个符号表
 */
data class ModuleNode(
    val name: String,
    val absPath: String,          // 绝对路径标识（唯一键）
    val dir: File,
    val children: MutableMap<String, ModuleNode> = LinkedHashMap(),
    val files: MutableList<File> = ArrayList(),
    var settings: ModuleSettings? = null,
)

data class ModuleSettings(
    val mounts: List<MountDecl>,
)

data class MountDecl(
    val targetAbsPath: String,    // 被挂载模块的绝对路径
    val alias: String?,           // as 别名；null 则用被挂载模块的目录名
)
```

**扫描函数**：

```kotlin
/** 从根目录递归扫描，构建模块树。忽略隐藏目录（. 开头）和 build/ 等非源码目录。 */
fun scanModuleTree(root: File): ModuleNode
```

**加载函数**：

```kotlin
/** 读取模块的 settings 文件（<模块名>.settings），解析挂载声明。文件不存在 → mounts 为空。 */
fun loadSettings(node: ModuleNode): ModuleSettings
```

#### 3.1.2 与现有 `Symbols` 的关系

当前 `Symbols` 是**全局扁平**的符号表。改为**每模块一个 `Symbols`**，全局持有一个 `Map<String, Symbols>`（键为绝对路径）。

**关键**：不要一次性重写 `Symbols`——先在 `Checker` 里加一个可选的"模块上下文"，让单文件路径不破。

### M8：合并编译（codegen 的模块作用域）

#### 3.8.1 改动点

**关键决策：本轮所有模块合并成一个 JS 文件。** 不为每个模块生成独立的 IIFE/文件。

**命名 mangle 规则**：

- 顶层函数名加模块路径前缀：`<mangled_module>__<name>`
- 例：`core/math.subl` 里的 `gcd` → `core_math__gcd`
- 跨模块调用按 mangle 后的名字引用

**但**：同一个 `.subl` 文件里的**内部辅助函数**（模块私有的）不需要前缀——因为它们不跨模块。**为了简化，本轮全部加前缀**，不做优化。

**mangle 规则**你定，建议：

```kotlin
/** 模块路径 → 合法 JS 标识符前缀 */
fun mangleModule(absPath: String): String =
    absPath.trim('/').replace('/', '_').replace(Regex("[^A-Za-z0-9_]"), "_")
```

**main 函数**：整个项目有且仅有一个 `main`（在哪个模块下都行，但全局唯一）。codegen 在产物末尾追加 `<mangled>__main();`。

#### 3.8.2 M8 验收

- e2e：两模块项目，模块 A 调模块 B 的函数 → `node out.js` 输出正确
- e2e：多模块项目调 `main` → 入口正确
- 快照：生成产物里模块前缀出现在函数名上（可 grep）
- 现有 183 测试全绿

| `E-UNBOUND-NAME`（复用） | 访问不可见模块的符号 |
| `E-DUP-DECL`（复用） | 同模块内跨文件重名；本地目录名与挂载别名冲突 |
| `E-AMBIGUOUS-INSTANCE`（复用，模块版本） | 挂载的多个模块提供同一 impl |
| `E-CIRCULAR-MOUNT`（新） | 挂载链成环 |
| `E-PARSE-SETTINGS`（新） | settings 文件语法错 |

## 5. 必须遵守的不变量

除现有 I-1~I-19 全部适用外，本轮**新增一条**（记入《工程规范.md》§2）：

> **I-20 模块可见性是"计算出来的集合"，不是"查表的布尔"。**
> `canSee(from, to)` 不能只判断父子关系——它必须计算 from 的**完整可见路径集合**（后代 + 挂载目标及其后代），因为挂载使可见性不再由树结构单独决定。任何"按单点父子关系判断"的实现都是错的。
>
> **推论**：每次符号查找都要传入这个集合，不能依赖全局符号表。

**已有不变量中本轮高危的**：

- **I-5 α-等价**：命题匹配靠 alphaEq，别改成字符串比较
- **I-15 Type.name/args 是兼容层**：加模块前缀时别把哨兵名也加前缀
- **I-18 字典留痕按 CallExpr 实例**：`IdentityHashMap` 不要换成普通 HashMap

## 9. 补充：与 stdlib 自举的关系

模块系统落地后，**下一轮**才能开始 stdlib 自举：

- 内建原语（`Str` 操作、IO、数组）：仍由编译器注入

- 型类实例（`impl Show for Int`）：放 `stdlib/show.subl` 之类的模块，用户通过挂载选择性地引入

**本轮不碰 stdlib**，但模块系统的设计要能承载它——所以 `stdlib/` 目录结构在本轮测试里应该可以正常扫描。
