## 0. 摘要

### 0.1 问题

**v1.0 的 `pure` 只检查"不调用 `@unpure` 函数、不写外部变量"**——不检查"函数修改了传入的可变对象"。一个 `fun addOne(list: List): List { list.append(1); return list }` 在当前语义下**是纯的**，但调用者的 `list` 被改了。**这是健全性漏洞。**

**现有方案的两难**：

- **Kotlin 路线（子类型）**：`MutableList <: List`——与决策 31（v1 排除子类型）冲突
- **Scala 路线（显式转换）**：`.toList()`——**必然拷贝**，性能损失大

### 0.2 答案

**Sublimation 引入"自然命题"体系**——编译器自动为一些构造生成保守命题，**用户可显式证明更强/更弱的命题**：

| 自然命题 | 默认行为 | 用户可证 |
|---|---|---|
| **`pure<f>`** | 未标 `@unpure` 的函数自动获得 | `@unpure` 函数可证明条件纯（决策 34） |
| **`untouch<param>`** | 非 `@mut` 参数自动获得；`@mut` 参数**默认不可得** | `@mut` 参数的函数体可证明 `untouch<param>`（**本文档新增**） |
| **`immutable<T>`** | 基本类型与不可变结构体自动获得；`@mut` 属性的结构体**默认不可得** | 有 `@mut` 属性的结构体可证明条件 immutable（**本文档新增**） |

**三者共用同一机制**：编译器默认给出保守命题，用户可在函数体内证明更强的命题。

### 0.3 拷贝判据

**浅拷贝 vs 深拷贝由 `immutable<T>` 决定**：

- **`immutable<T>` 可证** → **浅拷贝**（元素共享，零风险）
- **不可证** → **深拷贝**（元素复制，安全但有代价）

**`immutable<T>` 的定义**：

- 基本类型（`Nat` / `Int` / `Rat` / `Str` / `Bool` / `Null` / `Nothing`）**自动 immutable**
- **无 `@mut` 属性**且**所有属性类型都 immutable** 的结构体 / 枚举**自动 immutable**
- **`Any`** 默认可变——除非证明它是某个 immutable 结构体（受限顶类型的另一面）
- **`@mut` 属性**使整个结构体**不再自动 immutable**——除非用户显式证明

### 0.4 `@mut` 参数的双面语义

**函数体内**：`@mut` 参数**可以改，也可以不改**——灵活。

**函数体外（调用者视角）**：`@mut` 参数**保守假设会被改**——除非函数证明 `untouch<param>`。

**这是"保守接口 + 精确实现"的分离**：

- 调用者**默认认为**函数改了 `@mut` 参数（安全）
- 函数可以**显式证明**没改（性能优化）

### 0.5 与 Rust 的关系

**这是 Rust 借用检查的软化版**——Rust 强制静态检查（违反编译不过），Sublimation **默认正确（拷贝）+ 优化可选（证明省略）**。

**用户在大多数场景下不需要理解这套机制**——只在性能敏感处显式优化。

## 1. 纯函数的规范定义

### 1.1 三条规则

**定义**：纯函数是满足以下三条的函数。⟨目标⟩

| 规则 | 含义 | 违规诊断 |
|---|---|---|
| **P-1 不纯调用** | 不能调用 `@unpure` 函数（除非经 `unchecked` 逃逸或持有 `pure<f>`） | `E-IMPURE-CALL` |
| **P-2 停机** | 必须被证明停机（结构递归或 `unchecked` 逃逸） | `E-NON-STRUCTURAL-REC` |
| **P-3 不修改外部** | 不能修改函数体外的可变变量——**除非是显式标记 `@mut` 的参数** | `E-IMPURE-MUTATE` |

**P-1 已有实现**（决策 54）。**P-2 已实现**（P9）。**P-3 是本文档的新规则。**

### 1.2 P-3 的精确表述

**"函数体外"的边界**：

- **局部变量**（`var` 声明在函数体内）——**可以修改**（`@mut` 局部变量）
- **`@mut` 参数**——**可以修改**（显式批准的可变位置）
- **非 `@mut` 参数**——**不可修改**（默认不可变）
- **全局变量**（如果有）——**不可修改**（除非 `unchecked`）

**关键**：**参数是"函数体外"的，但 `@mut` 参数是"调用者显式批准修改的"**。这是 P-3 的例外条款——类比 Rust 的 `&mut T`。

### 1.3 与 `pure<f>` 的关系

**`pure<f>` 命题**（决策 54）：持有它 ⇒ 编译器认为对 `f` 的调用是纯的。

**现有语义**：`pure<f>` 只声明 P-1 和 P-3（对全局）的满足。

**扩展后**：`pure<f>` 的完整语义 = P-1 ∧ P-2 ∧ P-3（对全局，不含 `@mut` 参数）∧ **"f 对每个非 `@mut` 参数保 `untouch`"**（见 §6）。

## 2. 自然命题体系

### 2.1 定义

**自然命题（natural propositions）**：编译器**自动生成**的保守命题。它们的共同特征：

- 由编译器在符号收集阶段自动注入 Γ
- **保守**——宁可假设"更严格"的约束，也不放松
- **可被用户显式证明覆盖**——函数体或类型声明中可以证明"实际更宽松"的命题

**当前有三个自然命题**：`pure<f>` / `untouch<param>` / `immutable<T>`。

### 2.2 三个自然命题

| 命题 | 位置 | 默认 | 覆盖方式 |
|---|---|---|---|
| **`pure<f>`** | 函数 | 未标 `@unpure` 的函数**自动获得** | `@unpure` 函数在体内证明条件纯 |
| **`untouch<param>`** | 参数 | 非 `@mut` 参数**自动获得**；`@mut` 参数**默认不可得** | `@mut` 参数在函数体内证明 `untouch<param>` |
| **`immutable<T>`** | 类型 | 基本类型与"全 immutable 属性的结构体"**自动获得** | 含 `@mut` 属性的结构体可证明条件 immutable |

### 2.3 统一机制

**三个自然命题共用同一套"生成 → 供给 → 推理"流程**：

1. **生成**：符号收集阶段，编译器按保守规则生成自然命题，注入 `globalFacts`
2. **供给**：调用点/类型使用点自动从 Γ 检索（同 `pure<f>` 的 0 元候选机制）
3. **推理**：证明器把自然命题当作普通命题对待——可被 `→` 链接、`∧` 分解等

**这意味着**：新增自然命题**不引入新机制**——只是往 `globalFacts` 里多注入一类事实。

### 2.4 为什么叫"自然"

**"自然"是因为它们"不用写就有"**——就像 `var n = 0` 自动产生 `n = 0`。它们是编译器的**默认假设**，不是用户显式声明的。

**"命题"是因为它们住在 Γ 里**——和 `e : T` / `a = b` 是同层的东西。

**"体系"是因为三者共用机制**——它们不是三个独立特性，是同一设计原则的三个实例。

## 3. 类型层的 `@mut` 维度

### 3.1 语法

**`@mut` 可作类型前缀**：⟨目标⟩

```sublimation
var list: @mut List = listOf()      // 可变视图
var list2: List = list              // 不可变视图（转换点）
```

**`@mut` 可作方法注解**：⟨目标⟩

```sublimation
class List[T] {
    @mut fun add(e: T): Null        // 只能对 @mut List 调用
    fun length(): Nat               // 两种视图都能调用
}
```

**`@mut` 可作形参注解**：⟨目标⟩

```sublimation
fun f(list: @mut List): Null { ... }   // 显式可写参数
fun g(list: List): List { ... }        // 默认不可写
```

**`@mut` 可作结构体属性注解**：⟨目标，本文档新增⟩

```sublimation
struct Test(a: Nat, @mut b: Nat)        // 含可变属性的结构体
```

### 3.2 类型表示

**`MutType(inner)` 作为 `Type` 的新子类**：⚠️ 待定

```kotlin
/** 可变视图类型 `@mut T`（v1.1 目标） */
data class MutType(val inner: Type) : Type {
    override val name: String get() = "(mut)"
    override val args: List<Type> get() = listOf(inner)
    override fun render() = "@mut ${inner.render()}"
    override fun substT(sub: Map<String, Type>) = MutType(inner.substT(sub))
}
```

**代价**：`Type` 的所有 `when` 分支需要处理 `MutType`——`typeEq` / `typeLooseEq` / `isNominal` / `containsAny` / `substT` / `unify` 等。

**新不变量 I-25**：`MutType` 是**类型层的新维度**，不是 `NamedType` 的标记。类型相等判定把 `@mut T` 和 `T` 视为**不同类型**。

### 3.3 类型层规则

- **M-1**：`@mut T` 与 `T` **不是子类型关系**——它们是**同一数据结构的两个视图**。⟨目标⟩
- **M-2**：`@mut T` 可以**隐式转换**为 `T`——转换点为拷贝点（见 §5）。⟨目标⟩
- **M-3**：`T` **不能**转换为 `@mut T`——需要显式 `toMutable()` 调用。⟨目标⟩
- **M-4**：`@mut T` 不能作为类型参数**逃逸**出当前函数——`fun f(): @mut List` 非法。⟨目标⟩

## 4. 不可变性：`immutable<T>` 自然命题

### 4.1 定义

**`immutable<T>`**：类型 `T` 的所有值在构造后**不会发生可观测的变化**。⟨目标，本文档新增⟩

**语法**：作为命题在 Γ 中出现，形式 `immutable<T>`。

**例**：

- `immutable<Nat>` — 自动成立
- `immutable<Str>` — 自动成立
- `immutable<Point>` — 若 `Point` 无 `@mut` 属性且所有属性类型 immutable，自动成立
- `immutable<Test>` — 若 `Test` 含 `@mut` 属性，**默认不成立**

### 4.2 自动生成规则

**规则 I-1**：基本类型自动 immutable。⟨目标⟩

```
immutable<Nat>  immutable<Int>  immutable<Rat>
immutable<Str>  immutable<Bool>  immutable<Null>  immutable<Nothing>
immutable<EmptyTuple>  immutable<SingleTuple<T>>（若 T immutable）
```

**规则 I-2**：结构体默认 immutable——**当且仅当**无 `@mut` 属性且所有属性类型都 immutable。⟨目标⟩

```sublimation
struct Point(x: Nat, y: Nat)               // immutable<Point> 自动成立
struct Test(a: Nat, @mut b: Nat)           // immutable<Test> 默认不成立
struct Wrapper(t: Test)                    // immutable<Wrapper> 也不成立（传递性）
```

**规则 I-3**：枚举与结构体同规则。⟨目标⟩

**规则 I-4**：`Array[T]` **默认可变**——它本质是可写容器。⟨目标⟩

**规则 I-5**：`Any` **默认可变**——受限顶类型的另一面。**但若能证明 `e : T` 且 `immutable<T>`，则 `e` 也 immutable**。⟨目标⟩

**规则 I-6**：函数类型 `immutable<(A) => B>` 恒成立——函数值本身不可变（闭包捕获的变量另算）。⟨目标⟩

**规则 I-7**：`@mut T` **不 immutable**——明确的可变视图。⟨目标⟩

### 4.3 用户显式证明

**场景 1**：含 `@mut` 属性的结构体，**实际使用中不修改**——用户可证明 immutable。⟨目标⟩

```sublimation
struct Counter(@mut value: Nat)

// 用户提供证明：Counter 被当作 immutable 用
fun counterIsImmutable(c: Counter): <immutable<Counter>> { ... }
```

**场景 2**：`Any` 是某个 immutable 结构体——用户可证明。⟨目标⟩

```sublimation
fun anyIsPoint(x: Any, proof: <x : Point>): <immutable<Any>> { ... }
```

**这是受限顶类型的"逃逸"机制**——`Any` 默认可变，但**显式知道真实类型**时可 immutabilize。

### 4.4 与决策 34 的同构

**`pure<f>`**：`@unpure` 函数**默认不纯**，但可证明条件纯。
**`immutable<T>`**：含 `@mut` 属性的结构体**默认不 immutable**，但可证明条件 immutable。

**两者都是"保守默认 + 显式证明"**——这是**自然命题体系的核心设计**。

## 5. 视图转换与浅/深拷贝

### 5.1 转换语义

**`@mut T` → `T` 转换点**：⟨目标⟩

- **判据**：`T` 是否 `immutable<T>`？
  - **immutable** → **浅拷贝**（元素共享，零风险）
  - **非 immutable** → **深拷贝**（元素复制，安全）
- **优化**：如果能证明转换后 `@mut T` 变量不再被访问，**省略拷贝**

**为什么浅/深由 immutable 决定**：

- **`immutable<T>`** 意味着元素不会被修改——**两个视图共享元素安全**
- **非 immutable** 意味着元素可能被修改——**必须深拷贝隔离**

### 5.2 浅拷贝

**定义**：拷贝顶层容器结构，**元素共享**。⟨目标⟩

**适用**：`immutable<T>` 成立时。

**例**：

```sublimation
var m: @mut List[Nat] = listOf(1, 2, 3)
var i: List[Nat] = m                // immutable<Nat> 成立 → 浅拷贝
m.add(4)                            // 修改 m
print(i.length())                   // 3（不受影响——顶层结构已拷贝）
```

**关键**：顶层 List **结构**被拷贝（`head`/`tail` 引用独立），但元素（`1`/`2`/`3`）**共享**——因为 `Nat` 不可变，共享无风险。

### 5.3 深拷贝

**定义**：递归拷贝所有嵌套结构。⟨目标⟩

**适用**：`immutable<T>` 不成立时。

**例**：

```sublimation
struct Counter(@mut value: Nat)
var m: @mut List[Counter] = listOf(Counter(1), Counter(2))
var i: List[Counter] = m            // immutable<Counter> 不成立 → 深拷贝
m.at(0).value = 99                  // 修改 m 的第一个元素
print(i.at(0).value)                // 1（不受影响——元素已深拷贝）
```

**代价**：深拷贝的开销 = 元素数量 × 元素拷贝开销。**这是 correctness 的代价**——不深拷贝会有别名 bug。

### 5.4 拷贝省略

**局部证明**（同一函数内）：⟨目标⟩

**分析对象**：`@mut T` 变量的**使用图**。

**规则**：

1. 找到 `@mut T` → `T` 的转换点
2. 分析转换后，原 `@mut T` 变量是否**还有任何使用**
3. 无使用 → **省略拷贝**（所有权转移）
4. 有使用 → **必须拷贝**（浅或深由 immutable 决定）

**示例**：

```sublimation
fun useBoth(): Null {
    var list: @mut List[Nat] = listOf(1, 2, 3)
    var snapshot: List[Nat] = list       // 转换点
    list.add(4)                          // list 被再次使用 → 必须拷贝
    print(snapshot.length())             // 3
    print(list.length())                 // 4
}

fun useOnce(): Null {
    var list: @mut List[Nat] = listOf(1, 2, 3)
    var snapshot: List[Nat] = list        // 转换点
    print(snapshot.length())              // list 不再被使用 → 省略拷贝
}
```

### 5.5 跨函数转换

**跨函数**（参数传递）：⚠️ 待定

**两个方案**：

- **A（v1.1，Max 倾向）**：**保守拷贝**——`f(mutableList)` 内部可能持有引用，默认拷贝
- **B（v1.2）**：**逃逸分析**——加 `@noescape` 注解，用户显式声明参数不逃逸

**Max 倾向 v1.1 保守拷贝**——简单、可预测，性能损失只在函数边界发生一次。

### 5.6 嵌套可变的处理

**`@mut List<@mut List<T>>`**：⟨目标⟩

- 若内层 `@mut List<T>` 也参与拷贝，需要递归深拷贝
- **v1.1 限制**：**不支持嵌套可变**——`@mut List<@mut List<T>>` 报 `E-NESTED-MUT`

**理由**：嵌套可变的拷贝省略分析复杂，留待 v1.2。

## 6. `@mut` 参数的双面语义

### 6.1 核心设计

**函数体内**：`@mut` 参数**可以改，也可以不改**——灵活。

**函数体外（调用者视角）**：`@mut` 参数**保守假设会被改**——除非函数证明 `untouch<param>`。

**这是一次"保守接口 + 精确实现"的分离**。

### 6.2 `untouch<param>` 自然命题

**定义**：`untouch<param>` 表示函数**不修改**形参 `param` 指向的对象。⟨目标，本文档新增⟩

**默认生成规则**：⟨目标⟩

- **非 `@mut` 参数** → **自动获得 `untouch<param>`**（编译器自动注入 `globalFacts`）
- **`@mut` 参数** → **默认不获得**——调用者保守假设"会被改"

### 6.3 用户显式证明

**场景**：`@mut` 参数**实际没被修改**——函数可证明 `untouch<param>`。⟨目标⟩

```sublimation
fun maybeAdd(list: @mut List[Nat], flag: Bool)
    : <untouch<list> ∨ flag = true>
{
    // 语义：若 flag = false，则 list 未修改
    if flag {
        list.add(1)
    }
    // 需证：untouch<list> ∨ flag = true
    // 若 flag = false，走 else 分支，list 未被触碰 → untouch<list> 成立
}
```

**这需要 P-3 规则的扩展**：函数体内追踪 `@mut` 参数的**触碰点**（touch points）。

**触碰点**：

- 对 `@mut` 参数调用 `@mut` 方法（如 `list.add`）
- 对 `@mut` 参数直接赋值（`list.value = x`）
- 把 `@mut` 参数传给另一个函数（可能被修改）

**若函数体内**：所有分支路径上**都没有触碰点**——则可证 `untouch<param>`。

### 6.4 与 `pure<f>` 的同构

| 特性 | `pure<f>` | `untouch<param>` |
|---|---|---|
| **位置** | 函数 | 参数 |
| **默认** | 未标 `@unpure` 的函数**自动获得** | 非 `@mut` 参数**自动获得**；`@mut` 参数**默认不可得** |
| **用户可证** | `@unpure` 函数可证明条件纯 | `@mut` 参数可证明条件 untouch |
| **机制** | 编译器注入 `globalFacts` | 编译器注入 `globalFacts` |
| **推理** | 从 Γ 检索 | 从 Γ 检索 |
| **逃逸** | `unchecked` | `unchecked` |

**两者是同一机制的两个实例。**

### 6.5 为什么"函数外保守"

**用户视角一致性**：

- 调用 `maybeAdd(list, false)` 时，调用者**不知道** `list` 是否被修改——除非函数签名承诺
- **默认保守**（假设改了）→ 用户不会因"以为没改其实改了"而出 bug
- **显式证明**（`untouch<list>`）→ 用户主动承担"我保证没改"

**这是"编译器不是天才"的落地**——编译器不猜，只按签名走。

## 7. `@mut` 方法的调用规则

### 7.1 调用约束

**规则 MM-1**：`@mut` 方法只能对 `@mut T` 接收者调用。⟨目标⟩

```sublimation
var m: @mut List = listOf()
m.add(1)          // ✅ 合法

var i: List = m
i.add(1)          // ❌ E-NOT-MUT
```

**规则 MM-2**：非 `@mut` 方法对两种视图都能调用。⟨目标⟩

**规则 MM-3**：`@mut` 方法体内，`self` 是 `@mut T` 类型——可以修改字段。⟨目标⟩

**规则 MM-4**：`@mut` 方法体内，修改 `self` 的字段**不算"修改外部"**——`self` 是显式批准的。⟨目标⟩

### 7.2 与 P-3 的关系

**纯函数可以调用 `@mut` 方法**——**前提是接收者是 `@mut` 参数**。

**纯函数不能调用 `@mut` 方法**——**如果接收者是外部变量**（非参数）。

**示例**：

```sublimation
fun f(list: @mut List): Null {
    list.add(1)      // ✅ 合法：list 是 @mut 参数
}

var global: @mut List = listOf()

fun g(): Null {
    global.add(1)    // ❌ E-IMPURE-MUTATE：global 是外部变量
}
```

## 8. 与 Rust 生命周期的对比

### 8.1 对照表

| Rust | Sublimation | 差异 |
|---|---|---|
| `&T` | `List` | 不可变视图 |
| `&mut T` | `@mut List` | 可变视图 |
| `&mut T` 转 `&T` | `@mut List` 转 `List` | **Rust reborrow（零拷贝）；Sublimation 拷贝（可优化）** |
| **借用检查**：违反 = 编译错 | **拷贝省略**：失败 = 多一次拷贝 | **Rust 强制正确；Sublimation 默认正确 + 优化** |
| 生命周期标注 `'a` | 不需要显式标注 | **Sublimation 无生命周期语法** |
| 借用规则：`&mut` 独占 | 无强制别名规则 | **Sublimation 无别名约束** |
| 所有权 move | `@mut` 参数调用后可选作废 | ⬜ 待定（见 §10.2） |
| **`Send` / `Sync` trait** | **`immutable<T>` 自然命题** | **Sublimation 的 immutable 更宽（含不可变视图语义）** |

### 8.2 设计立场

**Rust 借用检查是"编译正确性要求"**——违反借用规则的程序**编译不过**。

**Sublimation 拷贝省略是"性能优化"**——**失败只是多一次拷贝，永远不违反正确性**。

**两个后果**：

1. **用户友好**：不需要理解生命周期标注、借用规则、所有权转移。**99% 用户只需知道"传 `@mut List` 给 `List` 参数会拷贝"**。
2. **性能可控**：性能敏感处可写辅助证明（局部变量不再使用、参数不逃逸），编译器省略拷贝。

### 8.3 为什么不做完整借用检查

1. **复杂度爆炸**——Rust 借用检查器（NLL / Polonius）是编译器中最复杂的部分之一
2. **错误消息难写**——Rust 借用错误消息虽经典但极难让用户理解
3. **JS 后端不支持**——Sublimation 的 `@mut` 是语义层抽象，JS 里就是普通对象引用

**结论**：**借用 Rust 的心智模型**（可变/不可变视图分离），**不借 Rust 的检查机制**（编译期借用规则）。

## 9. 拷贝省略的证明强度

### 9.1 语法级 vs 语义级

**"变量不再使用"的判定**——是**语法级**（无后续引用）还是**语义级**（无后续可达路径）？

- **语法级**：分析 AST，找转换点后的引用
- **语义级**：数据流分析，考虑分支、循环（但 Sublimation 无循环）、函数调用

**Max 倾向语法级**——简单、可预测、不引入数据流分析的复杂度。

### 9.2 触碰点的语法级判定

**`@mut` 参数的触碰点**——语法级识别：

- 对参数调用 `@mut` 方法
- 直接赋值给参数或其字段
- 把参数传给另一个函数（保守假设会被改）

**若所有分支路径上都无触碰点** → 可证 `untouch<param>`。

## 10. 待定问题

### 10.1 五个核心待定

**Q1：`@mut` 参数是"可以改"还是"必须改"？**

**已定**：可以改，也可以不改。函数体外保守假设会改，除非证明 `untouch`。

**遗留**：证明 `untouch` 的语法形式——是直接写在函数后件里，还是专门的注解？

**Max 倾向**：写在后件里——`fun f(list: @mut List): Null <untouch<list>>`。**这是上下文系统的自然用法。**

**Q2：调用 `@mut` 参数函数后，变量作废吗？**

- **A（仿射类型）**：变量作废——`m` 后续使用报 `E-MOVED`。更安全，但用户要习惯。
- **B（引用语义）**：变量保留——`m` 后续可用（`f` 的修改可见）。更宽松。

**Max 倾向 B（v1.1）**——**默认宽松，用户可显式请求 `@move`**。

**折中**：默认 B，提供 `@move` 显式标记请求 A。**这符合"编译器不是天才"原则**——不猜，用户显式操作。

**Q3：内建修改操作的标记方式**？

- **A（Max 倾向）**：`@mut` 注解显式标注
- **B**：型类 `Mutable` 自动派生
- **C**：编译器内置清单

**Max 倾向 A**——清晰、可扩展、用户能自定义。

**Q4：跨函数转换是否支持逃逸分析**？

- **A（v1.1，Max 倾向）**：不支持——跨函数一律拷贝
- **B（v1.2）**：加 `@noescape` 注解——用户显式声明参数不逃逸

**Q5：嵌套可变容器的支持**？

- **A（v1.1，Max 倾向）**：不支持——`List<@mut T>` 报错
- **B**：支持但需深拷贝——性能可能爆炸
- **C**：支持但用户显式选择浅/深拷贝

### 10.2 `@mut` 参数调用后的变量语义

**未定**——是否引入 `@move` 显式标记。

### 10.3 `immutable<T>` 的传递性

**规则 I-2 说**："无 `@mut` 属性且所有属性类型都 immutable 的结构体自动 immutable"——**这是递归定义**。

**问题**：递归结构体 `struct Node(next: Optional<Node>)` 怎么办？

- `Optional<Node>` 的 immutable 依赖 `Node` 的 immutable
- `Node` 的 immutable 依赖 `Optional<Node>` 的 immutable
- **循环依赖**

**Max 倾向**：**结构性递归采用"余归纳"（coinductive）判定**——假定类型自身 immutable，检查所有构造路径。**递归类型默认 immutable**（除非有 `@mut` 字段打破）。

### 10.4 `immutable<T>` 与型类约束的交互

`fun f[T: Show](x: T)` 里 `T` 的 immutable 状态**未知**——是保守假设可变，还是需要额外约束？

**Max 倾向**：**约束 `T: immutable`**——用户显式声明"T 必须 immutable"。

### 10.5 `@mut` 和 `Any` 的交互

`@mut Any` 是什么？**未讨论**。

### 10.6 `@mut` 和函数类型的交互

`(@mut List) => Null` 是什么？**未讨论**。

### 10.7 `@mut` 和元组的交互

`@mut (List, List)` vs `(@mut List, @mut List)`——语义不同。**未定**。

## 12. 设计权衡记录

### 12.1 为什么不用子类型（Kotlin 路线）

- 决策 31 明确 v1 排除子类型
- 子类型引入类型系统复杂度（协变/逆变、型变标注）
- 即使子类型，Kotlin 的 `MutableList <: List` 仍**不能防止**"传入后修改"——用户仍需自觉
- Sublimation 的 `@mut` 是**显式标记**——调用者一眼看到"这个参数可写"

### 12.2 为什么不用强制借用检查（Rust 路线）

- 编译器复杂度爆炸
- 错误消息难写
- JS 后端不支持真实所有权
- **用户负担过重**——Rust 学习曲线是公认的

### 12.3 为什么用"拷贝 + 优化"

- **默认正确**——拷贝总是安全的
- **优化可选**——性能敏感处才需证明
- **编译期零开销**——不引入运行时引用计数或写屏障
- **可预测**——用户知道"什么时候会拷贝"

### 12.4 为什么用"自然命题"

**`pure<f>` 已有先例**——编译器自动为未标 `@unpure` 的函数注册 `pure<name>`。**这是"默认保守 + 用户可证"的原型。**

**`untouch<param>` / `immutable<T>` 是它的扩展**——同一机制，不同应用。

**统一为"自然命题体系"**——不引入新机制，只扩展 `globalFacts` 的内容。

### 12.5 为什么 `immutable` 决定浅/深拷贝

**`immutable<T>` 是"元素不会变"的证明**——共享元素无风险时用浅拷贝。

**非 immutable** 必须深拷贝隔离——否则别名 bug。

**这条判据可被用户**：

- **放宽**：`immutable<T>` 不可证 → 深拷贝（默认安全）
- **收紧**：用户证明条件 immutable → 浅拷贝（性能优化）
