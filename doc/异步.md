# 异步

> **本文档状态**：设计草案 v0.1（2026-10-09）
>
> **本文档定位**：定义 Sublimation 的异步模型——`Task` / `Channel` / `@async` 传染 / 挂起与恢复。目标：**从 Java 过来的人，知道线程怎么写就能上手；并发的心智负担最小。**
>
> **本文档与现有文档的关系**：
> - 依赖《上下文系统.md》的智能转换机制——通道状态的收窄是智能转换的又一实例
> - 依赖《副作用与可变性控制.md》的"局部语法检查 + 保守默认 + 用户逃逸"哲学——通道状态检查是同一模式
> - 明确**不做代数效应**（handler + 续延）——和上下文系统的单调性冲突
>
> **维护纪律**：本文档记录**设计**。每条规则标 ⟨目标⟩ / ⟨实现⟩ / ⬜ 待定。

## 0. 摘要

### 0.1 问题

Sublimation 编译到 JS。JS 是**单线程 + 事件循环**——没有真并行，只有协程。但用户**需要并发**：并行处理任务、任务间通信、挂起等待。

### 0.2 目标

**从 Java 过来的人，知道 `Thread` / `Runnable` / `join` 就能上手。**

三个概念，一套机制：

| 概念 | 用户想做什么 | API |
|---|---|---|
| **线程** | 并行启动一个任务 | `Task { }` + `start()` + `join()` |
| **协程** | 挂起与恢复 | `@async` + 编译器自动插入 `await` |
| **通道** | 任务间通信 | `Channel[T]` + `send` / `receive` |

**底层全部编译到 JS 原生 `async/await` + Promise。零运行时库。**

### 0.3 比 Java 简单的地方

**JS 单线程——没有数据竞争、不需要锁。**

- ❌ 不需要 `synchronized` / `Lock` / `volatile`
- ❌ 不需要 `ConcurrentHashMap`
- ❌ 不需要 `AtomicInteger`
- ✅ 共享变量天然安全

**用户从 Java 过来，最痛的那部分（多线程并发）在这里完全不存在。**

### 0.4 与代数效应的关系

**做效应追踪**——`async<f>` 是自然命题，和 `pure<f>` 同族。

**不做效应处理**——handler + 续延需要非单调推理，和上下文系统冲突，且 JS 后端不支持 CPS 转换。

**本文将"异步"明确定义为"协程 + 通道"——不是代数效应。**

## 1. Task——线程式并发

### 1.1 API

```sublimation
Task[T]                     // 任务类型，T 是任务体的返回类型
Task { ... }                // 创建任务（不启动）
t.start()                   // 启动
t.join(): T                 // 等待完成，返回结果（挂起）
t.isAlive(): Bool           // 是否还在跑
```

### 1.2 心智模型

**和 Java 一一对应**：

| Java | Sublimation |
|---|---|
| `new Thread(() -> {...})` | `Task { ... }` |
| `t.start()` | `t.start()` |
| `t.join()` | `t.join()` |
| `t.isAlive()` | `t.isAlive()` |

**逐行可迁移**。

### 1.3 创建与启动分离

**规则 TASK-1**：`Task { ... }` **创建**任务对象——**不启动**。⟨目标⟩

**规则 TASK-2**：`t.start()` **启动**——**不阻塞**。⟨目标⟩

**规则 TASK-3**：`t.join()` **挂起**直到完成——返回任务体结果。⟨目标⟩

**规则 TASK-4**：`t.isAlive()` 返回任务是否还在跑。⟨目标⟩

```sublimation
fun main() {
    var t1 = Task { print("A") }
    var t2 = Task { print("B") }
    t1.start()
    t2.start()
    t1.join()      // 挂起直到 t1 完成
    t2.join()      // 挂起直到 t2 完成
}
```

**为什么创建与启动分离**：和 Java 一致。用户熟悉两步。

### 1.4 任务体的能力

**规则 TASK-5**：`Task { ... }` 体**天然是 `@async`**——内部可自由挂起。⟨目标⟩

**规则 TASK-6**：`Task { ... }` 体**可访问外部变量**——闭包语义。**单线程无竞争，安全。**⟨目标⟩

```sublimation
var counter = 0
var t = Task {
    counter = counter + 1   // ✅ 可改外部变量
    readFile("...")         // ✅ 可挂起（Task 体天然 @async）
}
```

### 1.5 `Task[T]` 的返回类型

```sublimation
var t: Task[Nat] = Task { 42 }
var result: Nat = t.join()      // join 返回 T
```

**`Task[T]` 对应 Java 的 `Future<T>`**——但**不需要显式 `.get()`**，`join()` 直接返回 `T`。

### 1.6 未 start 就 join

**规则 TASK-7**：函数体内有 `t.start()` 调用 → `t.join()` 合法。否则报 `E-NOT-STARTED`。⟨目标⟩

**这是局部语法检查**——和通道状态检查同一模式（见 §3）。

```sublimation
fun f() {
    var t = Task { 42 }
    t.join()        // ❌ E-NOT-STARTED：函数体内无 t.start()
}

fun g() {
    var t = Task { 42 }
    t.start()
    t.join()        // ✅
}
```

## 2. 挂起与恢复

### 2.1 用户视角

**规则 SUSP-1**：用户**不写 `await`、不写 `suspend`**。编译器在挂起点**自动插入 `await`**。⟨目标⟩

```sublimation
@async
fun fetchConfig(): Str {
    var raw = readFile("config.json")   // 挂起点——编译器插入 await
    var parsed = parse(raw)              // 恢复后继续
    return parsed
}
```

**对照**：

| 语言 | 挂起标记 |
|---|---|
| JS | `async function` + `await` |
| Kotlin | `suspend fun` |
| **Sublimation** | **`@async fun`——无 `await`** |

**用户只标 `@async`——其余交给编译器。**

### 2.2 挂起点

**规则 SUSP-2**：以下操作是挂起点——编译器自动插入 `await`。⟨目标⟩

| 操作 | 原因 |
|---|---|
| `readFile()` / `readLine()` / `writeFile()` | IO |
| `ch.send(v)` / `ch.receive()` | 通道通信 |
| `t.join()` | 等待任务 |
| `sleep(ms)` | 显式延时 |
| 调用 `@async` 函数 | 传染 |

### 2.3 `@async` 传染

**规则 ASYNC-1**：函数体内调用 `@async` 函数或挂起操作 → **该函数必须标 `@async`**。⟨目标⟩

否则报 `E-NEED-ASYNC`：

```sublimation
fun f(): Str {
    return readFile("...")   // ❌ E-NEED-ASYNC：f 必须标 @async
}

@async fun g(): Str {
    return readFile("...")   // ✅
}
```

**规则 ASYNC-2**：`@async` 函数的调用点——**编译器自动插入 `await`**。⟨目标⟩

**规则 ASYNC-3**：`main` **天然是 `@async`**——不需要标注。⟨目标⟩

**规则 ASYNC-4**：`Task { ... }` 体**天然是 `@async`**——内部可自由挂起。⟨目标⟩

### 2.4 传染范围

**规则 ASYNC-5**：`@async` 传染通过**调用链**传播。一处异步，上层全标。⟨目标⟩

**缓解**：**大部分函数是同步的**——只有真正做异步操作的函数需要标。**传染链通常很短。**

### 2.5 `@async` 是自然命题

**`async<f>`**：函数 `f` 是异步的。⟨目标⟩

| 自然命题 | 默认 | 注入方式 |
|---|---|---|
| `pure<f>` | ✅（未标 `@unpure`） | 自动 |
| `untouch<param>` | ✅（非 `@mut`） | 自动 |
| `immutable<T>` | ✅（无 `@mut` 属性） | 自动 |
| `open<ch>` | ✅（创建时） | 自动 |
| `started<t>` | ❌ | 显式 `start()` |
| **`async<f>`** | **❌** | **显式 `@async` 标注** |

**`async<f>` 和 `started<t>` 同型**——默认不给，显式注入。

**规则 ASYNC-6**：`async<f>` 用于编译器判断"调用 `f` 是否需要 `await`"。⟨目标⟩

### 2.6 `unchecked` 逃逸

**规则 ASYNC-7**：`unchecked` 前缀可逃逸 `E-NEED-ASYNC` 检查。⟨目标⟩

```sublimation
fun f(): Str {
    return unchecked readFile("...")   // 逃逸——用户承担
}
```

**逃逸的语义**：编译器不插入 `await`——**运行时行为由用户负责**。这是危险操作，应极少使用。

## 3. Channel——通道

### 3.1 API

```sublimation
Channel[T]()                // 无缓冲通道（同步握手）
Channel[T](cap)             // 有缓冲通道，容量 cap
ch.send(v): Bool            // 发送——返回是否成功
ch.receive(): T?            // 接收——关闭后返回 None
ch.close(): Null            // 关闭（幂等）
ch.isClosed(): Bool         // 是否已关闭
```

### 3.2 缓冲

**规则 CH-1**：`Channel[T]()` 创建**无缓冲通道**——发送和接收必须同步握手。⟨目标⟩

**规则 CH-2**：`Channel[T](cap)` 创建**有缓冲通道**——容量 `cap`。⟨目标⟩

```sublimation
var ch1 = Channel[Nat]()        // 无缓冲
var ch2 = Channel[Nat](10)      // 有缓冲，容量 10
```

**默认无缓冲**——Go 语义，最纯粹。

### 3.3 `send` 返回 Bool

**规则 CH-3**：`ch.send(v)` 返回 `Bool`——`true` 成功，`false` 通道已关闭。⟨目标⟩

```sublimation
ch.send(1)              // Bool——用户可忽略
if (ch.send(2)) { ... } // 也可以检查
```

**注意**：即使编译器知道通道没关，`send` 仍返回 `Bool`——**"默认关闭"的设计**（按失败可能性设计）。

### 3.4 `receive` 返回 `T?`

**规则 CH-4**：`ch.receive()` 返回 `T?`——`Some(v)` 成功，`None` 通道关闭。⟨目标⟩

```sublimation
var x = ch.receive()    // T?
when (x) {
    Some(v) -> print(v)
    None -> print("closed")
}
```

### 3.5 通道智能转换

**规则 CH-5**：当编译器**确定通道未关闭**时，`ch.receive()` 返回类型**智能转换为 `T`**。⟨目标⟩

**智能转换的场景**：

| 场景 | 编译器判定 | `receive` 返回 |
|---|---|---|
| **本地新建，函数体内任何路径都无 `close(ch)`** | open | **`T`** |
| **本地新建，`close(ch)` 在某条路径上** | 可能关闭 | `T?` |
| **参数 `ch`** | 未知 | `T?` |
| **`if (!ch.isClosed()) { ... }` 分支内** | open | **`T`** |
| **`unchecked` 逃逸块内** | 编译器不管 | **`T`** |

```sublimation
fun local() {
    var ch = Channel[Nat]()
    var x: Nat = ch.receive()   // ✅ 编译器知道 ch 未关闭 → 智能转换为 Nat
}

fun conservative(ch: Channel[Nat]) {
    var x: Nat? = ch.receive()  // T?——参数位保守
}

fun runtimeCheck(ch: Channel[Nat]) {
    if (!ch.isClosed()) {
        var x: Nat = ch.receive()   // ✅ 分支内智能转换为 Nat
    }
}
```

**这是 Kotlin 智能转换的扩展**——不是新机制。

### 3.6 通道状态检查——局部语法

**规则 CH-6**：`ch.send(v)` 报 `E-CHANNEL-CLOSED`——当且仅当**同一函数体内存在 `close(ch)` 调用**（保守：任何路径都算）。⟨目标⟩

```sublimation
fun f() {
    var ch = Channel[Nat]()
    ch.send(1)      // ✅ 函数体内无 close(ch)
    ch.close()
}

fun g(flag: Bool) {
    var ch = Channel[Nat]()
    if (flag) {
        ch.close()
    }
    ch.send(1)      // ❌ E-CHANNEL-CLOSED：close 在可能路径上
}
```

**注意**：`E-CHANNEL-CLOSED` 是**编译期错误**——不是运行时失败。**保守：可能误报。**

**规则 CH-7**：`unchecked ch.send(v)` 逃逸检查。⟨目标⟩

### 3.7 和《副作用与可变性控制》的一致

| 维度 | 可变性控制 | 通道状态 |
|---|---|---|
| **保守默认** | `@mut` 参数默认"会被改" | `send` 默认放行（除非有 close） |
| **局部语法检查** | 函数体内触碰点分析 | 函数体内 close 位置分析 |
| **跨函数** | 保守拷贝 | 信任调用者 |
| **智能转换** | `if (e ? T)` 收窄 | `if (!ch.isClosed())` 收窄 |
| **用户逃逸** | `unchecked` | `unchecked` |

**同一哲学——局部语法检查 + 保守默认 + 智能转换优化 + 用户逃逸。**

## 4. 完整示例

### 4.1 生产者-消费者

```sublimation
@async
fun producer(ch: Channel[Nat]): Null {
    var i = 1
    while (i <= 10) {           // 假设 while 是语法糖（或递归展开）
        ch.send(i)              // Bool——不检查
        i = i + 1
    }
    ch.close()
}

@async
fun consumer(ch: Channel[Nat]): Null {
    var x = ch.receive()
    when (x) {
        Some(v) -> {
            print(v)
            consumer(ch)        // 递归继续
        }
        None -> Null            // 通道关闭
    }
}

fun main() {
    var ch = Channel[Nat](10)   // 有缓冲
    var p = Task { producer(ch) }
    var c = Task { consumer(ch) }
    p.start()
    c.start()
    p.join()
    c.join()
}
```

### 4.2 工作池

```sublimation
fun main() {
    var jobs = Channel[Nat](100)
    var results = Channel[Nat](100)

    // 4 个 worker
    var workers = [Task; 4]     // 假设的数组语法
    for i in 0..3 {
        workers[i] = Task {
            var job = jobs.receive()
            when (job) {
                Some(j) -> {
                    results.send(j * 2)
                }
                None -> Null
            }
        }
        workers[i].start()
    }

    // 生产者
    var producer = Task {
        for i in 1..10 {
            jobs.send(i)
        }
        jobs.close()
    }
    producer.start()

    // 收集结果
    producer.join()
    var i = 0
    while (i < 10) {
        var r = results.receive()
        when (r) {
            Some(v) -> print(v)
            None -> Null
        }
        i = i + 1
    }
}
```

## 5. JS 编译映射

### 5.1 `@async` 函数

```sublimation
@async fun fetch(): Str {
    var x = readFile("f")
    return x
}
```

编译为：

```js
async function fetch() {
    var x = await readFile("f");
    return x;
}
```

### 5.2 `main` 天然 `@async`

```sublimation
fun main() {
    var x = fetch()
    print(x)
}
```

编译为：

```js
(async () => {
    var x = await fetch();
    console.log(x);
})();
```

### 5.3 `Task`

```sublimation
var t = Task { print("A") }
t.start()
t.join()
```

编译为：

```js
// Task { } 创建——返回一个包装对象
const t = (() => {
    let promise = null;
    return {
        start: () => { promise = (async () => { console.log("A"); })(); },
        join: () => promise,
        isAlive: () => promise !== null,   // 简化
    };
})();
t.start();
await t.join();
```

**实际实现需要更精细的任务对象**——但映射方向是明确的。

### 5.4 `Channel`

**无缓冲**：

```js
class Channel {
    constructor(cap = 0) { this.cap = cap; this.queue = []; this.waiting = []; this.closed = false; }
    async send(v) {
        if (this.closed) return false;
        // ... 握手逻辑
        return true;
    }
    async receive() {
        // ... 握手逻辑
        return { tag: "Some", 0: v };  // 或 { tag: "None" }
    }
    close() { this.closed = true; }
    isClosed() { return this.closed; }
}
```

**注意**：`Channel` 需要一个**小运行时**——这是 Sublimation 目前**唯一的运行时组件**。可接受——它只有几十行。

## 6. 与其他子系统的交互

### 6.1 与上下文系统

- **`async<f>`** 是自然命题——和 `pure<f>` 同族
- **通道状态检查**是局部语法分析——不是 Γ 推理
- **智能转换**在 `if (!ch.isClosed())` 分支内生效——复用现有机制

**通道状态不进 Γ**——避免非单调推理。

### 6.2 与副作用与可变性控制

- **`@async` 函数的 `@mut` 参数**——待定 ⬜（挂起期间状态可能变化）
- **`untouch<param>` 的保证**在挂起点需要重新评估

### 6.3 与空安全系统

- `receive(): T?` 与 `T?` 类型糖一致
- 智能转换机制共享

### 6.4 与型类字典

- **`Channel[T]` 是泛型类型**——型类实现走现有字典机制
- **`Task[T]` 同理**

## 7. 待定问题

**Q1：`@async` 函数的 `@mut` 参数怎么处理？**

- **A（倾向）**：不允许 `@mut` 参数——保守
- **B**：允许，但 `untouch` 保证在挂起点"重置"

**Q2：`send` / `receive` 是否总是挂起？**

- **A（倾向）**：总是——调用者必须 `@async`
- **B**：有缓冲且未满时不挂起——编译期无法确定

**Q3：`cancel()` 做不做？**

倾向**不做**——v1 最小 API。

**Q4：`Channel` 的 `send` 是否需要 `@mut`？**

倾向**不需要**——通道是内建可变引用类型，像 `Arc<Mutex<T>>`。

**Q5：`while` 循环要不要引入？**

示例里用了 `while`——但 v1.0 明确不做循环。**示例应改用递归。**

**Q6：`Task` 的错误传播**

- **A（已定）**：传播到 `join()`——`join()` 返回 `Result[T, E]`（如果任务体可能抛错）
- **B**：`join()` 返回 `T`——任务体内部错误必须自行处理

**Q7：`Channel` 是否需要 select？**

Go 的 `select` 允许同时等待多个通道——v1 不做。

### 阶段 1：`@async` 传染 ✅

- 解析器识别 `@async` 注解
- `async<f>` 自然命题注入
- `E-NEED-ASYNC` 检查
- Codegen 生成 `async function` + `await`

### 阶段 2：`main` 和 `Task` 体天然 `@async` ✅

- `main` 特殊处理
- `Task { }` 体的 `@async` 上下文

### 阶段 3：`Task` 类型与 API ✅

- `Task[T]` 类型
- `Task { }` / `start()` / `join()` / `isAlive()`
- `E-NOT-STARTED` 检查

### 阶段 4：`Channel` 类型与 API ✅

- `Channel[T]()` / `Channel[T](cap)`
- `send(): Bool` / `receive(): T?` / `close()` / `isClosed()`

### 阶段 5：智能转换 ✅

- `readFile` / `readLine` / `writeFile` 标记为 `@async`（同步函数调用报 `E-NEED-ASYNC`；挂起点产物包 `await`）
- `sleep` 内建（`new Promise(r => setTimeout(r, ms))`）

- 《语言语法》加 `@async` / `Task` / `Channel`

## 9. 设计权衡记录

### 9.1 为什么不用代数效应

**做效应追踪**（`async<f>` 自然命题）——和 `pure<f>` 同族。

**不做效应处理**（handler + 续延）：

- 需要非单调推理——和上下文系统冲突
- 需要 CPS 转换——JS 后端不支持且违背零运行时
- 和"给普通程序员的编译期验证"定位不符

**如果将来需要效应处理，那是独立子系统，不在上下文系统里。**

### 9.2 为什么创建与启动分离

**和 Java 一致**——用户从 Java 过来，心智模型零成本迁移。

**代价**：多写一行 `t.start()`。

### 9.3 为什么 `send` 返回 `Bool` 而不是 `Null`

**"默认关闭"设计**——按失败可能性设计，用户可忽略可检查。

**和 `receive` 返回 `T?` 对称**——都是保守接口。

### 9.4 为什么通道状态检查用局部语法

**避免非单调推理**：

- 反驳 `open<ch>` 破坏单调性
- 缺省真（closed-world）也是非单调
- 局部语法检查保持单调性
- 和《副作用与可变性控制》一致

### 9.5 为什么智能转换只在"绝对确定"时生效

**保守优先**——不确定时返回 `T?`，用户按传统方式处理。

**绝对确定的场景**：

- 本地新建，函数体内无 close
- `if (!ch.isClosed())` 分支内

**这是 Kotlin 智能转换的扩展**——同一机制，同一边界。

### 9.6 为什么加 `Channel` 运行时

**JS 没有原生 Channel**——必须实现。

**运行时很小**（几十行）——可接受。

**唯一运行时组件**——其他地方仍零运行时。

## 10. 与 Java 的对照表

| Java | Sublimation | 说明 |
|---|---|---|
| `new Thread(r)` | `Task { ... }` | 创建 |
| `t.start()` | `t.start()` | 启动 |
| `t.join()` | `t.join()` | 等待 |
| `t.isAlive()` | `t.isAlive()` | 状态 |
| `Thread.sleep(ms)` | `sleep(ms)` | 延时 |
| `Future<T>` | `Task[T]` | 有返回的任务 |
| `BlockingQueue<T>` | `Channel[T](cap)` | 有缓冲通道 |
| `SynchronousQueue<T>` | `Channel[T]()` | 无缓冲通道 |
| `synchronized` / `Lock` | **不需要** | 单线程无竞争 |
| `volatile` | **不需要** | 同上 |
| `AtomicInteger` | **不需要** | 同上 |
| `InterruptedException` | **不存在** | 协程不会被强制中断 |
| `Thread.interrupt()` | **不做** | v1 无 cancel |

**从 Java 过来——只需要学 `Task` / `Channel` / `@async` 三个概念。**
