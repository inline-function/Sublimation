# 高阶类型

> **本文档状态**：设计草案 v0.1（2026-10-10）
>
> **本文档定位**：定义 Sublimation 的高阶类型（HKT）——让类型构造子（如 `List`）本身可以作为类型参数传递，从而支持 `Functor[F[_]]` 这类抽象。
>
> **本文档与现有文档的关系**：
> - 依赖《形式化规范.md》§2 的类型系统——扩展 `TypeParam` 与合一算法
> - 依赖《上下文系统.md》§2.6 的型类字典机制——HKT 与字典传递协同工作
> - 明确**不做子类型**（宪法第二条）——HKT 是"参数化抽象"，不是"子类型继承"
> - 与《空安全系统.md》交互——`T?` 是 `*→*` 构造子的具体实例
>
> **维护纪律**：本文档记录**设计**。每条规则标 ⟨目标⟩ / ⬜ 待定 / ⚠️ 争议点。
> **归档注记**：v0.1 由 Max 按用户指示归档；示例中的反斜杠 lambda 已同步为 v1.1 大括号语法（`{ n -> … }`）。

## 0. 摘要

### 0.1 问题

现在的型类只能表达"具体类型的抽象"：

```sublimation
class Show[T] {
    fun show(v: T): Str
}
```

`T` 是**类型**（kind `*`）。但很多抽象需要"类型构造子的抽象"：

```sublimation
class Functor[F[_]] {
    fun map[A, B](f: (A) => B, fa: F[A]): F[B]
}
```

`F` 不是类型——它是**类型构造子**（kind `*→*`）。`F[A]` 才是类型。

**这就是高阶类型（HKT）的需求。**

### 0.2 答案

**四层组合**：

1. **语法**：`[F[_]]` 声明 kind 形参，`[F[_, _]]` 支持多参构造子
2. **类型层表示**：`KindVarType(name, arity)` 作为 `Type` 的新子类
3. **合一**：限制在 **pattern unification** 片段——可判定、可预测
4. **四条安全限制**：禁止嵌套 kind 变量、禁止类型层 λ、约束链深度上限、pattern 唯一解

**风格参考 Scala（Kotlin 没有 HKT）——但明确不是子类型系统。**

### 0.3 与 Haskell / Scala 的对比

| 特性 | Haskell | Scala 2 | Sublimation |
|---|---|---|---|
| HKT | ✅ | ✅ | ✅ |
| Pattern unification | ✅ | ✅ | ✅（限制） |
| 子类型 | ❌ | ✅ | ❌（宪法第二条） |
| 类型层 λ | ✅（type families） | ✅（type lambdas） | ❌ |
| 隐式搜索 | ❌（显式字典） | ✅（隐式解析） | ❌（显式查表） |
| **可判定性** | ✅ | ❌ | **✅** |

**Sublimation 的生态位 = Haskell 的 HKT - 类型层 λ - type families**——**可判定的核心区域。**

### 0.4 与 Any 的关系（用户拍板）

**遇到 `Any` 不做类型推导——编译器要求显式标注。**

HKT 场景下的落地：`fun f[F[_]](x: F[Any])` 调用时，**编译器不推导 `F`**——用户必须显式写 `f[List](x)`。

## 1. 语法

### 1.1 kind 形参声明

**规则 HKT-S1**：kind 形参用方括号声明，语法为 `[F[_]]`。⟨已实现：parseTheory 支持 `[F[_]]`，TypeParam.arity⟩

```sublimation
class Functor[F[_]] {
    fun map[A, B](f: (A) => B, fa: F[A]): F[B]
}
```

**单个 `_` 表示一元构造子**（kind `*→*`）。

**规则 HKT-S2**：多参构造子用 `[F[_, _]]`。⟨已实现：同 S1，`_` 计数即 arity⟩

```sublimation
class Bifunctor[F[_, _]] {
    fun bimap[A, B, C, D](f: (A) => C, g: (B) => D, fab: F[A, B]): F[C, D]
}
```

**`n` 个 `_` 表示 `n` 元构造子**（kind `*ⁿ→*`）。

**规则 HKT-S3**：kind 形参与类型形参可以混用。⟨已实现⟩

```sublimation
class Functor[F[_], T] {
    fun f(x: F[T]): F[T]
}
```

`F` 是 kind 形参，`T` 是类型形参。

### 1.2 应用

**规则 HKT-S4**：kind 变量 `F` 只能出现在**应用头位置**。⟨已实现：非应用头由 E-KIND-MISMATCH S5 拦截⟩

```sublimation
F[A]        // ✅ F 是应用头
F[A, B]     // ✅ 多参
[A]         // ❌ A 不是 kind 变量——语法错误
F           // ⚠️ 单独出现——见规则 HKT-S5
```

**规则 HKT-S5**：kind 变量 `F` **不能单独作为类型使用**。⟨已实现：checkTypeResolvable → E-KIND-MISMATCH⟩

```sublimation
fun f[F[_]](x: F): Null   // ❌ E-KIND-MISMATCH：F 需要应用
fun g[F[_]](x: F[Nat]): Null   // ✅
```

**理由**：`F` 是 kind `*→*`——不是类型。`F[Nat]` 才是类型。

### 1.3 impl 的 self

**规则 HKT-S6**：`impl` 的 self 用**显式 kind 占位** `List[a]`。⟨已实现：checkDeclTypes 占位变量并入 tps 豁免 E-UNBOUND-NAME⟩

```sublimation
impl Functor for List[a] {
    fun map[A, B](f: (A) => B, fa: List[A]): List[B] = ...
}
```

**`a` 是隐式引入的类型变量**——`impl` 声明中自动绑定。

**对照 Scala**：

```scala
implicit def listFunctor[A]: Functor[List] = new Functor[List] {
    def map[A, B](f: A => B, fa: List[A]): List[B] = ...
}
```

**Sublimation 更简洁**——`List[a]` 里的 `a` 由编译器自动引入，用户不写 `A =>`。

**规则 HKT-S7**：`impl` self 的 kind 占位变量**不可在方法签名中复用**。⟨目标⟩

```sublimation
impl Functor for List[a] {
    fun map[A, B](f: (A) => B, fa: List[A]): List[B] = ...   // ✅ A 是方法自己的类型参数
    // fun bad(x: List[a]): List[a] = ...                     // ⚠️ a 已在外层绑定——遮蔽或报错待定
}
```

**待定** ⬜：方法签名中出现与 impl self 占位同名的类型参数——遮蔽还是报错？

### 1.4 与现有 `[T]` 语法的关系

**规则 HKT-S8**：类型形参 `[T]` 和 kind 形参 `[F[_]]` 在同一 `[...]` 里声明。⟨已实现：parseTheory 顺序解析，arity 表统一维护⟩

```sublimation
class C[T, F[_], U] { ... }
//      └┬┘ └─┬─┘ └┬┘
//     类型   kind   类型
```

**判定规则**：形参名后跟 `[` 是 kind 形参（arity = 括号内 `_` 的数量）；否则是类型形参。

**与命题参数的统一**：

```sublimation
class C[T, F[_], @p] { ... }
//     类型   kind  命题
```

`@p` 是命题参数（决策 58）——三种参数**统一在同一个 `[...]` 里声明**。

## 2. 类型层表示

### 2.1 `KindVarType` 子类

**规则 HKT-T1**：新增 `KindVarType(name, arity)` 作为 `Type` 的子类。⟨目标⟩

```kotlin
/** kind 变量类型：`F` 表示 arity 为 n 的构造子变量（v2.0 HKT 目标）
 *  - arity = 1 对应 `F[_]`
 *  - arity = 2 对应 `F[_, _]`
 *  - 单独出现（不被应用）时报 E-KIND-MISMATCH */
data class KindVarType(val kvName: String, val arity: Int) : Type {
    override val name: String get() = "(kind:$arity)"
    override val args: List<Type> get() = emptyList()
    override fun render() = if (arity == 1) "$kvName[_]" else "$kvName[" + "_,".repeat(arity - 1) + "_]"
    override fun substT(sub: Map<String, Type>) = this   // kind 变量不参与类型实参替换
}
```

**选择理由**：和 `MutType` 加入 `Type` sealed 的理由相同——**编译器穷尽检查帮我们找全所有 `when` 分支**。若用 `NamedType` 加 `arity` 字段，会失去这个护栏。

**代价**：`Type` sealed 加子类会触发全图检查——`typeEq` / `typeLooseEq` / `containsAny` / `substT` / `baseOf` / `isNominal` / `isSynthetic` / `isUnsealed` / `unify` / `checkTypeResolvable` / `typeToExpr` 全部要加分支。

### 2.2 应用形态

**规则 HKT-T2**：`F[A]` 的类型表示是 `NamedType("F", [A])`。⟨已实现：方案 A⟩

**三个候选**：

- **A**：`NamedType` 复用——`F[A]` 是 `NamedType("F", [A])`，`F` 的 kind 由符号表记录（**已选，已实现**）
- **B**：新增 `KindAppType(kvName, args)` 子类
- **C**：`NamedType` 加一个 `isKindApp: Boolean` 字段

**实现口径**：`F[A]` 和 `List[A]` 结构上相同（都是应用），kind 差异由**符号表 arity** 记录（`tpArityOf`，arity=n ⇔ 类型 `*ⁿ→*`）。实体是 `TypeParam.arity`。`typeEq` 只看结构照旧——kind 校验发生在**可解析性检查**（`checkTypeResolvable`）与**合一**（`unifyInto` 带 arity 表）两个显式环节，不在结构比较里偷换语义。实践验证：`Functor[F[_]]`/`Bifunctor[F[_,_]]` 端到端编译运行通过。

**倾向 A**——`F[A]` 和 `List[A]` 在**结构上相同**（都是应用），差异只在 `F` 的 kind。符号表记录 `F` 的 kind 即可。

**代价**：`typeEq(F[A], List[A])` 时，编译器要知道 `F` 是 kind 变量——**不能只看结构，要看符号表**。这违背了"类型相等只看结构"的原则。

**若选 B**——`KindAppType` 明确区分——但增加一个子类。

**⚠️ 已拍板：方案 A 已实现**（见上文实现口径）。§2.3 的子类连锁影响表不再适用。

### 2.3 子类新增的连锁影响

新增 `KindVarType` 后，以下函数**必须**加分支：

| 函数 | 新分支处理 |
|---|---|
| `typeEq` | 两个 `KindVarType` 同名同 arity → true |
| `typeLooseEq` | 同 `typeEq` |
| `substT` | kind 变量**不参与替换**——返回 `this` |
| `containsAny` | `false`——kind 变量不含 Any |
| `isNominal` | **`false`**——kind 变量不是名义类型 |
| `baseOf` | **`null`**——kind 变量不在符号表 |
| `isSynthetic` / `isUnsealed` | `false` |
| `typeToExpr` | 特殊表示——`NameRef("(kind:$arity)")` |
| `unify` | kind 感知合一（见 §3） |

**Kotlin 编译器会在所有 `when (t)` 处报错**——按 §2.1 逐一补分支。

## 3. 合一规则

### 3.1 四条基本规则

**规则 HKT-U1**：kind 变量与具体构造子合一——**kind 必须匹配**。⟨已实现：unifyInto arity 分支⟩

```
unify(F[_], List)      → F := List    (arity 1 = arity 1) ✅
unify(F[_], Optional)  → F := Optional  ✅
unify(F[_], Nat)       → 失败         (arity 1 ≠ arity 0) ❌
unify(F[_,_], List)    → 失败         (arity 2 ≠ arity 1) ❌
```

**规则 HKT-U2**：kind 应用合一——**递归到实参**。⟨已实现：unifyInto 绑构造子名 + 递归参数合一，TypeInferTest 覆盖⟩

```
unify(F[A], List[Nat])   → F := List, A := Nat    ✅
unify(F[A], List[Str])   → F := List, A := Str    ✅
unify(F[Nat], F[Str])    → 失败                   (Nat ≠ Str) ❌
unify(F[A], G[A])        → F := G                 (kind 相同) ✅
```

**规则 HKT-U3**：kind 变量不能与普通类型变量混淆。⟨已实现：arity 表区分，kind 形参不参与普通变量替换⟩

```
unify(F[_], T)        → 失败     (kind *→* ≠ *)
unify(F[A], T)        → 失败     (kind *≠ *)
```

**规则 HKT-U4**：pattern 边界——**禁止嵌套 kind 变量**。⟨已实现：E-NON-PATTERN-HKT，见 §4.1⟩

```
unify(F[G[Nat]], List[List[Nat]])   → ❌ E-NON-PATTERN-HKT
```

**理由**：`G[Nat]` 作为 `F` 的应用实参——`G` 是变量，`F` 也是变量。这超出 pattern 片段，可能不可判定。

**用户替代方案**——显式标注类型：

```sublimation
fun f[F[_], G[_]](x: F[G[Nat]]): Null { ... }
// 调用点必须显式：f[List][Optional](x)
```

### 3.2 与现有 `unify` 的整合

现有 `TypeInfer.unify(a, b)` 返回 `Type?`——**统一后的类型或 null**。

HKT 需要**扩展为返回替换表**：

```kotlin
/** 合一结果：类型变量替换表 + kind 变量替换表 */
data class UnifyResult(
    val typeSub: Map<String, Type>,       // A := Nat
    val kindSub: Map<String, Type>,       // F := List
)
```

**⚠️ 这是 `TypeInfer` 的重写点**——现有 `unify` 只返回单一类型，HKT 需要返回多个绑定。

**若不做替换表**——只支持"单一 kind 变量的场景"——复杂度降低但覆盖不全。

**倾向**：**v2.0 先做替换表**——一次到位，避免后续返工。

### 3.3 可判定性保证

**规则 HKT-U5**：合一限制在 **pattern 片段**内。⟨已实现：构造子名零实参 + pattern 递归合一⟩

**Pattern 的定义**（Miller 1991）：

```
F(x₁, ..., xₙ)   其中：
  - F 是自由 kind 变量
  - x₁, ..., xₙ 是互相独立的普通类型变量
  - 没有重复变量
```

**Sublimation 的落地**：`F[A]` 里 `A` 必须是**独立的类型变量**（如 `[A]` 声明的）——不能是复合项（如 `List[Nat]`）。

**规则 HKT-U6**：pattern 片段内**有唯一最一般解**（unitary）——不存在歧义。⟨已实现：占位判据（零实参+小写首字母）保证唯一解⟩

**这是可判定性的核心保证**——不需要搜索，直接解。

## 4. 四条安全限制

**这四条不是"未来扩展"——是 HKT-1 的核心约束。从第一天就守住。**

### 4.1 限制一：禁止嵌套 kind 变量

**规则 HKT-R1**：kind 变量的应用实参**必须是独立类型变量**——不能是另一个 kind 变量的应用。⟨已实现：E-NON-PATTERN-HKT⟩

```sublimation
F[A]         // ✅ A 独立类型变量
F[G[Nat]]    // ❌ G 是 kind 变量——嵌套
F[List[A]]   // ❌ List[A] 是复合项
```

**违反**：`E-NON-PATTERN-HKT`。

**用户替代**：显式标注类型——`f[List][Optional](x)`。

### 4.2 限制二：禁止类型层 λ

**规则 HKT-R2**：**不引入类型层 λ**——没有 `type Id = [T] => T`。⟨已实现：语言无此语法，天然达成⟩

**理由**：类型层 λ 配合 β-归约会超出 pattern 片段——Scala 的 type lambdas 和 Haskell 的 type families 都走这条路。

**替代**：用**具名类型别名**：

```sublimation
type PairOf[T] = (T, T)     // ✅ 具名
// type Id = [T] => T       // ❌ 匿名 λ——不引入
```

### 4.3 限制三：约束链深度上限

**规则 HKT-R3**：型类约束链**深度上限 8**。⟨⬜ R3：约束解析链路待 HKT-4（约束槽 `[T: Functor]` 泛型场景）⟩

```sublimation
fun f[F[_]](x: F[Nat]) <Functor<F>, Monad<F>, Traversable<F>, ...>
```

**超限**：`E-CONSTRAINT-DEPTH`。

**理由**：即使每步可判定，搜索可能指数爆炸。**Sublimation 的字典是显式查表**（决策 60），不搜索——但仍需防御性上限。

### 4.4 限制四：pattern 唯一解

**规则 HKT-R4**：`unify(F[A], X)` 里 `X` 必须是**具体的 kind 应用**或**另一个 pattern**。⟨已实现：同 R1 保证（类型层 λ 与嵌套均被禁）⟩

```sublimation
unify(F[A], List[Nat])   → ✅ F := List, A := Nat
unify(F[A], G[B])        → ✅ F := G, A := B（两边都是 pattern）
unify(F[A], [T] => T)    → ❌ 类型层 λ——不引入
```

**理由**：保证 unitary（唯一最一般解）。

## 5. 与 Any 的交互（用户拍板）

### 5.1 核心规则

**用户原话**："遇到 `Any` 时不进行类型推导，编译器要求显式标注。"

**规则 HKT-A1**：`F[Any]` 出现时，**编译器不推导 `F`**。⟨目标⟩

```sublimation
fun f[F[_]](x: F[Any]): Null { ... }

f(List[Any])           // ❌ E-KIND-ANY：F 推导失效，须显式标注
f[List](List[Any])     // ✅ 显式标注 F := List
```

### 5.2 为什么这样设计

`Any` 是**受限顶类型**——它接受任意值，但**推导失效**（决策 59）。HKT 场景下：

- `F[Any]` 的 `F` 可以是 `List` / `Optional` / `Array` ...
- 仅从 `F[Any]` 无法反推 `F` 是哪个构造子
- **子类型系统会做"向上推导"**——但 Sublimation **不是子类型系统**

**保守做法**：拒绝推导，要求显式。

### 5.3 三个子问题

**子问题 1：`Functor[Any]` 合法吗？**

- **A**：合法——`Any` 是类型，`Functor[Any]` 是具体应用
- **B**：不合法

**倾向 A**——但所有对 `A` 的操作需显式标注。

**子问题 2：`unify(F[Any], F[Nat])` 成功吗？**

**失败**——`Any` ≠ `Nat`，`F` 的实参不同。

**子问题 3：`Functor[Any]` 能作为 `Functor[F[_]]` 的实参吗？**

```sublimation
fun g[F[_]](x: F[Nat]) <Functor<F>>: Null { ... }

g(Functor[Any])   // ❌ Functor[Any] 不是类型——它是 kind *→* 的应用
```

**失败**——`Functor` 是 kind `*→*`，`Functor[Any]` 是 `*`。`g` 需要 `F[_]` 的实参（比如 `List`），不是 `Functor[Any]`。

## 6. 与现有系统的交互

### 6.1 与型类字典

**规则 HKT-D1**：HKT 的型类实例**仍走字典传递**（决策 60）。⟨已实现：dict 名不含占位，`dict_Functor_List`⟩

```sublimation
impl Functor for List[a] {
    fun map[A, B](f: (A) => B, fa: List[A]): List[B] = ...
}
```

**字典名**：`dict_Functor_List`——**`List` 是构造子名，不含 `[a]`**。

**规则 HKT-D2**：字典的 self 是**构造子**（`List`），不是具体类型（`List[Nat]`）。⟨已实现：kind 型类字典签名 `(d, f, fa)` 无 `__self`，kind 应用位分发，点号式与自由式双形态⟩

**理由**：`Functor[List]` 的实例对**所有** `List[T]` 有效——不只是 `List[Nat]`。

### 6.2 与 `MutType` / `FunType` / `TupleType`

**规则 HKT-X1**：`KindVarType` 与现有类型子类**正交**。⟨目标⟩

- `F[MutType]`——`F` 应用可变类型——**合法**（待测试）
- `F[(A) => B]`——`F` 应用函数类型——**合法**
- `F[(A, B)]`——`F` 应用元组类型——**合法**

**规则 HKT-X2**：`KindVarType` **不参与** `containsAny` / `immutable` / `mut` 等检查。⟨目标⟩

- `F[_]` 本身不含 Any（无论 `F` 实例化成什么）
- `F[_]` 不参与 `immutable<F>` 判定

### 6.3 与空安全系统

**规则 HKT-X3**：`T?` 是 `Optional` 的语法糖——`Optional` 是 kind `*→*` 的具体实例。⟨目标⟩

```sublimation
class Functor[F[_]] { ... }

impl Functor for Optional[a] {
    fun map[A, B](f: (A) => B, o: Optional[A]): Optional[B] = ...
}
// 也可以写 impl Functor for Nat? 吗？
// ⚠️ 待定：`Nat?` 是 `Optional[Nat]`，是具体类型，不是构造子
```

**`impl Functor for Nat?` 非法**——`Nat?` 是具体类型（kind `*`），不是构造子。

**正确写法**：`impl Functor for Optional[a]`。

### 6.4 与副作用与可变性控制

**规则 HKT-X4**：HKT 与 `@mut` / `immutable` 的交互**待设计**。⟨目标，⬜ 待定⟩

```sublimation
fun f[F[_]](x: F[MutType]): F[Nat] { ... }
```

`F` 应用可变类型——`F` 是泛型的，未知其是否支持可变——**语义待定**。

**倾向**：v1 只支持 `F` 应用**不可变类型**。`F[@mut T]` 报错。

## 7. 完整示例

### 7.1 `Functor` 的完整形态

```sublimation
class Functor[F[_]] {
    fun map[A, B](f: (A) => B, fa: F[A]): F[B]
}

impl Functor for List[a] {
    fun map[A, B](f: (A) => B, fa: List[A]): List[B] = when (fa) {
        Nil -> Nil
        Cons(h, t) -> Cons(f(h), map(f, t))
    }
}

impl Functor for Optional[a] {
    fun map[A, B](f: (A) => B, o: Optional[A]): Optional[B] = when (o) {
        None -> None
        Some(v) -> Some(f(v))
    }
}

fun main() {
    var xs = Cons(1, Cons(2, Nil()))
    var ys = map({ n -> n * 2 }, xs)   // 字典分发：Functor[List]
    print(ys)   // Cons(2, Cons(4, Nil()))
}
```

### 7.2 `Bifunctor` 的多参形态

```sublimation
class Bifunctor[F[_, _]] {
    fun bimap[A, B, C, D](f: (A) => C, g: (B) => D, fab: F[A, B]): F[C, D]
}

struct Pair[A, B](first: A, second: B)

impl Bifunctor for Pair[a, b] {
    fun bimap[A, B, C, D](f: (A) => C, g: (B) => D, p: Pair[A, B]): Pair[C, D] =
        Pair(f(p.first), g(p.second))
}
```

### 7.3 与 Any 的交互

```sublimation
fun process[F[_]](data: F[Any]): Null { ... }

// ❌ 编译器拒绝：F 推导失效
process(Some(5))

// ✅ 显式标注
process[Optional](Some(5))
```

## 10. 设计权衡记录

### 10.1 为什么用 `[F[_]]` 而不是 `[F: Kind1]`

**理由**：

- `[F[_]]` 更直观——`_` 的数量直接对应 arity
- 和 Scala 一致（Scala 2 的 `Functor[F[_]]`）
- Kotlin 没有 HKT——没法参考
- `[F: Kind1]` 需要引入 `Kind1` / `Kind2` 等独立类型——复杂

### 10.2 为什么不是子类型系统

**宪法第二条明确**——**不做子类型**。

**HKT 是"参数化抽象"**——`F[_]` 是"未知的构造子变量"，不是"某类型集合的子集"。

**与 Scala 的对比**：

- Scala 有子类型 + 型变 + HKT——**复杂**
- Sublimation 只有 HKT——**简单**

### 10.3 为什么限制在 pattern 片段

**可判定性保证**：

- 一般高阶合一——Huét 证明 **undecidable**
- Pattern 合一——Miller 1991 证明**可判定且 unitary**

**Sublimation 的 HKT 停在 pattern 片段——这是唯一的"安全区"。**

### 10.4 为什么不做类型层 λ

**理由**：

- 类型层 λ（`[T] => T`）配合 β-归约会超出 pattern 片段
- Scala 的 type lambdas 和 Haskell 的 type families 都走这条路——**代价是不可判定**
- Sublimation 用**具名类型别名**代替——够用

### 10.5 为什么 HKT 与 Any 不推导

**用户拍板**——"遇到 Any 不推导，编译器要求显式标注"。

**理由**：

- 不是子类型系统——不能从 `Any` 反推
- 保守——避免"看似推导成功实则错误"
- 用户显式标注——和"编译器不是天才"哲学一致

### 10.6 为什么字典的 self 是构造子

**`Functor[List]` 对所有 `List[T]` 有效**——不是只对 `List[Nat]`。

**字典名 `dict_Functor_List`**——不含 `[a]`。

**和现有 `dict_Show_Int` 同构**——只是 self 从具体类型变成了构造子。
