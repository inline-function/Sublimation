## 0. 摘要

**上下文系统 = 把 Kotlin 智能转换泛化到任意命题。**

Kotlin 的智能转换：`if (x is String) { x.length }` —— 编译器在分支内自动知道 `x : String`，用户什么都不用写。

Sublimation 的泛化：

- `var n = 0` → 编译器自动知道 `n = 0`、`n : Nat`
- `if c { ... }` → 分支内自动知道 `c = true`
- `when (o) { Some(v) -> ... }` → 分支内自动知道 `o = Some(v)` 与 `v` 的类型
- `f(x)` 调用后 → 自动吸收 `f` 的后置命题
- `if[P] { ... } else { ... }` → 在两个分支里分别知道 `P` 与 `¬P`（需经典逻辑挂载）

这些**命题事实**在作用域里**弥散**——跨语句、跨块、跨函数。编译器维护一个命题多重集 Γ，所有语法构造都在向 Γ 注入事实或从 Γ 索取证据。

**核心承诺**：用户写普通代码，编译器自动推理。**用户手写命题的次数，是衡量系统成功的指标**——v1.0 的验收标准即"500 行真实程序里 `unchecked.axiom` 出现 < 5 次"。

**三条逃生通道**：自动证不出 → 手动 tactic 补 → 再不行才 `unchecked.axiom`。**编译器不是天才**——90% 自动覆盖是设计目标，不是缺陷。

## 1. 定位：智能转换的泛化

### 1.1 起源

Kotlin 的智能转换解决一个具体问题：**编译器如何在分支内知道比类型声明更多的信息**。

```kotlin
fun describe(x: Any): String =
    if (x is String) x.length.toString()
    else "not a string"
```

在 `then` 分支内，`x` 的类型从 `Any` **收窄**为 `String`。这是编译器**从语法结构推断出的额外事实**。

Kotlin 只做了一件事：**类型收窄**。

### 1.2 泛化

Sublimation 问：**为什么只收窄类型？**

- `var n = 0` 之后，编译器能否知道 `n = 0`？—— 能。
- `if n > 0 { ... }` 之内，编译器能否知道 `n > 0`？—— 能。
- `f(x)` 之后，编译器能否知道 `f` 的所有后置命题？—— 能。
- `if[P] { ... } else { ... }` 两个分支内，编译器能否分别知道 `P` 和 `¬P`？—— 能（需经典逻辑）。

**一旦把"编译器知道什么"从类型扩展到任意命题，就得到了上下文系统。**

### 1.3 三个隐含结论

**结论一：命题不是值。** 它不进 JS、不占内存、不作为参数传递。它**只存在于编译期**，是编译器维护的一张事实表。

**结论二：命题不是手动输入的。** 用户写 `var n = 0` 时不需要写 `n = 0`；编译器**从语法结构自动吸收**。前/后置命题是**接口保证**（写才有），不是**日常工具**。

**结论三：跨函数推理是自然的。** `f(x)` 的调用者不需要知道 `f` 里怎么算的——只需要知道 `f` 的后置命题。这是**接口契约**在编译期的落地。

## 2. 核心概念

### 2.1 Γ（命题多重集）

**定义**：Γ 是作用域内命题事实的多重集。条目 ::= 命题（`p`、`n<ts>`、`e = e'`、`e : T`、`∀x.p`、`p → q`、伴生记录 `f<args>`、`pure<f>` …）。⟨实现⟩

**性质**：

- **多重集**而非集合——同一命题可以出现多次（不同来源），去重由证明器在判定时做
- **不跨函数边界**——函数体是独立帧（决策 21）
- **块事实回溢父帧**——嵌套块内的注入在块结束后并入父帧，但**内层命题不外溢**（除块回溢约定外）

### 2.2 弥散

**定义**：命题像气体一样在作用域里流动。

**来源**：⟨实现⟩

1. **显式注入**：`unchecked.axiom[q]`、`by [q]`
2. **声明注入**：`var n = e` 注入 `n = e`（仅纯值、非 `@mut`，决策 35）与 `n : T`
3. **类型测注入**：`n : Nat` 作为语句时，注入 `n : Nat`（智能转换）
4. **分支条件**：`if`/`when` 分支内注入条件命题
5. **调用后置**：`f(x)` 调用后，`f` 的下文注入
6. **伴生记录**：`f(x)` 调用后，伴生命题 `f<x>` 注入

### 2.3 上文与下文

**上文（前置）**：`fun f(...) <P> : T` 里的 `<P>`。调用 `f` 前必须在 Γ 里找到 `P` 的证明。缺 → `E-PRE-UNPROVEN`。⟨实现⟩

**下文（后置）**：`fun f(...) : T [Q]` 里的 `<Q>`。**函数体的证明义务**——体末尾 Γ 必须蕴含 `Q`。缺 → `E-POST-UNPROVEN`。⟨实现⟩

**函数体是证明义务，声明不是可信公理**。逃生门只有 `unchecked.axiom`。`fun bad() <P> : Null = {}` 必须报错——`P` 不可凭空合法。⟨决策 18⟩

### 2.4 伴生命题

**定义**：函数 `f` 被调用 ⇔ 伴生命题 `f<args>` 被证明。⟨决策 38/55⟩

**作用**：承载**调用痕迹性质**。

**例**（用户原话）：map 函数的下文

```
self.size() ≠ 0 ↔ ∃a. a ∈ self ∧ f<a>
```

读作"列表非空，当且仅当 `f` 以某元素被调用过"。**伴生命题是"参数被调用过"的表达方式**。

**伴生公理**：`f<x> → ps₂[x]`（决策 38）——下文可由伴生命题经公理派生。

**当前实现**：调用点**直接注入下文**与**伴生记录**两条，**共存不二选一**（决策 55）。伴生公理规则库待扩展。⟨实现⟩

### 2.5 供给

**定义**：调用点向上文提供证据。

**两种**：

- **自动**：从 Γ 检索，0 元候选。歧义 → `E-PROP-AMBIGUOUS`。⟨实现⟩
- **显式**：`f<q>()` 尖括号。显式仅用于解歧，平时禁止冗余显式。⟨决策 4⟩

### 2.6 上下文驱动行为

**命题不只是传参用，还能改变编译行为**。⟨决策 54⟩

**三个落地实例**：

1. **`e : Nat` 智能转换**：持有 `e : Nat` 时，`e` 可使用 `Nat` 的方法
2. **`pure<f>` 放行非纯调用**：持有 `pure<f>` 时，编译器认为对 `f` 的调用是纯的
3. **约束事实**（P6）：`T : Show` 与命题参数同构，走同一套供给机制

## 3. 命题层

### 3.1 命题语法

**Prop 树**（`Prop.kt` sealed interface）：⟨实现⟩

```
Prop ::= ⊤ | ⊥
       | ¬P
       | P ∧ Q | P ∨ Q | P → Q | P ↔ Q
       | ∀x.P | ∃x.P | ∃!x.P
       | PAtom(head, terms)         # 一切原子命题
```

`PAtom` 承载：0 元（`p`）、参数化（`valid<7>`）、比较/等式（`$ == 7` → `PAtom("==", [$, 7])`）。

**结构事实**（`PAtom` 的特殊 head）：

- `=`、`==`、`!=`、`<`、`>`、`<=`、`>=`——比较与等式
- `:`——类型事实
- `$`——返回值指代
- `pure`——纯度命题
- `\$${n}`——参数引用（`$n`）

### 3.2 命题算符

**Unicode 是唯一写法**：⟨实现⟩

| 类别 | 记法 |
|---|---|
| 命题等式 | `e₁ = e₂` |
| 类型事实 | `e : T` |
| 函数比较 | `==` `!=`（Bool 函数，禁中缀） |
| 逻辑 | `∀ ∃ ∃! ∧ ∨ ¬ → ↔ ⊤ ⊥` |
| 返回值 | `$` |
| 参数引用 | `$1` `$2` … |

**u-系算符退役**：`u->` / `u&` / `u|` / `u<->` / `u!=` **不是语言的一部分**——它们是打不出 Unicode 时的心理替代，由**语言服务**在录入时替换为 Unicode。**编译器不识别它们**。⬜ 待执行（见《待办.md》修-1）

### 3.3 量词

**支持**：⟨实现⟩

- `∀x.P`——单名全称（多元待扩展，见 §4.4）
- `∃x.P`——单名存在
- `∃!x.P`——解析支持，**推理待 P4 后**

**待扩展**：⬜

- **多元量词** `∀x,y. P<x,y>`——当前 `names.size != 1` 直接跳过（形式化规范 §4.2）
- **多名字量词**——同多元量词

### 3.4 类型事实与相等

**类型事实**：`e : T`。⟨实现⟩

- **智能转换**：`n : Nat` 作为语句，注入 Γ，使 `n` 可用 `Nat` 方法
- **类型参数**：泛型变量在函数体内以 `T : <类型>` 形式存在（隐式）

**相等**：`e₁ = e₂` 是**纯命题**，编译期概念，**不代表运行时相等**。⟨实现⟩

- 用 `==` 函数表达**运行时结构相等**（Bool 值），禁中缀（决策 32）
- 用 `=` 命题表达**编译期相等事实**

### 3.5 命题来源（弥散六通道）

参见 §2.2，此处列**具体语法形态**：

| 来源 | 语法 | 注入的命题 |
|---|---|---|
| 变量声明 | `var n = 0` | `n = 0`、`n : Nat`（P4 起：纯函数调用也注入，决策 80） |
| 类型测语句 | `n : Nat` | `n : Nat` |
| 公理 | `unchecked.axiom[q]` | `q` |
| 辅助 | `by [q]` | `q`（决策 48，暂缓） |
| 分支条件 | `if c { ... }` | 分支内 `c = true` / `c = false` |
| when 分支 | `when(o) { Some(v) -> ... }` | `∃v. o = Some(v)`（分支内 ground） |
| 调用后置 | `f(x)` 后 | `f` 的下文（`$` 替换为调用表达式） |
| 伴生记录 | `f(x)` 后 | `f<x>` |
| **命题分派** | `if[P] { ... } else { ... }` | 分支内 `P` / `¬P`（需 `core.classic`）⬜ |
| **重写** | `a => b : P` | `P[b]`（重写后）⬜ |
| **存在见证** | `∃ n = e . P` | `P[n := e]` 已证时，`∃n. P` ⬜ |

## 4. 自动推理（自动层）

**目标**：覆盖日常推理的 90%。**健全但不完备**——证不出的用 `unchecked.axiom` 或手动 tactic 补。

### 4.1 饱和闭包

`Prover.closure`：从 Γ 迭代推出新事实至不动点。⟨实现⟩

**规则**：

1. **合取分解**：`P ∧ Q` → `P`、`Q`
2. **双否消去**：`¬¬P` → `P`
3. **∀ 单名实例化**：`∀x. P<x>` + 候选项 → `P<t>`
4. **MP 前向链接**：`p` 与 `p → q` → `q`
5. **矛盾检测**：`p ∧ ¬p` → `⊥`

**候选项**：Γ 现有 ground 项 ∪ **目标项**（工程规范 I-7）。⟨实现⟩

**轮数**：`maxRounds = 3`（经验值）

### 4.2 目标判定

`Prover.prove`：⟨实现⟩

- **语法同一**：`goal ∈ facts`
- **`=`/`==` 自反律**
- **`∃` 单见证**：遍历 ground 项
- **`∨` 子集**（方向受限，I-6）：事实的析取子项 ⊆ 目标的析取子项
- **`⊥` 爆炸**：Γ 含 `⊥` → 一切可证
- **`PImp` 前件/后件匹配**
- **构造子单射**：`C<a> = C<b> → a = b`
- **α-等价**：绑定变量按出现序重命名后比较（I-5）

### 4.3 等式推理（P4 已落地，决策 80）⟨实现⟩

**方案**（与 v1.0 计划 §6.3 一致，2026-10-09 落地）：

- **对称**：并入**等式图 BFS 的无向边**——`a = b` 建边 a↔b，天然双向匹配，Γ 只存一个方向
- **传递**：**等式图 BFS**（I-23：目标侧做，不改 Γ；I-24：不递归；O(V+E) 有界）——`proves` 入口一次性预提取 `=`/`==` 事实（`eqs`）供整次证明共享
- **代换**：**浅层重写**（`proveWithSubst`）——一层，不递归；**端点预筛**（目标项不落在任何等式端点上直接失败）；`d+1` 参与深度上限
- **类型事实**：目标 `e' : T` 时，`typeFactEq` 用 `eqReachable(e, e')` 找 `e : T`
- **配套**：证明路径**环剪枝**（同目标在路径重现即剪，防双向替换横跳 `<f(5),5>↔<x,5>`）；`isPureValue` 放宽——**纯函数调用**（无 `@unpure`）也注入 `var x = f(5)` 等式，供 `x = f(5), f(5) = 5 ⊢ x = 5` 类链式推理（决策 80；@unpure 不注入）

**性能**：showcase 从无 P4 的 ~8.5s 降至 ~3s（visited 剪枝 + eqs 预提取）；合成 243 行 ~3.5s。

**P4 之后的升级路径**（**P11 压测暴露性能问题再考虑**，现不投入）：⬜

- **Congruence closure**：并查集 + 函数符号一致性，O(n log n)
- **Superposition**：有序重写（需要项序，引入不确定性）

### 4.4 关键表达式池（新设计）⬜

**用户方案**（2026-10-08 讨论）：

**核心思想**：编译器维护一个**项池**，量词实例化对所有池中项产生实例。

**池来源**：

1. 源码 AST 的所有子表达式，**递归拆到原子**
2. Γ 里的 ground 项
3. **推理产生的新表达式**（不动点迭代）

**例**：`print(1 + 2)` 产生四个关键表达式：`print(1+2)`、`1+2`、`1`、`2`。

**量词实例化**：

- `∀a. p<a>` 对**池中每个项**生成 `p<t>`
- `∀a,b. p<a,b>` 生成**笛卡尔积**

**风险与对策**：

- **指数爆炸**：多元量词笛卡尔积 → **锚点机制**（trigger-based）
- **终止**：**预算机制**代替超时
  - 每轮最多产生 K 条新事实（建议 K = 1000）
  - 总量上限 N（建议 N = 10000）
  - 量词每次最多 M 个实例（建议 M = 100）
  - 超预算 → `E-SATURATION-BUDGET`（提示级，非错误）
- **爆炸范围限制**：**仅支持纯表达式的量词**——涉及类型和命题的量词**不实例化**（用户原话："太爆炸了"）

**多元量词锚点**：

- 一元：全池实例化（原方案）
- 多元：**要求至少一个模式锚点**——`∀a,b. f<a,b>` 只有 Γ 里出现 `f<x,y>` 时才实例化 `a := x, b := y`
- 三元以上：**v1 不支持**

**待决**（见 §10）：

- 池的收集范围：函数体 / 模块 / 全项目？
- 新表达式何时进池：每轮批量还是实时？
- 类型量词是否永久不支持？

### 4.5 与主流算法的对比

**现代定理证明器**（Vampire/E/Z3）有更成熟的算法：term indexing、E-matching、superposition、congruence closure。

**Sublimation 的取舍**：

- **可预测性 > 理论最优**——编译器错误要能解释"为什么证不出"，SMT 求解器只会说 `unknown`
- **窄域不需要通用优化**——项池有界（几十到几百项），量词都来自用户显式声明，无算术推理
- **吸收三招**：有向重写（对称律退役）、预算（超时退役）、锚点（多元量词限制）

**明确不做**：CDCL(T)、MBQI、完整 Inst-Gen、算术片段、完整 superposition。

## 5. 手动推理（手动层）⬜

**目标**：自动层覆盖 90%，**剩下 10% 用函数化的 tactic**。不引入独立证明脚本语言。

### 5.1 Tactic 即函数

**核心洞察**（用户 2026-10-08）：**函数就是 tactic**。

```sublimation
fun powerRuleForExponents(a, b, c)
    : <(a ^ b) ^ c = a ^ (b * c)>
{ ... }
```

调用 `powerRuleForExponents(√2, √2, √2)` → 后置命题注入 Γ。**不需要 `by`、`apply`、`refine` 这些命令词**。

**用户自写 tactic**：任何 `fun f<...> : <...>` 都是 tactic。`core.*` 模块是官方库。

### 5.2 命题层构造

**三个新增构造**（语法见《语言语法.md》命题层章节，待写）：

#### 5.2.1 存在见证：`∃ n = e₁, m = e₂ . P`

⟨部分实现：需要"给定见证"形态⟩

**语义**：把 `P` 中的 `n, m` 替换为 `e₁, e₂`，自动尝试证明替换后的命题；成功则把 `∃n,m. P` 注入 Γ。

**位置**：语句位（作为断言）、表达式位（返回命题）。

#### 5.2.2 莱布尼茨重写：`a => b : P`

⬜ 待实现

**语义**：

- 单向：在 `P` 中把 `a` 的所有出现替换为 `b`
- 语法等价匹配（不 α-等价）
- 作为**语句**：重写 `P` 产生 `P[b]`，作为新目标尝试证明
- **仅语句位**——P 到语句尾（避免 `:` 与类型测歧义）

**挂载要求**：**无**——莱布尼茨律是等式的核心规则，构造性和经典性都接受。

#### 5.2.3 排中律分派：`if[P] { ... } else { ... }`

⬜ 待实现

**语义**：

- **then 分支**：Γ ∪ {`P`}，需证外层目标
- **else 分支**：Γ ∪ {`¬P`}，需证外层目标
- 两分支均证 → 排中律消去，外层目标成立
- **不产生值**——纯证明构造。产物里**无对应 JS 分支**

**挂载要求**：**需 `core.classic`**——默认逻辑是构造性，`if[P]` 需显式声明"我用经典逻辑"。不挂载时报 `E-NEED-CLASSIC`。

**与 `when` 的分工**：

- `when e { pat -> ... }`：**值的形态**（枚举、字面量、类型、元组）
- `if[P] { } else { }`：**命题的真假**

两者正交，可嵌套。

### 5.3 无理数幂定理示例（全文）

**定理**：∃n,m. irrational(n) ∧ irrational(m) → ¬irrational(n^m)

**前提**：irrational(√2)、¬irrational(2)

```sublimation
fun irrPowCounterexample
    <irrational<sqrt(2)>, ¬irrational<2>>
    : <∃n, m. irrational<n> ∧ irrational<m> → ¬irrational<n ^ m>>
{
    if[irrational<sqrt(2) ^ sqrt(2)>] {
        powerRuleForExponents(sqrt(2), sqrt(2), sqrt(2))
        sqrtMulSelf(2)
        sqrt(2) * sqrt(2) => 2 :
            (sqrt(2) ^ sqrt(2)) ^ sqrt(2) = sqrt(2) ^ (sqrt(2) * sqrt(2))
        sqrtSquare(2)
        sqrt(2) ^ 2 => 2 :
            (sqrt(2) ^ sqrt(2)) ^ sqrt(2) = sqrt(2) ^ 2
        ∃ n = sqrt(2) ^ sqrt(2), m = sqrt(2) .
            irrational<n> ∧ irrational<m> → ¬irrational<n ^ m>
    } else {
        ∃ n = sqrt(2), m = sqrt(2) .
            irrational<n> ∧ irrational<m> → ¬irrational<n ^ m>
    }
}
```

**读法**：

- `if[P] { } else { }`：分两种情况（`P = irrational(√2^√2)` 或 `¬P`）
- `powerRuleForExponents(...)`：断言幂律，注入等式
- `sqrtMulSelf(2)`：断言 `√2 · √2 = 2`
- `a => b : P`：把 `P` 中的 `a` 换成 `b`
- `∃ n = e, m = e' . Q`：给出见证，构造存在命题
- 两个分支都构造出同一个存在命题 → `if[P]` 消去 → 定理得证

**文风对照**（见 §8）：**陈述派**——每行是**陈述**而非**命令**。

## 6. 逻辑基底与可扩展性

### 6.1 默认逻辑：构造性 ⬜（待正式拍板）

**立场**：Sublimation 默认是**构造性/直觉主义**逻辑。

**理由**：

- 排中律 `P ∨ ¬P` 不是自动有的——用户不构造地知道 `P` 或 `¬P`
- `if[P]` 需要显式挂载 `core.classic` 才能用
- 保持选择权——证构造性定理时不"作弊"地偷偷用排中律

**未定**：⬜

- **爆炸原理 `⊥ → P` 默认开吗？** 构造性逻辑里合法，但有些系统拒绝
- **默认逻辑的精确表述**——哪条规则集？

### 6.2 `core.classic` 挂载

**定位**：可选挂载的模块，提供经典逻辑公理与 tactic。

**示例**：

```sublimation
// core/classic.subl
fun lawOfExcludedMiddle[@p] : <p ∨ ¬p> { ... }
```

**挂载方式**：待 P0 模块系统落地后，用户显式 `mount core.classic`。

**未定**：⬜

- `core.classic` 是必需模块还是隐式可用？
- 是标准库一部分还是独立包？

### 6.3 用户自写 tactic

**形式**：任何 `fun f<...> : <...>` 都是 tactic。

**用途**：

- 领域公理（如 `powerRuleForExponents`）
- 常用推理模式（如 `lawOfLeibniz`）
- 用户特定领域的引理库

**组合性**：tactic 是函数，能互相调用。

## 7. 健全性、完备性、预算

### 7.1 健全性 100%

**承诺**：检查器通过 ⇒ 生成的 JS 不违反任何已证命题。

**例外**：`unchecked.axiom[q]` —— 用户**主动**信任 `q`。这是**审计痕迹**（`// axiom: q` 注释），不是漏洞。

**待写**：⬜ 精确的 soundness 论证（T 轨远期项）

### 7.2 完备性 90%

**立场**：自动证明**不追求证明一切**。用户原话："**我们只要求 90%，就是最常见的那种相等传递啊，蕴含啊之类的。允许编译器不是天才。**"

**技术含义**（形式化规范 §4.4）：

- 不做算术推理（`abs≥0`）
- 不做多名字量词（3 元以上）
- 不做递归等量代换（浅层够）
- 不做完整 `∨`/`¬`/`→` 规则
- 不做 congruence closure 全量

**P11 验收**：500 行真实程序里 `unchecked.axiom` 出现 < 5 次。

### 7.3 三条逃生通道

| 层 | 机制 | 何时用 |
|---|---|---|
| **自动** | `Prover` 饱和 + 等式 + 关键表达式池 | 90% 日常 |
| **手动** | 命题层构造 + `core.*` tactic 库 + 用户自写 tactic | 10% 复杂 |
| **信任** | `unchecked.axiom[q]` | 兜底（应罕见） |

**用户心智模型**：看到 `E-PRE-UNPROVEN` 的第一反应是"**编译器没证出来，我补一条 axiom 或用 tactic**"，而不是"我做错了"。

### 7.4 预算机制

**代替超时**（理由：确定性、可解释、可调参）。

**参数**：⬜

- 每轮最多 K 条新事实（建议 1000）
- 总量上限 N（建议 10000）
- 量词每次最多 M 个实例（建议 100）

**超预算**：报 `E-SATURATION-BUDGET`（提示级），提示"推理未完成，请补充命题或简化"。

## 8. 与主流证明器的对比

### 8.1 两大派别

- **Tactic 派**（Lean、Coq、Isabelle）：证明是**动作序列**。`by_cases`、`rw`、`destruct`——每行是命令。
- **Term 派**（Agda、HOL Light）：证明是**一个 term**，类型就是命题。

### 8.2 Sublimation 属于第三派：陈述派

**每行是陈述，不是命令**。

对照：

| Lean | Sublimation |
|---|---|
| `by_cases h : Irrational (√2 ^ √2)` | `if[irrational<sqrt(2)^sqrt(2)>]` |
| `refine ⟨√2 ^ √2, √2, h, irrational_sqrt_two, ?_⟩` | `∃ n = √2^√2, m = √2 . ...` |
| `rw [sqrt_mul_self]` | `sqrt(2) * sqrt(2) => 2 : ...` |
| `have h := ...` | 直接调用 tactic |

**一个命令动词都没有**。`if`、`∃`、`=>` 都是**陈述**。

### 8.3 与 Mizar 的关系

Mizar 是**自然语言形式化证明**：

```
proof
  per cases;
  suppose H: irrational (√2^√2);
    thus thesis by ...
  suppose ...;
    thus thesis by ...
end;
```

**Sublimation 是它的近亲**——但更简洁（不用 `proof` / `end` / `suppose` / `thus` 包装）。

### 8.4 独特之处

**1. 无关键字**——借控制流关键字 `if`，不引入 `case`/`lem`/`rewrite`

**2. Tactic 是普通函数**——不是证明器专用的命令

**3. 后件即注入**——不需要 `have`/`assert`

**4. 弥散替代目标状态**——无需显式追踪 `⊢ P`

**5. 值/命题不分离**——`fun` 统一二者，Curry-Howard 反向落地

**6. 存在见证即构造式**——`∃ n = e . P` 与 `Some(x)` 是同层构造

## 10. 未决与未来

### 10.1 命题层构造不完整（最紧急）

| 缺什么 | 场景 | 优先级 |
