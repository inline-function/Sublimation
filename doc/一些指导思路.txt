语义系统分成几个子模块，你自己也可以看着分，我这边给几个指导，先分两个子模块：
1.类型推导器
2.自动定理证明器
然后后面可能要加编译器插件之类的，注解处理器，让用户能自己添加注解以及相应的编译器处理链条，那个是之后的事情。
类型推导器首先要谈论一下类型系统，类型系统可以参考haskell和rust那样，原本是考虑想做kotlin那样的java系面向对象子类型系统的，不过我们没有面向对象中的类，所以就免了，主要是注重haskell和rust系的类型类。
类型中有内置的函数类型与元组类型
函数类型这样表示：(A,B)=>C
后面扩充一下，加入理论参数与上下文，例如：[T,@p](T)<p>=>T<q>
其中不能像正常函数那样使用函数的参数名在上下文中引用：
fun test(n : Nat)<n != 0>
换成函数类型就是(Nat)<$1 != 0>
用$n来指代参数
以及我以前说过，在上下文中多用unicode，所以也不应该写成!=，而是直接用unicode中的不等号，这个我后面会讲为什么。
因为目前对中缀语法糖，不能区分是函数调用表达式还是有参命题
比方说p<a,b>，可以写成中缀形式a p b
函数会有它的伴生命题，就像函数f(a,b)的伴生命题是f<a,b>，因此函数在上下文中不能使用中缀语法糖，这样会导致无法知道a f b指的是函数调用还是函数的伴生命题。
伴生命题给出函数的下文：
fun f(n : Nat) : <n != 0>
那么f<a>就有公理f<a> -> n != 0
上面说了函数和函数的伴生命题不能使用中缀语法糖，但是非函数伴生命题的命题可以使用中缀语法糖，这样，我们就可以这样：
fun ==(a : Any,b : Any) : Bool<$ = true <-> a = b,$ = false <-> a != b>
这样就有==<a,b> -> ==(a,b) = true <-> a = b,==<a,b> -> ==(a,b) = false <-> a u!= b
（额这里的!=实际上应该用unicode，但是我打不出来，所以用u!=和!=区分）
这样呢，!=是一个函数，它是==取反的结果，而u!=是一个命题，它表示两个表达式不相同
于是，我们发现!=不能中缀调用，因为!=是函数，需要区分!=(a,b)和!=<a,b>，但是u!=纯粹就是命题，不是函数，所以可以直接a u!= b
以及内置的命题：
p u-> q 蕴含
p u<-> q 等价
e : T 为
p u& q 合取
p u| q 析取
其他的命题因为不涉及类型与命题，就不用内置了
这里说的是=与u!=这种只涉及表达式的
类型系统还需要有元组，类型上用(T,U)表示元组，表达式上用(a,b)表示，比方说这样：
fun f() : (Nat,Nat) {
    return (1,2)
}
以及Any与Nothing，虽然这应该算是加入了子类型，我们以后还要加入高阶类型，所以还要权衡一下判定性与复杂度，这方面可以参考一下scala，另外我们不是scala那种面向对象子类型，我们可以参考一下haskell和rust，我看它们搞的代数子类型也挺行的，以后和你讨论一下ADT的可行性。
然后是未来可能会加入的代数效应，这方面可以向koka学习一下，毕竟我们的代码风格和koka也是有点像的。
以及模式匹配，模式匹配参考scala那样。
还有一个关键点，每一个表达式都可能带来命题，而作用域内的命题除了给函数传入外也有其他用途。
var n = 0会给后面带来n = 0的命题，以及n : Nat，函数的类似，不再赘述，或者说是留到以后讨论。
前面说到命题不一定只给函数传入用，假如上下文中有e : T的命题，那么表达式e就可以使用T的函数。
//n + 1 这里会报错，尚不知道n是Nat
n : Nat //这里做了一个类似kotlin的n as Nat,此时如果n不是Nat就会报错，所以运行到后面的话，n肯定是Nat，因此这里给出一个n : Nat的命题，你可以看成kotlin的“智能转换”
n + 1 //此时调用就正常，因为编译器通过n : Nat得知n可以使用Nat的+
模式匹配也是一个要点，在往常编程语言，作为表达式的模式匹配必须穷尽
在本语言，模式匹配应该融入上下文系统
遵循万物皆为表达式的原则，模式匹配在不密封的时候也应该有值，于是我们规定不密封的模式匹配固定返回Null
（参考模式匹配，变量与函数的声明也要返回值，规定变量声明语句返回变量初始值，即var n = 0的值是0，于是可以var n = var m = 0，函数的类似）
（配合模式匹配语句，应该是这样使用，when(var e = 0)，就像kotlin的when中声明的val变量）
（匿名函数有时候无法推导其类型或者有些东西用简单的尾随形式写不出来，比方说[T](T)=>T，用kotlin风格的尾随匿名函数写不出来）
（这个时候应该改成fun _[T](a : T) : T = a，这里用了类似kotlin的单表达式函数语法糖，去掉了花括号和return，改成=表达）
（标注为_的标识符，如函数，变量，均无法被后续引用）
（fun _[T](a : T) : T = a也是表达式，它返回的类型便是[T](T)=>T）
（出于简便，fun _[T](a : T) : T = a可以写成fun[T](a : T) : T = a）
模式匹配判断密封的规则是看模式匹配所有分支命题的合取是不是恒真命题
比方说这样
when(bool){
    true  -> 1
    false -> 0
}
此时模式匹配的true分支匹配条件是bool = true，而false分支是bool = false
又因为Bool是枚举，只有这两个取值，因此我们可以通过bool : Bool推出bool = true u| bool = false
我们推出了所有分支的合取是一个恒真命题，于是该模式匹配便是穷尽的，自动推导它的返回类型是所有分支返回类型的交类型，此处为Nat
因为模式匹配是顺序的，因此后面的分支有前面分支命题的否定
比方说false分支内的代码有bool u!= true的命题
还有类型匹配，解构匹配等模式匹配常见分支，仿照即可
守卫语句则是额外加了个合取给分支命题，比方说这样
when(n){
    is Nat if n u!= 0 -> 1
    is Nat -> 2
    else -> 3
}
此时is Nat if n u!= 0的分支条件是n : Nat u& n u!= 0
自动定理证明器不要求证明一切命题，要不然哥德巴赫猜想就可以机械破解了
但是理应要求能够自动推导出大部分常见的逻辑链条，有不能推导的再手动补充
类型推导器也是一样，应该能推理出大部分常见泛型
