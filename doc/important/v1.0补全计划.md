## 2. P0：模块系统

### 2.1 目标

编译器从**单文件**升级为**多文件 + 目录即模块 + 显式挂载**，让 stdlib 可以开始自举。

### 2.2 设计（已钉死）

#### 目录即模块，树状层级

```
/                          ← 唯一根模块
├── main.subl              ← 属于根模块 /
├── project
│   ├── project.settings   ← 模块清单（挂载声明）
│   ├── main.subl
│   ├── data/
│   │   ├── stringData.subl
│   │   └── numberData.subl
│   └── processor/
│       ├── formatter.subl
│       └── printer.subl
├── core
│   ├── core.settings
│   └── math.subl
└── other
```

- **一个目录 = 一个模块**，目录名即模块名
- **根目录**（编译入口目录）是**根模块 `/`**——放在根目录下、不属任何子目录的 `.subl` 文件**属于根模块**
- **同模块内的所有文件共享一个符号表**（扁平，无文件级隔离）

#### 可见性方向

| 方向 | 规则 |
|---|---|
| 同模块内文件 | **完全互相可见** |
| 父 → 子 | **可见**，且**传递**（父能看到任意深度的后代） |
| 子 → 父 | **不可见** |
| 兄弟 → 兄弟 | **默认不可见**，靠挂载建立 |
| 根 `/` | 可访问所有后代 |
| 后代 → 根 | **不可见**（子→父规则的特例） |
| 成员可见性 | 目前全部 public（不加修饰符，v1.0 不做可见性分档） |

#### 根模块的可见性边界

**根模块 `/` 是特殊的**：

- 根模块**能看所有后代**（父→子传递）
- 但**后代看不到根模块**（子→父不可见）
- **根模块里的函数不能被子模块引用**——这是**设计意图**：根模块只是"编译入口容器"，真正可复用的代码放在子模块（`core`、`stdlib`）里
- **唯一例外：`main` 函数**。`main` 可以在任何模块。codegen **扫全树找到唯一 `main`**，在产物末尾追加调用，**不走可见性检查**。这是 codegen 的特殊通道，不是语言的可见性规则

#### 挂载

- **声明位置**：模块目录下的 `<模块名>.settings`
- **语法**：每行 `mount <path> [as <alias>]`，路径**绝对**（从 `/` 起）
- **引用式**：挂载不复制代码，只在当前模块的命名空间里加一条映射
- **可多父**：一个模块可被多个父模块挂载，指向同一份符号（按绝对路径唯一标识）
- **impl 也要挂载**——"显式装配"，不是"隐式发现"。`d` 想用 `c` 里的 impl，必须挂载 `c`
- **传递性**：**挂载是传递的**。`project` 挂 `core`，`core` 挂 `foo` → `project` 能看到 `foo`（以及 `core` 通过 `foo` 能看到的，递归）
- **循环禁止**：挂载链成环报 `E-CIRCULAR-MOUNT`
- **命名冲突**：本地目录名与挂载别名冲突 → `E-DUP-DECL`（`as` 别名可解决，但不允许隐式覆盖）

#### 引用路径规则

**引用时的路径相对当前模块视角**：

- 从当前模块的**可见集合**里找**起点名字**，剩下的按路径走
- **挂载传递后，`project` 及其所有后代引用 `core` 时写法一致**——都是 `core.math.gcd`
  - `project/main.subl` 里写 `core.math.gcd`
  - `project/data/stringData.subl` 里也写 `core.math.gcd`（因为 `core` 通过 `project` 的挂载传递可见）
- **同模块内的引用用裸名**——`data/stringData.subl` 引用 `data/numberData.subl` 的函数直接写 `func(...)`（同模块共享符号表）
- **子模块引用用点号限定**——`project/main.subl` 引用 `project/data/` 里的函数写 `data.func(...)`（`data` 是 `project` 的子模块）
- **类型名同样支持点号限定**——跨模块的类型引用写 `c.Point`（M6 测试需要 `d` 用 `c` 的 `Point` 构造）

**挂载声明里的路径是绝对的，引用时的路径是相对的**——两者不冲突：

| 位置 | 路径形式 | 例 |
|---|---|---|
| `*.settings` 里的 `mount` | 绝对（从 `/` 起） | `mount /core` |
| 源码里的引用 | 相对当前模块视角 | `core.math.gcd` |

#### 模块的绝对路径标识

- 根模块的绝对路径 = `/`（实现时可约定为空串，但要**全局一致**）
- 子模块的绝对路径 = `/父/子/孙`（从根起）
- **绝对路径是模块的唯一标识**——同一个模块被多处挂载时，靠绝对路径识别是"同一份符号"，避免重复 codegen

#### mangle 规则（codegen）

- **根模块**的文件：函数名**不加前缀**
  - 例：`main.subl` 里的 `foo` → `foo`
- **非根模块**的文件：函数名加模块路径前缀 `<mangled_module>__<name>`
  - 例：`core/math.subl` 里的 `gcd` → `core_math__gcd`
- **字典名**同样加模块前缀：`dict_<mangled_module>_<Trait>_<Type>`
  - 例：`core/math.subl` 里的 `impl Show for Int` → `dict_core_math_Show_Int`
- **mangle 规则建议**：
  ```kotlin
  fun mangleModule(absPath: String): String =
      absPath.trim('/').replace('/', '_').replace(Regex("[^A-Za-z0-9_]"), "_")
  ```
  根模块的 mangle 结果为空串（不加前缀）

## 4. P2：集合

### 4.1 目标

从"没有任何集合"到"能处理一批数据"。

### 4.2 分两步

#### 步骤 A：内建数组原语

| 函数 | 签名 | JS 映射 |
|---|---|---|
| `arrayOf` | `@tuple T => Array[T]` | 打包 JS 数组 |
| `arrayGet` | `(Array[T], Nat) => Optional[T]` | `a[i] ?? None()` |
| `arraySet` | `(Array[T], Nat, T) => Array[T]` | 复制后设值 |
| `arrayLength` | `(Array[T]) => Nat` | `a.length` |

`Array[T]` 加进 `BASE_TYPES`。

#### 步骤 B：stdlib List

```sublimation
// stdlib/list.subl
enum List[T] { Nil(), Cons(T, List[T]) }

fun listLength[T](xs: List[T]): Nat = when(xs) {
    Nil -> 0
    Cons(_, t) -> 1 + listLength(t)
}
fun head[T](xs: List[T]): Optional[T] = ...
fun map[T, U](f: (T) => U, xs: List[T]): List[U] = ...
fun filter[T](p: (T) => Bool, xs: List[T]): List[T] = ...
fun fold[T, U](init: U, f: (T, U) => U, xs: List[T]): U = ...
fun append[T](xs: List[T], ys: List[T]): List[T] = ...
fun reverse[T](xs: List[T]): List[T] = ...
fun range(a: Nat, b: Nat): List[Nat] = ...
```

**注意**：这些**不需要泛型约束**，所以 **P2 不依赖 P6**。

**stdlib 的挂载方式**：`⬜ 待用户拍板`（见 §4.4）。

### 4.3 验收

- E2E：`map(\(x) => x + 1, Cons(1, Cons(2, Nil())))` 输出 `[2, 3]`
- E2E：`range(0, 3)` 走 `listLength` 得 `3`
- E2E：`arrayOf(1, 2, 3)` 走 `arrayLength` 得 `3`
- **验收标准**：能写"打印 1 到 10 的平方"这类程序

### 4.4 P2 的待拍板项

**`⬜ 待用户拍板`：stdlib 的挂载方式**

- **候选 A（编译器内嵌）**：`List`/`Optional` 等 stdlib 类型与函数**编译期注入**，用户源码看不见模块
- **候选 B（隐式挂载的模块）**：`stdlib/` 是模块树里的正常模块，编译器**自动为每个用户模块隐式挂载 `stdlib`**

**Max 倾向 B**——让 stdlib 是真代码而非编译器特例，P2/P5 的自举才干净。

**例外（无论选哪个）**：内建原语（`Str` 操作、IO、数组）**仍是编译器注入**，不作为 stdlib 模块存在（见 I-21）。

## 6. P4：基础自动推理（用户核心诉求）

> **用户的诉求**："至少，我们要实现基础的自动逻辑推理，要不然用户写一句函数要加三句命题推理语句才能跑通程序，自反、传递都要手写的话要累死了。"

### 6.1 现状盘点

**已有的推理规则**（`checker/Prop.kt`）：

| 规则 | 位置 |
|---|---|
| 合取分解 | `closure` |
| 双否消去 | `closure`/`normalizeFacts` |
| ∀ 单名实例化 | `closure` |
| MP 前向链接 | `closure` |
| 矛盾检测 `p ∧ ¬p → ⊥` | `closure` |
| α-等价 | `PropLogic.alphaEq` |
| 析取子集（方向受限） | `disjSubset` |
| 构造子单射 `C<a> = C<b> → a = b` | `injective` |
| 目标侧：同一、自反、∃ 单见证、∨ 子集、⊥ 爆炸、PImp 前件/后件匹配 | `prove`/`matchAtom` |

**缺失的规则**（本轮要补）：

| 规则 | 现状 | 影响 |
|---|---|---|
| **等式对称** `a=b ⊢ b=a` | ❌ | 顺序敏感 |
| **等式传递** `a=b, b=c ⊢ a=c` | ❌ | 链式调用无法自动证 |
| **等量代换** `a=b, p<a> ⊢ p<b>` | ❌ | 结构体后件推理失败 |
| **类型事实的等式推理** `e:T, e=e' ⊢ e':T` | ❌ | 类型事实在等式下不传播 |

**这就是"用户写一句函数要加三句命题推理"的根源**——等式推理几乎全缺。

**让下面的程序不需要任何 `unchecked.axiom` 就能通过：**


### 6.3 要实现的规则

#### 规则 1：等式对称

`a = b` ⊢ `b = a`

**实现**：在目标判定侧处理（不修改事实库）。

#### 规则 2：等式传递（新增）

`a = b, b = c` ⊢ `a = c`

**实现**：**等式图 BFS**。

```kotlin
/** 等式图可达性：a 和 c 通过 Γ 中的 = 事实（双向）是否连通 */
private fun eqReachable(facts: List<Prop>, a: Expr, b: Expr): Boolean {
    if (PropLogic.termEq(a, b)) return true
    val adj = HashMap<Expr, MutableSet<Expr>>()
    for (f in facts) if (f is PAtom && f.head == "=" && f.terms.size == 2) {
        adj.getOrPut(f.terms[0]) { HashSet() }.add(f.terms[1])
        adj.getOrPut(f.terms[1]) { HashSet() }.add(f.terms[0])
    }
    val visited = HashSet<Expr>(); val queue = ArrayDeque<Expr>()
    queue.add(a); visited.add(a)
    while (queue.isNotEmpty()) {
        val cur = queue.removeFirst()
        if (PropLogic.termEq(cur, b)) return true
        adj[cur]?.forEach { if (visited.add(it)) queue.add(it) }
    }
    return false
}
```

**在有界的等式图里是 O(V+E)**，安全。深度由等式数量决定，不递归。

#### 规则 3：等量代换（浅层，新增）

`a = b, p<a>` ⊢ `p<b>`（一层，不递归）

**实现**：**目标侧重写**。

```kotlin
/** 用等式事实浅层重写目标，看结果是否能直接匹配 */
private fun proveWithSubst(facts: List<Prop>, goal: Prop, d: Int): Boolean {
    val eqs = facts.filterIsInstance<PAtom>().filter { it.head == "=" && it.terms.size == 2 }
    for (eq in eqs) {
        val (l, r) = eq.terms
        for ((from, to) in listOf(l to r, r to l)) {
            val goalAlt = rewriteTerm(goal, from, to)
            if (goalAlt != goal && prove(facts, goalAlt, d + 1)) return true
        }
    }
    return false
}
```

**关键约束**：
- **浅层**：只做一次替换，不递归
- **只在目标侧**：不修改事实库
- **深度限制**：`d` 参与 `maxDepth` 检查

#### 规则 4：类型事实的等式推理（新增）

`e : T` 和 `e = e'` ⊢ `e' : T`

**实现**：**在 `prove` 的 `PAtom(":")` 分支里加**——目标 `e' : T` 时，先用 `eqReachable` 找某个 `e`，看 Γ 里有没有 `e : T`。

#### 规则 5-10：已有的规则

✅ 已有，不动。

## 7. P5：错误处理（Result）

> **⚠️ 需要用户拍板。**

### 7.1 目标

### 7.2 三个候选

**候选 A：`Result[T, E]` 枚举（最简单）**

- 缺点：`?` 是控制流，和 `return` 交互复杂

**候选 C：异常 / 代数效应**——依赖决策 56，v1.0 不做

### 7.3 若用户选 A

**`stdlib/result.subl`**：

```sublimation
fun isOk[T, E](r: Result[T, E]): Bool = when(r) {

    Err(_) -> false
```

## 14. 全局约束（不变量）

现有 I-1~I-19 全部适用。v1.0 新增：

> **I-20 模块可见性是"计算出来的集合"，不是"查表的布尔"。**
> `canSee(from, to)` 必须计算 from 的**完整可见路径集合**（后代 + 挂载目标及其后代，**递归传递**）。任何"按单点父子关系判断"的实现都是错的。

> **I-21 内建函数集是"语法写不出来的原语"，不是"方便函数"。**
> `concat`/`length`/`readLine`/`arrayGet` 这类**能通过内建访问 JS 原生能力**的才加内建。`map`/`filter`/`sort` 这类**能用 Sublimation 自己写**的一律进 stdlib。判断标准：**"用 Sublimation 能写出来吗？"能，就自举；不能，才内建。**

> **I-22 约束事实与命题参数同构（决策 20 落地）。**
> `T: Show` 编译期视为约束事实，和 `@p` 走同一套供给/歧义搜索机制。**不要为约束单独造一套解析逻辑**——复用 `resolveDict` + 可见性过滤。

> **I-23 等式推理必须在目标侧做，不在闭包侧。**
> 对称、传递、等量代换都不修改 Γ（避免事实库指数膨胀）。`Prover.prove` 在目标判定时按需搜索等式图，深度受 `maxDepth` 限制。**这是 P4 保持性能的关键。**

> **I-24 等量代换必须浅层（一层），不递归。**
> 递归等量代换会导致不动点计算，超出 v1.0 片段。浅层覆盖 90% 日常场景，剩余靠 `unchecked.axiom` 逃逸。
