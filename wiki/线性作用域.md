# 线性作用域

一句话：**让「正在变的本地状态」和「握在手里的资源」，在编译期依然能被追踪和证明。**

默认情况下，上下文系统对可变变量是「半死不活」的——可变的东西一旦出现，关于它的一切命题就证不出了。资源则完全没有确定性释放保证。线性作用域（`%{ … }`）是解决这两件事的同一把钥匙。

> 精确规范见 `docs/线性作用域规范.md`；设计推理见 `boring doc/线性作用域-白话版.md`。

## 基本写法

在块的花括号前加 `%`（必须紧贴，`%` 本身是取余运算符，靠邻接消歧）：

```subl
@impure
fun main() %{
    @mut var n = 0
    ∴ n = 0            // 成立：普通作用域里证不出
    n = n + 10
    ∴ n = 11           // 成立
}
```

编译器把 `n` 的每次赋值看成**一串不可变的版本**（`n#0`、`n#1`、`n#2`，编译期内部名，用户看不见）。每个版本只绑定一次、永不再改，于是每个版本都能进上下文系统参与证明。运行时**一分钱不多花**：生成的代码和普通 `@mut` 完全一样。

## 什么时候用

**场景一：改了状态，还想安全地调带前件的 API。**

```subl
struct PosPoint(x : Nat) <x > 0>
fun usePos(p : PosPoint) <p.x > 0> : Null {}

@impure
fun demo() %{
    var p : @mut PosPoint = PosPoint(1)
    p.x = 0
    p.x = 5            // 右侧 5 > 0 可证，伴生命题重新注入
    usePos(p)          // 放行：普通作用域里这里只能 E-PRE-UNPROVEN，且无药可救
}
```

这是它唯一不可替代的地方：把「先破坏、再重建、再使用」从 `unchecked.axiom` 的自担风险变成编译器亲自验证。它是 `unchecked` 的**安全替代品**——想硬塞事实之前，先问问能不能塞进 `%{ }`。

**场景二：资源——确定性释放，忘了关编译器替你关。**

把 struct 标 `@resource`，它的实例就在域里拥有了相位（伴生命题）与生命周期保证：

```subl
@resource struct File(path : Str) <open>

@impure fun openFile(p : Str) : File <open>
@impure fun close(f : @mut File) : Null <closed>
@impure fun write(f : @mut File, s : Str) : Null <open>

@impure
fun copyFile() %{
    var f = openFile("a.txt")     // 注入 <open>
    f.write("hello")             // 要求 <open>，当前相位满足
    f.close()                    // 转换到 <closed>
    f.write("x")                 // 证不出 <open> → E-PRE-UNPROVEN：用后释放被拦下
}                                // 忘了 close？域出口兜底释放，并给 D-RESOURCE-CLOSED 提示
```

资源保证三条：**不可别名**（`@ref` 域内被禁）、**不可逃逸**（不能返回、不能存进字段、不能被 lambda 捕获——`E-RESOURCE-ESCAPE`）、**不可复制**（深拷贝规则对资源例外——`E-RESOURCE-COPY`）。尾表达式、提前返回都带不走它，所以域出口是完备的收尾点。

**场景三：锁——临界区的相位机。**

锁是资源的同步特例，`lock`/`unlock` 就是相位转换：

```subl
@resource struct Mutex() <unlocked>
@impure fun lock(m : @mut Mutex) : Null <unlocked>
@impure fun unlock(m : @mut Mutex) : Null <held>

@impure
fun worker(m : @mut Mutex, shared : @mut Data) %{
    lock(m)                       // → <held>
    var snapshot = shared.x       // 临界区里先冻结成不可变值再证明
    shared.x = snapshot + 1
    unlock(m)                     // → <unlocked>
}                                // 忘了 unlock？域出口兜底
```

共享数据在域内**从不进入上下文**（它是域外声明的、不可追踪的实体），所以不存在「需要失效的事实」——临界区里建立的事实都建在你冻结的快照上，天然安全。死锁与锁顺序分析不在这把钥匙的管辖内（那是全程序分析）。

## 域内的三条支柱

1. **唯一所有权**：域内可变实体/资源不得别名——不能 `@ref`、不能被 lambda 赋值性捕获。否则「这个程序点的值」无法确定。
2. **版本化**：每次赋值出新版本；读取点解析到最近的前驱版本；分支合并点注入各支的**析取**。
3. **流敏感命题**：事实随程序点前进更新——赋值注入新版本等式；不纯调用让该实体的版本化事实**失效**（类型不变量不失效，`D-LINEAR-VERSION` 提示进展）；域结束事实全部销毁。

## 域里能干什么 / 不能干什么

| 能 | 不能 |
|---|---|
| 可变变量赋值后 `∴` 证其值 | lambda 捕获并修改域内变量（`E-LINEAR-ESCAPE`） |
| 就地改结构体字段并追踪（字段自身不必标 `@mut`，接收者持 `@mut` 视图即可） | 声明 `@ref`（`E-LINEAR-ALIAS`） |
| 嵌套域（共享域族版本计数器，连续递增） | 带值提前返回（`E-LINEAR-RETURN`）；尾表达式可以 |
| 普通块随便用（事实全量回溢，像透明的一样） | 把可变事实带出域（不回溢） |
| 传实体给不纯函数——合法，但之后该实体事实失效 | 资源逃逸/复制（`E-RESOURCE-ESCAPE`/`E-RESOURCE-COPY`） |
| 用域外声明的 `@mut` 变量（`LV-OUTER-MUT`） | 资源返回/存字段/被捕获 |

## 常见坑

**1. 循环累加写不了。** 凝华的循环只能靠高阶函数或递归，而域内 lambda 赋值性捕获被禁、自递归函数也有限制——`xs.forEach { n = n + 1 }` 直接报错。改法：把循环写成域外的递归函数，用函数**下文**表达不变量。

**2. 嵌套 `%{ }` 反而掉证明力。** 普通块是透明的（事实回溢），内层线性域出口**不回溢**：

```subl
%{ @mut var n = 0;  { n = 1 };  ∴ n = 1 }        // 成立
%{ @mut var n = 0;  %{ n = 1 };  ∴ n = 1 }       // 不成立
```

内层域的运行时值确实改了，丢的只是外层的证明力。**所以原则是：域越小越好，内部用普通块组织。**

**3. 无脑全 `%` 会怎样？** 不会破健全性（运行时一字不变），但：纯不可变代码加 `%` 零收益（版本表只追踪 `@mut`）；代价是全函数失去 `@ref`、lambda 累加、带值 return；而且嵌套越多丢的事实越多。它是**手术刀**，不是安全帽。

**4. 事实不回溢到域外。** 想在域后使用域内的结论，显式承接：

```subl
@mut var n = 0
%{ n = 5 }
var snapshot = n        // 冻结成不可变值
∴ snapshot = 5          // 成立
```

## 不做什么

域内**没有** `yield`/`await`/效应器。异步需要运行时（调度器、续体），与线性作用域的纯静态设计冲突（形式化版 §12.3 的裁决）。锁能搭车资源，正是因为它是**同步**原语。
