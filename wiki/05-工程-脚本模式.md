# 脚本模式（run-script）

卷名：05-工程-脚本模式
主题域：工程与工具链 / 执行模型
事实来源：_facts/_langfacts.md §7/§8；cli/src/main/kotlin/sugared/functor/Main.kt（USAGE 与调度，行号以当前源码为准）；interpreter/src/main/kotlin/sugared/functor/interpreter/Interpreter.kt、ScriptFrame.kt；并经 build/libs/sublimation.jar 实测（临时脚本写于 _facts_tmp，跑通后已删除）

Sublimation 有两种执行形态。**工程模式**以目录为模块、以 `fun main()` 为入口，走 `check`/`compile` 流水线；**脚本模式**让单个 `.subs` 文件像 `.kts` 一样：顶层语句直接运行，没有 main，也不写 import。脚本模式由 CLI 子命令 `run-script` 打开，可选旗标 `--global-inference` 提供脚本专属的类型/可变性/效应自动推导。

## 语法

### 文件与顶层文法

脚本文件以 `.subs` 为扩展名。解析器入口 `parseFile` 按模式分叉（_langfacts.md §2）：脚本模式下**脚本语句直接出现在顶层**，而工程模式只允许 `fun`/`type`/`enum`/`struct`/`impl`/`axiom` 等声明。因此在脚本里可以直接写：

```sublimation
print("hello")            // 表达式语句（print 为宿主函数）
var n = 1 + 2             // 变量声明
fun double(x: Nat): Nat = x * 2   // 顶层函数
axiom p, p → q            // 顶层命题公理（修正案后的独立 axiom 语句）
∵ p ∴ q                   // 顶层证明义务
```

所有顶层语句在文件加载时依次执行；`fun main()` 即使存在也只是普通声明，**不会被当作入口调用**（实测：含 `fun main() { ... }` 的 `.subs` 只打印顶层语句，main 体不执行）。脚本内允许使用当前文法的全部表达式形态——lambda 用 `=>`（`{ x, acc => acc + x }`）、零参 lambda 用 `{ => 7 }`、函数类型写作 `(Nat) => Nat`、命题蕴含用 Unicode `→`；ASCII 箭头 `->` 已废除（lexer 出 ARROW 仅供诊断）。

### CLI 形态

```
run-script <file.subs> [<file2.subs> ...]   脚本模式解释执行：顶层语句直接运行（无需 main）；多条脚本互不共享
run-script <dir>                            运行目录下所有 .subs 脚本（每个独立运行）；无 .subs 时按 .subl 工程（main）执行
--global-inference                          run-script 可选旗标：开启全局类型推导；脚本模式专属，编译模式不受影响
```

要点：

- 参数可以是任意多个 `.subs` 路径或目录的混合（Main.kt 的 `runScriptCmd` 逐一处理，目录与文件可混排）。
- `--global-inference` 只在 `run-script` 上有意义；对 `check`/`compile` 传它**没有任何效果**（USAGE 明示“编译模式不受影响”）。
- `-v` 旗标在脚本模式下被过滤丢弃（Main.kt:236 附近 `args.drop(1).filter { it != "-v" }`），不改变脚本运行行为。
- 旗标解析按参数全量匹配（`it == "--global-inference"`），出现在参数串任意位置都生效。

### 与工程模式的文法互斥

同一份 `.subs` 源，`check` 会用**工程模式**解析器（`parseEntry`）读它，于是顶层 `var` 直接报错：

```
[错误] [语法][gi.subs:2:1] 期望顶层只能写声明，执行代码请放进 `fun main()`（脚本模式后续支持），实际'var'
```

实测结论：**顶层带执行语句的 `.subs` 只能经 `run-script` 跑**（或改写为 `.subl` + `fun main()`）。反过来，工程目录里的 `.subs` 文件也不会被 `check <目录>`/`compile <目录>` 的全树扫描收录——那是 `.subl` 的事。

### `--global-inference` 放宽的文法

不带旗标时解析调用 `parseScriptSource(source, fileName)`，函数形参必须带类型标注；带旗标时调用 `parseScriptSource(source, fileName, allowUntyped = true)`（Interpreter.kt:105-108），允许写出 `fun add(a, b) = a + b` 这类**省略标注**的函数：

```sublimation
// 仅在 --global-inference 下可解析
var n = 1 + 2
fun add(a, b) = a + b
fun show(x) = print(x)
print(add(n, 3))
show(n)
```

实测：不带旗标跑此文件，解析器在第二个形参处报“期望 COLON，实际 ','”；带旗标则正常输出 `6` 与 `3`。注意 `run-script` 的目录回退分支（`.subl` 工程）**不**使用全局推导，仍按工程模式解析。

## 语义

### 执行管线

`run-script` 的实际引擎是解释器（Main.kt:350-356）：

1. **解析**：`parseScriptSource` 产出脚本模式 AST；
2. **注入**：宿主函数（`print` 等，含类型签名）与标准库被注入为声明——`core` 目录递归收集、按相对路径排序（Interpreter.kt:36-42），所以脚本**无需 import** 即可用 `listOf`/`fold` 等（实测通过）；
3. **Checker 类型检查**：脚本仍要整体过语义检查（命题义务、纯度、可变性闸门照常生效）；失败时以“脚本类型检查失败”为头逐条列出诊断（实测含 `E-UNBOUND-NAME`、`E-IMMUT-ASSIGN` 等码）；
4. **Evaluator 求值**：大步求值，顶层语句依次执行。

### 每文件独立（互不共享）

“互不共享”是进程内的强保证，不是写法约定：

- 每个脚本一次独立的 `run`，而**每次 `run` 都重建全局帧** `globalFrame = ScriptFrame()`（Interpreter.kt:150-152，注释 H7：避免重复注册宿主/用户声明）；
- 标准库与宿主声明对每个脚本独立注入；
- 用户顶层声明只落在本脚本的全局帧里。

实测：`t1.subs` 定义了 `fun double(x: Nat): Nat = x * 2`，把 `t1.subs` 与引用 `double` 的 `t3.subs` 放在同一命令行执行，`t1` 正常输出后 `t3` 报 `E-UNBOUND-NAME 没找到函数 `double``。脚本之间**不存在任何隐式组合**，即使同目录、同命令行。

### 目录语义

`run-script <dir>` 时，`subsIn` 只收集**目录顶层**的 `.subs`（`listFiles` 非递归），按文件名排序后逐个独立运行（Interpreter.kt:147-148）。每个脚本执行前打印 `[脚本] <文件名>` 前缀；若目录下一个 `.subs` 都没有，则回退工程模式：合并目录顶层 `.subl` 文件（同样非递归，Interpreter.kt:120-124），以 `fun main()` 为入口解释执行，前缀变成 `[工程]`（Main.kt:396-399，实测通过）。注意 `subsIn` 找不到 `.subs` 时**不会**报错，而是静默走工程回退。

### 脚本内作用域

脚本运行时的作用域由 `ScriptFrame` 链承担（ScriptFrame.kt 全 62 行）：

- 嵌套帧继承外层（`lookupVar`/`hasVar`/`isMutable`/`isRef` 沿 `parent` 链上溯），顶层帧无 parent；
- 顶层帧装本脚本的变量（`declareVar` 记录 `@mut`/`@ref`）与函数（`declareFunction` 支持同名重载组，按接收者签名 `signatureKey()` 去重合并，ScriptFrame.kt:39-52）；
- 可变性闸门照常：不可变变量赋值报 `E-IMMUT-ASSIGN`（实测：`var n = 1 + 2` 后再赋值即触发——脚本里的 `var` 默认仍是不可变的，可变要显式 `@mut`）；
- 脚本与脚本之间不共享帧（H7 重建机制），但**同一脚本内**的函数/变量互相可见。

### `--global-inference`：全局类型推导

脚本模式专属（Interpreter.kt:19-24 的 V1/V2 描述，引用 idea doc/全局类型推导.md）。它由 `Interpreter(globalInference = true)` 开启，在 Checker 之前运行 `GlobalInference.infer`：

- **可省略**：类型、可变性、效应标注；构造点与使用点反推（按赋值链标 `@mut`、非纯调用/停机失败标 `@impure`）、递归返回类型走 SCC 假设-验证；
- **优先级链**（USAGE 原文）：**显式标注 > 构造点 > 使用点 > 默认 Any**——显式标注一律保留，不会被推导覆盖；
- **产物仍整体过 Checker**：推导不是法外之地；冲突直接以 `E-TYPE-CONFLICT` 在推导期抛出 `InterpreterError`（错误级即终止），补充级诊断（如 `D-AUTO-IMPURE`）收集进 `inferNotes`，由 CLI 以 `[提示] [CODE] message` 形式逐条打印（Main.kt:392/404）；
- **不影响编译模式**：`--prover=aggressive` 等旗标只作用于 `check`/`compile`，全局推导只作用于 `run-script`。

### 退出码与失败传播

- 目标为空（光旗标无路径）→ 打印 USAGE 并退出码 2；路径不存在 → `[错误] 路径不存在` + 退出码 2（Main.kt:377-385）；
- 任何一个脚本的检查/求值抛异常，会被外层 `catch (RuntimeException)` 兜住打印 `[错误]` 并以退出码 1 结束（Main.kt:366-369）——**中途失败会中断后续脚本**，没有“继续跑下一个”的语义；
- 全部跑完才打印 `[完成] 脚本执行结束`；目录回退走工程入口时同样以该行收尾；一个脚本都没跑成时退出码 1（Main.kt:408-410）。

### 脚本模式 vs 工程模式（对照表）

| 维度 | 脚本模式 | 工程模式 |
|---|---|---|
| 入口单元 | 单个 `.subs` 文件 | 目录即模块（根 `/` 扫全树，Main.kt:242） |
| 入口点 | 顶层语句直接执行，无需 main | 单一 `fun main()` |
| 典型命令 | `run-script <文件|目录>` | `check <文件|目录>` / `compile ... -o out.js` / `run` |
| 文件间关系 | 每文件独立执行，互不共享（实测 E-UNBOUND-NAME 隔离） | 同模块树内声明共享（mount） |
| 复用手段 | 单文件自足：stdlib + 宿主自动注入，无需 import | 工程内 `import` 模块；`-p` 装载注解处理器 |
| 标注省略 | 默认必须完整；仅 `--global-inference` 下可省 | 必须显式（推导旗标不作用于编译） |
| 执行方式 | 解释器直接求值（Checker → Evaluator） | check → compile 生成 JS；`run` 解释执行 |
| 目录参数语义 | 每个顶层 `.subs` 各自运行；无 `.subs` 时回退 `.subl` 工程 | 整目录合为模块（子目录参与扫描） |
| 顶层语句约束 | 任意脚本语句（var/fun/axiom/when/unchecked/表达式语句） | 只能写声明，执行代码须进 `fun main()` |
| 诊断 | 脚本检查失败统一报告 + 推导 `[提示]` | 分级诊断报告（`-v` 出补充级） |

注解处理器与脚本模式还有一层特殊关系：**处理器本身就是 `.subs` 脚本**（文件名 = 处理器名 = 关注的注解），编译时由解释器解释执行（USAGE），而工程编译时处理器先于 B/C 检查跑（Main.kt:250-254）。

## 示例

### 1. 最小脚本（无需 main、无需 import）

```sublimation
// hello.subs
print("hello from script")
var n = 1 + 2
fun double(x: Nat): Nat = x * 2
print(double(21))
```

```
$ java -jar build/libs/sublimation.jar run-script hello.subs
[脚本] hello.subs
hello from script
3
42
[完成] 脚本执行结束
```

（实测输出，退出码 0）

### 2. 单文件自足：标准库与命题

```sublimation
// math.subs —— 无 import，stdlib 自动注入；顶层公理 + 证明
axiom p, p → q
∵ p ∴ q

var xs = listOf(1, 2, 3)
var total = xs.fold(0, { x, acc => acc + x })
print(total)
```

实测：命题义务通过，`total` 输出 `6`（`listOf`/`fold` 均来自自动注入的标准库，未见 `E-UNBOUND-NAME`）。

### 3. 多文件隔离

```sublimation
// a.subs
fun double(x: Nat): Nat = x * 2
print(double(21))
```

```sublimation
// b.subs —— 不应看到 a.subs 的声明
print(double(21))
```

```
$ run-script a.subs b.subs
[脚本] a.subs
42
[脚本] b.subs
[错误] 脚本类型检查失败:
[E-UNBOUND-NAME] 没找到函数 `double`——拼写错了？还是没 mount 它所在的模块？
（退出码 1，且不会再输出 [完成]）
```

### 4. 目录方式运行（按文件名排序、逐个独立）

```
$ ls scripts/
01_hello.subs   02_math.subs
$ run-script scripts/
[脚本] 01_hello.subs
hello
[脚本] 02_math.subs
6
[完成] 脚本执行结束
```

若 `scripts/` 下没有 `.subs` 而有顶层 `.subl`，则回退工程模式（实测）：

```
$ run-script proj/
[工程] proj
project main entry
[完成] 脚本执行结束
```

（`proj/main.subl` 内含 `fun main() { print("project main entry") }`）

### 5. `--global-inference`：省略标注

```sublimation
// gi.subs
var n = 1 + 2
fun add(a, b) = a + b          // 形参/返回类型均省略
fun show(x) = print(x)         // 非纯调用 → 推导标 @impure（补充级 D-AUTO-IMPURE）
print(add(n, 3))
show(n)
```

```
$ run-script --global-inference gi.subs
[脚本] gi.subs
6
3
[完成] 脚本执行结束
```

同一文件不带旗标则在解析期失败（“期望 COLON”）。若脚本里有显式标注（如 `fun f(x: Nat): Nat`），推导将原样保留——显式标注优先级最高。

### 6. 对照：同一逻辑的工程模式写法

```sublimation
// proj/main.subl —— 工程模式：执行代码必须进 main
fun double(x: Nat): Nat = x * 2

fun main() {
    print(double(21))
}
```

```
$ run-script proj/          # 目录无 .subs → 按工程执行
$ compile proj/ -o out.js   # 或走编译流水线
```

## 陷阱

1. **`.subs` 与 `.subl` 不可互换解析**。顶层带执行语句的 `.subs` 被 `check`（工程模式解析器）直接拒绝：“期望顶层只能写声明，执行代码请放进 `fun main()`”。只想检查脚本逻辑别用 `check <file.subs>`；反过来工程树里塞 `.subs` 也不会被模块扫描收录。

2. **脚本里写 `fun main()` 不会执行**。脚本模式的入口是顶层语句本身；main 只是落在全局帧的普通函数声明（实测：只有顶层 `print` 输出，main 体被忽略）。从 Kotlin/工程模式迁移脚本时记得把 main 体拆到顶层。

3. **多脚本一次跑，一个失败全部中断**。`runScriptCmd` 顺序执行，任一脚本抛错被外层兜住即以退出码 1 结束，后续脚本不再运行，也不会有 `[完成]` 行。批处理目录时若希望容错，需要外层循环逐个调用。

4. **`run-script <dir>` 只扫顶层**。`subsIn` 用 `listFiles`（非递归）收集 `.subs`（Interpreter.kt:147），子目录里的 `.subs` 被**静默忽略**——既不执行也不报错。工程回退分支的 `runDir` 同样只看目录顶层 `.subl`（Interpreter.kt:121），与编译模式 `MultiModule` 的**扫全树**不同：同一个目录交给 `compile` 与交给 `run-script` 覆盖的文件集合可能不同。

5. **“无 .subs 的目录自动当工程跑”是静默回退**。目录里只有 `.subl` 时前缀从 `[脚本]` 换成 `[工程]`（Main.kt:396-399）；若本意是跑脚本却不小心建错了扩展名，会得到工程模式的运行结果而非报错。

6. **`--global-inference` 不是绕过 Checker 的后门**。推导产物仍整体过类型检查；推导自身冲突（`E-TYPE-CONFLICT`）在推导期就以 `InterpreterError` 终止。同时该旗标**只认 `run-script`**：给 `check`/`compile` 传它毫无效果（USAGE 明示），编译产物也不会因此带上推导。

7. **推导优先级是“显式优先”**。链路为 显式标注 > 构造点 > 使用点 > 默认 Any；已有显式标注（`@mut`、返回类型、`@impure` 等）原样保留，不会被使用点信息改写。若推导结果与预期不符，先查是否有手写标注锁住了形状。

8. **默认 Any 的坑**。未约束的省略参数最终落为 `Any`，相关类型错误往往推迟到**调用点**才暴露（Checker 的 `Any` 准入宽松）；翻了半天调用处才发现是推导期就放行的占位类型。

9. **`var` 默认仍不可变**。脚本里 `var n = 1 + 2` 后赋值会触发 `E-IMMUT-ASSIGN`（实测）；可变要显式写 `var n: @mut Nat` 之类，与 `.subl` 里的规则一致——脚本模式的“随意”只在结构层面，可变性闸门（`uncheckedDepth == 0`）照常把关。

10. **脚本之间的共享只能靠“工程化”**。一旦需要跨文件复用函数，正确做法是把逻辑搬进 `.subl` 目录模块（工程模式 + mount），或把第二个脚本写成注解处理器（`-p` 装载，处理器本身即 `.subs`）——脚本模式刻意不支持脚本间引用。

11. **排序决定执行顺序**。目录模式按文件名排序逐个运行（`subsIn` 的 `sortedBy`）；依赖先后顺序的脚本要用 `01_`/`02_` 前缀固定顺序，且仍要自己承担失败中断的风险。

12. **`->` 是非法箭头**。脚本里写 lambda/函数类型只能用 `=>`，命题蕴含只能用 `→`（`->` 由 lexer 产出 ARROW 仅供诊断）。从旧代码粘进脚本前先替换，否则解析期直接报错。

13. **宿主环境依赖 cwd（实测推断）**。解释器把 stdlib 目录默认为相对路径 `File("core")`（Interpreter.kt:18）；须在仓库根目录下执行 `java -jar build/libs/sublimation.jar run-script ...`，否则标准库装不上，`listOf` 等名字直接 `E-UNBOUND-NAME`。待核：是否有分发包装改写该路径——实测均在仓库根目录进行。
