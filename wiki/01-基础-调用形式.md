# 调用形式
> 卷：wiki/01-基础 · 主题域：基础（表达式层·调用）
> 事实来源：_facts/_langfacts.md §2；Parser.kt（binops 50–56、opPrefixKinds 58–60、symbolCallStart 61、parseExpr 1015–1097、infixOperandAhead 1100–1116、parseUnary 1152–1165、parsePostfix 1166–1230、parseArgs 1233–1255、parsePrimary 1352–1364、parseBraceLambda 1684–1712、braceIsLambda 1721–1747）、Checker.kt（950、1064–1078）、CallCheck.kt（checkCall 83 起）、Prop.kt（48）、Evaluator.kt（evalSymCall 673–683）、ScriptValue.kt（51–58）、JsCodeGen.kt（symbolCall 968–975）；另以 build/libs/sublimation.jar 的 `run-script` 实测五种形态（结果见「示例」「陷阱」）

表层五种调用记号——括号调用、中缀糖、符号前缀、运算符前缀、尾随 lambda——在解析期归一到两个 AST 节点：**CallExpr**（按名解析的普通调用）与 **SymbolCallExpr**（比较符的内建调用）。中缀糖与尾随 lambda 是纯解析期糖：脱糖后的 AST 与括号形式逐字相同，解析器以 supplement（D-INFIX / D-TRAILING）留痕。

## 语法

| 写法 | 产出的 AST | 成立判据 |
|---|---|---|
| `f(a, b)` | `CallExpr(NameRef(f), [a, b])` | `(` 紧贴 f；实参以逗号分隔，允许尾随逗号 |
| `a f b` | `CallExpr(NameRef(f), [a, b])` | f 前后均带空格、f 与左右操作数同行、右操作数为合法表达式起始 |
| `==(a, b)` | `SymbolCallExpr("==", [a, b])` | 比较符紧贴 `(`；六个符号之一（见下） |
| `+(1, 2)` | `CallExpr(NameRef("+"), [1, 2])` | 运算符紧贴 `(`；七个算符之一（见下） |
| `f(a) { … }` | `CallExpr(f, [a, …, lambda])` | lambda 追加为**最后一个位置实参** |

### 1. 括号调用 f(a, b)

- 实参两条通道：**位置实参**（按序）与**命名实参** `f(name = value)`——单等号 `=` 即 ASSIGN token，与命题等式同 token，与值相等 `==` 的 EQ 是不同 token（Parser.kt:1236–1241）
- 空参 `f()`、尾随逗号 `f(a, b,)` 均合法（v3.0）
- 括号调用在后缀循环里，故可链式：`f(a)(b)`；`o.m(a)` 中 `o.m` 是 FieldExpr、整体是接收者方法糖；`id<Nat>(7)` 先 InstExpr 实例化再调用

### 2. 中缀糖 a f b

- 判据（Parser.kt:1086–1097 + infixOperandAhead 1100–1116）：f 本身带前空格；**右操作数也带前空格**；f 与左右操作数同在一行；右操作数是合法表达式起始——排除 `->` `,` `}` `]` `;` `)` `=` `return`
- 整个表达式层级**左结合、无优先级**：`a f b g c` 即 `((a f b) g c)`
- `in` 是特例：`a in b` 直接解为 `in(a, b)`，右操作数额外吞并区间 `lo..hi`（Parser.kt:1067–1069）
- 注意相邻的另一通道：**符号名中缀** `a ○ b`（SYMBOL 带前空格）解为 `BinExpr("○")`、运算符中缀 `a + b` 解为 `BinExpr("+")`——它们是中缀**表达式**，不是调用

### 3. 符号前缀 ==(a, b)

- `symbolCallStart` = `<` `>` `==` `!=` `<=` `>=`（Parser.kt:61）
- 只取**位置实参**（`parseArgs().first`，命名通道不适用，Parser.kt:1355）
- 类型**恒为 Bool**（Checker.kt:950）；命题层规范化为 `PAtom(op, args)`（Prop.kt:48）

### 4. 运算符前缀 +(1, 2)

- `opPrefixKinds` = `+` `*` `/` `%` `&` `|` `<->`（Parser.kt:58–60）
- 把运算符**当作普通函数名**调用，交给 checkCall 按名解析——用户可用 `fun +(a: Nat, b: Nat)` 命中（Parser.kt:1357–1362）
- 不含 MINUS（一元负号优先）；不含六个比较符（它们走符号前缀通道）

### 5. 尾随 lambda f(a) { … }

- lambda 追加为**最后一个位置实参**，等价于在括号里写 `{ … }`（Parser.kt:1208–1214，D-TRAILING）
- 无括号形态 `f { … }` 同样成立（callee 直接是名字时 `CallExpr(f, [lambda])`）
- lambda 体三种写法：显式参数 `{ x, y => 体 }`、零参 `{ => 7 }`、隐式单参 `{ _ + 1 }`
- 接收者限制：字面量 / BinExpr / UniExpr 结果后的 `{` 不视为尾随 lambda（Parser.kt:1208 的排除条件）
- `Task { … }` / `Flow { … }` 是任务 / 冷流构造，体是代码块而非 lambda（决策 93）

## 语义

### 归一到两种节点

- 括号调用、中缀糖、运算符前缀、尾随 lambda → 全部是 **CallExpr**，语义层统一按名解析（checkCall，CallCheck.kt:83 起）
- 符号前缀 → **SymbolCallExpr**，语义层是六个比较的内建实现，类型恒 Bool

### CallExpr 的解析顺序

checkCall（CallCheck.kt:83 起）按名解析的要点：

- 内建（`print`、`in` 等）优先；其后查构造子 / 结构体（跨可见模块，含 core 标准库），再查自由函数
- 扩展调用规则：名字同时是类型类方法时，有可见自由函数则**自由函数优先**，类型类方法仅兜底（CallCheck.kt:102–107）
- 方法双形态：`o.m(a)` 与 `m(o, a)` 等价（O2 决策 69）；自由形态下首实参即接收者
- **命名实参只用于自由函数路径**：方法路径（callee 是 FieldExpr，或自由形态方法名）传命名实参报 E-NAMED-ARG（CallCheck.kt:131–132）

### SymbolCallExpr：内建比较

- 求值：`< > <= >=` 按数值比较；`==` / `!=` 走宿主相等（Evaluator.kt:evalSymCall 673–683）
- JS 生成：`==` 编译为 `__eq(a, b)`（结构相等），`!=` 取反，其余直接编译为 JS 比较算符（JsCodeGen.kt:symbolCall 968–975）
- 命题位：整个符号前缀规范化为原子命题 `PAtom(op, args)`，进入 Γ 事实池参与 MP 闭包（Prop.kt:48）

### 糖落在解析期

中缀糖与尾随 lambda 不引入新 AST 节点、不改变作用域，也不参与类型检查的任何特判——类型层看到的只是 `f(a, b)`。解析器通过 supplements 留痕（D-INFIX：`a f b` 展开为自由函数 `f(a, b)`；D-TRAILING：尾随 lambda 已作为最后一个实参传入），CLI 的 explain 表有对应条目（Main.kt:126 附近）。

## 示例

以下为脚本模式（.subs，逐文件独立执行）的可运行汇总，已用 `build/libs/sublimation.jar run-script` 实测；注释为实际输出：

```subl
// ① 括号调用：位置实参、命名实参（单 =）、尾随逗号
fun add(a: Nat, b: Nat): Nat = a + b
fun greet(name: Str, punct: Str): Str = "hi, " + name + punct
print(add(1, 2))                          // 3
print(add(1, 2,))                         // 3（尾随逗号）
print(greet(name = "subl", punct = "?"))  // hi, subl?

// ② 中缀糖：a f b ≡ f(a, b)
fun mul(a: Nat, b: Nat): Nat = a * b
print(3 mul 4)                            // 12

// ③ 符号前缀：比较符直接作函数名（内建，恒为 Bool）
print(<=(1, 2))                           // true
print(!=(1, 2))                           // true

// ④ 运算符前缀：声明运算符函数并按名调用
fun +(a: Nat, b: Nat): Nat = a * 10 + b
print(+(3, 4))                            // 34

// ⑤ 尾随 lambda：f(a) {…} ≡ f(a, {…})；无括号形态亦成立
fun each(n: Nat, f: (Nat) => Nat): Nat = f(n)
fun answer(f: () => Nat): Nat = f()
print(each(7) { x => x * 2 })             // 14
print(each(7) { _ * 3 })                  // 21（隐式单参）
print(answer { => 42 })                   // 42（零参 lambda + 无括号形态）

// in 中缀解为普通调用
print(3 in 1..5)                          // true（≡ in(3, 1..5)）

// 命题位的符号前缀：函数上下文 <…> 内以括号表达式出现（core/logic/logic.subl 的实际写法）
@theorem fun symref[a, b]: Null <(a = b) → (b = a)>
```

## 陷阱

1. **中缀糖对空格与同行极敏感**：`a f b` 要求 f 前后都有空格、三者同行；`a f(b)`（无空格括号）不构成中缀。
2. **`a f(b)` 会静默变成两条语句**：实测 `1 add(2)` 被解析为语句 `1` 与调用 `add(2)`，报 E-ARITY「想要 2~2 个实参，但你传了 1 个」——既非中缀也不是语法错，排错时极隐蔽。
3. **表达式起点的 `<(1, 2)` 不可用**：parseUnary 的命题括号分支（Parser.kt:1159–1162）优先拦截 LT，实测 `fun lt(): Bool = <(1, 2)` 报「[语法] 期望GT」——`<…` 只能进入命题括号 / 角表位。前缀比较符实际可用的是 `>` `==` `!=` `<=` `>=`；`<` 虽在 `symbolCallStart` 集合中（Parser.kt:61），但被该分支截断而不可达——此点与事实表 §2 的表述不一致，此处按源码 + 实测写，是否为既定行为 `待核`。
4. **`-(1, 2)` 不是调用**：MINUS 不在 opPrefixKinds（一元负号优先，Parser.kt:57）；实测 `fun n(): Nat = -(1, 2)` 被解析为「一元负号作用于元组」，类型检查报「函数体是 (Nat, Nat)」。
5. **`==(a, b)` 不能用于自定义比较函数**：比较符前缀是内建 SymbolCallExpr（Parser.kt:1355、Checker.kt:950），`fun ==` 无法经此形态调用；自定义比较请起普通函数名。
6. **符号前缀只收位置实参**：`==(a = 1, b = 2)` 形态的命名通道不适用（`parseArgs().first`）。
7. **`==` 在脚本解释器与编译后端行为不一致**：evalSymCall 用宿主 `==`（Evaluator.kt:679），而 ScriptValue.Struct 未重写 equals（ScriptValue.kt:51–58，引用相等）——实测 `run-script` 下 `==(P(1,2), P(1,2))` 得 false；编译端走 `__eq` 结构相等（JsCodeGen.kt:970）。差异是否为既定边界 `待核`。
8. **无优先级**：`1 + 2 * 3` 是 `(1 + 2) * 3`；需要先算的部分一律加括号。
9. **尾随 lambda 的接收者限制**：字面量 / 二元 / 一元表达式后的 `{` 不触发（`1 {` 是 ∃ 消去块边界）；`Task { … }` / `Flow { … }` 走任务 / 冷流构造。尤其注意**带 `=>` 的体不会被判作 Task 体**——实测 `Task { x => x }` 走尾随 lambda 分支解析为 `Task({ x => x })` 调用，报 E-UNBOUND-NAME「没找到函数 `Task`」。
10. **方法路径不支持命名参数**：`o.m(x = 1)`（含方法名自由形态）报 E-NAMED-ARG；命名实参只用于自由函数 `f(x = 1)`。
11. **when 模板体内的「空格 + `(`」不是调用**：stopArrow 机制下 `print(1) (11..20)` 的 `(11..20)` 不会成为 `print(1)` 的后缀调用，而是下一分支的模式前导（Parser.kt:1019–1020）。
12. **`in` 的右侧必须是区间**：`x in xs`（xs 非区间 / Range 值）报 E-TYPE-MISMATCH（v3.0 V1；集合成员待 v3.1）。
13. **隐式单参不是零参**：`{ x + 1 }` 是单参 lambda（`_` 引用形参），零参必须写 `{ => 7 }`。
14. **旧代码迁移**：`->` 全位非法（修正案）；尾随 lambda 与 when 分支的箭头一律 `=>`，命题蕴含一律 `→`（详见「箭头家族」条目）。
