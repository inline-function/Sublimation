# 05 · 工程 —— 注解与注解处理器

> **一句话**：注解是「贴在代码上的标签」——有的标签语言核心认识（@impure、@theorem、@root……），贴了就改变编译器对这段代码的行为；有的标签语言核心不认识（@allMut、@view、@myLint），它们的含义由**注解处理器**赋予——处理器本身是一段 Sublimation 脚本（.subs），在语义检查前后改写 AST，把「标签」兑现成「代码」。

Sublimation 的注解系统分两层。**语言层**：注解是声明/类型上的修饰符，改变检查器与代码生成的行为（容许副作用、标记定理、声明内建……）。**工程层**：注解处理器是编译期的用户扩展点，模型是「AST → AST」的变换管道（接近 Babel/PostCSS 插件；不同于 Java APT 只能生成新文件、也不同于 Rust proc-macro 只能生成 token）——处理器按注册顺序链式执行，产物作为**新代码**重新接受语义检查。当前实现形态是**脚本式处理器**：一个 .subs 文件就是一个处理器，由解释器解释执行；root doc/注解处理器.md 里描述的 Kotlin 接口式处理器（typeOf/SymbolsView 等）是设计草案，typeOf 在现行实现中恒返回 null（Processor.kt 的 ProcessorInput 注释明示「尽力查询，不应依赖它做关键分支」）。

## 语法

### 注解的字面文法

声明位注解：`@名字`，只读标识符、**不读实参**（parseAnnotations：Parser.kt:261–265，`while (peek(AT)) { next(); out += at(IDENT).text }`）；可堆叠多个（`@impure @android fun …`）；名字空间不受限制，但内置名字以外的注解语言核心不认识（见语义节）。

类型位注解只有三个合法名字（Parser.kt:506–522）：

| 写法 | 含义 | 非法时 |
|---|---|---|
| `@mut T` | 唯一所有权可变类型 | — |
| `@atomic T` | 原子读写类型（异步文档） | — |
| `@impure (A) => Null` | 函数类型标不纯（纯度随函数值传递） | `@impure` 修饰非函数类型、或写别的名字，报 E-PARSE「类型位注解只支持 @mut / @atomic / @impure」 |

可挂注解的节点（Ast.kt 里带 annotations 字段者）：函数声明、结构体声明、类型类声明、语句位 var、表达式位 var、形参（`@mut n: Nat`、`@tuple xs: Nat` 等）。枚举/impl/类型别名/自定义命题 def **没有注解字段**，写了也不被收集（AnnotationScanner.kt 注释明示）。`@ref` 是声明位注解（`@ref var view: Cell = c`），不是类型位——类型位写 `@ref` 会触发上面那条 E-PARSE（详见 02-类型-@ref 条目）。

### 策略调用：披着注解皮的语句

`@simp[(3 * 2 + 6) = 12]` 不是注解，而是**策略调用语句**（StrategyStmt，Ast.kt:296–303）：`@` + 策略名 + 方括号命题。策略名现支持 `simp`（化简）与 `subst`（代换）。探针实测：`@simp[(3 * 2 + 6) = 12]` 输出 `[补充] D-STRATEGY: @simp 证出 <=(+ (* 3 2) 6), 12>`；证不出报 E-STRATEGY-FAILED。

### 注解处理器的装载语法

CLI（Main.kt:201–231、USAGE）：

```
sublimation check|compile <文件|目录> [-p <处理器.subs|目录>]… [-A key=value]…
```

- **一个 .subs 文件 = 一个处理器**：处理器名 = 文件主名，关注的注解 = 文件主名（引擎据此跳过无关 AST）；目录参数装载其下**全部** .subs（按文件名排序，保证注册序稳定；只取一层，不递归）。
- 脚本源码里的注释行可声明额外关注：`@interested view`（composable.subs 用它跨注解纪律：工程里有 @view 就也要跑）。
- 脚本里可声明编译后阶段入口：`@postcompile build`。
- `-A key=value`（或 `-A key`，值为空串）可多次，汇成 options 表传给处理器；脚本内用 `option("key")`/`optionOr("key", "默认")`/`optionKeys()` 读取。
- 默认内建处理器目录是**工作目录下的 `annotation processer/`（中间带空格）**：BuiltinProcessors.DEFAULT_DIR。cwd 不对就装不上内建处理器——这是常见坑。

### 处理器脚本的宿主 API

脚本（.subs 顶层语句，无需 main）在解释器上跑，host 函数分六组（ProcessorApi.kt）：

| 组 | 函数 |
|---|---|
| 只读查询 | `structNames`/`structsWithAnnotation(a)`/`structHasAnnotation(n,a)`/`structAnnotations(n)`/`structFields(n)`/`fieldAnnotations(s,f)`/`funNames`/`funsWithAnnotation(a)`/`funHasAnnotation(n,a)`/`funHasBody(n)`/`funAnnotations(n)`（不存在的名字返回空列表，不抛异常） |
| 编译参数 | `option(k)`/`optionOr(k,d)`/`optionKeys()` |
| 宿主执行 | `runShell(cmd)`（返回 "exit\|stdout\|stderr"）、`writeFile`/`readFile`/`fileExists`、`buildAndroidApk(appDir,jsPath,outDir,sdkDir)` |
| 注解编辑 | `addStructAnnotation`/`removeStructAnnotation`/`addFieldAnnotation`/`removeFieldAnnotation`/`addFunAnnotation`/`removeFunAnnotation`（增删幂等） |
| 结构性编辑 | `setFunBody(name,src)`/`prependStmts(name,[src…])`/`addDecl(src)`/`replaceDecl(name,src)`（源码片段由宿主收尾解析嫁接） |
| 诊断 | `processorError(m)`/`processorWarn(m)`/`processorHint(m)`/`processorInfo(m)` |
| 视图支撑 | `fieldDeclText`/`structHasFieldList`/`viewCtorSites()`（"fun\|view\|序"）/ `rewriteViewCtors()`/`injectViewStruct(name)` |

## 语义

### 语言层注解：谁认识它，就改谁的行为

| 注解 | 挂点 | 语义 | 认识它的地方 |
|---|---|---|---|
| `@impure` | 函数 | 容许副作用调用；纯函数里调它 → E-IMPURE-CALL；豁免递归停机检查（CallCheck.kt:747）；其调用在 lambda 体内把 lambda 标不纯（:753–754） | Checker |
| `@mut`/`@ref` | 类型位/声明位/字段/形参 | 所有权与可变性（深拷四规则的输入） | Checker/Evaluator/JsCodeGen |
| `@atomic` | 类型位 | 该类型的读写视为原子操作 | Ast.kt:196 |
| `@theorem` | 函数 | 登记进定理空间供 `∴` 合一搜索；**运行时擦除**——JS 顶层不生成定义，值级调用返回 null（编译期已注入后件事实） | Symbols/Diffusion/JsCodeGen:576,1042 |
| `@axiom` | 函数 | 签名即公理：**下文免证**——函数体的返回后保证不做自动证明义务检查，只补一条 D-AXIOM-POST；函数体自身照常类型检查与生成 | Checker.kt:410–413 |
| `@root` | 无体函数 | 声明编译器内建：须在白名单，否则 E-ROOT-NOT-ALLOWED；调用点直接翻译为原生 JS（H-ROOT-BUILTIN）；脚本模式标准库装载时跳过 @root 声明避免撞声明 | Symbols.kt:246–268、Interpreter.kt:255–258 |
| `@host` | 无体函数 | 脚本模式宿主注入：体由宿主侧 Interpreter.register 提供 | Symbols.kt:251 |
| `@classic` | 任一声明 | 挂载 core.classic：`if[p]` 排中律语句与 classic 系策略可用（否则 E-NEED-CLASSIC） | Symbols.kt:187、Checker.kt:703 |
| `@simp`/`@subst` | 语句位（策略调用） | 证出目标命题即注入 Γ（D-STRATEGY），否则 E-STRATEGY-FAILED | Checker.kt:684–698 |
| `@async` | 函数/IO | 异步上下文标记（详见异步条目） | Types.kt 等 |

### 处理器层注解：语言核心不认识，由脚本赋义

`@allMut`（结构体连同全部字段变 @mut）、`@view`（视图结构体）、`@composable`（可组合函数）、`@android`（安卓内建）都不在语言核心内——它们的语义全部由 `annotation processer/` 下的 .subs 实现。唯一例外是 `@android` 有**双重身份**：Checker 侧 Symbols.kt:253–260 对 `@android` 无体函数做白名单门（E-ANDROID-NOT-ALLOWED）与提示（H-ANDROID-BUILTIN），JsCodeGen.kt:223 把它登记为内建 JS 桥接；处理器侧 android.subs 再做一遍白名单/纯度/无体校验（双保险）。

### 处理管线的运行语义

**单文件模式**（check：Main.kt:296；compile：Main.kt:312）：parse → 处理器多轮变换 → 语义检查。**目录（模块）模式**（Main.kt:254 → MultiModule.processModules）：阶段 A（全树符号收集）完毕后、阶段 B（类型可解析性/impl/pure）与阶段 C（声明体检查）**之前**跑处理器——处理器产出（如 @allMut 引入的 @mut）是要被合法化的代码，先变换再统一检查；任一模块 AST 有变化，则每模块重建 Checker 重跑阶段 A，再统一重跑 B/C（跨模块交叉引用的重新检查只在模块层做才完整）。这就是「A 处理器先于 B/C 检查运行」：处理器永远在符号就位之后、完整语义检查之前。

**多轮循环**（ProcessorEngine，maxRounds = 5）：每轮先 AnnotationScanner.scan 收集带注解节点 → 按注册顺序逐处理器：扫描结果里没有它关注的注解就跳过（性能优化）→ 脚本在解释器上跑一次，累积编辑与诊断 → 收尾把编辑不可变地作用回 AST（先结构性、后注解，两者按声明名匹配互不干扰）→ AST 与当前结构相等（FileAst 是 data class）即本轮无变化。某轮所有处理器都无变化 → 结束；超过 5 轮仍有变化 → E-PROCESSOR-LOOP。有变化时可触发 recheck：单文件模式每轮变化后用全新 Checker 重查；模块模式把重查交给模块层统一做。

**编辑的不可变性与幂等性**：脚本运行期不碰 AST——host 函数只累积指令（AnnotationEdit/AstEdit），ScriptProcessor.process 收尾时重建。注解增删幂等（已存在视作已兑现，不产生变化，引擎据此停机）；`addDecl` 同名声明跳过；`rewriteViewCtors` 改写过的构造点不再匹配；`setFunBody`/`replaceDecl` 同体替换深度相等即停。**`prependStmts` 天然不幂等**（每轮都往块首插一遍）——需脚本自守：插之前用 `funHasAnnotation(f, "标记")` 判断，插完 `addFunAnnotation(f, "标记")`（见示例节与陷阱节）。

**编译后阶段**（postCompile，V2）：check + JS 生成成功之后执行；脚本以 `@postcompile <函数名>` 声明入口（约定执行脚本里该名的 0 参函数）；options 经 `-A` 传入；安卓 APT 在此把 JS 装进 app 的 assets 并驱动构建 APK。其诊断**只报告不阻断**（Main.kt:284/347 打印「[警告] 注解处理器编译后阶段出错」）。

### 处理器诊断码族

| 码 | 触发 | 阻断 |
|---|---|---|
| E-PROCESSOR-LOAD | `-p` 指了非 .subs 文件（目录装载失败不抛异常，只记错） | 是（check 失败退出 1） |
| E-PROCESSOR-ERROR | 脚本抛异常（类型检查失败/运行时错误）；处理器 Kotlin 侧抛异常同码 | 是 |
| E-PROCESSOR-SCRIPT | 脚本主动 `processorError` | 是 |
| W-PROCESSOR-SCRIPT / H-PROCESSOR-SCRIPT / D-PROCESSOR-SCRIPT | 脚本主动 warn/hint/info | 否（info 要 -v） |
| E-PROCESSOR-EDIT | 结构性编辑的源码片段解析失败：该条编辑丢弃，同批其余继续 | 是 |
| W-PROCESSOR-EDIT | 编辑未命中（声明/字段名拼错、setFunBody 遇无体函数） | 否 |
| E-PROCESSOR-LOOP | 5 轮未收敛 | 是 |
| E-PROCESSOR-IO | writeFile 失败 | 是 |
| E-POSTCOMPILE-ERROR / E-POSTCOMPILE-SCRIPT | 编译后阶段异常 | 否（只报告） |

另有两个 CLI 侧入口错误：`-p` 路径不存在 → stderr「注解处理器路径不存在」+ 退出码 2；`-p` 后缺参数 → 退出码 2（均为 usage 错误，不经诊断码）。

## 示例

### @allMut：内建处理器端到端（jar 实测）

```subl
@allMut
struct Point(x: Nat, y: Nat)

@impure
fun main() {
  var p: @mut Point = Point(1, 2)
  p.x = 5                       // 字段未标 @mut 时这里 E-NOT-MUT
  print(toStr(p.x))             // 5
}
```

allMut.subs 的全部逻辑就是两条递归：给每个带 @allMut 的结构体加 @mut、给其每个字段加 @mut。实测：`check` 通过（输出「[完成] 语义检查通过」）；把 `@allMut` 摘掉再 check 即报 `E-NOT-MUT: 字段 x 不可变`。装载路径上不需要 -p——默认 `annotation processer/` 目录已含它。

### 自定义 lint 处理器（-p + -A 实测）

文件 `myLint.subs`（文件名即处理器名即关注注解）：

```subl
fun checkFuns(xs: List[Str]): Null = when(xs) {
    Nil => null
    is Cons(f, rest) => { checkOne(f); checkFuns(rest) }
    else => null
}
fun checkOne(fn: Str): Null {
    if (funHasAnnotation(fn, "myLint")) {
        var mode: Str = optionOr("mode", "default")
        if (mode == "strict") processorError("strict 模式禁止 @myLint 函数：" + fn)
        else processorWarn("myLint 命中 " + fn + "，mode=" + mode)
    } else null
}
checkFuns(funNames(0))
```

被检查代码 `@myLint fun risky(): Nat = 1`。实测结果：

```
$ subl check main.subl -p myLint.subs -A mode=warn
[警告] W-PROCESSOR-SCRIPT: myLint 命中 risky，mode=default keys=[]
$ subl compile main.subl -p myLint.subs -A mode=strict
[错误] E-PROCESSOR-SCRIPT: strict 模式禁止 @myLint 函数：risky    （退出 1，拒绝生成 JS）
```

注意两条命令的 mode 值不同——见陷阱节「check 不吃 -A」。

### 结构性编辑：注解守的 prependStmts（收敛写法）

```subl
// trace.subs：给每个 @trace 函数块首插一句 var t = 1，插过就记账
fun containsFun(f: Str): Bool = contains(funAnnotations(f), "traced")
fun loop(xs: List[Str]): Null = when(xs) {
    Nil => null
    is Cons(f, rest) => {
        if (containsFun(f)) { null } else {
            prependStmts(f, listOf("var t = 1"));
            addFunAnnotation(f, "traced")
        };
        loop(rest)
    }
    else => null
}
loop(funsWithAnnotation("trace"))
```

表达式体函数（`fun expr(n: Nat): Nat = n + 1`）会被脱糖成块（`var t = 1` + `return n + 1`）。其它结构性编辑：`setFunBody("n", "7")` 整体换体；`addDecl("fun triple(x: Nat): Nat = x * 3")` 追加声明（同名幂等跳过）；`replaceDecl("magic", "fun magic(): Nat = triple(2)")` 原位替换。产物一律过重查——把体换成 Str 字面量会被重查的 E-TYPE-MISMATCH 拦截（测试 structuralEdit_typeUnsafeOutputFailsRecheck 同理）。

### 语言层注解速写

```subl
@theorem fun LEM[@p]: Null <p ∨ ¬p>          // 定理函数：∴ 可合一搜索；值级调用运行时得 null
axiom p ∨ ¬q                                 // axiom 语句：直接注入上下文（与 @axiom 注解无关）

@axiom fun trusted(): Nat <$ = 999> = 1      // 下文免证：D-AXIOM-POST；去掉 @axiom 即 E-POST-UNPROVEN

@classic fun mount(): Null = null             // 任一声明带 @classic 即挂载 core.classic
@impure fun main() {
  @simp[(3 * 2 + 6) = 12]                     // 策略调用：D-STRATEGY
  if[p] { ∴ p } { ∴ ¬p }                      // 排中律：需 @classic，否则 E-NEED-CLASSIC
}
```

### 宿主外壳：在 Kotlin/脚本里驱动处理器

```kotlin
val host = AnnotationProcessorHost()          // init 即装载默认内建处理器
host.loadProject("myproject/")                // 或单个 .subl 文件
val result = host.processAnnotations()        // 初检 → 多轮（含重查）→ 汇总
println(host.diagnosticsReport())
host.writeGenerated("out.subl")               // 处理器 emit 累积的生成代码
```

脚本侧的对应形态是 @host 函数：`loadProject(path)`/`processAnnotations()`/`writeGenerated(path)`，外加 `annotatedCount()`/`diagnosticReport()`/`hasErrors()`（ProcessorHost.kt 的 hostFunctions）。

## 陷阱

- **`@axiom`（函数注解）≠ `axiom`（语句）**：前者让函数的**下文**免自动证明（D-AXIOM-POST）；后者是顶层/函数内通用的公理注入语句（`axiom p1, p2`，返回 Null）。旧的 `unchecked.axiom[p]` 已废除。名字像，机制完全不同。
- **`@simp[命题]` 不是注解**：它是策略调用语句（`@` + 策略名 + `[…]`），不能写在声明前；声明前写 `@simp fun x()` 只会给函数挂一个没人认识的注解。
- **check（单文件）不吃 `-A`**：Main.kt:296 的 `runBuiltin(ast, extraProcessors)` 是两参重载，options 为空表；只有 compile（:312）与目录模式（:254）传 processorOptions。实测 check 带 `-A mode=strict` 时脚本读到的是 `mode=default, keys=[]`。给 check 用的处理器别依赖 options（或把它当待核的差异对待）。
- **默认处理器目录带空格且相对 cwd**：`annotation processer/`——在别的目录跑 jar 就没有内建处理器（`@allMut` 静默失效，连 W 都没有）。测试/CI 要么固定 cwd，要么显式 -p。
- **无关注注解就整个跳过**：处理器只对同名注解起反应（外加 `@interested`）。反过来说：脚本里 if 判断用了别的注解（如 composable.subs 要看 @view），必须用 @interested 声明，否则引擎根本不会跑它。
- **`prependStmts` 不幂等 → E-PROCESSOR-LOOP**：每轮插一遍、每轮都有变化，5 轮封顶报错，且每轮重查的诊断会**累加**（实测一次 Loop 输出 6 条相同的 W-UNUSED——单文件模式不做袋内去重，只有 MultiModule 路径调 dedupe）。一定用「插前查注解、插完加注解」的自守模式。
- **处理器顺序 = 注册顺序**：内建集按**文件名排序**（allMut → android → composable → view），`-p` 追加在后面；`-p a.subs -p b.subs` 按命令行序。顺序就是流水线顺序，依赖关系自己管。目录装载只取一层（不递归子目录）。
- **结构性编辑的片段是源码字符串**：解析失败整条丢弃并报 E-PROCESSOR-EDIT（同批其它编辑照常）；目标声明不存在只报 W-PROCESSOR-EDIT（不阻断）——拼错名字是最常见的静默失效。所有编辑都按**声明名**匹配（impl 无名，不参与按名替换）。
- **脚本异常 ≠ 编译失败的一种可选路径**：脚本崩了报 E-PROCESSOR-ERROR（错误级，阻断），但 AST 原样返回、不改你的代码。别把它当 try/catch 用。
- **root doc 的接口式处理器是草案**：`ProcessorInput.typeOf` 恒返回 null（类型信息在 Checker 的弥散上下文里，不在 AST 节点上）；`SymbolsView` 只读；`emit` 只在宿主外壳里有写出端。按 root doc/注解处理器.md 3.1 的 Kotlin 接口写处理器会失望——现役形态是 .subs 脚本。
- **`@android` 的双重身份**：Checker 对它有白名单门（E-ANDROID-NOT-ALLOWED，仅认 log/toast/layout/7 个生命周期/androidRecompose 等），JsCodeGen 把无体 @android 函数桥接为内建 JS；处理器 android.subs 又做一遍校验并可选构建 APK——三处认识的名字清单要保持一致（意图/平台能力类名字在处理器白名单里更全，Checker 侧是否同步待核）。
- **注解没有实参**：`@anno(x)` 现在解析不了（parseAnnotations 只吃 @IDENT）。需要参数化注解的语义，走角表 `<…>`（上文/下文）或处理器 options，别等 `@Anno(常量)`。
- **类型位注解白名单只有三个**：`@mut`/`@atomic`/`@impure`。`@ref` 是声明位的（`@ref var x: T = e`）；`@view struct` 的 @view 是声明位注解、不是类型位。
