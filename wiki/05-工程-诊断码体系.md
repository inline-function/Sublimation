# 05 · 工程 —— 诊断码体系

> **一句话**：编译器对你说的一切都带一个「身份证号」——`E-TYPE-MISMATCH` 这样的码。`explain <CODE>` 是只凭身份证号就能查到「含义 + 修复建议」的子命令；`check -v` 决定要不要把最安静的第四级（补充级）也放出来。

Sublimation 的每条诊断都不是裸文本，而是「严重级 + 诊断码 + 位置 + 消息」的四元组。截至本文写作，编译器自带的诊断码解释表（`EXPLAIN`，Main.kt:64）共收录 **106 条**：E 族 70、W 族 10、D 族 19、H 族 7。本条目讲码的写法、族的语义、分级输出与查询入口；具体某条语言的规则（可变性、证明、when）见对应领域条目。

## 语法

### 诊断码的字面文法

`<家族字母>-<大写单词>[-<大写单词>…]`

- 家族字母：`E` / `W` / `D` / `H`，大写；
- 家族字母后恰一个连字符 `-`；
- 正文由大写字母（`A-Z`）与数字组成，词与词之间以连字符分隔，如 `E-IMMUT-ASSIGN`、`E-CONSTRAINT-VIOLATED`、`W-NON-EXHAUSTIVE`、`D-PLUSBECAUSE-PROVED`；
- 正文常是「规则名缩写 + 违反点」的压缩英语（immutability assign → `IMMUT-ASSIGN`、non-sealed match → `NON-SEALED-MATCH`），不含空格与全角字符。

写作约定：文档、Issue、终端输出中一律写规范形（大写连字符）；`explain` 子命令内部会把入参 `uppercase()`（Main.kt:102），所以终端里敲小写也能查到，但码本身的规范拼写仍是全大写。

### 严重级与家族的对应

诊断的严重级在 `Diag.kt:4` 定义为四级枚举：

| 严重级（Severity） | 渲染标签 | 对应码族 | 是否阻断编译 | 默认是否输出 |
|---|---|---|---|---|
| `ERROR` | `[错误]` | `E-` | 是 | 是 |
| `WARN` | `[警告]` | `W-` | 否 | 是 |
| `HINT` | `[提示]` | `H-` | 否 | 是 |
| `SUPPLEMENT` | `[补充]` | `D-` | 否 | **否**（仅 `-v`） |

注意常说的「E/W/D 三族」（langfacts §8）是以**阻断性与可见性**划线：E 阻断、W 警告、D 补充。代码实现上 HINT 是独立一级、对应 `H-` 前缀码；「三族」是就编译器对外宣传的主干而言的概括，H 族（7 条）同样收录在 EXPLAIN 表里。

### 单条诊断的输出形态

`Diag.render`（Diag.kt:13–32）的固定格式：

```
[标签][行:列] <CODE>: <消息>
  <右对齐行号> | <源码该行>
  <空格对齐> | <箭头>
```

位置为空时省略 `[行:列]`；`pos` 非 `line:col` 形态或源文本未给时，不追加源码片段。`check` 单文件路径给 `source = src`（Main.kt:303），目录模式不给（Main.kt:257）——即**目录模式目前没有源码片段上下文**。

### CLI 入口

| 命令 | 语法 | 作用 |
|---|---|---|
| 查询 | `subl explain <CODE>` | 打印该码的含义与修复建议；无需源文件 |
| 查询（失败） | — | 未收录时 stderr 打印 `[错误] 未收录诊断码 <CODE>（现有：…全部码排序列表…）` 并 `exitProcess(2)`（Main.kt:105–108） |
| 分级输出 | `subl check <文件/目录> -v` | 报告时同时输出补充级（`report(includeSupplement = verbose)`） |

`-v` 是**全局旗标**（对整个 args 数组 `contains` 判定，Main.kt:94），与命令位置无关，且对 `check`、`compile`、目录模式、单文件模式一致生效；它与激进证明旗标（见「03 · 证明 —— 激进模式」）正交。

## 语义

### 各族的判定语义

- **E 族（ERROR，70 条）**：编译失败的前提条件被违反——类型/名字/可变性/证明义务/模块配置任一不成立，`check` 输出 `[错误] 语义检查未通过` 并以退出码 1 结束；`compile` 拒绝生成 JS（Main.kt:305 / 322）。少数 E 是「编译器自身的通道」：`E-CHECK` 是 Checker 抛出意外异常时的兜底（表内明示「通常是编译器自身的 bug，请保留源码并反馈」），`E-LEX`/`E-PARSE` 是词法/语法层失败的总码。
- **W 族（WARN，10 条）**：代码**可疑但不阻断**。W 族的常见语义是「编译器证不出，但不敢断言你错」——`W-CONSTRAINT-UNPROVEN`（实参是运行时变量时只给警告）、`W-NON-EXHAUSTIVE`（分支可能没走完）、`W-UNUSED`/`W-UNREACHABLE`（卫生类）。看到 W 要读消息判断是真 bug 还是推导能力边界。
- **D 族（SUPPLEMENT，19 条）**：**确认性回声**，不是问题。它告诉你在某处编译器做了什么：糖展开了什么（`D-INFIX`/`D-TRAILING`/`D-METHOD-SUGAR`）、发生了深拷贝（`D-DEEP-COPY`）、类型是推导出来的（`D-TYPE-INFERRED`）、命题已注入或证出（`D-BTS`/`D-PLUSBECAUSE-PROVED`/`D-THEREFORE`）。默认隐藏，`-v` 放出——用途是学习语言与调试「编译器到底理解成了什么」。
- **H 族（HINT，7 条）**：风格建议与教学提示，不阻断也不隐藏：`H-ARITH-PRECEDENCE`（语言无运算符优先级，混用 `+`/`*` 时建议加括号）、`H-FIELD-SHADOW`（参数名遮蔽同名字段）、`H-AMBIGUOUS-CTOR`（多枚举同名构造子，用 `枚举::构造子` 消歧）等。

### 报告的伸缩：`-v` 之外的三道闸

1. **默认隐藏补充级**：`report()` 过滤掉 `SUPPLEMENT`（Diag.kt:65）；`-v` 才放进报告。
2. **多模块噪声过滤**：`dropSupplementsOutside(rootPath)`（Diag.kt:51）把非根模块（典型是 `core` 标准库）的补充级诊断整体丢弃——即使 `-v`，你也看不到标准库自身的推导补充，这是有意设计。
3. **去重**：`dedupe()`（Diag.kt:56）按 `code + pos + message` 三元组去重，保留首轮——类型推导定点迭代重查 lambda 时会重复产生同一条诊断，循环后只留权威首发。不同位置的同码错误互不吸收。

### `explain` 的查询语义

`explain` 是**纯查表**：`EXPLAIN[code]` 精确命中或失败（Main.kt:96–109），不读源码、不跑管线。表项文本是固定两段式：含义句以「。——」分隔、后接修复建议；`explain` 原样打印 `$code — $text`。查询大小写不敏感（入参先 `uppercase()`），但未知码不会做模糊匹配；失败时把全部已收录码按字典序列出（106 条会刷很长一屏），本身是个「全表目录」的副带入口。

### 诊断的产生与归并

词法/语法层的诊断在 parse 阶段产生；语义诊断由 Checker 写进 `DiagBag`（`error/warn/hint/supplement` 四个入口，Diag.kt:39–42）；多模块时各模块的袋经 `absorb` 合并（Diag.kt:48），每条诊断带 `modulePath` 归属。注解处理器的诊断按 severity 映射进同一个袋（Main.kt 编译后阶段的 `PostCompileCtx` 回调），编译后阶段的诊断只报告不阻断。脚本模式（`run-script`）另有一条通道：解释器的推导提示经 `interp.inferNotes` 以 `[提示] [CODE] message` 直接打印（Main.kt:289–291、371–372），`D-AUTO-IMPURE` 这类全局推导降级提示就走这里（待核：该通道与 EXPLAIN 表的覆盖是否完全一致）。

## 示例

### 精选速查表（常用码 → 含义 → 修复建议）

EXPLAIN 表每次查一条；下表按场景精选最常碰到的码，三列分别为码 / 一句话含义 / 修复动作。全表用 `subl explain ` 加一个拼错的码（触发失败列表）或直接翻源码 Main.kt:64–169。

**可变性与所有权**

| 码 | 含义 | 修复建议 |
|---|---|---|
| `E-IMMUT-ASSIGN` | 给不可变变量赋值 | 声明处改 `@mut var`，或换新变量名 |
| `E-NOT-MUT` | 改字段需可变视图 | 字段加 `@mut` 且变量类型写 `@mut T` |
| `E-IMPURE-REQUIRED` | 参数带 `@mut T` | 函数声明加 `@impure` |
| `E-IMPURE-CALL` | 纯函数里调了有副作用的函数 | 外层标 `@impure`，或去掉该调用 |
| `E-ASSIGN-TARGET` | 赋值左边不是变量 | 左边写成变量名/可变字段 |

**类型与名字**

| 码 | 含义 | 修复建议 |
|---|---|---|
| `E-TYPE-MISMATCH` | 值类型与期望不符 | 对齐声明处的参数/返回类型标注 |
| `E-UNBOUND-NAME` | 名字未定义 | 查拼写、先声明，或 `mount` 所在模块 |
| `E-ARITY` | 实参个数不对 | 数清声明与调用的参数数 |
| `E-ANY-CALL` | 推导成了 Any | 手动标注，如 `var x: Nat = …` |
| `E-KIND-MISMATCH` | 类型构造子裸用 | 带上类型参数，如 `List[Nat]` |
| `E-DUP-DECL` | 重复声明 | 改名或合并两份声明 |
| `E-MAIN-PARAMS` | main 带了形参 | 写成 `fun main() { … }` |

**证明与命题**

| 码 | 含义 | 修复建议 |
|---|---|---|
| `E-CANNOT-PROVE` | ∴ 的目标证不出 | 前置 `∵` 注入、或 `axiom` 声明公理 |
| `E-PREMISE-UNPROVEN` | ∵ 的前提证不出 | 前提须为上下文已知事实，先证它 |
| `E-PROP-UNBOUND` | 前提命题不在已知事实里 | 先用 `∵` 或 `∃` 引入 |
| `W-PROP-UNBOUND` | when[p] 的析取前提不在上下文 | 用 `axiom p ∨ q` 或前置证明注入 |
| `W-CANNOT-PROVE` | ∵/∴/+∵ 里的命题推不出 | 检查是否漏前提，或换能自动证的写法 |
| `E-DEEP-SATURATION` | 证明太复杂，搜索饱和 | 拆成小步骤，逐步 `∴` 中间结论 |
| `D-BTS` | ∵ 注入支撑 ∴ 结论，已入上下文 | 无需修复——确认性回声 |
| `D-NAT-PROP` | 注入 n ≥ 0 自然命题 | 无需修复——可直接用于自动证明 |

**when 与控制流**

| 码 | 含义 | 修复建议 |
|---|---|---|
| `E-NON-SEALED-MATCH` | when 作表达式但无兜底 | 补全构造子分支或加 `else` |
| `W-NON-EXHAUSTIVE` | when 可能没走完所有情况 | 补剩余构造子；区间 when 查端点衔接 |
| `E-MISSING-RETURN` | 块体函数缺 return | 补 `return`，或改表达式体 `= 值` |
| `E-RETURN-OUTSIDE` | return 出现在非法位置 | return 只能在具名函数体/lambda 体语句流里 |
| `W-UNREACHABLE` | return 之后不可达 | 删掉或上移 |

**Async 与处理器**

| 码 | 含义 | 修复建议 |
|---|---|---|
| `E-NEED-ASYNC` | 异步调用需异步上下文 | 外层加 `@async`（main 天然 async） |
| `E-NOT-STARTED` | Task 未启动先 await | 先调 `t.start()` |
| `E-PROCESSOR-LOAD` | 处理器脚本加载失败 | 查 .subs 脚本语法与附带错误消息 |
| `W-PROCESSOR-EDIT` | 处理器编辑没命中目标 | 查脚本里的名字拼写（不阻断） |

**W/D/H 全量余码**（表短，列全）：`W-WHEN-NO-COMMON`（分类讨论各支结论不同）、`W-CONSTRAINT-UNPROVEN`（约束表条件证不出，只警告）、`W-DIV-ZERO`（字面量除零）、`W-PROCESSOR-SCRIPT`（脚本 `processorWarn`）；D 族其余 14 条：`D-AXIOM-POST`、`D-WHEN-PROP`、`D-STRATEGY`、`D-AUTO-IMPURE`、`D-TYPE-INFERRED`、`D-METHOD-SUGAR`、`D-AUTO-AWAIT`、`D-INFIX`、`D-TRAILING`、`D-BECAUSE-PROVED`、`D-BY`、`D-EXIST-INTRO`、`D-LOCAL-FUN`、`D-PROCESSOR-SCRIPT`；H 族 7 条全列：`H-ROOT-BUILTIN`、`H-FIELD-SHADOW`、`H-PARAM-REF`、`H-AMBIGUOUS-CTOR`、`H-EMPTY-DECL`、`H-ARITH-PRECEDENCE`、`H-PROCESSOR-SCRIPT`。E 族前文未列的约 40 条（元组解构、结构体构造、impl 一致性、类型参数、模块/设置、注解处理器等）逐条以 `explain` 查。

### `explain` 用法

```shell
subl explain E-IMMUT-ASSIGN
# E-IMMUT-ASSIGN — 给不可变的变量赋值了。—— xxx 声明时没标 @mut，
#   不允许重新赋值。要么改成 @mut var xxx = …，要么换个新变量名。

subl explain e-imm-assign        # 小写也行：explain 内部 uppercase()
subl explain E-NOPE             # [错误] 未收录诊断码 E-NOPE（现有：E-AMBIGUOUS-INSTANCE / …全 106 条…）
```

成功路径退出码 0、只打印一行到 stdout；失败路径退出码 2、走 stderr，**无需任何源文件**——这是它在 CI 与文档里的典型用法（拿到码就能查，不必带着整个工程）。

### 一段触发多族诊断的代码

```subl
fun main() {
  var n: Nat = 1
  n = 2                                   // E-IMMUT-ASSIGN：n 未标 @mut
  ∵ p                                     // E-PREMISE-UNPROVEN 或 W-CANNOT-PROVE：p 无来源
  ∴ q                                     // E-CANNOT-PROVE：上下文无 q 的依据
  var x = 1                               // W-UNUSED（若后续不用）；D-TYPE-INFERRED（-v 才看见）
  when (n) {                              // Nat 上 when：分支穷尽性另受 W-NON-EXHAUSTIVE 约束
    0 => print("zero")
    1 => print("one")
  }
}
```

`check f.subl -v` 的输出形态（节选，示意）：

```
[错误][3:3] E-IMMUT-ASSIGN: 给不可变的变量赋值了。—— n 声明时没标 @mut……
  3 |   n = 2
    |   ^
[警告][8:3] W-NON-EXHAUSTIVE: when 可能没走完所有情况。……
[补充][5:1] D-TYPE-INFERRED: 变量类型是编译器推导出来的。……
  5 |   var x = 1
    | ^
[错误] 语义检查未通过
```

补充级排在最后不是排序保证，而是袋内插入顺序；唯一的硬过滤是「无 `-v` 时 D 族整族不出现」。

## 陷阱

- **「证不出」有三种码、严重级不同**：`E-CANNOT-PROVE`（∴ 的**目标**证不出）、`E-PREMISE-UNPROVEN`（∵ 的**前提**证不出）、`W-CANNOT-PROVE`（∵/∴/+∵ 里的命题推不出，**降级为警告**）。码名相似，阻断性截然不同——看到 W 开头先判断是不是推导能力边界而非代码错误。
- **`W-PROP-UNBOUND` 与 `E-PROP-UNBOUND` 是两件事**：前者是 `when[p]` 分类讨论的析取前提不在上下文（警告），后者是通用前提命题不在已知事实（错误）。别按名字前缀猜语义。
- **「三族」说法与四级实现**：文档常说 E/W/D 三族，但 Severity 实为四级、EXPLAIN 表还收了 7 条 `H-` 提示码。按家族字母（而非严重级标签）记码：`D-` 对应的是 `[补充]`，不是 `[提示]`；`H-` 才是 `[提示]`。
- **`-v` 放不出 core 的补充**：多模块模式下 `dropSupplementsOutside` 先把非根模块的补充级整族丢弃，`-v` 只是开闸、不复活被过滤的噪声。目录模式同时不给源码片段上下文（`report` 未传 source）。
- **`explain` 失败列表很长**：拼错码会刷出全部 106 条字典序列表；写脚本解析它的输出别按行数假固定。
- **`->` 的诊断落在 E-LEX/E-PARSE 一侧**：修正案后 `->` 全位非法，lexer 仍出 ARROW 仅供诊断——看到 E-LEX 提到箭头类字符，先想是不是想写程序位 `=>` 或命题位 `→`。
- **同码不同位置都会保留**：`dedupe` 只吸收 `code+pos+message` 完全相同的重复（定点迭代产物），两处同种错误会各报一次，别误以为只够修一处。
- **处理器诊断分两条路**：装载失败是 `E-PROCESSOR-LOAD`（阻断），编译后阶段错误只打印 `[警告] 注解处理器编译后阶段出错`、不阻断；脚本主动消息是 `H-PROCESSOR-SCRIPT`/`D-PROCESSOR-SCRIPT`，前者默认可见、后者要 `-v`。
- **E-CHECK 不是你的错**：它是 Checker 内部异常的兜底码，消息明示「通常是编译器自身的 bug，请保留源码并反馈」——修代码前先怀疑编译器。
- **`D-AUTO-IMPURE` 只在脚本模式**：全局推导的停机检查降级走 `inferNotes` 通道（`run-script`），工程模式 `check` 里看不到它；同理脚本模式的推导提示不进 DiagBag（待核：两通道码覆盖一致性）。
- **退出码约定**：`explain` 命中、`check` 通过退出 0；`check`/`compile` 有 E 族退出 1；`explain` 未收录、参数缺失、文件不存在退出 2——CI 脚本可据此区分「编译失败」与「命令本身用错」。
