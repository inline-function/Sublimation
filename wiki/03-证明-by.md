# 03 · 证明 —— by（辅助策略供给）

> **一句话**：「by」 是把「人给的中间命题」**直接注入**当前作用域 Γ 的供给语法——不经证明器检验、不带证明义务；后缀式 「expr by [q]」 在注入的同时**返回 expr 的值**，把证据绑定在产生它的表达式上。

「by」 有两种形态：**语句式** 「by [q₁, q₂]」（独立语句，值固定为 Null）与**后缀式** 「e by [q₁, q₂]」（表达式位，值即 e 的值）。两者共用同一句子成分——方括号命题列表 「[…]」——注入的命题进入**当前帧** Γ，之后与 axiom 事实、自动事实同权参与一切推理（MP 闭包、∀ 实例化、算术通道、调用点上文供给）。它跟 axiom 的区别不在机制（都不验证），而在**语义标注**：axiom 是「信任逃逸」（外部事实、数学前提），「by」 是「辅助策略」（把大结论拆成小步、由人背书中间命题），编译器以 「D-BY」 补充级诊断留痕。

## 语法

```subl
by [q]                          // 语句式：注入 q，语句值 Null
by [q1, q2, valid<7>]           // 多条，逗号分隔
expr by [q]                     // 后缀式：注入 q，表达式值 = expr 的值
f(x) + 1 by [q1, q2]            // 目标可为任意表达式（左结合先并 f(x)+1）
```

**词法**：「by」 是保留关键字（Lexer.kt:43 「"by" to Kind.BY」），不能当变量名用（实测 「var by = 1」 报「期望标识符，实际 'by'」）。

**两种入口**：

| 形态 | 解析入口 | AST |
|---|---|---|
| 语句式 | parseStmt 见 BY 即 「pos++; ByStmt(parseBracketList())」（Parser.kt:652） | ByStmt(props)（Ast.kt:259） |
| 后缀式 | parseExpr 中缀循环：「if (t.kind == Kind.BY) { pos++; left = ByExpr(left, parseBracketList()); continue }」（Parser.kt:1027） | ByExpr(target, props)（Ast.kt:436） |

**命题列表文法**（parseBracketList，Parser.kt:1657-1673，by 与 axiom 语句共用）：

```ebnf
G-26  by语句  ::= "by" "[" 表达式 ("," 表达式)* ","? "]"      /* 辅助策略注入 */
G-30  中缀位  ::= ... | "by" "[" 命题列表 "]"                 /* e by [q] 后缀式 */
```

- 每条命题按完整表达式解析（「parseExpr(angle = false)」）：比较 「k > 0」、蕴含 「p → q」、量词 「∀n. valid<n>」 皆可（angle=false 时 「>」 恒作比较中缀，不作角表终止符）
- 尾随逗号仅在随后的 「)」/「]」/「}」 前允许（Parser.kt:1665）；注意这与 axiom 的规则（「}」/「;」/EOF，Parser.kt:713）不同
- 空列表 「by []」 合法（注入 0 条命题，仅发 「D-BY」 留痕；实测）

**优先级**：表达式层无优先级、全左结合，「by」 只是普通中缀位：

- 「1 + 2 by [q]」 ≡ 「(1 + 2) by [q]」（先并完左边，by 接整个左操作数）
- 「a by [q] + 2」 ≡ 「(a by [q]) + 2」（by 在前，先成 ByExpr 再加 2）
- 需要其它结合顺序时一律加括号

**同名异物**：「impl C for T by field」 里的 「by」 是**委托语法糖**（v3.0 特性 2，ImplCheck.kt:36/296），要求 「by」 后跟字段名（IDENT），与本条目的命题供给毫无关系；两条解析路径互不干扰（委托 Parser.kt:971-978 vs 后缀 1027）。

## 语义

### 注入即成立，类型透明

后缀式检查（Checker.kt:1264-1269）：

```kotlin
is ByExpr -> {
    val t = checkExpr(e.target, f, pure)                    // ① 先查目标，得类型 t
    e.props.forEach { f.inject(PropLogic.fromExpr(it)) }    // ② props 规范化后注入当前帧 Γ
    d.supplement("D-BY", e.pos, "辅助策略注入 ${e.props.size} 条命题")  // ③ 补充级留痕
    t                                                        // ④ 表达式类型 = 目标类型
}
```

- **注入顺序**：目标先检查、命题后注入，所以供给对**之后**的语句/表达式可见，不能反过来帮目标自身通过检查
- 语句式（Checker.kt:762-766）同构：只注入、发 「D-BY」、语句类型 「Null」
- 平凡命题被丢弃：「Frame.inject」 跳过 「PTop」（Diffusion.kt:40），「by [⊤]」 是空操作
- 纯度：「containsImpureCall」 也会遍历 ByExpr 的 target 与 props（Diffusion.kt:159），但 props 属命题层、求值期被擦除，正常写法不影响纯性判定

判断式（与 boring doc/04-命题与证明.md §6.8 同义）：

$$\frac{}{\Gamma' = \Gamma \cup \{q_1, q_2, \dots, q_n\} \qquad \text{表达式值} = \llbracket e \rrbracket} \quad (\text{R-BY-EXPR})$$

$$\frac{}{\Gamma' = \Gamma \cup \{q_1, q_2, \dots, q_n\} \qquad \text{语句值} = \text{null}} \quad (\text{R-BY-STMT})$$

### 免验证——「辅助策略」而非证明义务

- by 命题**不跑** proveOrDeep、不搜定理、不产生任何 「E-CANNOT-PROVE」：实测 「by [1 = 2]」（伪等式）与 「by [a > 0]」（a 无处定义）均合法通过
- 与之对照：「∴ 1 = 2」 报 「E-CANNOT-PROVE」（义务）；「∵ … ∴ q」 的前提证不出报 「E-PREMISE-UNPROVEN」（Checker.kt:640）
- by 的语义定位是「把大结论拆成小步，由人负责中间命题的正确性」（boring doc/04-命题与证明.md:809）；「D-BY」 诊断（boring doc/10-诊断码.md:296）就是这份「人背书」的留痕

### 与 Γ、∵∴ 链的关系

「f.inject」 是 Γ 的唯一入库口（Diffusion.kt:40）——by 与 axiom、var 声明、下文弥散走同一条路，注入后**事实之间不可区分**：

- **MP 闭包**：「by [p ∧ (p → q)]」 ⇒ 下次查询时 Γ 饱和产出 「q」，「∴ q」 直通（实测）
- **∀ 实例化**：「by [forall n. valid<n>]」 可供给调用点上文 「valid<7>」（实测）
- **算术通道与等式链**：「by [r == 6]」 形态的等式原子进入 ArithProve 的等式双向边
- **充当 ∵∴ 链前提**：「∵ form, p ∴ q」 中前提 p 由 「proveOrDeep(f.allFacts())」 验证（Checker.kt:638）——by 注入的 p 直接合格；结论 q 由 「Γ + 前提」 推（Checker.kt:646），by 事实同样参与；链通过后**结论**注入 Γ（Checker.kt:647）。即：**by 供料、∵∴ 加工、结论回吐 Γ**
- 命题参数供给：「by [p]」 可为形如 「fun w[@q]<q>: Null」 的命题参数函数充当候选（与 axiom 同池；候选多于一条时同样报 「E-PROP-AMBIGUOUS」，未实测，**待核**）

「by」 与 「∵∴」 的分工：**「by」 是供给（直接成立），「∵∴」 是义务（必须证出）**。证不出的目标可以先用 「by」 把可信赖的中间步骤喂给 Γ，再让 「∴」 或下文核对自动完成最后一步（见例 6）。

### 作用域（帧语义）

注入目标是**当前帧** 「f」，不是全局符号表：

- 函数体从 「Frame(null)」 起步（Checker.kt:207/290）：函数内的 by **不外泄到调用者**（实测 「fun g(): Null { by [s] }」 之后顶层 「∴ s」 报 「E-CANNOT-PROVE」，Γ 为空）
- lambda 帧隔离（Checker.kt:1310 「Frame(f)」）：lambda 体内的 by（无论语句式还是后缀式）不外泄（实测 「var g = { 1 by [zz] }」 之后 「∴ zz」 证不出）
- **值块帧事实回溢父帧**（Checker.kt:1161 「nf.facts.forEach { f.inject(it) }」）：if/when **表达式**分支体里的 by 会对**块外**可见——实测 「var s = if(n == 0) { by [zero]; "z" } else { by [nz]; "n" }」 之后 「∴ zero」 与 「∴ nz」 **双双通过**（两支的事实都回溢）
- 工程模式（.subl）顶层**只放行 axiom**，「by」 属于执行语句：实测顶层 「by [q]」 报「期望顶层只能写声明，执行代码请放进 fun main()」（脚本模式 .subs 的顶层则一切照常）

### 求值与代码生成：命题擦除

- 解释器：ByStmt → 「ScriptValue.Null」（Evaluator.kt:191）；ByExpr → 只求值 target（Evaluator.kt:250），props 完全不参与运行时
- JS 生成：ByStmt → 审计注释 「// by: <命题>」（JsCodeGen.kt:821，可 grep）；ByExpr → **只留目标值**、**无注释**（JsCodeGen.kt:930）
- 实测编译产物对照（源码 「axiom p / by [q] / var x = 5 by [x == 5] / print(x)」）：

```js
async function main() {
    // axiom: p          ← axiom 语句留注释
    // by: q             ← by 语句留注释
    const x = 5;         // 后缀式擦除得干干净净，无 by 痕迹
    console.log(__dshtoStr(x));
    return null;
}
```

### 与相邻机制的区别

| 机制 | 语法 | 语义 |
|---|---|---|
| **by 语句** | 「by [q1, q2]」 | 命题直接注入 Γ，免验证，发 「D-BY」，语句值 Null（本条目） |
| **by 后缀式** | 「e by [q]」 | 同上，但表达式值 = e 的值，可出现在任意表达式位（本条目） |
| axiom 语句 | 「axiom p1, p2」 | 同为直接注入免验证，但属「信任逃逸」、无补充级诊断；工程模式顶层放行（by 不放行） |
| ∵∴ 链 | 「∵ form, p ∴ q」 | 证明义务：前提与结论都要证出，通过后结论注入 Γ（Checker.kt:633-654） |
| 裸 ∴ | 「∴ q」 | 只验证 q 是否已证（证不出报 「E-CANNOT-PROVE」），不注入新事实 |
| 策略语句 | 「@simp[…]」「@subst[…]」 | 调用特定证明器去**证**目标（化简/等量代换），不是注入 |
| unchecked | 「unchecked <语句>」 | 逃逸纯度/可变性闸门，与命题供给无关 |

## 示例

例 1 — 语句式最小形态（脚本模式，实测通过）：

```subl
// by1.subs
by [p]
∴ p                     // p 已在 Γ ⇒ 直通
print("ok")
```

例 2 — 后缀式：把证据绑定到产生它的表达式（实测通过）：

```subl
var x = 5 by [x == 5]   // 注入 =(x,5)，x 的值仍是 5
∴ x == 5
print(x)                // 打印 5
```

例 3 — 供给 MP 闭包（实测通过）：

```subl
by [p ∧ (p → q)]
∴ q                     // Γ 饱和自动产出 q
print("ok")
```

例 4 — 给 ∵∴ 链当前提（实测通过）：

```subl
var a = 1
by [a == 1]            // 自动证明器不折变量等式时，人来供料
∵ a == 1 ∴ a != 0
print("ok")
```

例 5 — 供给调用点的上文命题参数（实测通过）：

```subl
fun needP()<p>: Null { }
@impure fun main() {
    by [p]
    needP()             // 上文 <p> 由 by 的事实供给
    print("ok")
}
```

例 6 — 下文义务：自动证明器证不出时，by 是编译器**亲口推荐**的辅助手段。「E-POST-UNPROVEN」 的诊断文案即写道「必要时用 「by」 策略辅助证明」（Checker.kt:417；实测对照）：

```subl
fun double(n: Nat): Nat = n * 2

// ✗ 自动证明器不折叠函数调用，报 E-POST-UNPROVEN（下文 ==<r, 6>）
fun plain(): Nat <$ == 6> {
    var r = double(3)
    return r
}

// ✓ 同样的体，把人验算的中间等式就地供给
fun good(): Nat <$ == 6> {
    var r = double(3) by [r == 6]   // =(r,6) 进 Γ，下文 <$ == 6> 直通
    return r
}
@impure fun main() { print(good()) }
```

注意此模式必须**先绑定到名字**：表达式体 「fun f(): Nat <$ == 6> = double(3) by [$ == 6]」 不可行——下文核对以整个体为 「$」（dollarOf，Checker.kt:407），此时 「$」 指向 ByExpr 本身，等式两边的项对不上（实测仍报 「E-POST-UNPROVEN」，目标被渲染成 「==<?, 6>」）。

例 7 — 值块分支里的 by 会回溢外层（实测通过）：

```subl
fun cls(n: Nat): Null {
    var s = if(n == 0) { by [zero]; "z" } else { by [nz]; "n" }
    ∴ zero               // 两支的 by 事实都溢出到函数帧
    ∴ nz
    print(s)
}
@impure fun main() { cls(0) }
```

例 8 — 编译产物（compile 实测，语句式擦除为注释可 grep 审计）：

```js
async function main() {
    // by: q
    // by: a
    // by: b
    console.log(__dshtoStr(1));
    return null;
}
```

## 陷阱

**解析类（最危险：by 会被“吸走”）**

- ❌ **换行吞 by**：换行不是 token（_langfacts §1），而 「by」 在表达式层是中缀位，前一行的表达式会把它当后缀吸走：
  - 「var x = 5」 换行 「by [q]」 解析为 「var x = 5 by [q]」——命题**仍注入**（ByExpr 分支照常 inject），但语义上 by 不再是独立语句，JS 里也不会留 「// by:」 注释（实测）
  - 更糟：「axiom p」 换行 「by [q]」 解析为 「axiom (p by [q])」——by 整个消失进 axiom 的 prop，编译产物只剩一行 「// axiom: ?」（tag 函数不认 ByExpr，渲染为 「?」；实测对照：加分号后恢复 「// axiom: p」 + 「// by: q」 两行）
  - 对策：by 语句与前一个表达式之间用 「;」 显断句，或让 by 独占无前缀表达式的行首
- ❌ **工程模式顶层禁 by**：「axiom q」 在 .subl 顶层合法（parseEntry 放行特例），「by [q]」 却报「期望顶层只能写声明」（实测）；顶层要用 by 请写脚本模式（.subs，run-script）或放进 「fun main()」
- ❌ 「by」 是硬关键字：「var by = 1」 直接 parse 失败（Lexer.kt:43）
- ⚠️ 优先级：「a by [q] + 1」 是 「(a by [q]) + 1」，「1 + 2 by [q]」 是 「(1 + 2) by [q]」——后缀供给跟着左结合走，需要别的顺序就加括号（实测两种均按此解析）

**语义类**

- ⚠️ **by 命题永不验证**：「by [1 = 2]」 合法。它是辅助策略不是义务——错误命题注入后会随 Γ 一起污染推理：矛盾事实让 MP 闭包/爆炸通道产出任意结论（与 axiom 同样的破坏力，且只有 「D-BY」 补充级提醒、没有错误）。只把**你自己验算过**的中间步骤交给 by
- ⚠️ **props 里的名字不做解析**：「by [r2 == 6]」 中 「r2」 从未定义也不报警（命题层不走名字解析；「W-PROP-UNBOUND」 只管 when 分类讨论的析取前提，Checker.kt:662）——打错字静默通过，事实却供不上（实测 「double(3 by [r2 == 6])」 正常编译，但 「r2」 这个事实毫无用处）
- ⚠️ **作用域**：函数帧 「Frame(null)」、lambda 帧隔离——函数/lambda 内的 by 不外泄；要用在需要它的作用域里，别指望“顶层 by 一次，处处可用”
- ⚠️ **块弥散只走值块通道**：if/when **表达式**分支体里的 by 会回溢父帧（Checker.kt:1161）；但别用裸 「{ … }」 想要块语义——「{ by [w] }」 会被解析为**零参/隐参 lambda**（实测：之后 「∴ w」 证不出，Γ 里只有 「pure<?>」）
- ⚠️ **后缀式无审计注释**：语句式 by 在 JS 产物里留 「// by: q」，后缀式 「e by [q]」 擦除得只剩 「e」——CI 用 grep 审计“by 证据点”时记得只覆盖语句式，或统一用语句式风格

**机制混淆类**

- ❌ 把 「by」 当 「∴」 的替代：「∴ q」 是**义务**（证不出报错），「by [q]」 是**供给**（免验证）。用 by 去平掉 「E-CANNOT-PROVE」 在机制上可行，但每用一次都是在向 Γ 加未经证明的事实——根文档《手动证明》的预期用法是「中间步骤」，不是「证不出就塞进去」
- ❌ 「impl C for T by field」 的 「by」 是委托语法糖（跟字段名），与命题供给无关（ImplCheck.kt）
- ⚠️ 「by」 与 「axiom」 的区别只在**语义标注与诊断**（D-BY 留痕 vs 无诊断、顶层放行差异），注入机制完全相同；选 「by」 的理由应当是「这是中间步骤、不是外部公理」
- 待核：Ast.kt:257 注释称 by 可被语言服务「高亮为待补证明点」——language-service 正在重写（LspAnalysis.kt），未实测该提示行为；「by」 事实是否也可能触发命题参数歧义 「E-PROP-AMBIGUOUS」（与 axiom 同池）未实测
