# 项目结构（gradle 多模块布局）

> wiki/05-工程-项目结构 · 主题域：项目结构——settings.gradle.kts 声明的六模块依赖图（frontend ← compiler ← interpreter ← cli 主链；language-service、annotationproc 为侧枝）、各模块职责边界、e2e 测试位置（compiler 模块内）、core/ 标准库与 examples/ 的关系、_facts/ 重写事实工作区
> 事实来源：_facts/_langfacts.md §8、_facts/writer-contract.md；settings.gradle.kts；根 build.gradle.kts；frontend/compiler/interpreter/cli/language-service/annotationproc 各自 build.gradle.kts；compiler/src/main/kotlin/sugared/functor/checker/ModuleTree.kt；compiler/src/test/kotlin/sugared/functor/e2e/*.kt；examples/说明.md；examples/模块系统/；本会话对顶层目录与各模块源/测试文件的实测

## 语法

### 模块声明（settings.gradle.kts）

```kotlin
plugins {
    id("org.gradle.toolchains.foojay-resolver-convention") version "0.8.0"
}
rootProject.name = "sublimation"
include(":frontend")
include(":compiler")
include(":interpreter")
include(":language-service")
include(":annotationproc")
include(":cli")
```

- 顶层构建只有六条 `include`；foojay 插件仅为 JVM 17 工具链自动解析
- 每个模块统一形态：Kotlin `2.1.20` JVM 插件 + `jvmToolchain(17)`；组名 `sugared.functor`、版本 `1.1-SNAPSHOT` 由根 build.gradle.kts 的 `allprojects` 注入；`gradle.properties` 仅配 `kotlin.code.style=official`（实测）
- 所有模块共用包名前缀 `sugared.functor`：frontend 为 `sugared.functor.{ast,lexer,parser}`，compiler 为 `.{checker,codegen}`，interpreter 为 `.interpreter`，language-service 为 `sugared.functor.lsp`，annotationproc 为 `sugared.functor.annotationproc`，cli 入口类在 `sugared.functor` 下——模块边界靠 gradle project 划分，不靠包名前缀

### 依赖图（各 build.gradle.kts 的 `implementation(project(...))` 实测）

主链（自底向上的管线分层）：

```
frontend      ← compiler   ← interpreter  ← cli
（词法/文法/AST） （检查+生成）  （求值+推导）  （CLI 入口）
```

两条侧枝（不落在主链中间，各自被 cli 消费）：

```
annotationproc  → frontend + compiler + interpreter
language-service → frontend + compiler +interpreter + annotationproc
cli             → frontend + compiler + interpreter + language-service + annotationproc
```

- 「language-service、annotationproc 独立」指它们**不在 frontend→cli 的主链上**：两者都挂在 compiler/interpreter 层之侧，分别由 cli 的 `-p` 处理器链与编辑器服务消费；二者自身都仍有向下依赖（见各 build.gradle.kts）
- interpreter 是依赖最厚的库模块（frontend+compiler）；cli 是唯一汇聚全部五依赖的模块

### 产物与运行入口

- cli：`application` 插件，`mainClass = "sugared.functor.MainKt"`；`applicationDefaultJvmArgs = listOf("-Xss16m")`——build 注释说明：注解处理器对 `.subs` 脚本经 Evaluator 递归执行，偶发深帧 StackOverflow，故放宽线程栈
- cli 注册 `fatJar` 任务：产物名 `sublimation.jar`，输出目录刻意放在**仓库根** `build/libs`（注释明示「兼容原 README 的目录约定」），manifest `Main-Class` 同 MainKt，并排除 META-INF 签名与 `module-info.class`
- language-service：`application` 插件，`mainClass = "sugared.functor.lsp.LspServer"`（独立可运行的 LSP 进程）
- 其余四个模块是纯库，无 application 插件

### 测试约定

- 全部模块 `useJUnitPlatform()`；除 cli 外每个模块都在 `tasks.test` 里设 `workingDir = rootDir`
- 根 build.gradle.kts 注释解释原因：测试内的相对路径 `File("core")`、`File("examples/...")` 须以仓库根解析；且 `root/subprojects` 的 lazy `configureEach` 会被 KGP 重置，`workingDir` 必须在各模块自己的 `tasks.test { }` 内设置（实测确认各模块文件均如此）
- language-service 另开 `testLogging { showStandardStreams = true }`

## 语义

### 各模块职责边界（按 main 源码实测）

- **frontend**（4 个 .kt）：`Lexer.kt`（词法，224 行）、`Parser.kt`（文法，1724 行）、`Ast.kt`（AST、类型与命题的语法表示）、`AstPrinter.kt`。纯文法层：token 与树，零类型/零求值信息
- **compiler**（17 个 .kt）：`checker` 包（Checker、TypeInfer、Prop、ArithProve、CallCheck、Purity、Diffusion、Symbols、Types、WhenCheck、ImplCheck、ModuleTree、MultiModule、AndroidBuiltins、Aggressive、Real、Diag）+ `codegen/JsCodeGen.kt`（1797 行）。消费 AST，产出诊断与 JS
- **interpreter**（8 个 .kt）：`Evaluator.kt`（大步求值，924 行）、`ScriptValue/ScriptFrame/ScriptFunction/ScriptType`（脚本值模型）、`GlobalInference`（脚本模式全局类型推导）、`Interpreter`、`Annotation`
- **cli**（1 个 .kt）：`Main.kt`（402 行）——check/compile/run/run-script 子命令、`-p <处理器>`、`-A key=value`、`-v`、aggressive 标志、诊断 explain 全量表
- **language-service**（3 个 .kt）：`LspServer`（JSON-RPC 入口）、`LspProtocol`、`LspAnalysis`（诊断分析）。build 注释定调：脚本模式 `.subs` 复用 interpreter 的 GlobalInference 而**不引入运行时求值**；安卓工程编辑期先跑注解处理器（allMut/android/composable/view）再检查，「与编译链同构」
- **annotationproc**（11 个 .kt）：`AnnotationScanner`（扫描）+`AnnotatedNode/AstEdits`（改写原语）+`Processor(Pipeline/Engine/Host/Api)`（框架）+`BuiltinProcessors/ScriptProcessor`（内置与脚本处理器）。`@allMut` 等 APT 引入注解**先于 B/C 检查**执行，可改写 AST 后再交给 Checker

### 模块边界的语义不变量

- frontend 不依赖任何模块——文法层可被 compiler、interpreter、language-service 独立复用
- compiler 只依赖 frontend：检查与生成都只吃 AST，不做任何求值
- interpreter 依赖 compiler：求值器需要 Checker 的类型/命题结论（unchecked 闸、pure 传播等）
- annotationproc 站在 compiler/interpreter 之上，但不是主链的一环——它是「编译期改写」侧枝，被 cli（`-p`）与 language-service（编辑期同构链）消费
- language-service 复用整条前端链但不出产物：只诊断、不生成 JS、不运行

### e2e 测试位置：compiler 模块内

四个 e2e 文件全在 `compiler/src/test/kotlin/sugared/functor/e2e/`：

| 文件 | @Test 数（实测） | 内容 |
|---|---|---|
| E2ETest.kt | 63 | 单文件 B3：源 → Checker → JsCodeGen → node 实跑 → 断言 stdout |
| ModuleE2ETest.kt | 65 | 多模块目录树 → MultiModule → 合并编译 → node；`coreSpec()` 从仓库根 `File("core")` 读真实标准库整包内联进临时树（注释记 v4 改名 stdlib → core） |
| DailyScriptsE2ETest.kt | 7 | 读取真实 `examples/日常-*.subl` 七个文件做全链路断言 |
| JsEscapeE2ETest.kt | 1 | JS 转义边界 |

- 统一执行协议：`ProcessBuilder("node", ...)` 实跑生成的 JS 并断言退出码 0 与 stdout；node 不可用时以 `assumeTrue` **静默跳过**（不视为失败）
- @Test 实测总数：frontend 65、compiler 537（其中 e2e 136）、interpreter 52、cli 1、language-service 138、annotationproc 23；_langfacts.md §8 记 compiler 536，差 1 条新增（**待核**）
- e2e 放在 compiler 而非 cli 的语义：被测对象是「Checker+JsCodeGen 的端到端正确性」，不需要 CLI 参数层；管线由测试代码直接组装，不经过 Main.kt

### core/ 标准库与 examples/ 的关系

- core/ 是标准库的**源形态**：15 个子包（async、classic、collection、encoding、io、json、logic、math、net、number、random、real、regex、string、time），每包一个 `<包名>.settings` + 若干 `.subl`；core/ 根目录本身没有任何 `.subl`
- 识别与嫁接（ModuleTree.kt:48-94，实测）：编译入口下名为 `core`（或备选 `test/core`）的目录被发现后，一律以模块名 `core` 嫁接到模块树根；判据 `isStdlibPackage` = 只有子包、无直接源文件——用户自己目录下直接有 `.subl` 的 `core/` 仍当普通模块，不被劫持
- 隐式挂载（P2 决策 78，用户拍板 B）：为所有非 core 自身的模块追加 `mount core` 及其全部子包；本地同名子目录/挂载名优先，仅跳过冲突项（injectCoreMounts，ModuleTree.kt:248-267）。所以工程模式下 `core.collection.filter(xs, f)`、裸名 `Ok/size` 跨模块查找自然可达
- examples/ 是**示例集而非测试资源目录**，但被测试消费：CheckerTest 直接 readText `examples/上下文弥散.subl` 与 `examples/特性巡礼.subl`；DailyScriptsE2ETest 跑七个 `日常-*` 文件；`examples/说明.md` 声明全部示例经 compile + node 实测
- 单文件编译不挂 core（List/Set/Result 需文件内自声明）；目录（工程）模式自动隐式挂 core——`examples/说明.md` 仍写作「目录模式会自动把编译入口下的 `stdlib/` 隐式挂给所有模块」，系 v4 改名（stdlib → core）前的旧措辞，与 ModuleTree.kt 现状冲突（**待核**，以代码为准）

### _facts/ 的角色

- 重写工程的事实来源工作区，四个文件：`writer-contract.md`（全体写作代理契约与事实优先级）、`_langfacts.md`（语言事实表）、`rewrite-map.md`（落点分工：约 45 条 wiki 条目 + docs/ + boring doc 卷册映射）、`examples-spec.md`（22 个 examples 文件的重写规格）
- 契约规定的事实优先级：`_langfacts.md` > 源代码 > 旧文档；不确定一律标 **待核**，不推测
- 不参与 gradle 构建、不影响编译；与 `_facts_tmp/`、`_byprobe/` 一样是重写会话的工作区

## 示例

### 依赖声明（interpreter 与 cli 的 build.gradle.kts 摘录）

```kotlin
// interpreter/build.gradle.kts
dependencies {
    implementation(project(":frontend"))
    implementation(project(":compiler"))
    testImplementation(kotlin("test"))
}
```

```kotlin
// cli/build.gradle.kts —— 唯一汇聚全部模块的入口
dependencies {
    implementation(project(":frontend"))
    implementation(project(":compiler"))
    implementation(project(":interpreter"))
    implementation(project(":language-service"))
    implementation(project(":annotationproc"))
    testImplementation(kotlin("test"))
}
```

### 从源码到运行的常用路径

```bash
# 全量测试（compiler 模块会连带跑 e2e；node 缺失时 e2e 自动跳过）
./gradlew test

# 造独立 fat jar（产物落仓库根 build/libs/sublimation.jar）
./gradlew :cli:fatJar

# 编译并实跑一个单文件示例
java -jar build/libs/sublimation.jar compile examples/模式匹配.subl -o out.js
node out.js

# 编译一个多模块工程（目录即模块；core 标准库自动隐式挂载）
java -jar build/libs/sublimation.jar compile examples/模块系统 -o out.js
node out.js          # 预期输出 12 / 9
```

### 多模块工程的目录形态（examples/模块系统/ 实测）

```text
模块系统/
├── 主.subl                 // 根模块：fun main() { unchecked print(tool.triple(4)) }
└── tool/
    └── 工具函数.subl        // 子模块：fun triple(x: Nat): Nat = x * 3
```

根模块对子模块 `tool` 的调用是**父→子可见**的限定调用（`tool.triple(4)`、`tool.square(3)`），子→父不可见；此处无需 `.settings`——子目录天然是子模块，挂载指令用于跨子树引用。

### 新增一个 gradle 模块的最小改动

```kotlin
// settings.gradle.kts
include(":mypkg")

// mypkg/build.gradle.kts
plugins { kotlin("jvm") version "2.1.20") }   // 与其他模块对齐
kotlin { jvmToolchain(17) }
dependencies {
    implementation(project(":frontend"))
    implementation(project(":compiler"))
    testImplementation(kotlin("test"))
}
tasks.test { useJUnitPlatform(); workingDir = rootDir }
```

## 陷阱

1. **「language-service、annotationproc 独立」不是「零依赖」**：二者不在主链上，但分别依赖 frontend+compiler+interpreter（annotationproc）与四模块（language-service）。把它们当无依赖叶子模块会在重构依赖图时漏边
2. **e2e 的绿色可能来自跳过**：node 不可用时 `assumeTrue(nodeAvailable())` 直接跳过，136 个 e2e 全绿 ≠ 端到端真的跑过；CI 须先确认 node 在 PATH
3. **测试 workingDir 陷阱**：e2e/DailyScripts 与 CheckerTest 用相对路径 `File("examples/...")`、`File("core")`，依赖各模块 `tasks.test { workingDir = rootDir }`；根 build.gradle.kts 注释明示该设置若写在 allprojects/subprojects 的 lazy 块里会被 KGP 重置，从模块目录直接跑单测（IDE 默认行为）也可能解析失败
4. **`annotation processer/`（带空格）不是模块**：它是注解处理器脚本样例目录（allMut/android/composable/view 四个 .subs），与 gradle 模块 `annotationproc` 仅一字之差；旧文档检索极易混淆
5. **fat jar 不落在 cli/build/libs**：`fatJar` 刻意输出到仓库根 `build/libs/sublimation.jar`（兼容 README 约定）；按模块直觉去 `cli/build/libs` 找产物会扑空
6. **core/ 必须保持「包形态」**：根目录下一旦出现直接 `.subl`，`isStdlibPackage` 判据失效，core 降级为普通用户模块、失去隐式挂载；反之用户工程里名为 core 的纯包目录会被当成标准库嫁接
7. **examples/说明.md 的 stdlib 措辞已过时**：其「目录模式自动挂 `stdlib/`」与「见 show/ 演示包」系 v4 改名（stdlib → core）前表述，与 ModuleTree.kt 现状不符（**待核**，以代码为准）
8. **顶层目录鱼龙混杂**：demo/、show/、playground/、TESTVAL/、_byprobe/、_facts_tmp/、brand/、boring doc/、root doc/、idea doc/ 都不是产品代码；root doc 正被另一方实时编辑（契约告诫勿碰），误读为模块结构会得到错误的项目画像
9. **-Xss16m 只对 cli 的 application/fatJar 生效**：该栈宽设置是 cli build 的 `applicationDefaultJvmArgs`，起因是注解处理器对 `.subs` 的 Evaluator 递归；从 IDE 或 gradlew 直接跑测试不会继承该参数
10. **版本/工具链漂移**：全仓统一 Kotlin 2.1.20 + JVM 17 工具链 + 1.1-SNAPSHOT（实测）；若个别模块写死不同版本会破坏统一性（当前未见，**待核**后续漂移）
