# `$` 返回值指代 / `$n` 第 n 形参引用（ReturnSym · ParamRefExpr）

> wiki/03-证明-$与$n · 主题域：上下文系统的内联标识（_langfacts §1 词法 · §2 文法 · §5 上下文系统）
> 事实来源：_facts/_langfacts.md；frontend（lexer/Lexer.kt、parser/Parser.kt、ast/Ast.kt、ast/AstPrinter.kt）；compiler checker（Checker.kt、CallCheck.kt、Prop.kt、Diffusion.kt、Types.kt）；root doc/上下文系统.md（内联标识节）；examples/上下文弥散.subl、examples/特性巡礼.subl。本文全部代码示例以本仓库 fatJar 产物（sublimation.jar，1.1-SNAPSHOT）`check` 子命令逐条实测通过或复现；文中行号为近似定位，以代码语义为准。

上下文是写在函数签名尖括号里的**编译期命题契约**。命题里往往要提到「这个函数的返回值」「第几个形参」这类签名内部对象——它们在命题写成普通名字并不方便（返回值压根没有名字，形参名则可能被改名）。于是语言在词法层提供了两个内联标识：`$` 指代返回值，`$n` 指代第 n 个形参（从 1 数起）。二者与 `this`（函数本体）、`self`（方法接收者）同属根文档《上下文系统》的内联标识族，只在编译期存在：解释器与 JS 生成都不读它们，零运行时代价。

`$` 与 `$n` 是同一词法机制的两种产物，但语义地位不同：`$` 是**真符号**——它参与后件核对与调用点弥散，有着「$ := 什么」的完整解法；`$n` 则更像**位置语法糖**——声明期内联阶段就被改写成形参名，之后与手写形参名无异（并因此被提示级诊断「建议直接写形参名」）。

## 语法

### 词法：`$` 与 `$n` 的粘连

`$` 单字符即 DOLLAR token（Lexer.kt:129）。关键规则是**粘连**：`$` 后紧跟数字时，`$` 与全部后续数字被词法器吃成**一个** token（Lexer.kt:145-150）：

```
$7      →  token 文本 "$7"（DOLLAR）
$ 7     →  两个 token：DOLLAR('$')、INT(7)——不再是一个 $n 引用
$10     →  token 文本 "$10"（引用第 10 个形参，不是 $1 后面跟 0）
```

初等项解析据此分派（Parser.kt:1321-1326）：token 文本长度 > 1 → `ParamRefExpr(index = 数字)`；否则 → `ReturnSym`。AST 上两者是兄弟节点（Ast.kt:383/386），打印为 `$` / `$1`（AstPrinter.kt:94-95）。

字符串字面量里的 `$` 是**另一套机制**：`"$name"` / `"${expr}"` 是字符串插值（_langfacts §1），与本文的内联标识毫无关系。

### 出现位置

函数签名的完整形态（Parser.kt parseFun，279-306 行）：

```subl
fun 名字[理论参数](实际参数)<上文> : 返回类型<下文> { 体 }
```

冒号是分界：**冒号前**的 `<…>` 是上文（前件），**返回类型后**（或省略返回类型时冒号后直接）的 `<…>` 是下文（后件）。两个标识的合法位置：

| 标识 | 上文（前件） | 下文（后件） | 函数类型上下文 | 函数体内 | 结构体伴生命题 |
| --- | --- | --- | --- | --- | --- |
| `$` | ✗（不被替换，见陷阱 1） | ✓ | ✗ | ✗（类型为 Bool，见陷阱 5） | ✗ |
| `$n` | ✓ | ✓ | ✓ | ✗（E-PARAM-REF-IN-BODY） | ✗（用字段名） |

函数类型自己也携带上下文（Parser.kt:581-583）：

```subl
(Nat)<$1 >= 0> => Null          // 函数类型：形参位的上下文，$1 指其第 1 形参
fun zero(f: (Nat)<$1 >= 0> => Null) { f(0) }
```

语法形态小结：

```subl
fun get7(): Nat <$ = 7> { return 7 }              // $ 在下文：指代返回值
fun ordered(a: Nat, b: Nat) <$1 <= $2>: Null {}   // $n 在上文：指第 n 形参
fun double(n: Nat): Nat <$1 >= 0> = n * 2         // $n 也在下文出现
fun clamp(lo: Nat, hi: Nat, x: Nat)<($3 >= $1) ∧ ($3 <= $2)> : Nat<$ = $3> = x
```

注意：上下文里的表达式服从**全表达式无优先级、左结合**的总规则（_langfacts §2），合取/蕴含/算术混排时必须加括号（见陷阱 3）。

## 语义

### `$`：后件里的返回值——dollarOf 三规则

`$` 只在下文（后件）里有定义。声明期核对后件时，编译器先用 `dollarOf` 解出「`$` := 什么」（Diffusion.kt:45-59），再把后件里的 `$` 全部替换掉（Prop.kt:substDollar，247-256 行），然后作为证明目标：

$$rac{\text{体是块，且恰有一个带值的显式 } \texttt{return}\ e}{$ := e} \quad (\text{D-RETURN})$$

$$rac{\text{不带值的 return 之外的尾表达式 } te}{$ := te} \quad (\text{D-TAIL})$$

$$rac{\text{两者皆无}}{$ := \texttt{null}} \quad (\text{D-NULL，后件核对将显式失败})$$

三条规则的优先级即上表顺序：**先看块里有没有唯一一处带值的 `return e`**（Kotlin 风格的 `{ return 7 }`），有则 `$` := e；否则退回尾表达式（块体的尾表达式，或表达式体的整个表达式）；都没有（如空块、仅含无值 return）则 `$` := 名为 `null` 的项，任何引用 `$` 的后件此时都会证失败。多路 return（`if`/`else` 各 return 一个）v1 无法归一为单一项，**保守取 null 让后件核对显式失败，不猜测**——这是有意的健全性立场（Diffusion.kt:49-50 注释）。

核对与诊断：

$$rac{\Gamma \vdash \text{substDollar(后件, \$)} \qquad \text{proveOrDeep}(\Gamma, \text{目标}) \text{ 不成立}}{\text{E-POST-UNPROVEN（后件声明了但体内没证出）}}$$

对应 Checker.kt:407-417：`tail = dollarOf(body)` → `goal = substDollar(fromExpr(post), tail)` → `proveOrDeep(f.allFacts(), goal)` 失败即 E-POST-UNPROVEN。标了 `@axiom` 的函数例外：签名即公理，编译器信任、不做自动证明（D-AXIOM-POST 补充诊断，Checker.kt:410-412）。

调用点弥散：函数被调用且上文通过后，下文作为事实注入调用方作用域帧。此时 `$` := **调用表达式本身**（CallCheck.kt:940-942：`substDollar(…, c)`，c 为 CallExpr；Prop.kt:232 注释「调用注入 ≡ 调用表达式本身」）。即调用 `get7()` 后，调用方帧里多出事实 `get7() = 7`，供后续代码消费——这正是「下文兑现后弥散进作用域」。

### `$n`：前/后件里的第 n 形参——声明期即改写成形参名

`$n` 的语义在声明检查的**入口处**就收敛了：checkFun 检查函数前，先把上文与下文里的 `$n` 逐个替换为形参名（Checker.kt:375-376 调 rewriteDollarN）：

$$rac{\text{上文/下文命题中的 } \$n \quad (1 \le n \le \text{形参数})}{\text{改写为 } \texttt{NameRef(第 n 个形参名)}} \quad (\text{D-PARAMREF})$$

替换并发出诊断（Checker.kt:255-264）：越界（`n > 形参数`）报错 **E-PARAM-REF**；合法则发**提示级** H-PARAM-REF「可以直接使用参数名 …」。改写本身只认语法结构（BinExpr/UniExpr/CallExpr/InstExpr/TupleExpr 递归，Checker.kt:266-274）。因此：

- 在函数体内（任何表达式位）出现 `$n` → **E-PARAM-REF-IN-BODY**（Checker.kt:904-908），并回退用 paramTypes 里记录的形参类型序列（Checker.kt:139-140、331）给个类型，好让后续诊断继续。
- 命题层里 `$n` 与裸名同构：`ParamRefExpr` → `PAtom("$n")`（Prop.kt:33-34），便于在 Γ 中与形参等式匹配；`$` 则归一为 0 元原子 `PAtom("$")`（Prop.kt:32），且 `"$"` ∈ structuralHeads，不作为命题参数的自动供给候选（Prop.kt:27）——返回值符号是结构事实，不是可分派的命题。

一句话：**`$n` 语义上 ≡ 形参名**，区别只在「只能写在前后件位」这一位置约束，以及那条提示。

### 函数类型上下文中的 `$n`：三个观察点

函数类型 `(T)<$1 ∈ xs> => Null` 的上下文里，`$n` 按观察位置有三种含义：

1. **调用函数值时 = 第 n 个实参表达式**：CallCheck.kt:489-495——调用一个函数类型的值之前，须先证其类型携带的上下文；`$n` 经 substParamRefToArg 内联为第 n 个实参表达式（CallCheck.kt:500-508），证不出报 **E-CTX-UNPROVEN**。
2. **检查 lambda 体时 = lambda 的第 n 个形参**：Checker.kt:1112-1116——lambda 被期望类型（FunType）检查时，其上下文被改写（`$n` → lambda 形参名）后**注入 lambda 帧作前提事实**，lambda 体即可直接消费这份前提。
3. **调用点自由名内联**：CallCheck.kt:811-819——函数类型上下文里的自由名（如 `$1 in xs` 中的 `xs`）在调用点按形参名 → 实参内联，使 lambda 体拿到的是调用点真实表达式。

## 示例

以下全部以 `java -jar build/libs/sublimation.jar check` 实测。

**最小例：`$` 参与后件核对**（对应 examples/上下文弥散.subl:16-18、examples/特性巡礼.subl:95-97）：

```subl
fun get7(): Nat <$ = 7> { return 7 }
```

块体恰有一个带值 `return 7` → D-RETURN：`$` := 7，后件 `$ = 7` 即 `7 = 7`，自反成立，检查通过（实测通过）。

**表达式体走 D-TAIL**：

```subl
fun get7(): Nat <$ = 7> = 7
```

体不是块 → `$` := 整个尾表达式 `7`（Diffusion.kt:58 的 `else -> body` 分支），同样通过。

**`$` 携带类型信息**——后件不限于算术：

```subl
fun msg(): Str <$ = "ok"> = "ok"
```

实测通过；字符串字面量在命题层同样是合法项（Prop.kt:121）。

**`$n` 同时出现在上文与下文**（前件证不出时报 E-PRE-UNPROVEN）：

```subl
fun clamp(lo: Nat, hi: Nat, x: Nat)<($3 >= $1) ∧ ($3 <= $2)> : Nat<$ = $3> = x

fun inRange(): Nat = clamp(0, 10, 5)      // 上文 5 >= 0 ∧ 5 <= 10：算术通道证出，通过
fun outRange(): Nat = clamp(0, 10, 99)    // 上文 99 <= 10 证不出 → E-PRE-UNPROVEN
```

声明期 `$3/$1/$2` 已改写为 `x/lo/hi`，上文在调用点按实参重写为 `5 >= 0 ∧ 5 <= 10`，由常量原子真值通道（constAtomValue）直接判定；第二条调用的上文 `99 <= 10` 被证为不成立，报 E-PRE-UNPROVEN（实测复现）。合法的 `$n` 会附带 H-PARAM-REF 提示，属正常输出。

**函数类型上下文中的 `$1`**：

```subl
fun zero(f: (Nat)<$1 >= 0> => Null) { f(0) }    // f(0)：$1 := 实参 0，0 >= 0 成立，通过
fun bad(f: (Nat)<$1 >= 0> => Null) { f(-1) }    // f(-1)：-1 >= 0 证不出 → E-CTX-UNPROVEN
```

这里 `$1` 在「调用函数值」观察点被内联为实参表达式（实测两条分别通过/复现 E-CTX-UNPROVEN，错误信息中 Γ 可见 `1 >= 0` 等自然命题）。

**综合：下文弥散供后续消费**（实测整段通过）：

```subl
fun get7(): Nat <$ = 7> { return 7 }
fun needSeven()<get7() = 7>: Null {}   // 上文正好是 get7 的下文形态

fun main() {
  get7()         // 下文兑现：帧内弥散进事实 get7() = 7
  needSeven()    // 上文自动供给，无需显式证明
}
```

调用点弥散时 `$` := 调用表达式，故弥散进作用域的事实恰为 `get7() = 7`，与 needSeven 的上文逐字相同（手法同 examples/上下文弥散.subl 里 test1/test2 的串联）。

## 陷阱

1. **`$` 不能写进上文（前件）**。上文不做 `$` 替换（substDollar 只作用于后件与调用点弥散），`fun f(a: Nat)<$ = 7> : Nat = a` 的上文在调用点成为目标 `=<$, 7>`——一个含 0 元原子 `$` 的怪命题，任何调用都 E-PRE-UNPROVEN（实测复现，目标渲染为 `=<$, 7>`）。返回值是「函数兑现后才有」的东西，写进要求调用前已证的上文在语义上本就不成立。

2. **多路 return 让 `$` 保守失效**。`fun pick(b: Bool): Nat <$ = 7> { if (b) { return 7 } else { return 7 } }` 实测 E-POST-UNPROVEN——即使两条路都返回 7。dollarOf 只看块顶层的带值 return 列表，嵌套在 if 分支里的 return 不计入，且退回尾表达式（此处无）得到 `null`。要写多路返回的后件，目前只能保证「唯一一处带值 return」或改用表达式体（D-TAIL）。这是刻意的保守策略（Diffusion.kt:49-50），不是漏报。

3. **无优先级左结合坑坏后件**。`<$ = $1 + $2>` 实测 E-POST-UNPROVEN——它被解析成 `(($ = $1) + $2)`，后件根本不是等式。正确写法是 `<$ = ($1 + $2)>`（实测通过）。同理合取要写 `<($3 >= $1) ∧ ($3 <= $2)>`。记住：全语言无运算符优先级（_langfacts §2），上下文里更要随手加括号。

4. **计数从 1 起，`$0` 会让编译器崩溃**。越界判定是 `idx > params.size`（Checker.kt:260），`idx = 0` 漏网后执行 `params[idx - 1]`（Checker.kt:261）抛 `Index -1 out of bounds`——实测 `fun f(a: Nat)<$0 > 0> : Nat = a` 直接把 check 进程带崩（未捕获异常，非诊断码）。这是已知缺陷；在此之前请把 `$0` 视为非法（1 起编号）。

5. **`$` 在函数体内不是运行时表达式**。ReturnSym 在检查器里类型为 **Bool**（Checker.kt:903），`fun f(): Nat { return $ }` 实测报 E-RETURN-TYPE（Bool 与 Nat 不符）。`$` 只生活在命题层，别把它当「返回值的变量名」写进代码。

6. **字符串里的 `$` 是插值**。`"$x"` 走字符串插值通道（_langfacts §1），与返回值符号无关——实测 `var s = "$x"` 报 E-UNBOUND-NAME（找不到 `x`）。要字面美元符请用转义或拼接。

7. **`$n` 必须与数字粘连，且 `$10` 是单 token**。`$ 1`（中间带空格）不是引用；`$10` 引用第 10 个形参，不是 `$1` 后接 `0`（词法粘连吞掉全部数字，Lexer.kt:146-149）。

8. **`$n` 合法但被提示「直接用形参名」**。H-PARAM-REF 是提示级诊断（不阻断编译）：设计意图是 `$n` 服务于**签名形态抽象的上下文位**（尤其函数类型 `(Nat)<$1 ∈ xs> => Null`——那里形参尚无名），普通函数签名里直接写形参名更地道，也省一条提示。

9. **lambda 实参体的上下文前提可能被首轮检查误报**。lambda 实参会被检查两遍：先无期望地算类型（CallCheck.kt:84），再带期望类型复查（CallCheck.kt:824）。上下文注入只发生在第二遍（Checker.kt:1112-1116）。实测：

   ```subl
   fun needNonNeg(x: Nat)<$1 >= 0> : Null { }
   fun applyPolicy(f: (Nat)<$1 >= 0> => Null) { f(7) }
   fun use(): Null = applyPolicy({ n => needNonNeg(n) })
   ```

   第二遍已凭注入的 `n >= 0` 证出（对比无上下文版本会报两次同错），但第一遍的 E-PRE-UNPROVEN 仍留在诊断里。**待核**：此双重检查造成的误报是否已有跟踪议题；在确认前，lambda 体内依赖上下文前提的写法请预留一条噪声诊断。

10. **待核清单**：`$n` 在匿名函数（AnonFunExpr，Checker.kt:1320-1322）上下文位的行为未逐形态实测；`--prover=aggressive` 激进模式对 `$` 后件核对深度的影响未实测；`$0` 崩溃的修复进度未核对（本文基于 fatJar 构建 1.1-SNAPSHOT 实测）。
